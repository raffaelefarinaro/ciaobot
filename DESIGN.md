# Ciaobot Design System

## Overview

Ciaobot is a focused control surface for a personal AI assistant. Its visual identity combines the precision of a developer console with the warmth needed for daily conversation. It should feel capable, private, calm, and direct—not corporate, ornamental, or like a generic chatbot.

The PWA is information-dense but not cramped. A system sans carries prose and controls, monospace is reserved for technical metadata and terminal cues, restrained animation and a deep indigo foundation establish the console character, and a warm orange accent supplies personality and orientation. The interface must remain understandable without color, animation, hover, or prior knowledge of its icons.

An attended shell permission card shows the exact current command as submitted, up to 4096 characters, and the validated working directory when the provider supplies one (otherwise **Unknown**). Keep its multiline text unformatted, pre-wrapped, keyboard-scrollable and easy to review on a narrow screen. Keep the command and directory transient: only the live stream may replay them, never the registry, journal or push notification. Approval and denial each remain separate, clearly labelled controls with 44px minimum height; an approval is one-time only.

The home screen (**Home**) is the primary entry point and uses the Workbench composition. It has no headline, eyebrow or lede: the command surface is the page's subject. The surface holds the prompt, then one bar with the project chip (opens the shared project picker and only remembers the pick), a model chip (the workspace default unless the user picks a Claude or opencode model, which rides the chat-create call and resets on a workspace switch), and one icon send control whose accessible name stays **New** (it starts the chat in the chip's project without asking again, opening the picker only when the chip has no project to name; ⌘/Ctrl+Enter sends, bare Enter is a newline, as in chat). Typing `/` at the start of the prompt or after a space opens the same commands-and-skills listbox the chat composer shows, for the selected model's provider (or the workspace default): Up/Down move, Enter or Tab inserts the highlighted name, Esc closes, and ⌘/Ctrl+Enter still sends. Above the composer, in the same column, one **Needs you** list holds everything that is waiting on the operator: workspace-health errors (each with a *Fix* button that runs the engine's automatic remedy), blocking and other operator notices (including *A new Ciaobot version is ready to install*, *Switch to the new Ciaobot app* on a Mac still running the engine the 1.x installer set up — led by a *Download for Mac* link, and *Not now* hides it on every device for 30 days; it shows in the old Mac app too, since that app's users are exactly its audience — and anything Settings needs checked), the work the last update left behind, and the last Workspace care run when it left the owner something (described under Workspace care). It is one section with one title and one hairline-divided card of rows, in that order, with *Show N closed notices* under it; with nothing to show it renders no element at all, no all-clear row. Each row is one title, one line (a single plain-text line, ellipsised, never wrapped) and one primary button; the buttons are one width and 44px high, 8px or more from the ⋯ button beside them. Everything else a row can do (the other button, a release-notes link, *Copy command*, *Not now*, *Hide for now*) sits in the row's ⋯ menu, a real menu button (arrow keys, Home/End, Escape returns focus to ⋯). An error or blocking row carries a dot and a visually hidden *Error* / *Blocking* label, never colour alone. Below a 520px list width the controls drop under the text and the primary stretches. Beside the request column on wide panes, the rail holds *At a glance* only: one docked window in Chat details' vocabulary (`--bg2` surface, 1px border, 14px radius, the docked shadow, a 44px title bar with 16px insets) with no close control. *At a glance* opens with one quiet **Workspace care** line (status glyph, then one detail line; described under Workspace care), then lists only the queues that need a look (tasks the agent reported done and waiting for review — one opens its card, several open the board — then automations that failed, did not run, or lost their chat — one opens that automation, several open Automations; a missed one-time reminder is the install-wide notice instead) as plain hairline rows with no icons or action words. A failing automation's title reads in the warning colour. It says *Nothing to review.* when all are clear and there is no care line to show. Under the queues, always, a **Today** section (its heading carries a muted *Usage* link to the Usage page, 44px on a coarse pointer) lists hairline key/value rows: chats opened, messages sent, chats archived, projects worked on and tasks completed, each with its muted 30-day daily average (*avg N*, one decimal below 10 so a quiet row reads *avg 0.4* rather than *avg 0*), and the note *Averages over the last 30 days.* A count that is still loading, failed or unknown reads *—*; there is no spinner. While the page scrolls *At a glance* stays in view; under a 940px pane it drops below the request column. Home is top-aligned at every state, never vertically centred, and there is no *+ workspace chat* button: the composer and each lane's *+ new* are the ways to start, so the composer sits at the top of the column in every state. *Needs you* is not drawn until the first load of its two sources (workspace health, operator notices) has settled, so it arrives once rather than growing source by source; after the first load settles, the list changes only when a source changes: a row resolving, being hidden or newly arriving moves what is below it. The wait is bounded at 3 seconds, so a stalled read cannot hide blocking or error rows. Below the composer, the chat list (no visible heading; a screen-reader heading *Your chats*) shows the selected workspace's chats as flat rows — title, a project · status sub-line read from the row's tier, time on the right. Rows are grouped in this explicit order: **Needs you**, **Unread**, **Working**, and **Earlier**: a finished reply waiting to be read comes before a chat still working. A chat is in **Working** while its turn streams or while background shells it started still run after the turn (the engine's count, so it holds for a chat that is not open and after a reload); a chat there only for its shells says *1 shell running* / *N shells running* on its sub-line. Shells never add to the needs-you, unread or notification counts. Below those tiers a separate **memory insights** section carries one entry per archived conversation whose memory work is in flight, unfinished, or asking for an answer. The entry is named for the *conversation*, never for the internal memory pass behind it, and its status is a state in words — *archiving…*, *queued for memory*, *updating memory…*, *needs you* (with the pending question on a second line), *needs attention*, *memory updated*. Clicking it opens the memory pass, which is a real chat: the live turn, the question and the reply all live there, and the archived transcript is the fallback only while no pass exists. A declared memory pass is never a chat row in the tiers and never appears in the sidebar. A pass whose helper failed closed has no memory-insight row, so it remains an ordinary chat row as the way back to its pending question; notification, unread and needs-you counts still exclude it by project kind. The workspace name appears once, in the sidebar's workspace scope: the Home header says only *Home*, and the selected lane has no visible header (its status sentence remains for screen readers). Rescue lanes for stale or unknown workspaces keep a visible name and New action, because the name is what explains them. Switching workspaces swaps the home content instead of adding a column. Arrow-key navigation follows the visual order, using up/down between stacked lanes and left/right within a lane. Signals are shape-and-text-first (tier labels, weight, dots) so no tier relies on color alone. Counters are sparing: the sidebar's workspace scope shows only the name (counts and key hints live in its menu), New chat carries its shortcut in its tooltip, Home shows a subtle count when chats need you, Tasks shows a quiet count of the tasks waiting for review; every link's accessible name keeps the number. When the pane (not the window) is narrower than 940px the rail drops below the request column; *Needs you* stays above the composer at every width. The expanded sidebar stacks the wordmark row (ending in the back / forward pair, a hairline, then the collapse control; the pair drops below the toggle on the collapsed 40px rail, and on phones, where the sidebar is a drawer, the pane header shows a Back chevron after the menu button whenever there is in-app history; ⌘[ / ⌘] in the browser), the workspace scope, New chat, the destinations as a labelled list (38px rows, 44px on coarse pointers; the current one on an accent-tinted fill), then the `Projects` tree at 36px row density. In a plain browser tab on a secure origin, Home shows a short *Set up this device* section (install the app, turn on notifications, send a test; on the computer running Ciaobot, a *Use on your phone* row with the three Tailscale steps and a link to Settings → Other devices, which never counts toward finishing setup). It is plain rows with one primary action, dismissible per browser, and it disappears once the app is installed and notifications are on. On an install whose password setup generated, Home shows a one-time *Your Ciaobot* window above *Set up this device*. It names the workspace folder (with Show in Finder on the computer running Ciaobot), the password (masked; Show and Copy only on that computer, elsewhere a line saying where it is shown) and the AI tool. Its X dismisses it for every device.

Core product work follows one visible model: **request → run → output → durable knowledge**. The transcript remains the reasoning surface. Chat details (context, skills and MCP used, files) sits beside the conversation on a wide pane and opens over it on a narrow one, without forcing a permanent multi-column IDE layout. The chat header holds only close, the **title rail** (described under Chat title rail), and **Archive** as a filled primary button with its label (it is the header's one action; on a narrow pane, where the Chat details opener sits beside it, Archive is icon-only). Code mode is not shown in the header: the sidebar row carries the `›_` glyph and Chat details' Repository section the repository facts. On a phone (767px and under) the close × is hidden so the title keeps the room: Back and the menu already leave the chat. Outside code mode the header says nothing about the repository. Archiving a chat that holds an open board task, from the header or the sidebar menu, asks first: *Complete task…* opens the same closure note as the rail (*Approve Done* while the result waits for review, which the engine follows by archiving the chat; *Mark done* otherwise, which then archives). The note is optional: one action completes, and a blank note completes without a resolution. *Keep task open* archives and leaves the task where it is, and *Cancel*. Any other chat gets the plain archive confirm. In the title rail each chat's project name sits in mono under its title; with the rail off (a lone chat, an archived or memory-pass chat, a split pane), the header shows no project. On a phone a header with nothing to centre (chat, pinned file) is one row — menu, Back (when there is in-app history), then the title block led by its own close button, and the actions. Chat details is not toggled from the header: a neutral × at the right end of the rail's title bar closes it. While it is hidden (or the pane is too narrow for a rail), an info (ⓘ) button sits as a small bordered tab at the chat body's top right and brings it back, opening the drawer on narrow panes. Project is the context envelope; Memory's Unsure list is where what Ciaobot could not settle waits; its Map (Graph/List) is the deeper exploration mode. **Tasks** is a workspace destination of its own: a four-column board — To do, In progress, In review, Done — built from the existing card, badge and chip tokens with no column drag, a card's status being a native select, and the four columns reading as one status-filtered list on a narrow pane. Memory lists its sections in the sidebar exactly as Settings lists its tabs — *Unsure* first on its own row, then *Explore* (Map, Categories, Import), each a route — so the page header only names the section ("Memory · Unsure") and carries no mode switch or tab row. Under that header every Memory section carries one collapsed-by-default *How memory works* disclosure (a hairline section, not a card, with a 44px toggle whose open state is remembered per browser in `ciao.memory.howOpen`): static text on what is saved, the memory pass, what is not saved, how to undo, the weekly decision rules, and a link to the Categories tab and to the site page. There is no review queue: the agent writes memory directly and Git is the record and the undo, so Unsure is a page of plain rows read from a Markdown file and carries no count in the sidebar. The map's search and category filters sit under the section list only while Map is showing.

There is no native shell: the engine serves the PWA, and every one of these
states is a page in it. Before the engine reports startup phases, the connecting
screen states that it is checking the connection, with indeterminate motion rather
than an invented 0% boot progress. When the engine reports phases, it shows their
real status in plain-language rows. This screen shares the calm indigo canvas,
type hierarchy and restrained accent of the engine recovery curtain; neither
pretends the browser is booting the host. The Updates card's progress overlay
remains the only place a running package update is reported, and a settled run
hands over to the app-level restart notice, which stays up until the
new engine answers and then reloads. In the PWA, an
engine that stops answering shows a full-screen recovery curtain over the kept
route. It uses the boot-screen language: a plain title, `ciao service
start|status` on this computer, Retry, and automatic reconnect. It is modal
(focus trapped, shortcuts suppressed), and it lifts without a reload when the
engine returns.

A chat turn that fails because the provider CLI is signed out keeps its
automatic retry, and both the retry card and the error notice carry a closed
**How to sign in again** disclosure: open a terminal, paste the sign-in command
(the one the engine reports for that provider, with a Copy button), then come
back and click the card's **Try now** or the error notice's **Retry**, repeated as the
last step. Nothing opens a terminal or signs in on the user's behalf.

On Home, the rail is the one *At a glance* window described above; operator notices are rows of the *Needs you* list in the request column, and device setup sits in its own window there. Each window has the pinned file tile's tonal surface, bordered header and close control. For operator actions, X hides the window until reload (or until **Show N closed notices**) and persistent Hide remains a separate, explicit action. The device-setup reminder is different: its X is the only dismissal control and persists for this browser, so it does not nag again after a reload. The *Your Ciaobot* window is install-wide: its X is its only dismissal control, it is not counted again by *Show N closed notices*, and once closed the engine stops serving the password. Chat-row signals sit right-aligned above the relative time in both wide and narrow panes. In-flight memory insight rows use one quiet **extracting…** label; blocked and completed phases retain distinct wording. A normal browser tab cannot know whether the app is separately installed; installed PWA windows use display-mode detection, and the retired Ciaobot.app desktop wrapper does not report itself as a PWA. An operator notice may carry a host-terminal action and its command. It shows **Update in Terminal** only in a browser on the engine's computer, and the command with **Copy** everywhere. Nothing installs on the user's behalf, **Check again** re-reads the version, and **Not now** hides it until a newer tested version ships. In Settings → Providers each provider row says which version this release was tested with, and offers the same command and button when the installed CLI is older. Closing a notice window never removes its inbox row. An inbox link to an operator or update notice opens `/?notice=<key>`, which reopens that one window, scrolls to it and focuses it; an unknown, deleted or dismissed key shows *This notice is no longer available* and reveals nothing else.

Chat details uses the pinned viewer's docked-window vocabulary: a tonal `--bg2` surface, border, 14px radius, inset spacing, and a separated title bar with a neutral × close control. On a wide pane it is only as tall as its content, resting 16px under the header (the composer's own gap to the pane's bottom edge), and scrolls once it would reach 16px from the bottom, where its edge lines up with the composer's. The info tab is only the opener. On a narrow pane the opener sits in the header beside Archive, so it never covers the transcript; it is a borderless icon button like Archive, and Archive is icon-only beside it. It is one panel at every width — the same stacked sections and one × close, read by scrolling — shown in place on a wide pane and, on a narrower one, as a full-height drawer from the right (a bottom sheet on a phone); there are no Context/Activity/Output tabs. Its sections come in one order: **Origin** (only when the chat has one), **Open**, **MCP** (connection health and recovery for supported active chats), **Repository** (only with a linked repository), **Context**, **Skills and MCP** (only once used) and **Files**. One 1px `--border` rule separates two sections, with none above the first. Every section heading is the same: sentence case, `--text-sm`, weight 600, `--fg3`, the proportional face (no mono, no uppercase, no tracking), with an optional count after it (`--text-xs`, tabular) and at most one quiet action at its right end; there are no sub-headings. Every row is the same grid (`chatDetails.css`, class prefix `cd-`): a 16px drawn icon in `--fg3` from `AppIcon`, the main text (`--text-base`, one line with an ellipsis unless it is a long title) over an optional detail line (`--text-sm`, `--fg3`, one line, full value in its title), and exactly one trailing item: a mono value, a quiet action, an arrow for a row that navigates, or a switch. Rows are at least 40px tall (44px on a coarse pointer), carry no rules between them, and only rows that open something take a `--bg3` hover surface and a focus ring. Quiet actions are borderless `--fg2` text at least 32px tall (44px on touch). Mono is kept for code and measurements: branch, path, tokens, ×count, age. **Context** is always there. Once a provider reports a figure, a thin meter reads *N% used* (role=meter), and a quiet *Compact* sits at the right of the heading (*Compacting…* and disabled while it runs); after a compaction makes the old figure unknown, the meter goes and Compact stays. Under it, **Always loaded** is a disclosure row: a drawn chevron in the icon slot that turns 90° when open, the label, and the rows' token total in mono. It starts closed, its open state is remembered per browser (`ciao.chatDetails.alwaysLoadedOpen`), and *See what Ciao knows* opens it (which is then remembered too, like any open). Its nested rows, indented to the text column, are the **Ciaobot system prompt** (a disclosure that opens the full text in a scrollable mono box with a quiet Copy), the workspace guide, the project brief as prose under the project's name, and in code mode the repository instructions. Each shows its tokens, and a row that could not be read shows a warning icon, the reason and a quiet Retry. **Open** lists the actions that leave the panel for another surface, on every chat, with or without a repository. It holds two rows: *Terminal* (terminal icon, the detail *Shell on the engine's computer*, an arrow; accessible name *Open terminal*), which opens the in-app terminal, and *Browse files* (folder icon, the detail *Folders in this workspace*, an arrow), which opens the folder browser at the chat's workspace folder. **Origin** (only when there is one) gathers where the chat came from: the automation that runs here (clock icon, its title, the detail *Automation*, opening its page), the board task a delegated chat works on (task icon, the title wrapping, the detail *Delegated task · <status>*, opening the task overlay), each task the chat is manually linked to (detail *Linked task*), and for a memory pass the conversation it distils (spark icon, the detail *Memory insight*). Under the delegated task's row, indented to its text, **Approve Done** is the panel's one filled primary button; otherwise a bordered *Mark done…* appears, and the completion form opens in the same place. **Repository** (only with a linked repository) has a repo row (folder icon, the name, the folder the chat works in as a mono detail with an ellipsis and the full path in its title, and a quiet *Copy path* icon button that says *Path copied* for 1.5 s), a branch row (branch icon, the branch in mono, its title naming the main checkout's branch when the chat works elsewhere, the detail *worktree* and *● uncommitted changes* or *clean*), or one warning row when the folder is missing, and nothing else: no note and no Code mode switch: a chat is in code mode exactly when its project has a linked repository that exists. There is no branch disclosure and no ⓘ button. **Skills and MCP** has one row per skill or MCP server: a star or plug icon, the name, the detail *Skill* or *MCP server*, a mono ×N when used more than once, and the server's tools in the row's title. **Files** is one list. The files the chat touched come first, newest first by their latest touch (detail *New · dir*, *Edited · dir*), then the files its replies mention that no turn recorded (detail *Mentioned · dir* or *Mentioned · workspace*); *None yet.* shows when there are none. Skills and MCP and Files each show five rows, with a quiet *Show all N* / *Show fewer* for the rest. Project context reads as prose directly below the linked project name. File mentions are clickable in place, with the canonical filename resolving to its full path; no separate document-link row or raw capsule fields are displayed. Token estimates still measure the sent capsule, not this presentation.

The task board keeps the same status groups on every device: **To do, In progress, In review** as three lanes side by side in one row, each a fixed 310px wide at every pane width (they never stretch or shrink, so a card's state and its action stay on one line). When the lanes do not fit, the row scrolls sideways inside the board; the page itself never scrolls sideways. **Done** is collapsed behind a **Done** tab at the end of the row (a 44px vertical tab with the lane's count), remembered per browser; opening it shows the Done lane with a **Hide** control, and the tab is also a drop target that opens the completion sheet. The **Done** status filter still lists every done task. The card's own surface drag, Move up / Move down in its menu and Shift+Left/Right place a card at every width, and the editor's status control is the path that needs no drag. A status filter draws its one group at full width. The lane heading names a card's status, so cards do not repeat it in a badge. Done keeps to tasks completed today (by completion time, not last edit); earlier ones, undated ones included, are one click away under Show all, which counts them. Every Done gesture opens the completion sheet. The note is optional and the sheet has one completion action (Mark done, Approve done, or Save resolution) plus Cancel: an empty or whitespace-only note completes without a resolution, a nonblank note is kept as typed, and the note and status are one write. A failed write keeps the note in its sheet. While a task is in progress or in review, the editor records progress notes (Save, or Save and send to the live attempt). Notes read as a comment feed, newest first under the box that adds to them: each is a bubble led by its author and time, rendered as Markdown with its links live, the agent's in a violet tint and named *Agent* in text; a note's Edit stays quiet until the note is hovered or focused (always shown on touch). The completion sheet for a result that is ready for review, the delete confirm and the Reject confirm (a *Reject…* button in the task detail, shown only for a review-ready task) carry an optional *Why?* field with five quick chips (*not mine*, *not a task*, *already done*, *wrong person*, *good as is*) and free text; it is skippable and never changes the number of clicks a decision takes.

A chat manually linked to board tasks names each task as its own row in Chat details' **Origin** section (the task title, the detail *Linked task*), opening the same task overlay as the delegated task's row. Multiple links are all shown, in title/id order; a task already named by the chat's delegation is not repeated. These read-only links show no agent state or completion controls. They do not make the chat a delegated attempt, change its Needs you tier or turn archive into task completion. The task record's `linked_chats` is the sole source; delegation keeps its existing separate lifecycle. Such a chat also carries the checkbox glyph in the sidebar and on Home, its tooltip and accessible name reading *Linked to a board task*, while a delegated chat's reads *Delegated board task*; the visible mark is the same for both.

A project page closes through one sheet: *How did it end?* picks **Completed** or **Stopped**, the note is optional, and one action closes the project — a blank or whitespace-only note closes it with no note, a typed note is kept trimmed. Like the task board's completion sheet, the sheet has no second action for closing without a note; it keeps *Cancel* and its × close control.

The workspace editor is the Workspace, Claude context trimming and Chats and models cards on Workspace › Overview, followed by All workspaces, always open for the active workspace. It keeps one consistent label/control row per field, with each explanation directly below its own field. A dirty form offers primary **Save changes** and neutral bordered **Discard**; there is no Close because the page is always open, and a clean form offers neither. Switching workspace discards the previous draft, and a switch started while the draft is dirty asks first ("Discard unsaved changes to NAME?") and stays when declined. The Chats and models card holds the default provider switch (a segmented radiogroup; arrows select) and, for the selected provider, this workspace's overrides of the Providers defaults: model, thinking, permission mode and session insights model. The first option of every field names the engine default (`Engine default (High)`), an empty choice means the engine default, and each provider keeps its own overrides when the switch changes. Claude context trimming lists the engine's trim catalog as one switch per option (On means Claude can use it; Off hides it from Claude), grouped, with groups of four or more behind a native disclosure that shows how many are hidden; locked options are disabled and say why; Extra denied tools and Reset to defaults close the card, and its changes ride the same Save changes. All workspaces is the last card of Workspace › Overview, below the active workspace's cards and above no other page. It is a list of boxed rows (10px radius, 16px padding): a drag handle, the workspace tile with its 1-9 key, the name with a Main workspace tag and a muted `Key n` for positions 1-9, a summary line `provider`, a `Settings ↑` link that makes that workspace active and scrolls to the top (the active workspace's row shows `Current` instead), and a `···` menu with Rename, Move up, Move down (disabled at the ends) and, when allowed, Archive. Rows reorder by dragging the handle (an accent line marks the drop row), by Alt/Option+Up or Down while the handle has focus, or from the menu, which is the touch path; the handle and the menu items are 44px on coarse pointers. The order is engine-wide, is saved at once (a failed save puts the row back and says so in the page's error line), and is the switcher order and the 1-9 shortcut mapping; when no workspace is named `personal`, the main workspace stays first: its row has no handle (a spacer keeps the rows aligned) or Move up / Move down, and nothing can be moved above it. Archived rows have no handle and a restored workspace goes last. Each move is announced in a polite live region ("Moved Work to position 2 of 3") and focus stays on the moved row's handle. There is no inline editor. The short New workspace form (Name, Accent, Agent CLI/Runtime) ends in **Create and open**, which creates the workspace, makes it active and lands on its cards at the top of the page; Claude context trimming (including claude.ai connectors) is set there. ## Colors

The Access & memory onboarding stage offers approval mode only, states that bypass is full user access, states that Claude Auto is not a safety guarantee, and never treats OpenCode model instructions as enforced safeguards.

Dark mode is the primary visual expression. It uses layered indigo surfaces instead of neutral black, keeping long sessions comfortable while preserving clear hierarchy.

- **Primary orange (`#fb923c`, the `amber` preset):** The brand accent and primary-action color. Use it for the current location, focus, progress, and the single most important action in a region. It replaced the earlier pink `#ff4d6d`, which sat about 15° of hue from the error red and made a primary action read as a failure. Workspaces may override it with a saved accent preset (`amber`, `pink`, `cyan`, `emerald`, `violet`, `blue`, `teal`, `lime`, `fuchsia`); a workspace that saved pink keeps it, and only an unset colour follows the default. Canvas and surface tokens stay fixed.
- **Neutral accent while loading:** Until the active workspace's colour is known, the app wears `neutral` (`#b4b4c4` dark / `#5f607d` light), or the colour this browser showed last, so the first paint never flashes an accent that then changes.
- **On-primary (`--on-accent`, `#1a1a2e` dark / `#ffffff` light):** The label colour on any filled accent surface: primary buttons, active pills and toggles, accent badges. Never hard-code white on the accent. The dark accents are bright, so white on them measures about 2–3.6:1; the indigo canvas colour clears 4.5:1 on every dark accent and its hover shade (orange 7.54 / 4.79, pink 5.31 / 4.69). Light accents are deep enough for white (orange 5.18 / 7.31, pink 4.95 / 7.02).
- **Accent presets:** Each preset pairs `--accent` with a hover shade `--accent-strong`, and both must keep `--on-accent` at WCAG AA. Dark: amber (default) `#fb923c`/`#ea580c`, pink `#ff4d6d`/`#ff2e54`, cyan `#38bdf8`/`#0ea5e9`, emerald `#34d399`/`#059669`, violet `#a78bfa`/`#9670f7`, blue `#60a5fa`/`#3b82f6`, teal `#2dd4bf`/`#14b8a6`, lime `#a3e635`/`#84cc16`, fuchsia `#e879f9`/`#d946ef`. Light: amber `#c2410c`/`#9a3412`, pink `#d81b60`/`#b00d46`, cyan `#0369a1`/`#075985`, emerald `#047857`/`#065f46`, violet `#7c3aed`/`#6d28d9`, blue `#1d4ed8`/`#1e40af`, teal `#0f766e`/`#115e59`, lime `#4d7c0f`/`#3f6212`, fuchsia `#a21caf`/`#86198f`. Red and yellow are excluded: red reads as an error, yellow collides with `--warning`. The light shades also keep accent-coloured text at AA on white.
- **Violet (`#6a47b8`):** A secondary accent for selected filters, contextual information, and supporting distinctions. It must not compete with the primary action.
- **Background (`#1a1a2e`):** The deepest application canvas.
- **Surfaces (`#1f2240`, `#23264a`, `#2a2e54`):** Cards, elevated controls, hover, and pressed states. Prefer tonal separation and borders over large shadows.
- **Text (`#e8e8f0`):** Primary content. Muted dark text uses `#b4b4c4`; `#8f90a8` is the AA-compliant tertiary token for metadata and secondary controls. In light mode the tertiary token is `#66687f`; never reuse the old washed-out `#8e90a8` value for meaningful text.
- **Soft text contrast (opt-in):** `data-text-contrast="soft"` on `<html>` lowers only `--fg` (dark `#e8e8f0` → `#d2d2de`, 14.0 → 11.4:1 on `--bg`; light `#1a1a2e` → `#2e2f46`, 15.6 → ~11.9:1). `--fg2`/`--fg3` do not change. The default is unchanged.
- **Body font (opt-in):** `data-body-font` on `<html>` swaps `--font` between system sans (default), a serif stack (`Charter, 'Iowan Old Style', 'Palatino Linotype', Palatino, Georgia`) and `--font-mono`. It applies to chat prose, UI body text and titles (titles use `--font`). Code, badges, commands, timestamps and the wordmark stay `--font-mono` regardless. Components use `var(--font)`, never `var(--font-sans)`, for prose and controls.
- **Custom colours (opt-in):** `custom_colors` stores a background and text colour per theme; the active theme's pair is written as inline custom properties on `<html>` (`--bg --bg2 --bg3 --bg-elev --fg --fg2 --fg3 --border --border-strong`), with surfaces and secondary text derived from the pair by `lib/contrast.ts` (`deriveCustomTokens`). A pair is applied only if body text clears WCAG AA 4.5:1 on `--bg` and on the hover surface `--bg3`; otherwise the dialog refuses it and says why. Accent, status and canvas-painted surfaces (Memory map) are not recoloured. A custom pair overrides Soft text contrast for that theme.
- **Engine-wide appearance:** Settings › Appearance (theme, font size, text contrast, body font) is stored on the engine, so every device agrees; `system` theme still resolves per device from its OS. `ciao-theme`, `ciao-font-scale` and `ciao-appearance` in localStorage are paint caches only, restored before mount and overwritten by the engine value. The first browser to load against an engine that has never stored a theme or font size seeds it once from its own values.
- **Error text (`--error-text`, `#ff7f75` dark / `#b3201f` light):** The colour of any red *text*, including `color-mix()` text built on red. `--error` (`#f44336` / `#c62828`) stays for fills, borders and tints; as 0.8rem text it measures 4.19:1 on dark `--bg2` and 3.53:1 on `--bg3`. `--error-text` is 6.94 / 6.28 / 5.28:1 on dark `--bg` / `--bg2` / `--bg3` and 6.10 / 6.68 / 5.48:1 on light `--bg` / `--bg2` / `--bg3`. It also clears 4.5:1 under the 15% `--error` tint of `.badge--error` on every surface (lowest: 4.67 dark `--bg3`, 4.56 light `--bg3`), so a red-tinted badge or line may sit on any surface. Never set `color: var(--error)`.
- **Semantic colors:** Green communicates success, orange caution or recoverable risk, and red destructive actions or errors. Never use semantic colors decoratively, and never for a status glyph: accent presets (pink, amber, lime) sit next to them in hue, so status marks take the row's accent and shape carries the meaning.

Light mode keeps the same hierarchy with a soft lavender canvas, white surfaces, crisp crimson accent, and slate text. It is an adaptation of the same system, not a separate aesthetic.

Color is never the only state signal. Pair status colors with text, an icon, a shape, or an accessible label. Verify WCAG AA contrast in both themes whenever a token or component changes.

## Typography

Native installer setup uses a compact in-app hierarchy: retain the setup wordmark and form, while omitting terminal chrome, terminal-only instructions, and the product tour. Native setup controls keep 44px minimum touch height and 16px input text; visible keyboard focus and browser zoom/reflow remain available.

The product uses a **hybrid typography system** (the proportional face is the opt-in **Body font** below): a clean system proportional sans-serif stack (`-apple-system`, `SF Pro`, `Segoe UI`, `Roboto`) for conversational chat prose and general UI, paired with a monospaced stack (**SF Mono**, **Fira Code**, **Cascadia Code**, `monospace`) for code blocks, badges, commands, schedules, timestamps, and terminal identifiers.

- **Titles:** 15–16px, bold, with slightly tight tracking. Titles should remain visible when actions compete for space.
- **Body:** 14px on desktop with comfortable 1.6 line height for natural reading.
- **Font scale:** every size is multiplied by `--font-scale`, whose default is `1.15` (`DEFAULT_FONT_SCALE` in `useFontScale.ts`): 14 × 1.15 = 16.1px body, the platform's 16px body, with Settings showing that as 100%. A stored scale still multiplies every token. On a phone the composer uses the same body size, floored at 16px so iOS never zooms a focused field, so typed and sent text are the same size.
- **Chat prose:** a request keeps 1.5 leading; a reply uses 1.55. Markdown headings inside a reply are 1.35em / 1.18em / 1.08em (h1/h2/h3) of the message font.
- **Mobile form text:** At least 16px to prevent browser auto-zoom while keeping user zoom available.
- **Labels & Badges:** Monospaced 11px, semibold, often uppercase with 0.5px tracking for technical precision.
- **Brand mark and wordmark:** The expanded sidebar uses `BrandMark.vue` at 30×30px: the C is inline SVG using `currentColor`, while its two dots use the selected `--accent`. The same vector source powers `CiaoMark.vue` (optional `progress` prop, geometry in `lib/ciaoRing.ts`, shared with the website header). `BrandMark` is a button: hovering or focusing it slowly closes the C into a ring, leaving reopens it from wherever it got to (so it can be stopped midway and reversed), reduced motion keeps the static C, and a click hard-refreshes the app (service workers updated, caches cleared, reload with a cache-busting query), with a 44px touch target around the 30px mark. The Settings mark stays static. No raster masks. The startup, login, restart and update screens use `Wordmark.vue`, which shows the supplied wordmark artwork (`web/public/brand/`): the ink image on light themes and the off-white image on dark themes, switched by the `theme-light` class on `<html>`. It is an image, so no workspace accent or body-font preference recolours or re-fonts it. The login screens sit in a plain bordered box with no window chrome. The mark is not required when the sidebar is collapsed or the phone drawer is closed; the toggle or hamburger remains the navigation entry point. Pane headers have no mark or `brand` prop; page tags, titles and header controls remain unchanged. The supplied small logo (`web/brand/ciaobot-icon-source.png`) remains the source for app icons, generated by `npm run build:icons`; the iOS home-screen icon remains a fixed PNG because iOS reads it once when the app is added. A blinking caret may appear only in startup or explicitly terminal-like moments.

Respect the user-controlled font scale. Truncate compact navigation labels only when the full value remains available through context, title text, or an expanded view.

## Elevation & Depth

Hierarchy comes primarily from tonal layers, one-pixel borders, and spacing. Cards sit on the page background; inputs may use the deeper canvas; modals and popovers use the elevated surface. Use stronger borders for focus and separation before adding shadows.

Shadows are reserved for content that genuinely floats above another interaction layer: mobile drawers, menus, modals, and toasts. Toasts sit above the page but under an open dialog; they return on top when it closes. Keep them soft and dark. The normal application surface stays clean; CRT grain is reserved for startup, update, and native terminal surfaces where it carries product meaning. Scrollbars are hidden everywhere (`web/src/styles/app.css`): every region still scrolls by wheel, trackpad, touch and keyboard, and no surface may need a scrollbar to be usable. Nothing scrolls sideways unless it is meant to (a code block, a wide table, the turn-facts strip, the title rail); an element that spills past its container is a bug, not a reason to show a bar.

## Shapes

The shape language is compact and gently rounded. Standard controls and cards use a 10px radius, small nested elements use 6px, and modals use 14px. A tighter 4px radius (`--radius-xs`) is reserved for small squared tags that must not be mistaken for count badges: the needs-you state chip and the workspace key badges. Fully rounded shapes are limited to badges, status dots, avatars, and true pill selectors. The prompt surface (chat composer, Home intake) uses `--radius-composer`: 15px, and 28px on coarse-pointer phones so it sits concentric with the screen's corners; on that phone surface only, its model chip, attach and send controls are pills and circles to match.

Borders are structural, not decorative. Active navigation is marked by a slim accent edge plus a tonal background. Warning callouts use a muted warning-tinted surface with a 1px perimeter; quoted passages use a neutral 1px divider. Do not mix exaggerated rounding, glass effects, or unrelated shape styles into the same view.

## Do's and Don'ts

- Do reserve accent emphasis for the current location, focus, progress, and primary action.
- Do keep titles and textual state visible when layouts become narrow.
- Do use plain-language recovery guidance instead of exposing raw IDs or implementation details.
- Do make every touch target at least 44×44px and every core workflow keyboard accessible.
- Do preserve browser zoom, font scaling, safe-area behavior, and reduced-motion preferences.
- Do test dark and light themes at desktop and mobile widths.
- Don't turn a group of routine actions into competing accent bars.
- Don't rely on unexplained icons, color alone, hover, or animation to communicate state.
- Don't expose long prompts or diagnostics in full by default on mobile.
- Don't copy custom styling into a host-native surface when platform conventions are clearer.
- Don't introduce new colors, radii, shadows, or typefaces when an existing token serves the purpose.

- **Onboarding location:** Ask for the main Ciaobot folder before the workspace name. Before provisioning, it is a candidate location (empty or existing-notes folders are both valid); after provisioning, show the folder and workspace name as set, with Change leading to the guarded move flow (the name field appears only after Change). Remote browsers explain that the folder belongs on the Ciaobot computer. Typing never creates, moves, or saves anything; Continue in the setup footer is the explicit handoff to the next stage.

- **First-run separate notes:** Offer an optional existing notes folder alongside the Ciaobot operational folder. Show both locations, require a successful local inspection before finishing, and describe synchronization as the cloud client's responsibility.

The onboarding care stage follows the setup shell's calm, compact form rhythm: host availability guides the suggested local time, while the editable time and IANA zone are explicit controls. The fields propose 07:00 in the browser's timezone (availability can move the suggestion), and Continue saves what they show as the routine's timing, so an onboarded install runs care in its own morning; a routine already set to a zone other than the packaged UTC is proposed unchanged. A status line says exactly what is saved: *Care will run at 07:00 Europe/Zurich. Saved when you continue.*, then *Care runs at 07:00 Europe/Zurich.* once it matches the engine. There is no Save or Keep-default button, and a failed save shows an inline error and Continue retries it. Without a care routine Continue is available.

## Onboarding finish

Finish lists only the rows that need attention (attention or unknown), says “Nothing needs attention.” and how many items were left for later when none do, and keeps tools and the video behind a Tips disclosure. The first-task composer is an explicit, optional action; Continue (Finish setup) remains owned by the setup shell's single sticky footer.

## Onboarding: runtime and model

The runtime stage asks for a runtime, then an explicit model. Reported models and configured
aliases never share a list: the first is evidence from a connected runtime, the second is a set
of choices whose availability is unknown. Deferring is a first-class choice, not an error, and
the stage never starts a provider or a model turn on its own.

quiet resume row while setup is unfinished, because a new operator should never have to remember
a URL.
