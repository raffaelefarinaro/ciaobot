# Ciaobot Design System

## Overview

Ciaobot is a focused control surface for a personal AI assistant. Its visual identity combines the precision of a developer console with the warmth needed for daily conversation. It should feel capable, private, calm, and direct—not corporate, ornamental, or like a generic chatbot.

The PWA is information-dense but not cramped. A system sans carries prose and controls, monospace is reserved for technical metadata and terminal cues, restrained animation and a deep indigo foundation establish the console character, and a warm orange accent supplies personality and orientation. The interface must remain understandable without color, animation, hover, or prior knowledge of its icons.

The home screen (**Home**) is the primary entry point and uses the Workbench composition. It has no headline, eyebrow or lede: the command surface is the page's subject. The surface holds the prompt, then one bar with the project chip (opens the shared project picker and only remembers the pick), a model chip (the workspace default unless the user picks a Claude or opencode model, which rides the chat-create call and resets on a workspace switch), and one icon send control whose accessible name stays **New** (it starts the chat in the chip's project without asking again, opening the picker only when the chip has no project to name; ⌘/Ctrl+Enter sends, bare Enter is a newline, as in chat). Beside it on wide panes, the rail holds Home's alerts and *At a glance*. The alerts come first: operator notices (including *A new Ciaobot version is ready to install* and anything Settings needs checked), *After this update* cards, and *Show N closed notices*. They stack as separate windows. *At a glance* lists only the queues that need a look (tasks the agent reported done and waiting for review — one opens its card, several open the board — then memory proposals, notes to revisit, and automations that failed, did not run, or lost their chat — one opens that automation, several open Automations; a missed one-time reminder is the install-wide notice instead) as plain hairline rows with no icons or action words. A failing automation's title reads in the warning colour. It says *Nothing to review.* when all are clear. While the page scrolls the notices scroll away and *At a glance* stays in view. Below the composer, *Continue where you left off* lists the selected workspace's chats as flat rows — title, a project · status sub-line read from the row's tier, time on the right. Rows are grouped in this explicit order: **Needs you**, **Working**, **Unread**, and **Earlier**. Below those tiers a separate **memory insights** section carries one entry per archived conversation whose memory work is in flight, unfinished, or asking for an answer. The entry is named for the *conversation*, never for the internal memory pass behind it, and its status is a state in words — *archiving…*, *queued for memory*, *updating memory…*, *needs you* (with the pending question on a second line), *needs attention*, *memory updated*. Clicking it opens the memory pass, which is a real chat: the live turn, the question and the reply all live there, and the archived transcript is the fallback only while no pass exists. A memory pass is never a chat row in the tiers and never appears in the sidebar. The workspace name appears once, in the sidebar's workspace scope: the Home header says only *Home*, and the selected lane has no visible header (its status sentence remains for screen readers). Rescue lanes for stale or unknown workspaces keep a visible name and New action, because the name is what explains them. Switching workspaces swaps the home content instead of adding a column. Arrow-key navigation follows the visual order, using up/down between stacked lanes and left/right within a lane. Signals are shape-and-text-first (tier labels, weight, dots) so no tier relies on color alone. Counters are sparing: the sidebar's workspace scope shows only the name (counts and key hints live in its menu), New chat carries its shortcut in its tooltip, Home shows a subtle count when chats need you, Tasks shows a quiet count of the tasks waiting for review, and Memory a quiet count of its queues; every link's accessible name keeps the number. When the pane (not the window) is narrower than 940px the rail drops below the request column, and the alerts stay under the composer, above *Continue where you left off*, so on a phone they are never below the chat list. The expanded sidebar stacks the wordmark row (ending in the back / forward pair, a hairline, then the collapse control; the pair drops below the toggle on the collapsed 40px rail, and on phones, where the sidebar is a drawer, the pane header shows a Back chevron after the menu button whenever there is in-app history; ⌘[ / ⌘] in the browser), the workspace scope, New chat, the destinations as a labelled list (38px rows, 44px on coarse pointers; the current one on an accent-tinted fill), then the `Projects` tree at 36px row density. In a plain browser tab on a secure origin, Home shows a short *Set up this device* section (install the app, turn on notifications, send a test; on the computer running Ciaobot, a *Use on your phone* row with the three Tailscale steps and a link to Settings → Other devices, which never counts toward finishing setup). It is plain rows with one primary action, dismissible per browser, and it disappears once the app is installed and notifications are on. On an install whose password setup generated, Home shows a one-time *Your Ciaobot* window above *Set up this device*. It names the workspace folder (with Show in Finder / File Explorer on the computer running Ciaobot), the password (masked; Show and Copy only on that computer, elsewhere a line saying where it is shown) and the AI tool. Its X dismisses it for every device.

Core product work follows one visible model: **request → run → output → durable knowledge**. The transcript remains the reasoning surface. Chat details (context, what is running, skills and MCP used, files) sits beside the conversation on a wide pane and opens over it on a narrow one, without forcing a permanent multi-column IDE layout. The chat header holds only close, the title, a small accent mono `›_` glyph button after the title while the chat is in code mode (it opens Chat details at its Repository section), and **Archive** as a filled primary button with its label (it is the header's one action; on a narrow pane, where the Chat details opener sits beside it, Archive is icon-only). With code mode off the header says nothing about the repository. Archiving a chat that holds an open board task, from the header or the sidebar menu, asks first: *Complete task…* opens the same closure note as the rail (*Approve Done* while the result waits for review, which the engine follows by archiving the chat; *Mark done* otherwise, which then archives). The note is optional: one action completes, and a blank note completes without a resolution. *Keep task open* archives and leaves the task where it is, and *Cancel*. Any other chat gets the plain archive confirm. The chat's project stays in Chat details and the sidebar, not in the title header. On a phone a header with nothing to centre (chat, subagent, pinned file) is one row — menu, Back (when there is in-app history), then the title block led by its own close button, and the actions. Chat details is not toggled from the header: a neutral × at the right end of the rail's title bar closes it. While it is hidden (or the pane is too narrow for a rail), an info (ⓘ) button sits as a small bordered tab at the chat body's top right and brings it back, opening the drawer on narrow panes. Project is the context envelope; Memory's To decide section is the durable-knowledge inbox; its Map (Graph/List) is the deeper exploration mode. **Tasks** is a workspace destination of its own: a four-column board — To do, In progress, In review, Done — built from the existing card, badge and chip tokens with no column drag, a card's status being a native select, and the four columns reading as one status-filtered list on a narrow pane. Memory lists its sections in the sidebar exactly as Settings lists its tabs — *To decide* first on its own row, then *Explore* (Map, Categories) and *Records* (Retired, History), each a route with a quiet count at the row's end (accent on To decide) — so the page header only names the section ("Memory · To decide") and carries no mode switch or tab row. Under that header every Memory section carries one collapsed-by-default *How memory works* disclosure (a hairline section, not a card, with a 44px toggle whose open state is remembered per browser in `ciao.memory.howOpen`): static text on what is saved, the memory pass, what is not saved, a table of who settles each tag, the optional reason every decision carries, and a link to the Categories tab and to the site page. To decide holds both queues on one page: a row of filter chips (*All*, *Suggested*, *To revisit*, with counts and no zero chips) narrows it to one queue, and the filter rides in the address (`/memory/review?show=revisit`) so Home and the map link straight to the queue they name. Under *All* an empty queue steps aside for one that is not. The map's search and category filters sit under that list only while Map is showing. The two queues share one row shape: a 16px heading and one muted sentence, violet-tinted filter chips (by change type; by reason; and *Needs you*, the rows the memory pass or nightly run marked for the operator plus rows with no decider, shown only when it would hide something) with counts and no zero chips, a row showing its decider and a one-line reason, then hairline rows with a fixed-width action column of neutral bordered buttons and a text link — no pink primary on a row, since every row is the same routine choice. A suggestion names its change before it is opened: a bordered tag with a drawn icon (*New note*, *Add to a note*, *Merge into a note*, *Update a line*, *Move a note*, *Already saved*), the destination in mono, and a compact numbered diff; its button is the verb (*Create note*, *Add line*, *Merge*) and opens the decision card, which confirms against the previewed revision. A note to revisit shows *type · reason · backlinks*, and each reason is a disclosure for its evidence (the quoted line with the match marked, or the check date and where it came from). Every individual accept and dismissal in the queue asks for an optional reason (quick chips plus free text) before it writes: accepting opens the decision card with the reason on it, and a dismissal opens an inline confirmation naming the proposal and asking why. Picking the workspace for a re-home is the one exception — the destination is the answer — and the batch bar never asks. The reason is never required — with none typed the button says *Continue without a reason* and the card names the action it is about to take — and History shows the reason beside the decision. Memory handover is an operator-only Settings card shown with its evidence (the nightly run's agreement rate): new workspaces start at *Dismiss and accept*, existing choices are preserved, and *Off* remains one click away; the agreement rate never changes the setting on its own. Choosing *Dismiss and accept* says it lets queued text reach always-loaded memory, and the card says plainly when handover cannot act on this install. History marks a row the nightly run settled itself "Filed by Workspace care" and offers Undo from the row; a prediction miss is a muted *Missed* badge, information and never an error state.

There is no native shell: the engine serves the PWA, and every one of these
states is a page in it. Before the engine reports startup phases, the connecting
screen states that it is checking the connection, with indeterminate motion rather
than an invented 0% boot progress. When the engine reports phases, it shows their
real status in plain-language rows. This screen shares the calm indigo canvas,
type hierarchy and restrained accent of the engine recovery curtain; neither
pretends the browser is booting the host. The update overlay remains the only
place a package update is reported, and it says a restart is pending until the
new engine answers. In the PWA, an
engine that stops answering shows a full-screen recovery curtain over the kept
route. It uses the boot-screen language: a plain title, `ciao service
start|status` on this computer, Retry, and automatic reconnect. It is modal
(focus trapped, shortcuts suppressed), and it lifts without a reload when the
engine returns.

A chat turn that fails because the provider CLI is signed out keeps its
automatic retry, and both the retry card and the error bubble carry a closed
**How to sign in again** disclosure: open a terminal, paste the sign-in command
(the one the engine reports for that provider, with a Copy button), then come
back and click the card's **Try now** or the bubble's **Retry**, repeated as the
last step. Nothing opens a terminal or signs in on the user's behalf.

On Home, the review rail is titled **At a glance**. Actionable operator notices and update tasks sit in separate in-flow windows in the rail (under the composer on a narrow pane); device setup sits in its own window in the request column. Each window has the pinned file tile's tonal surface, bordered header and close control. For operator actions and update tasks, X hides the window until reload (or until **Show N closed notices**) and persistent Hide remains a separate, explicit action. The device-setup reminder is different: its X is the only dismissal control and persists for this browser, so it does not nag again after a reload. The *Your Ciaobot* window is install-wide: its X is its only dismissal control, it is not counted again by *Show N closed notices*, and once closed the engine stops serving the password. Chat-row signals sit right-aligned above the relative time in both wide and narrow panes. In-flight memory insight rows use one quiet **extracting…** label; blocked and completed phases retain distinct wording. A normal browser tab cannot know whether the app is separately installed; installed PWA windows use display-mode detection, and the retired Ciaobot.app desktop wrapper does not report itself as a PWA. An operator notice may carry a host-terminal action and its command. It shows **Update in Terminal** only in a browser on the engine's computer, and the command with **Copy** everywhere. Nothing installs on the user's behalf, **Check again** re-reads the version, and **Not now** hides it until a newer tested version ships. In Settings → Providers each provider row says which version this release was tested with, and offers the same command and button when the installed CLI is older.

Chat details uses the pinned viewer's docked-window vocabulary: a tonal `--bg2` surface, border, 14px radius, inset spacing, and a separated title bar with a neutral × close control. On a wide pane it is only as tall as its content, resting 16px under the header (the composer's own gap to the pane's bottom edge), and scrolls once it would reach 16px from the bottom, where its edge lines up with the composer's. The info tab is only the opener. On a narrow pane the opener sits in the header beside Archive, so it never covers the transcript; it is a borderless icon button like Archive, and Archive is icon-only beside it. It is one panel at every width — the same stacked sections and one × close, read by scrolling — shown in place on a wide pane and, on a narrower one, as a full-height drawer from the right (a bottom sheet on a phone); there are no Context/Activity/Output tabs. Repository, **Context usage**, **Always loaded** and Files use the same section-heading rhythm; Running and Skills and MCP retain their existing positions. Context usage appears only once a provider reports a figure, with its meter, percentage in words and Compact action. Always loaded contains, first, the **Ciaobot system prompt** row (a disclosure with its token count, closed by default, that opens the full text in a scrollable mono box with a Copy action), then the unchanged guide, project context and repository-instruction rows, behind a disclosure that starts closed: its summary row carries a drawn chevron, the label and the rows' token total, its open state is remembered per browser (`ciao.chatDetails.alwaysLoadedOpen`), and *See what Ciao knows* opens it (which is then remembered too, like any open). The terminal is one bordered full-width row (the `›_` prompt glyph, *Open terminal*, an arrow) under the Repository block, with no separate heading. The repository's branch line is a button disclosure (drawn chevron and branch icon, the name in mono, the worktree and dirty facts beside it, or under it when the name is long); its branch and path open underneath as an inset key/value block at the section's full width, and a locked Code mode says *Locked on for this chat* under its label so the switch row never wraps. Files, Mentioned in replies, and Skills and MCP used each show five entries — files newest first, by their latest touch — with a quiet *Show all N* / *Show fewer* text button for the rest. Project context reads as prose directly below the linked project name. File mentions are clickable in place, with the canonical filename resolving to its full path; no separate document-link row or raw capsule fields are displayed. Token estimates still measure the sent capsule, not this presentation.

The task board keeps the same status groups on every device: **To do, In progress, In review** as three lanes side by side in one row, each a fixed 310px wide at every pane width (they never stretch or shrink, so a card's state and its action stay on one line). When the lanes do not fit, the row scrolls sideways inside the board; the page itself never scrolls sideways. **Done** is collapsed behind a **Done** tab at the end of the row (a 44px vertical tab with the lane's count), remembered per browser; opening it shows the Done lane with a **Hide** control, and the tab is also a drop target that opens the completion sheet. The **Done** status filter still lists every done task. Pointer drag and Shift+Left/Right move a card between lanes at every width, and the editor's status control is the path that needs no drag. A status filter draws its one group at full width. The lane heading names a card's status, so cards do not repeat it in a badge. Done keeps to tasks completed today (by completion time, not last edit); earlier ones, undated ones included, are one click away under Show all, which counts them. Every Done gesture opens the completion sheet. The note is optional and the sheet has one completion action (Mark done, Approve done, or Save resolution) plus Cancel: an empty or whitespace-only note completes without a resolution, a nonblank note is kept as typed, and the note and status are one write. A failed write keeps the note in its sheet. While a task is in progress or in review, the editor records progress notes (Save, or Save and send to the live attempt). Notes read as a comment feed, newest first under the box that adds to them: each is a bubble led by its author and time, rendered as Markdown with its links live, the agent's in a violet tint and named *Agent* in text; a note's Edit stays quiet until the note is hovered or focused (always shown on touch). The completion sheet for a result that is ready for review, the delete confirm and the Reject confirm (a *Reject…* button in the task detail, shown only for a review-ready task) carry an optional *Why?* field with five quick chips (*not mine*, *not a task*, *already done*, *wrong person*, *good as is*) and free text; it is skippable and never changes the number of clicks a decision takes.

A chat manually linked to board tasks names each task in Chat details as **This chat is linked to the task …**, opening the same task peek as delegated-task links. Multiple links are all shown, in title/id order; a task already named by the chat's delegation is not repeated. These read-only links show no agent state or completion controls. They do not make the chat a delegated attempt, change its Needs you tier or turn archive into task completion. The task record's `linked_chats` is the sole source; delegation keeps its existing separate lifecycle. Such a chat also carries the checkbox glyph in the sidebar and on Home, its tooltip and accessible name reading *Linked to a board task*, while a delegated chat's reads *Delegated board task*; the visible mark is the same for both.

A project page closes through one sheet: *How did it end?* picks **Completed** or **Stopped**, the note is optional, and one action closes the project — a blank or whitespace-only note closes it with no note, a typed note is kept trimmed. Like the task board's completion sheet, the sheet has no second action for closing without a note; it keeps *Cancel* and its × close control.

The workspace editor is the Workspace, Chats and models and Google account cards on Workspace › Overview, always open for the active workspace. It keeps one consistent label/control row per field, with each explanation directly below its own field. A dirty form offers primary **Save changes** and neutral bordered **Discard**; there is no Close because the page is always open, and a clean form offers neither. Switching workspace discards the previous draft, and a switch started while the draft is dirty asks first ("Discard unsaved changes to NAME?") and stays when declined. Discarding never saves or changes file-access permissions. The Chats and models card holds the default provider switch (a segmented radiogroup; arrows select) and, for the selected provider, this workspace's overrides of the Providers defaults: model, thinking, permission mode and session insights model. The first option of every field names the engine default (`Engine default (High)`), an empty choice means the engine default, and each provider keeps its own overrides when the switch changes. Manage workspaces (`/settings/workspaces`, from the switcher, not the rail) is a list of boxed rows (10px radius, 16px padding): a drag handle, the workspace tile with its 1-9 key, the name with a Main workspace tag and a muted `Key n` for positions 1-9, a summary line `provider · file access · Google email or no Google`, a `Settings →` link to that workspace's Overview, and a `···` menu with Rename, Move up, Move down (disabled at the ends) and, when allowed, Archive. Rows reorder by dragging the handle (an accent line marks the drop row), by Alt/Option+Up or Down while the handle has focus, or from the menu, which is the touch path; the handle and the menu items are 44px on coarse pointers. The order is engine-wide, is saved at once (a failed save puts the row back and says so in the page's error line), and is the switcher order and the 1-9 shortcut mapping; when no workspace is named `personal`, the main workspace stays first: its row has no handle (a spacer keeps the rows aligned) or Move up / Move down, and nothing can be moved above it. Archived rows have no handle and a restored workspace goes last. Each move is announced in a polite live region ("Moved Work to position 2 of 3") and focus stays on the moved row's handle. There is no inline editor. The short New workspace form (Name, Accent, Agent CLI/Runtime, File access) ends in **Create and open**, which creates the workspace, makes it active and lands on its Overview; Google and connectors are set there. The Archived workspaces list stays on the page; there is no Google card here, since each workspace's account is managed on its own Overview. Memory handover is a three-way segmented control styled like Theme (Off / Dismiss / Dismiss and accept): arrows select, and `Dismiss and accept` asks first.

The device-setup reminder uses quiet task labels at `--text-base`, weight 600, and one aligned action column. Installation help is a real navigation link styled as a neutral bordered action; notification Enable and a browser-provided Install action retain primary emphasis. On narrow panes, row actions become full-width touch targets. *Use on your phone* is a closed native disclosure containing the existing three instructions and the permanent Settings → Other devices link. Phone setup remains host-only and informational, never a completion requirement; closing the reminder still persists for this browser.

Shared model-picker sections show readable names while retaining the exact technical identifier in each option's tooltip, data and search. Provider badges come only from the identifier's actual namespace, never an inferred upstream vendor, and remain beside any Default badge. Formatting changes presentation only: selected raw identifiers and provider routing stay unchanged.


The Google account card on Workspace › Overview is one row for the active workspace in three states: connected (name, email, a Connected badge and a `···` menu), Sign-in expired (an error badge and a primary **Sign in again**) and none (a sentence and a primary **Connect Google account**). It never lists other workspaces' accounts. Connect and Sign in again open a modal sheet (the `modal` token, edge-to-edge under 600px, focus trap and Escape through `useModalFocus`, focus returning to the row): a Display name field (the gws profile id is derived from the workspace name and never typed; the storage folder is shown), then three steps with finished ones as quiet status lines: gws CLI installed, OAuth client (create one with gcloud, or upload `client_secret.json`), and Sign in with Google (loopback) with **Paste a code instead**. **Done** enables once connected, and the workspace is linked automatically. **Disconnect and remove** confirms, naming any other workspace that uses the account.

The chat header keeps close, title and any `›_` code button on one vertical centre, so a wrapped title never moves the close control; project context stays in Chat details and the sidebar rather than being repeated in the title header. A long title wraps to at most two lines with the full title on hover. While the engine is naming a brand new chat, the header shows the shared shimmer also used in sidebar and Home rows, labelled *Naming conversation*, in place of the temporary title, and it gives way to the real title when the name lands. Reduced motion freezes the shimmer without shifting the layout.

A real chat reference links to that conversation: the visible label is the chat's own title, the raw id stays in its tooltip and data, and the link opens in this tab. This covers a bare id in prose or inline code and the app's own `@chat/<id>` mention (only the prefix stays plain). Only an id the reader's openable chat list knows becomes a link; an unknown, malformed or non-chat-looking id stays plain, and another path or URL that happens to contain one is never rewritten. Existing links, code blocks and file links are left alone, and the title is escaped like any other text.

The model picker has two intents. The composer chip only selects: a model change there is saved and never sends. The recovery picker, opened from a failed turn's *Switch model* or the retry card's *Continue with…*, is headed *Choose a model to retry immediately* and says that choosing retries and may incur usage charges, and that a Thinking level picked there applies to that retry, within the levels the current model offers. Choosing there retries exactly once — a pending deferred retry is fired, an error-bubble retry resends the original request with its images — while a provider change still asks for the handover confirmation and a cancelled or failed handover sends nothing. Recovery is discarded when the chat changes or the picker closes, and a rapid second choice cannot send twice. Thinking stays the app's chip control; in recovery a level is staged and validated against the chosen model, falling back to the provider default, and only then saved with the retry. The chips are the current model's set, in a recovery too: the pick applies the model and retries in one go, so there is no moment where they could follow a model the user has not chosen yet.

The first-run onboarding journey has five persisted steps — **Location, Runtime,
Access & memory, Care, Finish** — and six stage components: Access and Memory
share one screen and advance the same persisted step only when both are ready.
The shell owns navigation and progress writes; stages report readiness and
perform their own domain save or explicit deferral. Conflicts are surfaced for
the user to reload, never replayed automatically.

## Colors

The Access & memory onboarding stage keeps filesystem scope separate from approval mode, states that Claude Auto is not a safety guarantee, and never treats OpenCode model instructions as enforced safeguards. Windows has no filesystem sandbox.

Dark mode is the primary visual expression. It uses layered indigo surfaces instead of neutral black, keeping long sessions comfortable while preserving clear hierarchy.

- **Primary orange (`#fb923c`, the `amber` preset):** The brand accent and primary-action color. Use it for the current location, focus, progress, and the single most important action in a region. It replaced the earlier pink `#ff4d6d`, which sat about 15° of hue from the error red and made a primary action read as a failure. Workspaces may override it with a saved accent preset (`amber`, `pink`, `cyan`, `emerald`, `violet`, `blue`, `teal`, `lime`, `fuchsia`); a workspace that saved pink keeps it, and only an unset colour follows the default. Canvas and surface tokens stay fixed.
- **Neutral accent while loading:** Until the active workspace's colour is known, the app wears `neutral` (`#b4b4c4` dark / `#5f607d` light), or the colour this browser showed last, so the first paint never flashes an accent that then changes.
- **On-primary (`--on-accent`, `#1a1a2e` dark / `#ffffff` light):** The label colour on any filled accent surface: primary buttons, active pills and toggles, accent badges. Never hard-code white on the accent. The dark accents are bright, so white on them measures about 2–3.6:1; the indigo canvas colour clears 4.5:1 on every dark accent and its hover shade (orange 7.54 / 4.79, pink 5.31 / 4.69). Light accents are deep enough for white (orange 5.18 / 7.31, pink 4.95 / 7.02).
- **Accent presets:** Each preset pairs `--accent` with a hover shade `--accent-strong`, and both must keep `--on-accent` at WCAG AA. Dark: amber (default) `#fb923c`/`#ea580c`, pink `#ff4d6d`/`#ff2e54`, cyan `#38bdf8`/`#0ea5e9`, emerald `#34d399`/`#059669`, violet `#a78bfa`/`#9670f7`, blue `#60a5fa`/`#3b82f6`, teal `#2dd4bf`/`#14b8a6`, lime `#a3e635`/`#84cc16`, fuchsia `#e879f9`/`#d946ef`. Light: amber `#c2410c`/`#9a3412`, pink `#d81b60`/`#b00d46`, cyan `#0369a1`/`#075985`, emerald `#047857`/`#065f46`, violet `#7c3aed`/`#6d28d9`, blue `#1d4ed8`/`#1e40af`, teal `#0f766e`/`#115e59`, lime `#4d7c0f`/`#3f6212`, fuchsia `#a21caf`/`#86198f`. Red and yellow are excluded: red reads as an error, yellow collides with `--warning`. The light shades also keep accent-coloured text at AA on white.
- **Violet (`#6a47b8`):** A secondary accent for selected filters, contextual information, and supporting distinctions. It must not compete with the primary action.
- **Background (`#1a1a2e`):** The deepest application canvas.
- **Surfaces (`#1f2240`, `#23264a`, `#2a2e54`):** Cards, elevated controls, hover, and pressed states. Prefer tonal separation and borders over large shadows.
- **Text (`#e8e8f0`):** Primary content. Muted dark text uses `#b4b4c4`; `#8f90a8` is the AA-compliant tertiary token for metadata and secondary controls. In light mode the tertiary token is `#66687f`; never reuse the old washed-out `#8e90a8` value for meaningful text.
- **Soft text contrast (opt-in):** `data-text-contrast="soft"` on `<html>` lowers only `--fg` (dark `#e8e8f0` → `#d2d2de`, 14.0 → 11.4:1 on `--bg`; light `#1a1a2e` → `#2e2f46`, 15.6 → ~11.9:1). `--fg2`/`--fg3` do not change. The default is unchanged.
- **Body font (opt-in):** `data-body-font` on `<html>` swaps `--font` between system sans (default), a serif stack (`Charter, 'Iowan Old Style', 'Palatino Linotype', Palatino, Georgia`) and `--font-mono`. It applies to chat prose, UI body text and titles (titles use `--font`). Code, badges, commands, timestamps and the wordmark stay `--font-mono` regardless. Components use `var(--font)`, never `var(--font-sans)`, for prose and controls.
- **Custom colours (opt-in):** `custom_colors` stores a background and text colour per theme; the active theme's pair is written as inline custom properties on `<html>` (`--bg --bg2 --bg3 --bg-elev --fg --fg2 --fg3 --border --border-strong`), with surfaces and secondary text derived from the pair by `lib/contrast.ts` (`deriveCustomTokens`). A pair is applied only if body text clears WCAG AA 4.5:1 on `--bg` and on the hover surface `--bg3`; otherwise the dialog refuses it and says why. Accent, status and canvas-painted surfaces (Memory map) are not recoloured. A custom pair overrides Soft text contrast for that theme.
- **Engine-wide appearance:** Settings › Appearance (theme, font size, text contrast, body font) is stored on the engine, so every device agrees; `system` theme still resolves per device from its OS. `ciao-theme`, `ciao-font-scale` and `ciao-appearance` in localStorage are paint caches only, restored before mount and overwritten by the engine value. The first browser to load against an engine that has never stored a theme or font size seeds it once from its own values.
- **Semantic colors:** Green communicates success, orange caution or recoverable risk, and red destructive actions or errors. Never use semantic colors decoratively.

Light mode keeps the same hierarchy with a soft lavender canvas, white surfaces, crisp crimson accent, and slate text. It is an adaptation of the same system, not a separate aesthetic.

Color is never the only state signal. Pair status colors with text, an icon, a shape, or an accessible label. Verify WCAG AA contrast in both themes whenever a token or component changes.

## Typography

The product uses a **hybrid typography system** (the proportional face is the opt-in **Body font** below): a clean system proportional sans-serif stack (`-apple-system`, `SF Pro`, `Segoe UI`, `Roboto`) for conversational chat prose and general UI, paired with a monospaced stack (**SF Mono**, **Fira Code**, **Cascadia Code**, `monospace`) for code blocks, badges, commands, schedules, timestamps, and terminal identifiers.

- **Titles:** 15–16px, bold, with slightly tight tracking. Titles should remain visible when actions compete for space.
- **Body:** 14px on desktop with comfortable 1.6 line height for natural reading.
- **Mobile form text:** At least 16px to prevent browser auto-zoom while keeping user zoom available.
- **Labels & Badges:** Monospaced 11px, semibold, often uppercase with 0.5px tracking for technical precision.
- **Wordmark:** Bold monospace `ciaobot`, led in the sidebar by the Ciaobot face as a one-colour pixel mark (`CiaoMark.vue`, traced from `face.png` in three tones of `currentColor`) drawn in the workspace accent. A blinking caret may appear only in startup or explicitly terminal-like moments.

Respect the user-controlled font scale. Truncate compact navigation labels only when the full value remains available through context, title text, or an expanded view.

## Layout

The PWA is mobile-first and safe-area aware. Desktop uses a persistent project sidebar beside the active workspace. Narrow screens use an overlay sidebar and full-width panels, with secondary actions moving into menus or sheets before titles are sacrificed.

In project rows, fine-pointer action buttons yield their inline width while idle and return on hover or keyboard focus, so the project name uses the space when those actions are visually absent. Keyboard-focused actions regain their full target before activation. Coarse-pointer rows keep the full touch targets available.

Use the 4px-based spacing scale deliberately: 4px for internal micro-spacing, 8px between closely related controls, 12–16px for component rhythm, and 24–32px between major groups. Long-form surfaces stay readable on wide screens: settings cards are capped at `min(100%, 1040px)`; the home intake/review column is capped near 920px; project, Memory, and Automations use the available pane width but keep conversational rows within a readable measure.

Every pane uses one page grid (App.vue `--page-max` 1180px, `--page-gutter` 32px / 16px on phones, `--page-rail` 280px): a main column plus an optional right rail, centred, collapsing to one column when the pane (not the window) is under 940px. Chat is the other exception: its body spans the whole pane, the conversation (transcript, dock and composer) keeps a centred 768px reading measure (`--chat-measure`, about 75 characters) in the space beside the rail, and Chat details is a 320px rail against the pane's right edge, with the header's actions above it and the title on the column's left edge; a wide Markdown table may run past the measure into the free space on its right, up to 1120px. A wide window is spent on room around the chat, never on longer lines. Settings is the other exception: its rail is only an on-this-page index, so between 760px and 940px it stays beside the page as a compact 200px column and drops only below 760px. Long or implementation-oriented content must not dominate a mobile page. Collapse long prompts and diagnostics behind Preview/Expand/Copy controls, preserve the page title, and move secondary or destructive actions into an overflow menu or bottom sheet.

## Elevation & Depth

Hierarchy comes primarily from tonal layers, one-pixel borders, and spacing. Cards sit on the page background; inputs may use the deeper canvas; modals and popovers use the elevated surface. Use stronger borders for focus and separation before adding shadows.

Shadows are reserved for content that genuinely floats above another interaction layer: mobile drawers, menus, modals, and toasts. Keep them soft and dark. The normal application surface stays clean; CRT grain is reserved for startup, update, and native terminal surfaces where it carries product meaning. Visible thin scrollbars remain available in bounded data regions so scrollability never becomes an invisible assumption. The chat footer's turn-facts strip is the single exception: it scrolls sideways without drawing a bar, because a scrollbar under a reply reads as a rule across the transcript rather than as an affordance.

## Shapes

The shape language is compact and gently rounded. Standard controls and cards use a 10px radius, small nested elements use 6px, and modals use 14px. A tighter 4px radius (`--radius-xs`) is reserved for small squared tags that must not be mistaken for count badges: the needs-you state chip and the workspace key badges. Fully rounded shapes are limited to badges, status dots, avatars, and true pill selectors.

Borders are structural, not decorative. Active navigation is marked by a slim accent edge plus a tonal background. Warning callouts use a muted warning-tinted surface with a 1px perimeter; quoted passages use a neutral 1px divider. Do not mix exaggerated rounding, glass effects, or unrelated shape styles into the same view.

It is a shell on the engine's own machine and the pane says so, in words, before anything is typed. The panel names the shell's host, folder and platform and presents sessions as compact, switchable browser-style tabs. The header's **×** closes the pane and detaches its connection while leaving every shell running; the **×** on a session tab ends only that shell. The terminal keeps the keyboard while it has the focus — Escape, Tab, the arrows, Ctrl+C and Ctrl+D go to the shell — so the app's own shortcuts stay out of it and <kbd>Shift</kbd>+<kbd>Tab</kbd> hands the keyboard back to the panel's controls. A soft keyboard has none of those keys, so under a coarse pointer a row of on-screen keys (Esc, Tab, Ctrl+C, Ctrl+D, the four arrows, Enter) sits under the screen while a session is open: 44px mono buttons that send the bytes a hardware key would through the same input path, stay disabled until the session is live, and never take the focus from the shell. The panel asks for no password: the signed-in session is the terminal's trust boundary, and the pane asks the engine for its 15-minute grant on its own — the lifetime bounds a grant, not an open pane, because when the engine closes the socket the pane asks for a new grant and resumes — so a workspace that denies the agent `Bash` no longer has a host-shell boundary. A truncated output buffer says so plainly, because a truncated buffer cannot rebuild the screen it no longer holds.
- **Suggested command:** A command the assistant suggests in a chat appears as a transient card above the composer, under the fixed title **Suggested command — review before running**. The command is the assistant's own text and is shown as literal characters — never markup, never markdown, never a link — in a bounded, scrollable monospace box that wraps anywhere. The card says who wrote it and what has not happened: Ciao has not checked it and will not run it, and the shell it points at is on the engine's computer. Three actions, and no fourth: **Copy** (the exact text on screen, claiming *Copied* only when the clipboard took it, with a retryable error when it did not), **Open in Terminal** (the same *Terminal* section's way in, for this chat) and **Dismiss** (which names the suggestion it dismisses, so a newer one is never dismissed by mistake, and says so when the suggestion changed). The card never runs the command and never pastes it into the shell: *Open in Terminal* starts no shell and asks the engine to run nothing — an already-live session attaches and shows the screen it already holds, exactly like the rail's button. The user reviews the command and types it. The rail's *Terminal* section stays the persistent, manual way into the terminal; the card is the contextual one, and it belongs to the chat on screen.
- **Inputs and composer:** Inputs use the deep background, visible border, accent focus ring, and plain-language labels. The chat composer remains the strongest persistent interaction affordance. While an OpenCode reply has run a foreground shell command or subagent for 3 s, a quiet **Move to background** chip (*Background* on a phone) sits beside Stop; it ends the reply now and the work finishes as a background wake that streams into the chat. The chip is neutral, never the accent, has a 44px coarse-pointer target, and returns focus to the composer after use. Background agents and runs live in the composer bar's activity cluster (see Layout), which takes the bar's free space so the model chip and Send never shrink; its parts are 28px tall, 44px under a coarse pointer.
- **OS sharing:** Content shared into the installed PWA waits on Home in a neutral review strip until explicitly added to a draft or discarded; no share starts a chat or sends an agent turn. Native file sharing is an optional secondary action beside Download, never a replacement for it.
- **Badges and status:** Badges are compact supporting signals, never the sole explanation. The sidebar puts subtle numeric counts on the destinations, scoped to the selected workspace: chats needing you on Home (including a delegated chat whose agent asked for input or reported blocked), missed runs on Automations, tasks the agent reported done and waiting for review on Tasks, suggestions and notes to revisit on Memory; Settings shows the muted word *update* when one is available. Every count is the same muted numeral; Home's is not singled out. A failure (a missed or failed run, a blocking Settings action) is one warning dot at the row's right edge, never a tinted icon, a coloured word or a coloured timestamp, and the routine row that failed carries the same dot. A chat working shows the pulsing accent dot on Home. Nav icons never change colour, including on the current row, whose accent tint is the only accent in the destination list. List-label actions (New on Projects and Routines) are muted ghost buttons with a plus, filled on hover, never the accent. The workspace scope carries no counts, and a project row summarises its chats with one static dot only while collapsed, plus the static run glyph when any of its chats has a background run. Running, unread, failed, and disabled states need accessible text equivalents.
- **Activity glyphs:** Live work is told apart by shape, never by colour alone (`ActivityGlyph.vue`). A turn working is the pulsing accent dot. A subagent is a ring with a dot orbiting it, in the accent. A background shell run is a diamond outline with a dot tracing its edges, in the secondary text colour. A failed run is the same diamond in `--error`, still. The glyph is decorative (`aria-hidden`); every place that shows one gives it a text label or title. Under `prefers-reduced-motion` nothing moves. In a chat row, runs are not ranked against the other states: the run glyph sits beside needs-you, working or agents.
- **Live chat activity:** While a turn streams, its full timeline is collapsed by default into one expandable `Working` row with the latest safe activity description and elapsed time. The native button disclosure opens the complete bounded-scroll history, and an explicit open choice survives turn completion. New descriptions slide in place; reduced-motion preferences disable the slide. Never put hidden reasoning excerpts in the compact preview.
- **Injected turns:** A prompt the engine wrote into a chat (a finished background run, lost background tasks, an automation run, a resumed task, a webhook event, an update task) is not a user bubble. It is a full-width, muted notice card: 1px `--border`, `--radius`, no fill, `--fg2` text. One header line holds an icon, the kind and its key facts; it is a native button with `aria-expanded`, collapsed by default (44px under a coarse pointer). Expanded, it shows the details. A run's status is a pill with its word (*ok* `--success`, *cancelled* `--warning`, *failed* `--error`, tinted with `color-mix`, never colour alone), the log path as a file link, and the log tail in a monospace, keyboard-scrollable region capped at 240px. Every capped, scrollable prose or preformatted region in the notice is a named, keyboard-scrollable region. The raw prompt sits behind its own *Show full prompt* toggle. A retry the user asked for is the same notice shape, labelled *Retry started* with the facts *Same request · new attempt*: it is collapsed by default, shows a short explanation, and holds the original request behind its own *Show original request* disclosure instead of the generic prompt toggle, so the card itself never shows it twice. An automation turn's card links to its automation; the legacy `↻ auto` mark remains only on unattended turns with no recorded origin. The delegated task's first turn keeps its own Task handed over card.
- **Menus and sheets:** Overflow menus contain secondary and destructive actions when horizontal space is constrained. Mobile modals become edge-to-edge sheets and honor safe areas.
- **Peek overlays:** A record opened from a link (a task in a chat, a pinned file, the delegated-chat note) opens as a peek over the view it was on: the same window as the file viewer (`OverlaySheet`), read-only, with one text action, *Open task page*, to the full page. It closes on ×, Escape, a backdrop click or any navigation, and focus returns to the link. It adds no history entry and the URL does not change. A modified click still opens a new tab, and on the board the link navigates as before. Its touch targets are 44px.
- **Onboarding:** The Access & memory stage requires an explicit acknowledgement of the workspace memory-handover choice. A pending workspace with handover still off is offered “Accept and dismiss” as an unsaved draft; saved choices are shown as saved, and the stage never writes on mount or selection. It explains archive filing versus review queue, History and Undo, and states clearly that acceptance cannot act when the trusted service is unavailable. Spotlight backdrops suppress competing content. Skip is visibly actionable but secondary; Back and Next meet the same touch-target requirements as the rest of the app. Onboarding orients; it never becomes a gate or a wizard the user must finish. The seeded interview asks, in short turns the user can decline, what the workspace is for and what should stay out of it, how they want to be worked with, and the operating context around them; the scope answer goes to the workspace/project context rather than a bounded region, so the profile and memory regions keep holding personal facts. Before it asks, it reports what the workspace already holds from Ciaobot's own state, and afterwards it seeds starting knowledge from confirmed facts only, leaving anything uncertain in `Workspace/Memory-Proposals.md` and creating an entity folder only when a confirmed fact needs it. When it explains memory, it names the two layers — the bounded profile and preferences loaded into every conversation, and durable notes filed by category — and names the workspace's **effective** categories (enabled, not hidden, in registry order) from the registry that backs the Categories page, never a copy of the shipped list. That page stays the single editor, so the explanation links to it instead of adding a second way to change categories. A seeded welcome is a snapshot and makes no promise beyond what the feature does: it scans no history, calls no model, writes no category, and cannot claim that past conversations are imported. It may *name* the place where a non-automatic capability lives — past conversations are not imported on their own, and Memory → Import is where you choose which ones Ciaobot reads and see what would be sent before anything runs — and it stops there, because naming a page is not running it. It is skippable, ignorable, and readable by someone who never opens it — ordinary chatting and setup must stay usable when it is skipped.
- **Motion:** Use short 120ms interaction transitions and the shared easing curve. Longer fades are acceptable for startup and major overlays. Respect `prefers-reduced-motion`; never make meaning depend on animation.
- **Focus:** Interactive elements use a visible 2px accent focus outline with separation from the component edge. Do not remove focus styling unless an equally visible replacement exists.

## Do's and Don'ts

- Do reserve accent emphasis for the current location, focus, progress, and primary action.
- Do keep titles and textual state visible when layouts become narrow.
- Do use plain-language recovery guidance instead of exposing raw IDs or implementation details.
- Do make every touch target at least 44×44px and every core workflow keyboard accessible.
- Do preserve browser zoom, font scaling, safe-area behavior, and reduced-motion preferences.
- Do test dark and light themes at desktop and mobile widths.
- Don't turn a group of routine actions into competing accent bars.
- Don't rely on unexplained icons, color alone, hover, or animation to communicate state.
- Don't expose long prompts or diagnostics in full by default on mobile.
- Don't copy custom styling into a host-native surface when platform conventions are clearer.
- Don't introduce new colors, radii, shadows, or typefaces when an existing token serves the purpose.

- **Onboarding location:** Ask for the main Ciaobot folder before the workspace name. Before provisioning, it is a candidate location (empty or existing-notes folders are both valid); after provisioning, show the actual path as read-only and direct changes through the guarded move flow. Remote browsers explain that the folder belongs on the Ciaobot computer. Typing never creates, moves, or saves anything; Continue is the explicit handoff to the next stage.

The onboarding care stage follows the setup shell's calm, compact form rhythm: host availability guides the suggested local time, while the editable time and IANA zone are explicit controls. A clear saved/default status and inline error explain whether timing was written; keeping the packaged default is an explicit no-write choice.
## Onboarding finish

Finish uses observed status labels rather than implying completion, and the first-task composer
is an explicit, optional action; Continue remains owned by the setup shell.

## Onboarding: runtime and model

The runtime stage asks for a runtime, then an explicit model. Reported models and configured
aliases never share a list: the first is evidence from a connected runtime, the second is a set
of choices whose availability is unknown. Deferring is a first-class choice, not an error, and
the stage never starts a provider or a model turn on its own.

## Onboarding entry

The journey is a route, not a modal: `/onboarding` resumes at the recorded step, validates any
return path as an internal route, and leaves completed or legacy installs alone. Home carries a
quiet resume row while setup is unfinished, because a new operator should never have to remember
a URL.
