# Ciaobot Architecture

Orientation doc for the codebase. Read this before making any change in `ciao/`, `web/`, `scripts/`, or `deploy/`. After a change that affects layout, capabilities, env vars, endpoints, or commands, update this file, `docs/DEVELOPMENT.md`, and `INTEGRATIONS.md` so they match the repo.

## A meta-harness for personal AI assistance

Ciaobot is a **meta-harness**: a persistent personal workspace around existing agent harnesses, not a replacement model/tool execution loop. The layers are:

1. **Ciaobot — context and continuity.** Workspace and project context, chats and transcripts, files and feedback, automations, memory extraction and review, and scope-enforcing application operations.
2. **Agent harnesses — execution.** Claude Code through `claude-agent-acp` (ACP), and OpenCode through `opencode acp` (2.3.2+), handle model interaction and tool execution using the user's configured provider access. Ciaobot starts and supervises these sessions through provider adapters.
3. **Models and tools.** The configured cloud or local models, filesystem access, and integrations reached through each harness.

The product is organised around one person's work and knowledge, not an autonomous company's org chart. Its continuity loop is **request → run → output → durable knowledge**: project context accompanies work, archived conversations can produce scoped Markdown facts, and uncertain facts wait for review.

Provider-neutral application context and durable Markdown knowledge do not imply provider-session portability or identical tools, permissions, and capabilities. Switching harnesses preserves the personal workspace, not every detail of the execution environment. Application-operation guards are not a sandbox for arbitrary agent filesystem or credential access.

For task-oriented reading paths, start with the [documentation hub](README.md).

The Chat details rail is a closable docked window, using the pinned file viewer's visual vocabulary. `AgentContextSection.vue` shares readable project context and the canonical-document link between the rail and narrow-pane drawer; the underlying capsule and its token estimate are unchanged.
Chat file links resolve an exact canonical identity via `/api/chats/{chat_id}/file-path`, using the same agent root the provider executes in. Mentions in a completed reply that were never touched by a tool call are discovered by the separate browser-only `POST /api/chats/{chat_id}/file-paths/resolve` (#2118), which confines itself to the owning workspace's roots (see the filesystem-scope section). Manual pin requests use that root too. Once resolved, text, image, binary and HTML viewers all consume the absolute identity; pin failures never dismiss the preview (#1167).

Chat references in Markdown use the same active-project, local, unarchived chat set as the `@`-mention picker. `ChatPanel.vue` derives mention choices once and uses those rows for both the picker and the chat-link map, so a reference never links a conversation the reader cannot open from the offered list. The map key includes only chat id/title pairs; activity-only chat-list polls preserve its `Map` identity and leave both Markdown caches intact.
The task board derives four status groups and draws them as lanes side by side, each a fixed 310px wide at every pane width, with the Done lane collapsed behind a tab at the end of the row (`ciao.tasks.doneShown` in localStorage). A narrow pane scrolls the lanes sideways inside the board element, so the page never scrolls sideways; drag and Shift+Left/Right do not depend on pane width. The manual order of each column is one id sequence per status in `<vault>/Workspace/task-order.json` (`ciao/task_order.py`, see the layout below). Reads reconcile that file against the task files and never write it; a reorder or a status change with a position carries the order version the client read (`expected_order_version`), and a stale one is a 409 `task_order_conflict` that writes nothing. A status change with a placement writes the order file under the workspace lock before the task file and restores it if the task write fails. The web store adopts only the `order` the server returns and rolls back a failed write, so the client never sorts tasks itself. Cards, lanes and sidebar projects share one drag-sort engine, `web/src/composables/useDragSort.ts`, whose pure geometry is in `web/src/lib/dragSort.ts`; rows drag by their own surface with no handle, and reorder by the row menu's Move up / Move down. A card's Move… sheet chooses a column and landing row for a cross-lane placement, one write through `place()`. The engine persists nothing and hands each finished move to a commit callback; `useMenuFocusReturn` gives the trigger's focus back after a menu action without stealing it once the user has focused or pressed elsewhere. Done is one gesture: the completion sheet has one primary action and an optional note, and sends both on the same POST as the status — blank completes without a resolution, nonblank text is kept as typed. The Chat details rail's task origin and the archive-chat dialog follow the same contract: one completion action, and the note is optional in the field itself.

Production `/assets` serves hashed JavaScript and CSS with gzip negotiation above a 500-byte minimum; API responses and chat streams are outside that compression path. `ChatLayout.vue` loads chat and pinned-file panels on demand, begins the chat download for chat deep links alongside bootstrap data, and loads the file viewer on first open while retaining its mounted dialog lifecycle. Startup progress and the engine monitor share a bounded status request, and a short initial display delay avoids a ready-state curtain flash without persisting readiness. The monitor does not read one failed probe as a dead engine. The PWA is served to phones and laptops that reach the engine over a VPN or a relay, where a request that a loopback origin answers in milliseconds can take seconds, so the status request gets a ten-second budget, a request that merely runs out of time is graded as weak evidence and only becomes an outage after the engine has gone unanswered for twenty seconds, and the awareness socket — which the engine pushes a frame on every few seconds — is the arbiter: while it is still delivering, a failed probe is the path being slow and the "isn't reachable" curtain stays down. A request that is refused or errored is still decisive, so a crash is still reported within seconds.

Chat listings batch cross-cwd Claude session availability checks into one fresh
directory scan per request. Individual session lookups retain their separate
freshness contract; listing availability is never cached across requests.

Settings → MCP is one button per installed agent. Each button starts that agent's CLI (`mcp_command` on its provider row: `claude`, `opencode` or `codex`) in the in-app terminal for the active workspace's project, then types the row's `mcp_slash` (`/mcp`, or `/mcps` for OpenCode) once the CLI has started. The page does not read MCP inventory or turn servers on or off. Changes apply to new chats; a running chat loads them after `ciao chat reload`. A CLI that is not installed has no button.

Strictly validates schema and global revision, initializes existing installs as legacy-exempt, and rejects corrupt state rather than resetting it.
  onboarding_progress.py       Transport-neutral progress operations over the receipt; reads never initialize, new workspace creation registers runtime progress, and rename moves identity using the receipt writer's global revision contract.
  dev.py                       Local dev runner: backend on :8543 plus Vite frontend on :5173. CLI: `ciao dev`.

  port_in_use.py               The engine's port is taken by something else (#1654). One place owns the wording every reader shares: the operator-facing sentence (which port, and the two ways out — free it, or set `PWA_PORT` in the workspace `.env`), the port-in-use exit code (69: not the restart code 75, the workspace-access code 78 or the setup-memory code 3, so a service manager reads it as a failed run and not as "relaunch me"), the startup phase the failure is recorded under (`server_starting`), the errno test (`EADDRINUSE`), the bind the engine makes itself (`check_server_port`, with the addresses and the socket options asyncio's own `create_server` would use, so a failure here is the failure uvicorn would have had) and the probe the installer's preflight uses (`port_is_available`, the same bind, so its answer is the engine's). The reason is also *recorded*, outside every workspace at `~/.local/state/ciaobot/port-in-use.txt` (the way `workspace_access` records its denial), because an engine that cannot bind cannot serve the endpoint that would report it: the reader has to find the reason somewhere else. `ciao.main` binds the port itself (`check_server_port`), records the failed phase, and leaves with the port-in-use code; `ciao.supervise` holds the job on that code instead of exiting, so the service manager does not respawn the engine into the same failure.
  providers/                   Claude Code, Codex and OpenCode over ACP (`acp/`), the shared base, and one-shot calls.
    stdio_rpc.py               Async JSON-lines RPC process transport used by CLI app-server adapters.
    acp/agents.py              The real ACP agent specs (`CLAUDE`, `CODEX`, `OPENCODE`) and the provider classes that run them.
    oneshot.py                 Single-turn provider call (max_turns=1, no tools). Used by routine-model automations.
    acp/spec.py                `AgentSpec` and `ModeChoice`: per-agent data (binary, argv, fixed env, `clientCapabilities._meta` opt-ins, the config options each Ciaobot mode maps to, quiet period, initialize timeout) for the ACP client layer (#3137). No code outside this data names an agent.
    acp/connection.py          `AcpConnection`: spawns one ACP agent from an `AgentSpec` (argv from the spec only, engine environment minus Ciaobot's own internals: `CIAO_*` and the PWA token are withheld, while provider credentials pass through and the CLI handles its own login; in the bundled Mac engine `SSL_CERT_FILE` and `PYTHONDONTWRITEBYTECODE` are dropped too, see `os_support/child_env.py`; the spec's `unset_env` keys are kept out; engine bin dir first on PATH; a relative resolved binary is refused), connects the Agent Client Protocol SDK to its stdio and runs `initialize` with raw `_meta` capabilities. Keeps a bounded stderr ring (`StderrRing`), raises `AgentStartError` with the stderr tail when the binary is missing, the process exits or `initialize` times out, and `close()` is idempotent and cancellation-safe: the agent stays in the engine's process group (so a group kill still reaches it) and its whole descendant tree, found by a ppid walk (`os_support/processes.py` `process_table`/`descendant_processes`), gets SIGTERM, then SIGKILL after 5 s. The in-app terminal filters its environment on purpose differently: it strips secrets (`*_TOKEN`, `*_API_KEY`, `GOOGLE_APPLICATION_CREDENTIALS`, and similar), while agent processes inherit the engine environment minus `CIAO_*` and `PWA_AUTH_TOKEN`. `connect_client` routes each spec's unprefixed `extension_notifications` (opencode's `child_update`, codex's `auth/status_update`) to `ext_notification`, and drops any other unknown notification at DEBUG (once per method) so the SDK never logs it as an unhandled ERROR; requests still get method-not-found.
    acp/__init__.py            Agent Client Protocol client layer package (#3137).
    acp/normalize.py           Pure ACP `session/update` -> StreamEvent translation: key canonicalisation, tool-call tracking by id (refresh, result), subagent parent ids (Claude `parentToolUseId`, opencode child-session meta), usage, model/mode config values, compaction flag, per-turn top-level text (`TurnText`) and the stop-reason -> `ResultEvent` mapping. No I/O.
    acp/shell_liveness.py      Background shell liveness: the pid and start time a launch acknowledgement names, checked against the process table every few seconds (`ps`, never a signal); a pid that vanished or whose start time changed settles the call and emits one `ShellFinishedEvent` (the call id is remembered, so a replayed acknowledgement never re-fires). Pure, the table is passed in.
    acp/shell_output.py        The output tail of a finished shell, read only from the path its launch metadata reports (`metadata.outputPath`; no provider sends one yet, so tails are empty until one does). Allowed: no `.`/`..` segment, realpath equal to the path (no symlinked parent), under the OpenCode shell root (`<XDG data>/opencode/shell`) or with Claude's `tasks/<id>.output` shape (Claude's root is not determined here, so only the shape and realpath apply). A regular, non-blocking open (a FIFO is refused), owned by the engine's user, the last 64 KiB at most, sanitised by `normalize.sanitize_output` (every category-C character, U+2028/2029, unterminated OSC), 20 lines and 2000 bytes at most; an oversized last line keeps its end. `None` when unreadable, `[]` when empty.
    acp/permissions.py         ACP permission broker: host-generated request IDs stay unique even when a provider reuses a tool-call id; boolean cards require one unambiguous `allow_once` and select only unique `allow_once` / `reject_once` choices (otherwise `cancelled`). Shell cards carry the exact bounded command, invalid or unattended requests never show a card, and cancel answers every pending request. `mode_choices` / `pick_value` pick the agent config value for a Ciaobot mode.
    acp/session.py             One ACP session (`AcpSession`): open via `session/load`, else `session/resume`, else `session/new` (`_meta` on all three; additional directories only when advertised; a failed or unsupported resume is replaced), one prompt at a time, config apply, late turns after background updates, cancel, and a private 0600 JSONL journal (`SessionJournal`) under `<runtime>/acp-journal`.
    acp/provider.py            `AcpProvider`: the `BaseProvider` for any ACP agent (a subclass sets `spec`, and may override the `session_meta` / `oneshot_meta` / `spawn_env` hooks). Owns one agent process and at most one live session, reuses the connection on the key (provider reuse key, linked repo, workspace), always opens a fresh session when there is no resume id, reloads a live session when its `session_meta` changes (never under a late turn), maps a start failure to a short sanitized reason (`AgentStartError.stderr_tail` is logged, never sent to the PWA), and carries the `unattended` flag into the permission broker. Registered through `ProviderDescriptor.acp_spec_path`; the `claude` and `codex` descriptors set it (#3138, #3137). OpenCode runs over ACP too (`opencode acp`, `OpencodeAcpProvider` in `acp/agents.py`). A native slash command is sent as two blocks when the spec sets `slash_capsule_as_block`: the bare command, then the context capsule (as an embedded resource when the agent takes them), because claude-agent-acp keeps only the first text block as the command. Persisted-session classmethods (`delete_session`, `read_thread`, `native_title_candidates`) take the explicit `runtime_root` (`config.state_path.parent`), so they address the same journal the live provider wrote even when `CIAO_RUNTIME_ROOT` is outside `<workspace>/.runtime`. `read_thread` returns `{"acp_journal": rows}`, which the transcript service renders into chat history (`_render_acp_journal`). `model_catalog` probes the agent's model and thinking options in a throwaway session (no MCP servers), cached per agent and workspace for 300 s; `force` bypasses the cache, and a failed probe is logged and yields an empty list.
    acp/oneshot.py             `run_acp_oneshot`: one prompt through a throwaway session in a fresh empty temporary directory, in plan mode when the agent offers it, with every permission request rejected (the call is unattended). `ciao/providers/oneshot.py` `run_oneshot` dispatches here for a provider whose descriptor names an `AgentSpec`. An error stop reason raises `OneShotError` with a fixed detail, never the adapter's text.
    acp/agents.py              OpenCode over `opencode acp` (#3140): the `OPENCODE` spec (no bypass mode, every Ciaobot mode maps to `build`, `opencode/child-session-updates` opt-in), its version gate (`VersionGate`, refusing below 2.3.2 at start with the fixed `OPENCODE_V2_REQUIRED` text), and `OpencodeAcpProvider`, which nests a subagent's child session under the subagent's `Agent` tool call (linked by the launch's description and its `metadata.sessionID`) from `opencode/session/child_update`, a notification opencode sends without the underscore that `connection.connect_client` routes by name. A child with no launch behind it keeps a `Subagent` node (`child:<id>`). Only a child's message and thought chunks and tool calls reach the parent; its usage, model, mode and compaction updates are dropped. Claude Code over `claude-agent-acp` (#3138): the `CLAUDE` spec (memory and artifact env disables, the mode table), `ClaudeAcpProvider`, which sends Ciaobot's disable options as `_meta.claudeCode.options` (`disallowedTools`, `settings` as an object, the connectors env) on session/new, load and resume, and the no-tools one-shot options, `spawn_env` (the user's own `claude` as `CLAUDE_CODE_EXECUTABLE`), and `claude_auth_command`. The adapter runs from the machine's own copy at the pin when one is on the PATH, else from the private prefix (`ciao/adapter_install.py`). Codex's `CodexAcpProvider.spawn_env` sets `CODEX_PATH` to the user's `codex`, and its `ext_update` debug-logs `auth/status_update` (state and account count only, no events; the Providers card does not read it yet). `AcpSession.apply` sets the chat's model exactly when the adapter offers it; a bare tier name (`opus`) maps to the offered model with that tier word through `model_tiers.resolve_tier`. Any other value is not guessed at or sent: the adapter keeps its default and the session reports one status line that the model is not offered. Claude's title arrives as an ACP `session_info_update` and is applied as an adapter title; nothing polls for it (see "Chat titles from the agent" below). Codex over `codex-acp` (#3139): the `CODEX` spec (the Codex modes mapped to `read-only`/`workspace-write`/`agent`/`agent-full-access` and `collaboration_mode`), `CodexAcpProvider`, and `codex_auth_command`, which only builds the `codex login` line the Settings terminal runs. Ciaobot never reads or stores Codex credentials.
  context/                     Provider-neutral per-turn context capsule (workspace, project, vault hints, and one bounded task-board recipe line — never a board dump; see the capsule section).
  schedules.py                 Cron-style schedule dispatch.
  schedule_command.py          The optional shell command a schedule runs before its model turn (#1258): run in the workspace with a timeout, no chat when it exits 0 with empty stdout, otherwise the exit code and capped output go ahead of the prompt. Runs in its own process tree (`os_support.processes`), so a timeout kills pipelines and children too and keeps the partial output.
  task_board.py                Portable per-workspace Markdown task records and a revision-safe store (#978, child of #973): the canonical `<vault>/Workspace/Tasks/<id>.md` contract, a strict frontmatter parser, source-preserving patches, revision-checked `delete` and atomic writes. Reached by `/api/tasks*` and `ciao task` through the workspace-scoped service in `control_plane.py`; the board UI is B4. Its two nullable linkage fields (`chat_id`/`attempt_id`) are refused as ordinary patch fields — an agent naming its own chat would be claiming a delegation it never made — and get their own revision-checked door instead: `link()`/`unlink()`, called only by the delegation service, which is the whole of "a task with a turn in flight cannot be completed or reassigned". A task the agent files through the managed create carries an optional `created_by: agent` frontmatter key (absent for user-filed tasks and every task from before the field existed; never patchable), which the decision log records as `task_created_by`.
  task_order.py                The authoritative manual order of the task board (#2086, part of #2079): one JSON file per workspace, `<vault>/Workspace/task-order.json`, holding an id sequence per status and a version. Pure and stdlib-only: the baseline order (due, accent-stripped title, id), reconcile-on-read (stored ids that still fit, then unlisted tasks in baseline order; reads never write), and `apply_placement` (anchor-based insertion on the full sequence with an optimistic `expected_version`). `TaskBoardStore` does the I/O: create, status change and reorder write the file under the workspace lock, order file first, restored if the task write fails; a malformed file never blocks the board and is never rewritten.
  task_log.py                  The delegation log a task carries in its own Markdown body (#1064): one list item per attempt (when, how it ended in the shared label vocabulary, the chat and its archived transcript, the agent's summary) inside a `<!-- ciao:task-log -->` fence at the end of the body. The durable half of the attempt store, which lives in `.runtime/`: it survives a lost runtime directory and travels with the vault. Only the item for the attempt being recorded is rewritten (matched by its `<!-- attempt:<id> -->` mark); `strip_log` removes the section before the description is quoted into a delegation prompt.
  file_kernel.py               The small file kernel every durable vault write stands on, with no knowledge of proposals or receipts: `content_revision` (the revision a writer compares before it overwrites), `queue_lock` (a re-entrant cross-process lock for one file whose lock file lives outside the vault, `lock_path_for`, `CIAO_QUEUE_LOCK_DIR` in tests; a lock that cannot be taken raises `QueueLockError` and nothing is written), `write_queue_atomically` (same-directory temp file and `os.replace`, with an optional publish guard), and the portable file-name checks `safe_note_stem` and `portable_name_problem`.
  unsure_list.py               Direct appends to `<vault>/Workspace/Unsure.md`: `append_unsure` takes the file lock, skips an item the list already carries (compared on kind and text, ticked lines included), refuses credential-shaped lines and replaces the file atomically. Writers: the conversation import, vault re-homing and the workspace re-root. The line format and what a ticked line means are in the stock memory guide.
  learnings_writer.py          The one writer of `Workspace/Learnings.md` behind `ciao memory learn`: `append_learning` validates the path inside the vault (no symlink escape, pinned workspace descriptor where the platform has one), decides which entry a sighting belongs to using `learning_records`, and replaces the file atomically under the file lock; `render_learning_append` is the pure half.
  project_folder_move.py       Moving a project folder inside the vault and repointing every reference to it, all or nothing: `move_project_folder` is what closing a project (into `projects/completed/`) and reopening it use.
  proposal_files.py            The proposal-file validator behind `ciao proposal-check`: a `Workspace/Proposals/<slug>.md` file (type `skill-edit`, `upstream-issue`, `guide-edit` or `note-retire`, front matter `type, target, title, summary, rationale, evidence, proposed_change, created, status`, then a Markdown body) is checked for required fields, per-type target shape, evidence list, size and credential-shaped text; `check` returns every problem at once and never edits the file.
  decision_rules.py            Standing review rules distilled from the operator's decision logs (#1745): `build_digest` groups the last 180 days of operator task decisions (memory decisions are no longer recorded, so the memory section has no rows; agent-made ones are only counted, except an agent delete or complete that carries the user's reason, which is operator evidence) under closed-vocabulary keys with sanitised, capped excerpts and ready-made citations; `write_managed` lints model-written rule lines (known key, verbatim cite, no markup, 2500-char cap, no unapproved verdict flip) and splices them between `ciao:rules` markers in `Workspace/Memory-Review-Rules.md` / `Workspace/Task-Rules.md` without touching the operator's text; `load_for_prompt` returns the file fenced as evidence for the memory pass and task delegation. CLI: `ciao decisions-digest`, `ciao decision-rules-write`.
  task_decisions.py            The workspace-scoped, append-only log of operator task decisions (#1726): one JSON row per delete, reject (release of a `ready_for_review` attempt), approve and complete (an agent closing a task on the user's say-so), with a reason (optional except on the agent's delete and complete), in `Workspace/Task-Decisions.jsonl` in the vault. It outlives a deleted task file and is read by the weekly pass. `read_decisions_strict` (#3239-a) is the bounded reader the archive pass's task-decision context uses: it reports absent, unreadable, malformed or oversize instead of skipping lines.
  archive_capture.py           The workspace-scoped, append-only log of archive captures (#3239-c1): one JSON line per archive that enqueues a memory pass, in `Workspace/Archive-Captures.jsonl`, holding ids and counts only (the chat and workspace names, the attempt and decision ids the archive saw, and a status per read; never transcript text, reasons, titles or paths). `captured_at` is the engine clock's instant, the first-seen time a later consumer can trust. `read_captures` is the bounded strict reader (8 MiB ceiling, malformed rows counted, same-identity re-archives folded to the first row, a same-identity row with different counts or ids reported as a conflict and its identity left out). `archive_pipeline.py` writes one record per archive that enqueues a memory pass (#3239-c2), and the approved-task enqueue on an already-archived chat writes its `completion` record through `ProjectChatManager.capture_for_enqueue` before the pass (#3239-c3b); nothing reads the file yet. The live file rolls to a dated `Archive-Captures.<UTC-date>.jsonl` sibling once an append would pass half the read ceiling, keeping the newest 4 rotated files, and the reader reads only the live file, so a row that has rolled out no longer counts for the fold.
  task_context.py              The read-only task-decision context an ordinary archive memory pass carries (#3239-a): the decisions recorded against the attempts that ran in the source chat (newest 10, reasons capped at 300 characters, section capped at 4,000), fenced as data and stated complete or incomplete. Reads only this workspace's attempt store and decisions file; nothing is written or counted.
  linked_chats.py              The read-only linked-chat excerpts an archive memory pass carries (#3239-b): the first and last attended user message of up to three chats linked to the source (its fork parent and the other chats of its tasks' attempts), same workspace only, newest first, each read from its archive file (no-follow, regular file, 1 MiB ceiling) and labelled L1 to L3; an unavailable archive is marked, and the section is fenced apart from the task-decision context.
  task_resolution.py           The completion history a task carries in its own Markdown body (#1152, child of #1115): one list item per managed transition into `done` (when, the resolution text, the attempt it closed) inside a `<!-- ciao:task-completions -->` fence beside the delegation log. A resolution rewording moves only that item's `edited` stamp, never its `completed_at`; `strip_completions` removes the section before the description is quoted into a delegation prompt.
  task_updates.py              Progress notes on the same task file, inside a `<!-- ciao:task-updates -->` fence: one item per milestone or blocker, labeled user or agent. A description save restores the section, so a note is not an edit of the requested work. The delegation prompt quotes unseen notes; the completion memory pass reads the whole section. Newly written items carry `<!-- encoding:1 -->` so literal section-marker entities round-trip without conflation; unmarked saved items retain their original decoding. A service manager starts the engine with a low soft limit (macOS launchd's default is 256) unless the packaged unit raises it, so the in-process raise makes `ciao run`, `ciao supervise` and every service manager start with the same budget, independent of whether an upgrade rewrote the unit. Best-effort: a `getrlimit`/`setrlimit` failure is logged and swallowed. `terminal_posix.py` / `terminal_child.py`: the POSIX terminal adapter (#1692) — a real pty with a real controlling terminal, still internal (no route, no public API). The engine is threaded, so it does not fork: it opens a pty, spawns a fresh `-I -S` helper with `start_new_session=True`, and the helper claims the slave with `TIOCSCTTY` and `exec`s the shell, so the shell keeps the pid, the session and the process group `Popen` created (no second `setsid`, no shell child of its own). The environment is the canonical one (`host_terminal._terminal_env`, the engine's minus secrets) plus `TERM`, with `COLUMNS`/`LINES` dropped; there is no second secret filter. `read` is non-blocking (`None` = nothing yet, `b""` = EOF), `write` reports what it took and buffers nothing, `resize` is `tcsetwinsize`. Ctrl-C is the byte `0x03` to the tty, so the line discipline interrupts the foreground job, not the shell's group. Because an interactive shell puts every job in its own group, `close` lists the processes (`/bin/ps`, absolute path, bounded), authorizes each candidate by `os.getsid(candidate) == pid` and re-checks the representative immediately before `killpg`, so a process that left the session is very unlikely to be signalled; the check and the signal are not atomic, so a pid the system reused can still slip through in between. The engine's own group is never in that session and is never touched. Deliberately daemonized processes (their own session) are outside that guarantee: this is not a sandbox. The I/O calls and the close share one lock, so the pty descriptor cannot be closed while a call is using it and its number cannot be handed to something else in between; the close is serialized, so a second caller waits for the first. A cleanup that cannot finish is reported as a failure and reported again on every later close, never as a success: an EPERM is accepted only when a bounded status listing proves the group holds nothing but zombies, and a shell that stays unreaped is said so. A spawn that fails after the child existed is undone by that same session-wide cleanup, not by a weaker one, and the helper reports a failed claim or a failed exec with a status instead of a traceback in the user's terminal.

A gate-refused tick (`paused`) stamps no attempt, which is what makes the first tick after the gate lifts run at once — and because the delay is derived from that stamp, a refused tick owes the loop a full `BACKUP_INTERVAL_S` wait of its own instead of re-entering on a zero delay, or a turned-off or client install would call `run_backup` in a tight spin (each iteration a blocking `_scope_summary` read that forks git). Enable/pause and the last attempt/success live in `ciao/app_settings.py` as operational metadata only — never note contents — and the `origin` URL is reported with its userinfo stripped, because a status payload, a log line and a job-run record all copy that string. Completion is not detected by any of that: it is the same per-tick readiness re-derivation, so an external agent's setup is seen with no restart. A guided (in-app) setup additionally arms the service through `begin_guided_setup`, and the armed answer is applied by `_settle_guided_setup` only where readiness has *just* been re-derived as configured — dispatch alone changes nothing, and `_gate_reason` lets an armed setup read past `enabled: false` to make that read without ever staging or pushing on the strength of it. The pause is never read past and never cleared, so a pause taken during a setup is the one that counts. Categories that used to ship (Product, Feature, Automation, Document, Reference, Content) live in `ciao/stock/retired-entity-types.yaml`; `vault_migration.retain_retired_stock_types` copies one into a vault's own `entity-types.yaml` when a note still carries its `type:` or an alias, once per vault on skill sync (receipt-gated) and from `ciao vault-migrate`. `log`/`project-log` became aliases of `journal`. `<vault>` is the agent vault root (`CiaoConfig.agent_vault_root`, the one that owns `VOCABULARY.md`), passed explicitly because that root and the per-workspace notes root differ before the re-rooting. A vault file that is malformed fails closed to stock (logged, never raised, never half-merged); `builtin` is forced by origin, so a vault-only `id` is always custom, and it is never stored. A submitted row is read exactly like a file row — a partial override of the stock entry with that id — and only rows that differ from the shipped default are written, so the file holds overrides and custom entries and never freezes a default into the vault; `write_vault_file` is atomic (unique temp name, one `os.replace`, mode preserved) because a half-written file fails closed to stock rather than to the previous list, and it clears the load cache so the next read sees it. Loads are cached per vault by the vault file's mtime (`clear_entity_types_cache` is the hook). Two views are not fully derivable and keep a documented stock-only table: `_LEGACY_DIR_TYPE_MAP` (`active`/`completed` -> `project`, which `_workspace_of` membership inference needs) and `_ORPHAN_EXTRA_DIRS` (the lower-case `projects`).

The schema-3 receipt binds the canonical vault path, the vault directory's inode (`null` when the filesystem reports none) and a link operation id, and its images preserve exact UTF-8 bytes and permit interrupted apply or undo to resume; conflicts and invalid, foreign, replaced or stale evidence refuse safely. The portable `.ciao-vault-links.json` marker (`format`, `operation_id`, `state`) is committed with the vault and shares link state with other runtimes and clones: completion is the runtime's own current receipt, else the marker's `migrated` state. Stale or replaced evidence never authorizes undo or resume. Re-rooting stashes the marker with the regenerated root notes and relocation leaves it at the shared root.   update_tasks.py               Durable per-scope state and cheap applicability for "After this update" tasks — the half `update_task_catalog.py` deliberately leaves out (issue #756). **State** is `{"schema": 1, "tasks": {"<id>@<revision>": {...}}}` in two places, chosen by the task's own `scope`: a `workspace` task's decisions live in that vault's `Workspace/Update-Tasks.json` (so a backup or sync of the vault carries the operator's dismissal with it, and that file is in `vault_index.RESERVED_UNINDEXED_FILES` — a guard rather than a fix for a live leak, since every consumer of that set reads markdown only today — so no index or lint consumer can treat it as a note), an `install` task's live in `<runtime>/update-tasks.json` beside the other per-install records. A `TaskState` is `(task_id, revision, scope, lifecycle, updated_at, attempted_fingerprint, evidence, chat_id, prompt_digest)` over the lifecycles `offered`/`in_progress`/`failed`/`completed`/`dismissed`; keyed by the exact `(id, revision)`, so a dismissal suppresses that revision only and a material new revision re-offers the task. Writes go through `write_task_state`: read-modify-write under `async_reads.keyed_lock`, a unique temp file plus one `os.replace`, sorted keys so rewriting an unchanged state is byte-identical. Nothing absolute is ever stored — a state file is synced, backed up and read on another machine, so a path-shaped or deeper-than-four-level evidence entry is refused (`UpdateTaskStateError`) rather than repaired. A missing state file is a fresh scope that has decided nothing; a file that is there and unreadable (bad JSON, wrong schema) is never silently treated as empty, and `write_task_state` refuses to build on top of one. **Applicability** is `applicable` / `not_applicable` / `unknown`, and `unknown` is the answer whenever the answer is not known: a detector name with no entry in `DETECTOR_FUNCTIONS`, a detector that raises, a detector that returns something that is not a `Detection`, and a state file that cannot be read. Only a detector that ran and returned evidence can produce `applicable`; nothing here can fabricate one, because offering follow-up work this engine cannot substantiate is the failure that costs the operator's attention, while withholding a task that did apply is recoverable. `record_completion` is the only writer of `completed`, and only through the row's registered `COMPLETION_FUNCTIONS` check — an unregistered, raising or unsatisfied check records nothing, so a chat being opened is never mistaken for the work being done. **Nothing else writes it, and #756 left nothing calling it either**, which is why `evaluate` now settles: for a task whose fresh detector answer is being computed and whose record is in `SETTLING_LIFECYCLES` (`in_progress`/`failed` — an undecided attempt, as opposed to `offered` where nothing was started, or `completed`/`dismissed` where the verdict or the operator's decision already stands), it asks the check once and writes what the check says, then re-reads the record so one call reports both the unchanged `applicable` answer and the settled lifecycle. `dismissed` and `completed` are never re-asked — re-asking a verdict on a timer would reopen a decision nobody asked to reopen — and neither is a task with no record, or one in an unreadable scope: the evidence is about the workspace, the attempt is what says the workspace was asked, and a file this install cannot read cannot be written either. The settlement rides the *same* per-task window as the detector rather than adding a second clock, so the bound and the honest answer about how fast the world is looked at stay in one named constant (`APPLICABILITY_TTL_S`); the state file is still re-read on every call, so a settled record is visible on the very next listing. The lifecycle is revalidated **under** the write lock (`record_completion(only_from=…)`), not from the read that chose it: the check runs outside the lock on purpose, so a `dismissed`/`reopened` that arrives while it runs would otherwise be overwritten with `completed` — the lock serialising the writes while the decision came from before the first one. A settlement that loses that race, or whose write cannot land (`UpdateTaskStateError`/`OSError`), is logged and skipped and the record re-read, because this runs on a Home listing: one unwritable state file must neither take the strip down nor be reported as done. This is the difference between a task an operator can finish and one Home asks about forever: a task stays `applicable` while its detector is right (the work is still undone), so without a settlement the card never goes away. `evaluate` returns the eligible tasks (`catalog.eligible(installed_version)`) as `TaskStatus`, with `offered` = applicable and not suppressed at this revision, and it runs the whole check through `async_reads.run_read` (bounded, coalesced by scope/version/token, never blocking the loop) and reuses the previous answer for `APPLICABILITY_TTL_S` (300, a named constant — not a setting and not an env var) or immediately when the caller's `change_token` differs, so a detector that walks a large vault runs at most once per fresh window while the small state file is re-read every call and a dismissal never waits out a TTL. A downgrade hides the tasks this version cannot support and keeps their records, so upgrading brings them back. Every registry name has an implementation, because #833 landed the install-scoped `unrehomed-people` re-home with both probes behind it; a task whose detector is `not_implemented` must not be offered, and the layer is proved end to end over a test-injected catalog as well as over the shipped one. One rule the second shipped task brought with it: a task may share a **receipt** with a surface that cannot dismiss it, but it need not share its **evidence**. `unrehomed-people` is the same condition the audit reports as `unrehomed_people`, and it is the first pair where the two disagree about what happens next — the card can be dismissed or completed and disappear, the report cannot be silenced at all — so both probes call `migration_notices` rather than restating anything, and nothing in that module reads a task record. What they do not share is the strength of the answer: the audit keeps a cheap broad receipt check, while the detector runs one `plan_rehome` walk to establish a real candidate. **This is the only applicability probe in the catalog that reads the vault**, so the per-task `APPLICABILITY_TTL_S` window, the `run_read` hop and the coalescing key are what make it affordable at all, and the probe front-loads four cheap gates so the common answer costs no vault read. The evidence each probe returns is portable by construction: the re-home completion check carries the receipt's timestamp and two counts and deliberately not its `vault_root`, because a state file travels between machines. No `eval`, no shell, no remote fetch, no model call, and no chat launch — `chat_id` is a field this child always leaves empty for #729-C. No route, so no `PWA_API.md` entry.

  workspace_reroot.py          Plan and receipt for the per-workspace agent-root migration. Planning never writes. `read_receipt` gates on `status == "migrated"`, so a rehearsal cannot make the real migration look done. Three drifts are REPORTED, never guessed, and any of them makes the command exit 1: a root with no vault (which notes belong to a workspace is a question about the user's own material), a `.mcp.json` absent against a shared one (an MCP entry grants credentialed access and per-root composition does not exist yet), and a root with no guide while the install root still holds the pre-migration one — seeding the packaged stock guide there would replace the user's guide with empty memory regions, so the split has to run first. It never raises — a migration that cannot run is a condition to surface, not a reason to fail an upgrade — and it is receipt-gated, so it is a no-op on every start after the first. When it refuses, `operator_actions._detect_workspace_unmigrated` reads the refusal back out of the receipt (via `peek_receipt`, which unlike `read_receipt` returns a refused one) and raises a `blocking` housekeeping action whose run button retries through the same `migrate_if_needed`, so the button cannot drift from what startup does. Blocking means unmissable and not dismissible, deliberately NOT an app-wide lock: the one realistic refusal is an uncommitted vault, and locking the app would take away the assistant needed to fix it. CLI: `ciao workspace-reroot [--rehearse|--apply|--repair|--undo]`.

The entry detector selects only OLD and UNDATED entries: a valid `[verified:]` stamp inside the horizon is never a finding whatever the note's own `updated:` says, a stamp the parser cannot read (malformed, an impossible day, a day that has not come) is `unverified` rather than fresh whatever the note says, while a *missing* stamp is a finding only once the horizon has passed — a bullet with no stamp inherits the note's date and is current exactly as far as the note is, and selecting those unconditionally made every bullet written before stamps existed read as never checked, filling a nightly plan with one-day-old entries in any vault that had been re-stamped.   terminal_auth.py             Bounded terminal authorization grants (#1682, child of #1680): the browser terminal's credential, and only that — a foundation with no route, no shell and no session behind it. A grant is a 256-bit random bearer (minted by `issue` and handed to the caller exactly once, which puts it in a host-only, HttpOnly, SameSite=Strict `ciao_terminal` cookie) bound to the SHA-256 of the login cookie it was minted on, because the login cookie cannot identify a browser: two sign-ins inside one second can produce identical login cookies, and a grant that could not tell them apart would let one browser's logout revoke another's. A renewal revokes the grant it names only when that grant is bound to the same session, so a foreign bearer frees no slot and ends nothing. A credential that is not valid UTF-8 is a value, never an exception: an unusable session is refused and an unusable bearer or cookie verifies as nothing. There is no password in this module and no guessing budget: the signed-in session is the terminal's trust boundary, so the grant answers which browser may hold the socket and for how long, and the route that mints it asks the engine for nothing else — the unlock takes no body at all. The store authenticates nobody: a route must verify the session cookie itself, and it hands the store the session cookie the grant is bound to. In memory only: a grant is a short-lived capability, and a restart ends every one of them.

  terminal_replay.py           Bounded raw-byte replay for the browser terminal (#1705, child of #1680): the byte contract a reconnecting client replays from, and only that — no session, no process, no socket, no renderer, no persistence, and no runtime wiring yet. Terminal output is bytes, not text (a UTF-8 sequence or a VT sequence can be split across a read boundary), so the unit of position is the **absolute byte offset**: the total count of bytes the stream has produced, never rebased, and capped at `TERMINAL_REPLAY_MAX_OFFSET` (2**53-1) so every offset survives the trip to the browser as an exact JavaScript safe integer. Nothing is decoded, re-encoded or boundary-guessed here: a retained suffix may start halfway through a UTF-8 or escape sequence, and preserving the bytes exactly is the point, because repairing the screen is the renderer's job. Storage is one fixed `TERMINAL_REPLAY_BYTES` (256 KiB) `bytearray` and nothing else — no chunk registry, no full history, no output queue, no backlog — so the memory a terminal can hold is knowable in advance; the byte at offset `n` lives at `n % TERMINAL_REPLAY_BYTES`, which makes eviction a consequence of the write rather than a separate policy. The two losses are told apart, because they are different problems: a *stale initial* attach (an offset already evicted) is answered with a **truncated** snapshot of the retained suffix, so the caller resets the renderer and is honest about the gap, while a *live* read behind the oldest retained byte is refused as **`slow_consumer`** rather than silently clamped — a consumer that has lost bytes cannot be handed a stream with a hole in it, and giving it a second queue of output would be exactly the unbounded memory this module exists to prevent. One append and one read are each bounded at `TERMINAL_REPLAY_CHUNK_BYTES` (64 KiB), results are immutable copies that never alias the ring, and every refusal carries a closed reason (`invalid_offset`, `invalid_limit`, `chunk_too_large`, `sequence_exhausted`, `slow_consumer`) and a message that is the reason and nothing else. Tests: `tests/test_terminal_replay.py`.
  terminal_sessions.py         Bounded terminal session manager for the browser terminal (#1736, child of #1680): the one owner of the shells, and still no route, no WebSocket, no app wiring and no shell a user can reach — the transport-free half of the terminal, importable and testable on its own. It owns every process, every replay ring, every controller and every detached lifetime, and it keeps all four bounded. **Sessions**: at most `TERMINAL_MAX_SESSIONS` (4) are retained *in total*, exited shells included, because an exited shell still holds its output and its exit status for the UI; the slot is reserved *before* the shell is started, so a burst of creates cannot start a fifth process, and a spawn that fails, is cancelled or is overtaken by a shutdown closes the process it produced and releases the slot. **Output**: each session owns one `TerminalReplayBuffer` and nothing else — the ring's own 256 KiB window and absolute byte offsets are the contract, this module defines no second ring, no capacity and no chunk constant; a reader task polls the non-blocking process and appends each chunk once, so a client that falls behind the oldest retained byte is refused as `slow_consumer` rather than given a backlog, while an initial attach with a stale offset gets a `truncated` snapshot instead. **Controller identity**: a session has one optional *controller* — the random `connection_id` a route mints per attachment, never a grant fingerprint, never a cookie and never a browser, so two tabs of one browser are two controllers and the second one has to take over explicitly; a takeover replaces the controller and displaces the old attachment, and a stale detach, write or resize from the previous connection is refused rather than reaching the successor. **Lifetimes**: a detached session is pruned `TERMINAL_DETACHED_TTL_S` (900) after it became detached, and output never extends that deadline; an *attached* session is not pruned by this timer, because the unlock watchdog belongs to the route — but a shell that has *exited* has nothing left to control, so it releases its controller and ages out like any other detached record, keeping its final bytes and its exit code until it does. The expiry decision and the removal happen under one lock, so an attach that arrives in between cannot have its session closed under it. **Input**: bytes a terminal will not take stay pending, and the pending backlog is bounded, so nothing inside the engine grows without limit; one *flusher* task owns that backlog and is its only writer, so a terminal that will not take its input cannot stop its output, and a write that is cancelled can neither duplicate nor lose the bytes (they leave the queue before the write and exactly the refused remainder goes back). A write is *accepted*, not delivered: the caller never waits for a pipe that may block. **Lifetimes of a close**: a close is never abandoned — it runs in a manager-owned task that a cancelled caller cannot cancel, the process is marked closed only once the close has actually completed, and a shell is closed exactly once. `end()` closes the shell *before* it removes the record, so a cancelled end is retryable; `shutdown()` closes every shell before it clears the registry, so a cancelled shutdown still closes every shell. A close that still fails is logged, not retried: the platform adapter has already waited for its own threads. The process factory and the monotonic clock are injected (`spawn_terminal` and `time.monotonic` by default), which is how the tests reach every race without a pty and without waiting for a clock. Spawn, write, resize and close all run off the event loop, every task is observed and joined on end and shutdown, and nothing about the terminal's contents is written to a record, an error message or a log line — refusals are typed (`TerminalSessionError` with a closed reason). **Helper sessions**: `create(..., argv=...)` (engine-only; the routes never pass it) runs a fixed engine-built program instead of the shell; `helper_output`/`helper_input` read and type into a helper session without a controller and refuse a user shell (`invalid_target`). Tests: `tests/test_terminal_sessions.py`.

    update_task_launch.py       The launch half of the "After this update" pipeline (issue #761): `ciao/update_task_catalog.py` defines the tasks, `ciao/update_tasks.py` (#756) remembers their per-scope state and answers whether they apply, and this turns one eligible task into one chat — server-owned, and exactly once. **The prompt is server-owned**: it is read from the packaged resource by `read_prompt`, and no parameter accepts prompt text from a caller; what travels instead is `prompt_digest = sha256(prompt)[:16]`, so a later reader can tell whether the instructions changed without shipping them twice. **Start is idempotent per `(task id, revision)`**: the read of the record and the write that replaces it are one `update_tasks._record_lock` section (the same one the rest of #756 uses), so a double click, two tabs, a retry after a dropped response and a restart all get the SAME chat back — `resumed: true`, nothing created, nothing dispatched. A record naming a chat that is gone is the recoverable case: a fresh chat is created and the record re-stamped to it. Because records are keyed `"<id>@<revision>"`, a revised task cannot resume, or even see, the previous revision's chat, so an engine update can never substitute new instructions into a running chat. The record is written BEFORE the turn is dispatched, so a failed dispatch cannot orphan the chat: `UpdateTaskLaunchError` carries the id, the attempt is marked `failed`, and the next start sends the prompt into that same chat. The pre-dispatch write is `failed` and the flip to `in_progress` happens only once `start_stream` has returned, so a lifecycle in the file means what it says and a crash in that window is retried rather than reported as a resume that never ran; a write that *fails* in the same window is logged, not raised, because `UpdateTaskStateError` is a `ValueError` and a 409 would answer a running turn with no `chat_id` and invite the retry that dispatches it twice. A start on a `dismissed` record is a reopen: same chat, record written `in_progress`, nothing re-sent — which is only sound because `dismiss_task` drops the chat of a record that is `failed`, the one lifecycle that means the prompt never reached it, so a dismissal can never hand a later start an empty chat to call a running one. The chat is hosted in the workspace's own `General` project — the one `HousekeepingStrip.vue` finds by its `is_auto` flag, created if the install has none — and carries an `update_task` helper (`task_id`, `revision`, `scope`, `prompt_digest`) normalised fail-closed in `chat_service._normalize_chat_helper`, which is what makes the chat findable again after a restart. A `dismissed` or reopened-`offered` record with a live chat is un-declined in place (`in_progress`, same chat, nothing re-sent) so `dismiss → start` and `dismiss → reopen → start` agree, and a `completed` record is refused outright with a `ValueError` before the chat is looked at — by a start *and* by a dismissal, so no stale tab pressing either one, and no archived or deleted chat, can turn a finished task back into a running one. Routes: `GET /api/update-tasks?workspace=`, and `POST /api/update-tasks/{task_id}/{start,dismiss,reopen}`; each state-changing one carries the fresh task rows, dropped rather than raised if the listing fails. Each row reports **two clocks** and they are not merged: `applicability_checked_at` is when that row's answer was computed (`update_tasks.ApplicabilityResult.checked_at`, a wall-clock stamp taken where the detector ran) and `updated_at` is when the record was written. A dismissed task therefore has a decision time and a possibly-stale check time, and a client that showed one under the other's name would be claiming a re-check that never happened. Inside `APPLICABILITY_TTL_S` a row keeps the stamp of the call that computed the answer, so a repeated read does not re-date it; the state file is re-read every call regardless.

Workspace-move verification first probes a temporary file in the destination (or nearest existing parent), before draining or stopping the engine; this does not create the workspace tree. A macOS `EPERM` preflight is reported as an access denial, while `EACCES` stays an ordinary permission failure. The operation record preserves the forward denial and optional startup exit code before rollback can restart an engine that clears the shared denial record. ## Vocabulary

Three terms describe where things live. They are pinned here because the same
word once meant two different things.

- `workspace_root` — the install root directory (e.g. `~/repos/ciao`). Holds the
  vault, `.runtime/`, config, and the user's agent assets. Meaning unchanged from
  today.
- `workspace` — the logical workspace name (e.g. `personal`, `work`). A label,
  not a path. Meaning unchanged from today.
- `agent_root` — the per-workspace directory that will hold that workspace's own
  `AGENTS.md`, `.mcp.json`, `.claude/` assets, and `memory-vault/`. Today it
  resolves to `workspace_root` for every workspace, so it is a seam and not yet a
  distinct directory. The re-rooting release makes it a real subdirectory.

`handover` is pinned for the same reason: it is a provider-session word, and
the persisted key `handover_context_pending` cannot be renamed. It moves one
chat's recent turns into a fresh provider session
(`ChatInfo.handover_messages`, `handover_context_pending`); the workspace
re-rooting reuses it to mark chats whose old provider session was stranded by
the move (`workspace_reroot.flag_stranded_sessions`). The multi-device host /
client role handover that once shared the word is gone, along with
`/api/node/handover`; `POST /api/chats/{id}/handover` and
`POST /api/handover/merge` are both this provider/git sense of it.

## Workspace layout

`workspace_guide.migrate_config` follows `CiaoConfig.agent_root_targets()` rather than the raw install path. Before the workspace re-rooting, that seam returns the install root because it is the shared agent root; after the re-rooting it returns only the per-workspace roots, because `workspace_reroot` has moved the shared guide into the primary root and the install root is no longer an agent root. A root-level guide found after that transition is not a filename-migration target: it may be repository metadata or re-root drift, and renaming it independently would either mutate unrelated instructions or leave a parent guide for providers to load.

The app repo above is the installable package. A `workspace_root` is a separate directory (created by `ciao setup`, never committed to this repo) that holds the user's data and per-instance state: one root folder containing the vault (`memory-vault/` by default) alongside `commands/`, `subagents/`, `skills/`, `.runtime/`, and config. A fresh first logical workspace and every workspace created later in Settings are user-named folders under that configured vault root (`<vault>/<workspace-name>/`); Settings never accepts a filesystem path for them or follows a named-folder symlink outside the vault. Setup can preserve an existing notes folder in place; that folder is then the vault and the install folder at once, a supported layout that the re-root migration and the relocation notice both leave alone (#2021). Upgrade compatibility can temporarily pin any older nonstandard vault root. The AI OS audit reports each other nonstandard root with a Ciaobot-chat migration prompt so the model can inspect conflicts, back up the source, update the registry, and restart into the standard nested layout without moving data silently. Setup defers Git history by default; `ciao setup --initialize-git` explicitly creates local history and an initial commit of nonignored workspace and external-vault contents, with no remote or upload. Existing repositories still receive missing ignore guards, and setup never creates nested repositories. **Workspace and vault repos store exact bytes on every OS:** `ensure_workspace_git` (and `ensure_vault_git` for a vault rooted at its own repo) writes `core.autocrlf=false` into the repo's own `.git/config` when the repo does not set it already, and every git the engine runs there passes `-c core.autocrlf=false` (`git_proc.EXACT_BYTES`), so a repo that has not been re-checked yet behaves the same. The vault's revisions and hashes assume the bytes on disk are the bytes committed, and the engine writes exact bytes (`newline=""`); Git for Windows ships `core.autocrlf=true` in its system config, which would store a CRLF note as an LF blob. On macOS and Linux the default is already `false`, so nothing changes there. The vault may also point elsewhere (`CIAO_VAULT_ROOT`, e.g. an existing notes folder): with explicit `--initialize-git`, setup initializes that folder as its own git repository (`git init -b main`, a minimal `.gitignore` for `.DS_Store` and `.obsidian/workspace*`, and an initial commit); without it the folder is adopted untouched, and a vault nested inside the `workspace_root` repo — the default layout — is never double-initialized.

Fresh adoption of one existing notes vault is recorded as born per-root too: its vault path stays unchanged, while agent assets use the named workspace root. First startup must not treat those notes as an old shared-layout installation, create a migration snapshot commit, or relocate them. Existing registries, completed/legacy onboarding receipts, and detected nested-workspace layouts retain their upgrade behavior.

Ownership and the standard destination are separate questions, and the code keeps them apart.

- **Registered ownership.** On a per-root install, `agent_vault_root(name)` follows the registered `vault_root` for scans, health checks and custom categories. An adopted brain's entity snapshot and search rows share a private SQLite database under the install's search directory, keyed by workspace and resolved source folder. Refresh and search publish both projections in one transaction. The database and its journals require owner-only access inside an owner-only directory. Stored paths resolve from the original folder. A failed refresh preserves the previous transaction. Setup and refresh leave the adopted folder's `INDEX.md` under its owner's control. When the configured search directory lies inside any registered notes or shared-brain folder, the connected index uses an install-specific directory under `~/.ciao/connected-indexes/`. A registration that still points at the pre-re-rooting shared subfolder (`memory-vault/<name>`) is the superseded standard and keeps the derived location.
- **Standard destination.** `canonical_workspace_vault_root(name)` does not consult the registry. On a per-root install it is `<agent root>/<vault folder name>`, the location the vault-location check and the re-root migration compare against. A registered nonstandard location never becomes the standard merely by being registered.
- **Relocation offer.** `CiaoConfig.adopted_workspace_vault(name)` is the one rule for "adopted on purpose", and `agent_vault_root` and `migration_notices.relocation_state` both read it: on a per-root install, a registered vault that is neither the standard location nor the superseded `memory-vault/<name>` is reported as `adopted_vault`, so neither the audit's vault-location notice nor the `vault-relocate` task offers to move it (#2845). A registration still at `memory-vault/<name>` stays `misplaced_vault` and keeps the offer; the shared layout is unchanged.
- **Shared layout.** Before the re-rooting, every workspace resolves to the one shared vault's aggregate files, and `memory-vault/<name>` stays a notes subtree.

Setup decides the vault location from existing configuration before it writes anything; `docs/DEVELOPMENT.md` describes the selection order and the manual recovery for an adopted vault that was recorded at the wrong place.

## Server and chat pipeline

Linux production hosts run the engine under systemd. Settings uses the
authenticated `POST /api/admin/restart` endpoint, selected by `restart_only` in
`/api/local/status`, to enter the same chat-drain/re-exec lifecycle without a
source checkout or desktop rebuild. Code updates remain administrator-managed;
developer mode retains the deploy endpoint. `restart_only` is also true for
the legacy bundled-app install mode (`detect_install_mode() == "bundled_app"`,
whatever the dev mode) and for any macOS install that is not a deployable
checkout. The re-exec happens in-process (`ciao.cli._run_server`), so the
`com.ciao.server` LaunchAgent keeps tracking the same pid, and its `KeepAlive`
relaunches the job if the exec fails. `ciao supervise` (`ciao/supervise.py`) is
the cross-platform alternative: it runs `ciao run --supervised` as a child,
relaunches it on exit code 75 (with a crash-loop backoff) and forwards
SIGTERM/SIGINT. `POST /api/admin/deploy` refuses a bundled app up
front.

**Native host (#1008/#1009).** The installer plan separates the immutable
permission identity from the mutable engine: launchd → **Ciaobot Server.app**
native host → installed `python -I -m ciao.cli supervise` → engine → provider
tools. The host source is `native/server-host/ServerHost.swift`, built and
archived by `scripts/build-server-host.py`, documented in
[docs/SERVER_HOST.md](SERVER_HOST.md). It owns only two fixed operations
(`serve` and `request-accessibility`), spawns the supervisor with public
`posix_spawn` so it stays in launchd's job group, forwards a bounded stop to the
tracked child and mirrors its honest exit status, and never restarts itself or
the child; the engine's restart/backoff loop stays in `ciao/supervise.py`, and
launchd remains the final job-group owner. This child ships the host and its
artifact builder only — the installer, the update/rollback ownership contract,
release-manifest coverage, and every live launchd/TCC gate are later children of
#1008. `ciao setup` registers a hosted plist when `verify_owned_host` succeeds.

`ciao/` is a Starlette web server that mounts the PWA frontend, exposes a JSON API for projects/chats/schedules, and drives a Claude Code session over ACP (`claude-agent-acp`) for each chat turn. Auth is a pre-shared token (`PWA_AUTH_TOKEN` — the dashboard password) traded for a signed session cookie, and it is always required: there is no setting that runs the dashboard open. Settings can change the password (given the current one). Operational state lives in `.runtime/` under `CIAO_WORKSPACE`; durable memory lives under `CIAO_VAULT_ROOT` (default `<CIAO_WORKSPACE>/memory-vault`).

One backend process owns a runtime directory at a time. The engine is the only
process: on macOS it runs as the `com.ciao.server` LaunchAgent and the UI is the
localhost PWA, which treats the workspace `.env` (`PWA_PORT`,
`CIAO_RUNTIME_ROOT`) as authoritative. A browser cannot hand a page a Finder
path, because HTML `File` objects carry no absolute paths, so Finder drops
arrived through a native handler that wrote the exact paths into a five-minute,
single-use grant under `.runtime/desktop-drop-grants/` and dispatched only that
grant ID into the page. The local `/api/desktop-drop` endpoint consumes
the grant: the route returns bounded opaque file references, and the server
expands those references only in the provider prompt; clients transfer the
file bytes into the active project on the host. This does not add a native command
or general filesystem capability to the remote page. That shell is retired
(`#656`) and the grant route stays only for an old one still in the field.
`ciao/instance_lock.py`
holds `.runtime/server.lock` for the engine process lifetime, so a normal
server and `ciao dev` cannot run against the same registry concurrently.
Project/chat writes use a short-lived registry lock, merge field-level local
deltas onto the latest revision, and append mutation IDs to
`.runtime/web_projects.audit.jsonl`. A chat's pinned file (`pinned_file_path`,
`dismissed_pin_paths`, `pin_revision`) lives in that same registry rather than in
browser storage, so a pin survives a browser change of device and an engine
restart, and there is one writer instead of per-tab copies (#1118). A path is an
identity key: the transport resolves a manual path with the file viewer's exact
resolver (`_resolve_workspace_path(..., allow_fuzzy=False)`) and stores the
canonical absolute POSIX path, so pins carry the viewer's existing permissions
and never widen them; agent `file_surface` records the same identity through the
scoped path it already validated. Manual writes carry `expected_revision`, which
is compared before any mutation, so a device that raced a newer selection gets a
409 with the authoritative state instead of replacing it. Closing a pin
dismisses the path the server had selected, which is why an empty path never
touches the filesystem (a deleted file must still be closable) and why agent
surfacing skips a dismissed path. A real change publishes `chat_pin_changed` and
bumps the per-chat revision; a no-op does neither. The `/ws/events` snapshot
carries `chat_pins` for every persisted chat, including unpinned and archived
ones, so a reconnecting client can close stale state. `file_surface` is the only
place agent intent becomes a pin — replaying browser tool traces is deliberately
not a second writer — and its `viewers`/`stream_state` fields still say nothing
about whether a panel actually rendered. Its `pinned`/`dismissed` fields report
what the pin write did, so a surface skipped by a dismissal is visible to the
agent. Vault-backed project IDs are
deterministic for newly discovered `(workspace, vault_folder)` pairs. At
startup, archive discovery resolves both display names and vault-folder slugs;
missing active rows are reconstructed from normalized runtime transcripts only
when a surviving provider session or a non-deleted audit record proves they
were active. Explicit deletion clears provider state, normalized transcripts,
and session state so recovery cannot revive it.

Needs-you action cards (B1, `ciao/chat_actions.py`, `ciao/web/chat_actions_base.py`, `ciao/web/chat_actions_runtime.py`) are transient and memory-only: a card can name a sign-in URL or a command, so it never reaches the chat registry, its audit log or a backup of either (`ChatInfo.actions` and `ChatInfo.dismissed_action_keys`), published as `chat_actions_changed` with the whole list and kept in the `/ws/events` snapshot under `chat_actions`. Agents raise a card with `ciao chat needs-action`; the engine raises none by itself (there is no MCP sign-in detection after a turn and no `mcp_auth` kind: an MCP server signs in through its CLI's own MCP command). The runtime polls a started sign-in (`device_code`) until it finishes or fails, and gives up after 10 minutes. Continue wakes the chat once with origin `chat_action`. Dismissal and every lifecycle clear (new session, handover, archive) cancel the attempt through each handler's `cancel` hook. Agents may raise a card but never start, dismiss or continue one.

Chat transcripts are streamed via WebSocket and archived to `<agent root>/Logs/Chats/<chat-id>/<provider>/` (`transcripts.py`). The root is chosen per chat by `CiaoConfig.chats_root(workspace)`, through `ProjectChatManager.chat_archive_root` (registry → workspace, primary fallback), which `main` wires into `TranscriptStore.set_archive_root_resolver`. Before the re-rooting every workspace resolves to the shared `<vault>/Logs`; after it, each workspace archives under its own `<install>/<name>/Logs`. Readers scan `CiaoConfig.logs_roots()` / `chats_roots()` (each agent root, then the shared `logs_root`), or the standalone `logs_roots_for` when they hold only paths. Deriving a root as `vault_root / "Logs"` resolves to a path that does not exist on a migrated install, so archiving would recreate it and split the archive in two. A stored `archive_path` that moved is repointed by `_discover_archived_chats`, which prunes only when no root holds the file. Archive, delete, and new-session cleanup disconnect the live supported provider before reclaiming its session: Claude SDK JSONL blobs via `delete_session` and OpenCode sessions via `DELETE /api/session/{id}`. Cleanup is fail-open so a provider outage cannot prevent the durable Ciaobot archive, and it includes prior session IDs created by rotation. Archived `/messages` falls back to the vault markdown when the supported provider session is gone. Claude chats run through `claude-agent-acp` (`ciao/providers/acp/agents.py`), which loads the user, project and local setting sources, so `.claude/skills/`, `.claude/agents/`, and `.claude/commands/` auto-discover. Ciaobot sends no fallback model: a rate-limited schedule fails instead of downgrading. That provider's SDK client is closed by whoever takes it out of the provider's slot, and the slot is cleared *before* the close is awaited: the SDK's `disconnect()` is not idempotent (it clears its query only after the await) and the subprocess transport's `close()` is not re-entrant (it guards `if not self._process: return` only on entry, so two concurrent closes both pass it and the second reads `returncode` off the process the first cleared). A second close of the same client therefore raises `AttributeError: 'NoneType' object has no attribute 'returncode'`, which is what an engine teardown racing a fire-and-forget close produced; the single-owner slot makes exactly one close happen.

Chat document attachments are saved into the active project vault folder as
uploaded, with a Markdown conversion beside them. Uploads and desktop drops take
the same path. The prompt references the Markdown copy, plus the original for
formats the agent reads itself (PDF, where page images keep layout, figures and
scans that the conversion loses). Images and ordinary text retain their existing
behavior. A conversion error is per-file and non-fatal and leaves the original
in the folder; a PDF is still attached without its copy. Originals the file
viewers cannot preview (`.doc`, `.rtf`, `.epub` and the rest) are served by
`/api/workspace-binary` as downloads.

The control plane runs as the agent CLI surface. `CiaoControlPlane` wraps the
existing project/chat, schedule,
subagent, vault, memory, file-history, workspace-health, local-session, and
lifecycle managers; `CiaoMcpService` only performs bearer authentication,
operation dispatch (via the `AgentDispatcher`), plan-mode mutation policy,
stable error envelopes, and
telemetry. Each managed provider process receives a short-lived capability
carrying a chat/project/workspace/provider principal. What that principal
enforces is workspace confinement plus chat attribution, not isolation between
chats: every ownership check resolves through `_workspace`, so a chat token
reaches sibling chats in its own workspace and no others. The chat half drives
plan mode, the child-mode ceiling, background-run ownership, revocation and
telemetry. Claude receives the server and
Authorization header through the adapter's `mcp_servers`; opencode receives
equivalent per-process configuration, which is why it runs one server process
per chat (reclaimed by the idle sweep in
`ProjectChatManager.reap_idle_providers`). External MCP configuration and
credentials remain provider-owned; Ciaobot neither reads nor edits them and keeps no MCP inventory or status.
`ciao chat reload` (`ProjectChatManager.reload_provider`) drops a chat's provider the same way the idle sweep does, so the next turn respawns it and resumes the same session with changed MCP servers, plugins and skills; on the calling chat the drive loop does it when the turn ends and runs one hidden `RELOAD_CONTINUE_PROMPT` turn, and it is refused (`chat_busy`) while background agents or a question form hold the provider.
Claude workspace allowlists continue to constrain reachability. Self-disconnecting operations
defer until their caller chat drains.

The agent CLI control plane is mandatory and is the only agent-facing control
surface: there is no skill/direct-file fallback and no per-chat or
per-server surface selector. `ProjectChatManager.build_agent_request` raises
`AgentSurfaceUnavailableError` when the control plane or the chat's project is missing,
and `_drive` turns that into a normal failed turn in the transcript, so a chat
never runs an agent that silently cannot reach Ciaobot. First-run setup is the
one state without a control plane (no workspace yet); a chat attempted there
fails with the same error. The `legacy`/`auto` surfaces and the
`ciao benchmark-control-surfaces` evaluator that compared them were removed
once the evaluation had settled on MCP. Two deliberate CLI exceptions remain, both for surfaces that are not control-plane CRUD: `ciao proposal-check` validates a proposal file the agent wrote, and the vault-maintenance verbs (`ciao index`, `ciao lint`) wrap tools a file tool cannot replicate. The MCP surface keeps `memory_status`/`memory_update` for bounded memory itself.

Queued messages flush as the next turn; waiting entries leave by Send now. Messages sent while a turn runs live in `ChatStream`'s queue, which stays the source of truth. `ProjectChatManager.send_queued_now` starts a turn from named waiting entries when nothing is running, and moves them into the live queue ahead of later entries (`ChatStream.adopt_waiting`) when a turn is running so they flush after it. A user Stop holds the whole queue: the drive loop parks every queued entry on the chat instead of flushing it. The parked queue (`chat.pending_queue`) is never re-seeded or flushed by `start_stream`: it grows by appending when a stream parks, shows in every `queue_state` through `ChatStream.waiting`, and shrinks only through Send now, edit, remove or reorder. The wire protocol is in `PWA_API.md`.

`ChatInfo.user_turn_origin` records the origin of injected user turns, deliberate retries and the engine's deferred retries, and the engine repeats it on `user_echo`, queued delivery and `/messages`. The WebSocket client may supply only exact `origin: "retry"`; every other system origin remains engine-owned. A duplicate send repeats the stored origin, never rewrites it from the incoming frame. Origin is display metadata only: it does not alter authentication, permissions, providers, queue delivery or send-id idempotency. Retry transport and collapsed rendering consume this field without changing the original prompt.

Editing from the composer uses a server-confirmed `queue_take`: the synchronous take and drain cannot interleave. The manager takes from the live or parked queue, publishes the new queue, and retains a bounded one-hour receipt exposed as `ChatInfo.pending_takes` until `queue_take_ack`; this allows a reconnect to recover a result lost in transit.

Send-id dedup ownership follows the same queue lifecycle: live and parked entries both suppress replay, and drain/adopt/flush/cancel transitions carry their IDs until delivery. `ChatStream.drain_one()` retains the popped entry as a temporary pending owner while provider reload or other awaited work runs; successful delivery hands ownership to the turn history, while blank skips release it and teardown/error/Stop/question paths park it before releasing. A combined send-now turn stores all contributing IDs in its one `user_turn_send_ids` slot (legacy single-send slots remain strings), capped at 100 IDs per turn; an over-cap send-now leaves the overflow entries waiting so no active retry ownership is discarded. Lookup matches either representation. The slot history remains bounded to 64 turns, including after reload, and the IDs stay out of transcript-history rows. A send-now dispatch that fails to start restores its entries without recording delivery.

Server restart requests drain chat work before shutting down: active broker streams and already-queued follow-up turns are allowed to settle, while brand-new turns are rejected once draining begins. When drain starts, `ProjectChatManager.begin_restart_drain` publishes `server_restarting` on `/ws/events` (and the connect snapshot carries `restarting: true`) so every open PWA shows the full-screen restart overlay instead of treating turn rejection as a chat error. Shutdown starts only after several consecutive idle observations so the handoff from a completed parent turn to its follow-up turn cannot create a false-idle race. `ciao service restart|stop` gate on the loopback-only `GET /api/admin/restart-blockers` (reason-tagged, a superset of the drain's `active_chat_ids`, including a provider's outstanding background work and native question/permission cards held by a live provider), refuse when the answer cannot be read, and `--force` overrides. A turn records the process running it in `ChatInfo.turn_owner` (stamped by `start_stream`, cleared by the drive loop, kept once `_shutdown_providers` calls `begin_shutdown`). At boot `resume_interrupted_turns` consumes every stamp another process left and, when `resume_after_restart` is on, sends each eligible chat one `restart_resume` turn ("Continue after restart") in its own mode, model and permission mode. Archived chats, engine helper and delegated-task chats, chats waiting on a question, approval or deferred retry, unattended turns, and a resume that was itself cut off are skipped. `restart_resume` is not a person-typed origin, so task completion, deletion and needs-you requests (`ciao chat needs-action`) stay refused.

When the model calls `AskUserQuestion` (which the headless CLI can't render, and would otherwise auto-answer empty), `ProjectChatManager._drive` interrupts the turn so generation stops at the question; the PWA surfaces it in its own picker (persisted as `ChatInfo.pending_question` so it survives a reload) and the user's reply resumes the session as a fresh turn. A native OpenCode form is owned by its per-chat provider process; when no provider and no running turn exist (for example after an engine restart, which marks persisted forms `"stale": true`) the form is dead: cancel clears it, reply starts a normal turn carrying the answer as text, and an ordinary message supersedes it, while a form held by a live provider still blocks. A native permission card follows the same rule: once dead, Approve or Deny clears it (an approval cannot be applied and is reported as `expired`), and a new turn supersedes it.

When a supported Claude or Codex ACP adapter rejects a foreground prompt with its structured usage-limit error, `AcpSession` normalizes it to an internal quota flag and, for Claude, a UTC reset time only when the adapter reports a rejected bucket with a valid Unix timestamp. The raw adapter data stays out of the stream and journal. `ProjectChatManager` accepts a reset strictly in the future and at most 31 days away; otherwise the existing hourly retry applies. Attempts remain capped at a week (168). The persisted retry time and kind are exposed in the chat REST object and authoritative retry event, and the chat card shows the scheduled local date and time. `/api/chats/{chat_id}/retry` also lets the UI set, stop, or run that retry immediately. A retry of an unattended (automation) turn, including one armed after a connection, startup or auth failure, is replayed unattended: the flag is saved with the retry state (`retry_unattended`) so it survives a restart. A turn that ends in an error also persists a one-line `last_error` on the chat, which Home files under "needs you" until a new turn starts or a newer run of the same routine supersedes it. An unattended turn whose job could not reach an external service can arm a `network` retry itself (`ciao chat retry --action set --kind network`): the in-flight prompt is re-sent as an unattended turn after 10, 20, then 40 minutes, three times at most, and a result push is held while it is pending.

Conversation forks let a user start a new chat in the same project starting from any completed agent answer in an active or archived chat. When a fork is created via `/api/chats/{chat_id}/fork`, the system performs a provider-neutral history copy, copying the visible chat history up to the selected assistant response, normalizing the messages (with system notes for truncated older messages if bounds are exceeded), duplicating referenced images to ensure source independence, and initializing a new chat with `handover_context_pending=True`.

## Memory, insights, and self-improvement

Durable memory is written by the memory pass, not by the archive. The pass is a chat of the app's own — an attended `bypass` turn in the per-workspace `Memory` system project, on the configured session-insights model (`ciao/web/memory_pass.py`; model chosen in Settings → Providers) — and it does the vault work with its own tools instead of behind an extraction prompt: it reads the archived transcript, updates the note a person or a project already has, folds Decisions and open loops into that project's canonical doc, creates a note only for a genuinely new entity, promotes a durable fact to a region through the `ciao` CLI, and puts anything it is not sure about on `Workspace/Unsure.md`. When new advice supersedes guidance a note already stores, the pass rewrites the surviving line to one instruction plus its source and date and removes the superseded line; a genuine conflict is shown to the owner instead of stored as two current instructions. A single chat's passing remark, or an inference from a search that found nothing, is never the later correction of a recorded decision: the pass shows both as a conflict. One pass runs per workspace at a time, FIFO, because two turns writing the same vault notes would race. A turn the transcript marks as automated is not the user's, and the pass is told not to record it — extracting a maintenance session's own operating rules used to auto-promote the machinery's self-description into the bounded regions. Every queued bullet still names its destination (`[memory]`, `[profile]`, `[project]`, `[people: <Name>]`, `[review]`) and a time-bound fact still carries `[as-of:]`/`[expires:]` (design rationale: docs/MEMORY_DESIGN.md; retrieval eval: docs/MEMORY_EVAL.md).

Archiving a chat writes the markdown transcript, indexes it for search, and — when the archive has turns to read — queues a memory pass, a chat of the app's own that does all the vault work (the project-doc fold, region facts, people notes, learnings and proposals), so it can be resumed, inspected and steered like any other chat. The pass records its state on the archived chat as `postprocess` (`{steps: {memory_pass: {status, extra: {chat_id}}}, updated_at}`), published as the `chat_postprocess` event and persisted with the chat, so the archived chat can link to the pass that read it. On load only that step is kept; records from before the trajectory stage was removed also carried that pipeline's run state and manifest view.

For a managed source-chat pass, the engine signs its settled source relationship while its principal is live and stores the private attestation with `done` in one chat-registry replacement. After archival, a detached worker materializes the checkpoint and files only currently granted, destination-mapped evidence for review; it never publishes. The source chat records a pending or unavailable intake outcome for restart replay. A registry replacement protects the process-interruption seam but does not by itself claim power-loss durability.

Each session gets its bounded memory through the provider's native guide load, not an injected block: every chat, schedule, and subagent runs a CLI with `cwd` set to the workspace's agent root, so both read `<root>/AGENTS.md`, regions included. `core_prompt.py` renders only the compact Ciaobot core (`unified_core()`; for ACP providers it rides the capsule's stable block, see the capsule section), and does not render `ciao:memory` or `ciao:profile` into a second prompt block. Caps are advisory (3000 chars for `ciao:memory`, 1375 for `ciao:profile`; `ciao/memory_tool.py`); `os_audit` reports over-cap, oversize, duplicate, and invisible-Unicode issues. Consolidating entries a region already holds is the one region write the unattended nightly curator does perform, and only once usage reaches ~85% of the cap: it merges duplicate and superseded entries, drops entries whose `[expires:]` date has passed, tightens wording, and moves project-scoped facts out to their owning doc. Three guardrails bound it: every removed or replaced entry is copied verbatim into `<vault>/Workspace/Memory-Consolidations.md` under a dated, region-named heading first, so nothing is lost and any line can be restored; a removal needing judgment is never made, and becomes a `drop <region>:` line on the Unsure list instead (deleting the line keeps the entry; ticking it lets a later run remove it after copying it to the undo log); and a durable fact is never dropped merely to fit a cap. Promoting a NEW fact into a region is a direct write: the memory pass, an attended "remember" and the care run all write a confident fact themselves, and what they are unsure of goes on the Unsure list. A region still over cap after consolidation is reported for the user to act on — an attended chat consolidates further, or the region stays over its advisory cap. The agent edits the regions either with `Edit` or through the control-plane `memory_status` / `memory_update` operations, exposed as `ciao memory status` and `ciao memory update --region {memory,profile} --action {add,replace,remove}` (`ciao/agent_cli.py`). Doubtful items go on `Workspace/Unsure.md` (`unsure_list.append_unsure` for backend writers). A bounded entry tagged `[expires: YYYY-MM-DD]` remains active through that date. After it, the entry is deleted from the guide before the next turn: `ProviderService.execute_streaming` runs `prune_expired_entries` on the chat's agent-root guide before every turn and reconnects the provider when anything was removed, so a just-expired fact never stays in the native snapshot (daily curation drops them too). Curation removes only entries with valid, passed dates and reports malformed tags instead of guessing. `memory-audit` reports entries whose `[as-of:]` or learned-at date has aged out, for the weekly care run to re-verify. People notes merge rather than overwrite, and learnings entries are structured (`- [key] [first → last] (xN) … — sources:`) so re-observation increments a count instead of duplicating. Daily memory curation also appends durable learnings to the vault's `Workspace/Learnings.md`. Startup `ensure_regions` + legacy `~/.ciao/memory.md`/`user.md` migration folds old files into the regions once. Region contents are git-tracked with the workspace.

`provider_service.py` prunes valid expired entries from the guide before
provider startup, and the typed MCP `memory_status`/`memory_update` operations
write the same guide rather than maintaining a parallel store.

### Memory write policy

The agent writes memory directly (regions, notes, project docs, people) and puts what it is unsure of on `Workspace/Unsure.md`; Git is the record and the undo. The region cap is **advisory** on every path: a write goes through and reports `over_cap`, and consolidation, not refusal, bounds a region. The unattended care run only consolidates entries a region already holds and never promotes a new region fact on its own.

**Unattended runs defer; they do not route around the missing reviewer.** The
capsule marker (`ciao/context/capsule.py`, one string in
`ciao/memory_policy.py`) tells a schedule/automation turn not to ask or wait and
to report deferred work — a NEW region fact, a vault-note trash/delete, a
write into another workspace, a new automation in another workspace, and public
or destructive git actions — in its final output instead. The memory pass reads
the same marker in the transcript it is handed, and is told never to record a
fact out of an automation turn.

### Lesson routing contract

Where a reusable lesson goes, and what each route is allowed to do. A lesson is
the general case; the memory pass, `/remember` and the care run all produce
them.

| The lesson applies to… | Destination | What may happen |
| --- | --- | --- |
| A skill this workspace owns under `skills/` | a `skill-edit` proposal file under `Workspace/Proposals/` | a person, or an attended chat they ask, edits the skill from the file |
| A packaged, mirrored or shared skill | an `upstream-issue` proposal file | a person files the issue from the file |
| No skill at all | a `skill-edit` proposal file for a new skill | a person creates the skill |
| A project this workspace owns | that project's canonical vault note | written directly |
| A cross-project preference or identity | a bounded region when confident, else the Unsure list | written directly or ticked by a person |
| A one-off episode | the event log | the existing pass behaviour |

Two rules hold across every row. **An inventory match is a candidate, not proof:**
the filer reads the target's current source and cites both why it applies and
the failure it observed. **Nothing is promoted unattended:** an unattended run
may write a proposal file and report it; it may not edit a skill, edit
`AGENTS.md`, create a skill, or open a public issue. The care prompt states
this, and `ciao proposal-check` (`ciao/proposal_files.py`) holds the file format.
`x3+` recurrence is a **routing priority**, not permission.

**`/remember` keeps a real origin.** A `/remember` of a lesson usually happens in
a chat that is never archived, so there is no transcript turn to cite. The direct
`ciao memory learn --request ID` write records the user-request identifier as
`req:<id>` provenance, and the learning model deduplicates on it — so a retry of
the same `/remember` cannot inflate a recurrence count. It does not manufacture
an archive or cite a conversation that never happened.

**Legacy sidecars.** `Workspace/Memory-Proposals.md` and its decision and prediction sidecars are no longer read or written; the care run drains the queue file into the Unsure list and proposal files, and the sidecars stay on disk as history.

Workspace registry mutations share the runtime-local `locks/workspaces-registry.lock`. Settings, archive, restore and rename acquire affected checkout claims in sorted path order before taking registry ownership. Settings and workspace lifecycle operations compare the configuration’s loaded registry bytes with the current file before changing workspace files. Setup revalidates its vault selection under the same lock. Archive, restore, rename and offline maintenance keep the same owner through registry persistence and compensation. A busy or stale mutation can be retried after loading current settings. Cloud clients continue to own folder replication.

A workspace may carry `provider_overrides` (`WorkspaceConfig`, validated by `coerce_provider_overrides`, stored sparse in `.runtime/workspaces.json`): per provider, an override of `model`, `thinking`, `permission_mode` and `insights_model` that sits between an explicit value and the Settings → Providers default. `CiaoConfig.workspace_override` and the `default_*_for_*` methods resolve it keyed by the chat's effective provider; it is operator-only (the session-cookie workspace upsert), is not restored from an archive, and never applies to an MCP-spawned chat's permission mode, which stays clamped to its caller's (`ControlPlane._child_mode`).


**A filed upstream issue is not a deployed lesson.** `filed` on a draft means the
issue exists. The lesson is still not in any local skill, so nothing about the
local guidance changes and the learning stays Active until a local destination
is verified.

**Decisions behind this matrix (AI-01).** The policy is published as the
current behavior, not changed to match the older prose. Archive-time
auto-save was the default when this was written: confident, state-shaped
facts were applied at archive time, exactly as the code already did. That
default is gone with the one-shot pipeline (#627); the memory pass is the
post-archive writer now, and it runs attended. No "review everything" setting
is added — it would be new scope with its own migration, and the queue already
holds everything the guards reject. Because the default moved in code rather
than behind a setting, no migration is required. Making an uncertain or stale
reconciliation decision *queue* the competing fact rather than append it is a
separate behavior change tracked by AI-06 (#459); this document does not
reinterpret user consent that was given under the current defaults.

Runtime, workspace, project, and vault-entity context is built
once by `ciao/context/capsule.py` and prepended to the request for both supported
providers. For Claude native slash invocations, the capsule is not a prefix on the wire
message: `native_slash_prompt` splits it off, and the ACP provider sends the bare
command as the first block with the capsule as a second block (the retired SDK driver
delivered it through `UserPromptSubmit.additionalContext`). A prefix
prevents native command expansion, including explicit-only skills such as `/retro`. Ordinary prompts
keep their capsule inline; no prompt receives both forms. Trust is explicit, not
inferred: `AgentRequest.injected_context_prefix` records the exact capsule
`build_agent_request` prepended (empty for compact) and `prepend_stable_context`
extends it when restoring stable context, so the provider strips that one prefix
and nothing else. A user-authored `[CIAO_CONTEXT_BEGIN]` block after it stays
user text, and a missing or mismatched prefix means the message is not treated
as a native command. Pending capsules are matched to the submitted prompt,
excluded from subagent prompts and cleared when a
send fails, a turn ends or the provider disconnects.

The Ciaobot core is part of the stable block for ACP chats only. `build_context_capsule(core=...)`
puts `core_prompt.unified_core()` first, ahead of `workspace=`, so it rides the same once-per-session
and after-compaction schedule as the other stable facts. `stable_context_digest` hashes the core as
its own digest (only when non-empty), so editing `ciao/system_prompt.md` re-sends the core on the next
turn. Non-ACP chats never receive it in the capsule (`ProjectChatManager._core_for_chat`). An agent-side
compaction is reported by `AcpSession` as `ContextCompactedEvent`, emitted after the agent reports a
completed compaction. The drive loop and the between-turns drain clear the stable-context marker on it,
and the drive loop also marks the turn compacted, so the turn's own result does not re-commit the marker.
The event is host bookkeeping: `event_to_json` returns `None`, so it is never serialized to the PWA.
Retrieval is driven by the system prompt (`vault_search` tool) rather
than a per-turn heuristic hint. The managed SDK CLI owns background shell
processes and stops them when the turn ends, while their terminal notification
is delayed until a later turn resumes the session. Keeping these calls in the
active turn makes the real shell result part of the same streamed response.

The capsule carries **one** line about the task board, `TASK_BOARD_HINT`
(#1040): the `ciao task list | get | delegate` recipe, the rule that an agent
fetches the tasks this turn needs rather than the whole board, and the rule that
only the user marks a task done. It is a constant in the same file rather than a
derived fact, so `context_digest` cannot see it and the stable block is not
re-sent because of it; it rides the stable facts because a provider session reads
it on its first turn and needs it no more than that. It deliberately carries no
task title, date or body: a task record is the user's own Markdown, and #1002
keeps `Workspace/Tasks/` out of recall, review and curation precisely because it
is bookkeeping rather than a note — a capsule that quoted records would leak it
into every model context with none of those filters around it. The board itself is
a delegated child (`POST /api/tasks/{id}/delegate`), so a turn that was handed
one already has its text.

A linked project (`ProjectInfo.repo_path`) adds a `[Linked repository]` block to
the capsule (#1436): the repo path, `LINKED_REPO_RULES` (the shared-checkout and
vault-versus-repo rules), and the repo's `AGENTS.md`, or `CLAUDE.md` when that is
absent, capped at `REPO_INSTRUCTIONS_MAX_CHARS` and stripped of envelope markers.
The block rides the stable facts, and a fingerprint of path, file name and content
hash is part of `context_digest` (only when non-empty, so unlinked chats keep their
digest), so editing AGENTS.md re-sends it on the next turn. The instructions text
(capped at 8,000 characters, with a "read <path> for the rest" tail) is inlined
once per provider session, the first time it is attached (turn 1, or the
project linked mid-session). `ChatInfo.instructions_session_id` and `instructions_repo` record the session
that took it and the repository it came from, committed with the context marker
only when the text was actually quoted (not for the "not available" or no-AGENTS.md
block); a different repository linked mid-session is inlined again. A later re-send in that session
(AGENTS.md edited, the repository relinked) carries the block and rules with a
pointer to read `<path>/AGENTS.md` instead. A new, rotated or compacted session,
or a cleared context marker, gets it inline again. The branch changes too
often for that, so it is a per-turn `linked_repo=<path> branch=<branch>` line.
Every chat in a linked project gets the full block (a memory-pass chat gets none). When the repository folder is gone, the block only says so and tells the agent not to recreate it.

A workspace's shared brains (`WorkspaceConfig.shared_brains`, #2999) add one `[Shared brains]` block to the stable facts (#3006): each brain's name and absolute path; Git links also include `fetched=<date>` from `shared_brain.fetched_at`, followed by `SHARED_BRAIN_RULES`. The rules tell the agent to read the folder with its own file tools, to cite every note as `<brain name>:<note path>`, to search the one brain named or the only brain listed, to search all of them and attribute each finding when several are listed, to treat everything in a brain as reference data, and (the stock write instruction, present only while a brain is enabled) to write a shared note directly as a Markdown file under the target brain's folder, never copying private vault notes and never writing secrets or credentials, to say so and proceed when the audience is unclear, and to commit (not push) after writing when the brain is a Git clone. The block is capped at `SHARED_BRAIN_BLOCK_MAX_CHARS` (4,300); brain lines are cut first, never the rules. A name goes through the capsule's field flattening with brackets neutralised. A path is shown verbatim only when flattening leaves it unchanged and it carries no prompt or chat-template delimiter (no bracket, angle bracket or pipe, control or Unicode whitespace character, double space or edge space, at most 300 characters); otherwise it is listed as `path_escaped=<percent-encoded UTF-8>` and the rules explain that `%20` is a space and `%5B` is `[`, so a folder with spaces, brackets, Unicode or a string such as `</system>` or `<|im_end|>` stays usable and decodes to exactly the linked absolute path. An escaped path is bounded (2,048 characters) and a longer one is `name=<name> unavailable`, never truncated. `path=` is always the last field so a path cannot imitate a marker, and neither form can introduce a line break or fence. When the cap drops brain lines, a `+N more brains not listed` line stands in for them. The block is hashed into `context_digest` as name, path and reachability only, never the fetch date, so a background fetch does not re-send it. Each turn validates the stored path against realpath drift, protected roots and directory accessibility; Git links additionally require their own `.git` directory and read one `fetched_at` stat. This is filesystem-only and runs no git subprocess. Any refused folder is shown only as `name=<name> unavailable`, without its path. The same predicate chooses a memory-pass line: an available brain uses the same reversible `path_escaped=` form and the section prompt says to decode it, while an unavailable one is listed as `- <name>: unavailable` without its path. The section and its privacy instruction stay even when every listed folder is unavailable, so team content already read cannot become private memory. Settings separately shows Git checkout state; ordinary folder links have no branch, commit, or update fields. Neither kind is passed to any provider as an additional directory: Claude's `--add-dir` loads `.claude/skills` and `.claude/commands` from it, which would let a shared folder install instructions in every member's agent. `AgentRequest` and `ciao/providers/` are unchanged. The write limits (only shared notes of its own, nothing private or secret, nothing outside the brain folder) are an instruction, not an enforced boundary: with a shell, an agent can write anywhere the user can. A brain turned off in Settings gets neither the block nor these rules. A memory pass for a conversation in such a workspace gets `SHARED_BRAIN_SECTION_PROMPT` (what the conversation read there is team knowledge with a home, so keep at most a pointer); memory-pass chats get no block.

A chat is in code mode exactly when its project is linked to a repository whose folder exists on this machine (`ProjectChatManager.linked_repo_for_chat`), except a memory-pass chat. Nothing is stored per chat and there is no switch: chats in a project with a linked repository work in code mode automatically; put a chat in a project without a repository to keep it out. Linking, relinking or unlinking a project mid-chat (or moving the chat to another project) reaches the chat's next turn by the same mechanisms as an AGENTS.md edit: the repo fingerprint in `context_digest` changes, so the stable block is re-sent, and the request's `linked_repo` changes, which is part of Claude's spawn key and of opencode's server-reuse check, so the provider process restarts with the new add-dir, skills paths and write roots. Moving a chat to another project clears its `repo_location`. Transcripts written while code mode was a per-chat switch can still hold its hidden continuation prompt (`cli_envelopes.LEGACY_CODE_MODE_CONTINUE_PROMPT`); it stays in `is_hidden_continuation` so their turn numbering is unchanged.

Chat details can explicitly request `GET /api/chats/{chat_id}/worktree-changes` for one bounded staged/unstaged patch and untracked-name snapshot. The manager binds the read to the chat's live project and registered worktree (or linked checkout when no worktree is recorded), then rechecks scope afterward. Git uses an ephemeral metadata directory with no repository configuration or hooks; unsupported index/object/filter states return unavailable. The response is read-only, capped at 256 KiB and 200 untracked names, and is never cached.

## Schedules and background automation

Schedule dispatch (`ciao/schedules.py`) runs cron-shaped jobs through the normal chat pipeline. One packaged routine is left and it is `per_workspace`: **Workspace care** retains the persisted base id `system-memory-curation`. Fan-out materializes `<base-id>@<workspace>` rows with independent enable and last-run state. The other packaged routine, **Skill reflection** (`system-skill-evolution`), was removed in #697; because the set is derived from the packaged file on every read, its persisted `<base>@<workspace>` rows retire by id and never by a name match, so a user-authored schedule is untouched. Workspace care carries its curation procedure directly in the packaged schedule prompt; it processes memory proposals and learnings every night, then uses `Workspace/Curation-Log.md`'s `last_full_pass` marker to run an overdue full pass even when the server missed Sunday. The full pass refreshes `INDEX.md`/`VOCABULARY.md`, reviews stale notes without unattended deletion, runs `os-audit --scope workspace`, and applies only safe structural repairs. Install-wide failures are not a weekly model schedule: startup triage and Automation surface failed jobs on every install, housekeeping surfaces upgrade actions, and development mode adds the verbose debug report. Proposal helper chats carry persisted proposal IDs and an archive policy; resolution helpers archive only after a clean idle turn and after every owned proposal is absent, while review/discussion helpers remain manual. User schedules live in `.runtime/schedules.json`; mutable packaged state lives in `.runtime/system_schedules_state.json`. Each row's overlay records `first_seen_at`, stamped by `tick` and `catch_up` (and on any save) for rows with no stored state; it becomes the row's `created_at`, so a slot from before a routine existed on the install (fresh setup, a newly added workspace, an upgrade-added routine) is never reported missed or caught up. Rows whose overlay predates the key keep the epoch floor. Compare persisted and live system IDs through `system_base_id` because fan-out qualifies live IDs by workspace.

Sub-day recurrence is the `interval` frequency of the same primitive — what used to be a second one, in-chat loops. The bounded, chat-owned form (`owner_chat_id`, made only by `ScheduleStore.create_owned_loop`, driven by `ciao loop`) is a loop: it has an expiry and a run cap and is deleted when it ends. A run that ends `error` (a denied permission included) adds one to the loop's `fail_streak`, a clean run resets it, and a busy skip, a deferral, a question or a retry counts for nothing (`last_status` `busy`, `skipped`, `retrying`). At two in a row the scheduler deletes the loop and calls `ProjectChatManager.note_loop_stopped`. The engine raises the one notification itself, at once and never held: the fixed text of `loop_wake.loop_stop_text` (the denied tool's name only, never its command) goes out as a banner event and a push, and the failed run's own pending push is cancelled. A run that would stop the loop leaves its own reply's banner and push out (`_loop_run_will_stop`), so the stop is the only notification. The same text is queued into the owner chat as a `loop_stop` turn for the model (its own origin, so it is not a background-run wake and draws its own notice card). The reply to that note is not announced (`_stop_notice_chats`, set only when the note's turn actually started, and spent at the turn's end, along with a note held while an open question waits, which goes out when the chat is idle), and the chat's archive or delete drops both. If the owner chat is gone, the notification still goes out. The permission mode is never touched. An interval entry carries `interval_minutes` (floor: 1) and fires that many minutes after its last dispatch rather than at a wall-clock slot, so it needs no `daily_time_utc`.

Bound to an existing chat via `web_chat_id`, an interval entry keeps everything the loop primitive guaranteed: each run uses the target chat's own model and mode (an empty `model` means "inherit", which `schedule_effective_routing` resolves at dispatch, and `prepare_schedule_chat` does not overwrite the chat's settings for these); overlap protection is skip-not-queue, so a run due while the chat still has a turn in flight is skipped and retried on the next ~20s tick with `last_status: "busy"` rather than queued; a target chat that was archived is forked and one that is gone is replaced inside the entry's own project, and only when no project resolves either is the entry disabled with `last_status: "missing-chat"`. A chat-owned loop (below) is the exception: it is deleted with its chat and never re-homed. Bound to a `web_project_id` instead, an interval entry opens a fresh chat per run with its own model and provider — the combination neither primitive offered before the merge.

A fixed-chat binding is the same dead-target hazard at any cadence, not just interval: dispatching into an archived chat resumes a reclaimed provider session and fails in under a second with a `stream error` that nothing user-visible ever reports (issue #407). `prepare_schedule_chat` therefore re-homes a chat-bound entry whose target is archived or missing at any frequency — fork the archived transcript, or open a fresh chat in the entry's project (primary binding, then `fallback_project_id`, then General) — and re-points `web_chat_id` at the replacement, exactly as the interval path already did; except a chat-owned loop, which is deleted with its chat and never re-homed. A dispatch failure is also stamped as `last_status: "error"` on the stored row, so the Automations sidebar flags the schedule for attention instead of leaving an endless string of invisible failed job records; the PWA detail view shows the status row for a wall-clock entry that carries one.

An unattended run (a scheduled tick) keeps its chat's permission mode, and the ACP permission broker denies any approval it would have to wait on at once (`unattended` on the request, `acp/permissions.py`); that denial is carried on the status event as `denied_tool`, and the dispatcher records the run as `error` naming the denied tool, so a run that finished without the action is never shown as a success. System routines are the exception: they run in bypass, because the packaged care routines must finish with nobody watching. Every dispatch path stamps `last_status: "running"` before the turn starts and the dispatch pipeline writes the outcome back, because `last_triggered_on`/`last_dispatched_at` are stamped at dispatch and therefore cannot tell a served slot from one whose turn died mid-flight. Without that distinction an interrupted run (a server restart, a killed provider subprocess) marked the day as fired: `catch_up` skipped it, the Missed list excluded it, and the work was silently lost until the next occurrence — a week, for a weekly routine (issue #486). `run_failed_since` is the shared rule: a dispatch at or after the expected fire satisfies its slot only if the run it started did not fail. A failed run therefore reports as missed in the PWA, where "Run all" can recover it, and `catch_up` re-fires it on the next launch. Two bounds keep that from replaying work: only `"error"` qualifies — a completed run, and a `"skipped"` one still waiting on the user or the provider, are never re-dispatched — and `last_recovered_on` spends one automatic recovery per slot, so a run that keeps failing (or that takes the server down with it) leaves the entry flagged for the operator rather than dispatching again on every restart. An outcome is applied only to the dispatch that produced it. `last_dispatch_id` (`<slot-day>#<token>`, minted on the entry before the run starts and carried back by the entry snapshot the pipeline holds) is what makes that possible: `last_dispatched_at` and `last_status` are separate fields, so two non-interval dispatches that overlap — a manual "Run now" started shortly before the cron slot — used to pair the newer timestamp with whichever run happened to finish last, which hid an interrupted slot from catch-up in one completion order and retried an already-successful one in the other (issue #490). `stamp_run_outcome` splits the two things being recorded: `last_status` describes the entry's latest dispatch, so a superseded run's status is dropped rather than misattributed (its own result stays in the job-run log, which records the `dispatch_id`, and in its chat), while `last_completed_on` records the occurrence a completed run *served* whether or not a later dispatch replaced it — which is what stops a slot whose work is done being replayed because a second run for it failed. The occurrence is decided at dispatch and never re-derived at completion, so a run dispatched at 23:58 for the 23:55 slot belongs to that slot however long past midnight it streams; `last_triggered_on` already worked that way, and this composes with it. `reconcile_interrupted_runs` runs at the head of `catch_up` and converts a `"running"` stamp left by a previous process into `"error"`, which is how a hard kill is recognised; ownership is tracked by schedule id in memory, not by comparing timestamps, so the startup tick and the catch-up pass can race without a run this process just started ever being replayed. A run whose agent armed a network retry is stamped `"retrying"`, which is neither failed nor completed: `catch_up` leaves it alone and it never reads as missed. The retried turn's end writes `"ok"` (crediting the slot through `stamp_run_outcome`) once no retry is pending; spending the cap, stopping the retry, or archiving the chat writes `"error"`, which the Missed list and the next launch's `catch_up` then treat like any failed run. Both automatic paths are host-only: `tick()` and `catch_up()` return immediately when the startup writer gate says this machine is not the host — the one boot verdict from `ciao.legacy_node_state`, which is the whole gate now that node mode's routes can no longer rewrite the role under a running server — so a former client Mac neither dispatches slots nor rewrites run state (the catch-up guard sits ahead of `reconcile_interrupted_runs` for exactly that reason). Manual `dispatch_now` is deliberately not gated — "Run now", the MCP run tool, and the operator strip's "fire missed one-timers" are a person asking for a run on this machine, not an automation.

Two things interval entries deliberately do not participate in. `compute_last_expected_run` returns `None` for them, so they never report a missed run: their cadence is relative, and every skipped tick (a busy chat, a paused entry, a restart) would otherwise read as missed. And `catch_up()` skips them, so a restart resumes the cadence instead of replaying every interval that elapsed while the server was down. `last_status` is what reports their health instead.

Chat-owned loops. A loop is an interval entry with `owner_chat_id` set: it runs only in that chat and never re-homes. Its lifetime is fixed at creation by `expires_at` (ISO UTC, computed from a duration the caller gives, never an absolute time) and `max_runs`, and `run_count` counts the turns it started. `ScheduleStore.create_owned_loop` is the only door that makes one; it caps a chat at `LOOP_MAX_PER_CHAT` (3) loops and the engine at `LOOP_MAX_GLOBAL` (20), refuses over-cap values rather than clamping them, and counts the caps under the writer lock. The run cap counts a turn when it starts, so a busy skip, an admission deferral, or a prepare failure does not count, while "Run now" does. The first run waits one interval from `created_at`, because a never-run interval would otherwise fire the moment the creating turn ends. A loop ends by deletion: the scheduler's tick deletes the row once it is expired, has used its runs, is invalid, or its owner chat is gone, and a run already in flight finishes first. There is no paused state for a loop. Removing its owner chat ends it in the same synchronous section as the removal: deleting the chat, archiving it, completing or deleting its project, or archiving its workspace (`_drop_owned_loops` on the delete, archive, project-removal, empty-chat and transcript-prune paths) deletes the chat's loops, publishes `schedules_changed` once when any were removed, and leaves other chats' loops and the chat's ordinary routines alone. A refused delete or archive keeps them, because the archive's drop runs only after its last refusable check. A workspace archive never snapshots a loop, and restore cannot bring one back. A chat is never un-archived in place, so a loop never follows a fork or a continued chat. The tick ends a loop whose owner is gone and skips, for that tick, one whose owner is mid-archive. A chat reset (`new_session`) keeps the chat id, so its loops keep running into the fresh session. Every write door checks the loop's shape and refuses a change to its owner, expiry or cap, and the restore path does not carry a loop out of an archive. Downgrade: an engine built before loops strips the four loop keys when it saves, so a loop it touches would run as an ordinary chat-bound interval that never expires, which is why a workspace holding loops must not be opened by an older engine.

There is one runtime flag, `enabled`, where loops had two (`running` now, `autostart` after a boot). The split existed so a loop could tick until the next restart and then be silently dead — the "model says running, loop isn't" failure — so it was collapsed rather than carried over. A legacy `.runtime/loops.json` is imported once on startup by `schedules.migrate_loops`, keeping each `loop-…` id as the `schedule_id` (deep links and recorded ids keep resolving) and mapping `autostart` to `enabled`; the file is then renamed `loops.json.migrated` with one log line. A loop's `web_project_id` becomes `fallback_project_id`, not `web_project_id`: on an interval entry that field is the primary binding and means "a fresh chat per run", which outranks `web_chat_id`, so carrying it across would change what the automation does — but it was the loop's re-home target when its fixed chat went away, and dropping it sent those runs to the workspace's General instead. `resolve_automation_project` therefore tries the primary binding, then `fallback_project_id`, then General, each step a weaker claim about where the user meant the run to land. The loop compatibility surface is fully retired: the `loops_list`/`loop`/`loop_action` MCP tools, their control-plane backing methods, the `GET/POST /api/loops`, `PATCH/DELETE /api/loops/{id}`, and `POST /api/loop-run/{id}` REST routes, and the `loops_changed` event are all gone. `schedule`/`schedule_action` and `schedules_changed` are the only automation surfaces.

Background automations are instrumented through `ciao/job_runs.py`: title generation, schedule dispatch, the memory pass, and startup/system tasks (vault index refresh, skills update, the five-minute memory backup, the one-time legacy memory migration) each record one run (status, duration, model/provider, error) to `.runtime/job_runs.jsonl`. The debug report (`ciao/debug_report.py`) reads the grouped view, and the workspace audit checks the log files; jobs in `RETIRED_JOBS` (removed from the code, but still present in the never-expiring `job_runs_latest.json`) are left out.

`GET /api/agent-assets/audit` exposes `ciao.os_audit.run_os_audit()` to Settings. A successful response is the full report object: `status` (`healthy`, `needs_attention`, or `error`), `total_issues`, `total_errors`, `timestamp`, section objects for `setup_audit`, `vault_hygiene`, `skill_audit`, `rule_audit`, `memory_hygiene`, and `job_runs_audit`, plus the flattened `scan_errors` list. `skill_audit.warnings` lists over-budget `SKILL.md` files in the user-global `~/.config/opencode/skills`, `~/.claude/skills` and `~/.agents/skills` (OpenCode loads them in full); they are warnings, never defects or scan errors. `error` means the scan was not reliable, not merely that actionable findings exist. An unexpected handler failure returns HTTP 500 with `{"error":"failed to run AI OS audit"}`.

Schedules carry an `archive_policy`: `manual` or `auto`. All schedules execute through the normal chat pipeline for permissions and transcripts. `auto` runs a post-run classifier and archives only when the user does not need to see the result; failed, permission-blocked, retrying, or useful runs stay visible.

**Automatic behavior.** Ciaobot automatically archives chat transcripts. Archiving a chat with a transcript to read enqueues a memory pass: an attended chat of the app's own, in the per-workspace `Memory` system project, on the configured session-insights model, which reads the archive and does the vault work itself (notes, the project doc, region facts, and the Unsure list for anything it is unsure about). One pass per workspace at a time, and a pass whose turn ends cleanly is auto-archived while one that does not is left open for the owner. Ciaobot also dispatches enabled schedules, records background-job telemetry, refreshes the vault index, updates configured skill mirrors, and backs up the device branch according to the startup/system automation configuration.

**Not automatic.** The memory pass records what it is confident about, but it will not lift a fact out of an unattended turn, and anything it is unsure about waits on the Unsure list instead. A skill edit is a proposal file under `Workspace/Proposals/`; Ciaobot does not apply those edits automatically. Scheduled chats still run through the normal provider pipeline and permission flow, and an unattended run defers and reports any approval-requiring action instead of seeking an alternate route. A schedule with `archive_policy: auto` is archived only when the post-run classifier says the result does not need user attention; failed, blocked, retrying, or useful runs remain visible. Routine-model choices do not change an active chat's selected provider/model.

## Providers

The set of runtime providers lives in one place: `ciao/provider_registry.py`. Each `ProviderDescriptor` carries the provider's id, its label forms, and dotted import paths for its factory, login command, system-skill listing, readiness probe, and CLI upgrade, plus its thinking levels, default model/bucket, and default-model settings attribute. Paths resolve lazily, so enumerating providers never imports an agent SDK. Everything that needs to list, label, validate, or probe providers reads the registry rather than repeating a provider-name literal, and `ciao/provider_service.py` resolves the factory and owns the live instance. Adding a provider is a descriptor plus an adapter, and a short list of call sites that branch on `claude` and `opencode` only for their on-disk command or cache layout. Claude-only behaviour is a descriptor flag, not a branch. The checklist is [Adding a provider](ADDING_A_PROVIDER.md).

Dispatch is provider-driven, not model-driven. Each chat and schedule carries an explicit provider and model. The three supported runtime providers are `claude`, which runs Claude Code through `claude-agent-acp` (ACP) against Anthropic, `codex`, which runs `codex-acp` (ACP) with the user's own `codex` CLI, and `opencode`, which runs `opencode acp` (ACP, OpenCode 2.3.2+) with each child session nested under its `Subagent` node. OpenCode runs as `opencode acp` (ACP, OpenCode 2.3.2+) with each child session nested under its `Subagent` node; the chat's drain, idle reaper and permission and form routing are the ACP provider's (`ciao/providers/acp/provider.py`, `ciao/providers/acp/agents.py`). The HTTP driver that ran one `opencode serve` per chat was removed in slice D2.

Anything the Claude and Codex providers do not serve directly is reached through OpenCode, which is bring-your-own-provider: a user configures Ollama, OpenRouter, or any OpenAI-compatible endpoint in OpenCode itself, and Ciaobot lists whatever OpenCode reports as connected. Ciaobot previously reached those upstreams itself by injecting `ANTHROPIC_BASE_URL` into the Claude Code CLI; that layer is gone. The backend keeps provider routing explicit so schedules, handovers, and archived chats remain reproducible.

### ACP agents (A5 notes)

Known gaps:

- Stdio JSON-RPC lines are not capped. `_STDIO_LIMIT` only sizes the stream buffer: the SDK's reader catches `LimitOverrunError` and keeps appending, so a longer line is assembled in memory. The SDK offers no hook to refuse it, and no custom transport is built for this.
- Deleting a chat removes its opencode session from opencode's own store with `session/delete` when the agent advertises it (`OpencodeAcpProvider.delete_session`). The agent is started only when the chat's journal exists, and a cleanup that runs past its timeout leaves the session in opencode's store. The probe and one-shot sessions are removed with `session/delete` when the agent advertises it.

ACP agents (`ciao/providers/acp/`, #3137) keep their chat history in a session journal. Journal history reads the whole file on each read, as OpenCode's history does; the journal has no size bound yet. Accepted gaps, to follow up: the background-wake notice card is not rebuilt from the journal on reload, and file-card errors are not mirrored into the journal. The model catalog probe is bounded at 25 s and a timed-out probe returns an empty catalog without caching it. Codex's thinking levels (`minimal`, `low`, `medium`, `high`, `xhigh`) in `ciao/provider_registry.py` are an UNVERIFIED static default taken from the codex-acp 2.7.0 source: codex-acp reads the efforts from its runtime model catalog, so confirm the names against a live probe at the real-Mac/live checkpoint before relying on them.

Known parity gaps after C1 (for follow-up issues; none is fixed in C1):

- Ciaobot does not maintain provider quota snapshots or poll provider usage. It only uses the confirmed Claude and Codex ACP prompt-error shapes to schedule the failed turn; no other provider's data or prose supplies a reset time.
- Claude's native title is no longer read from the CLI's session file. C2a takes it from the protocol: the agent's `session_info_update` is applied as an adapter title. There is no SDK-era reader left: the Claude provider class and its `native_title_candidates` were deleted with the SDK driver.

### Chat titles from the agent

Claude's own session title reaches Ciaobot as an ACP `session_info_update`. `normalize.py` turns a non-blank title into a `SessionTitleEvent` (`ciao/models.py`), and `chat_streaming` hands it to `ProjectChatManager.apply_adapter_title`. That method reduces the agent's text to one printable line (`chat_service._clean_adapter_title`: first non-empty line, C-category characters dropped, the 60-character cap of `_clean_llm_title`), checks it with `_real_title`, and stores it with `ChatInfo.title_origin = "adapter"`. The title is untrusted text, so nothing else is stored or broadcast from it.

`title_origin` records who owns the title. `default` is the New Chat placeholder, `fallback` is Ciaobot's own deterministic or model title, `adapter` is the agent's title, and `user` is a rename in Ciaobot. An adapter title replaces only `default`, `fallback` and an earlier `adapter`, never a `user` title, and once one exists Ciaobot's fallback is not written. A rename made in the Claude CLI (`/rename`) arrives through the same update and is applied as an adapter title, unless the chat was renamed in Ciaobot.

### Claude harness overrides

Ciaobot runs the vendors' CLIs but trims the harness features the PWA already owns, or the workspace does not use. The catalog is `TRIM_OPTIONS` in `ciao/claude_trim.py`: each option is a built-in tool, a bundled skill, or a setting, with a default and a one-sentence reason. A workspace stores only the options that differ from their default, as a sparse `claude_trim` map in `.runtime/workspaces.json`, so a catalog change reaches every workspace that has not chosen otherwise. `trim_tool_denies` turns the effective map into tool denies and `Skill(name)` denies, and `claude_settings_layer` turns it into the CLI settings layer (`skillOverrides` plus `disable*` keys). A trimmed `setting:claude_ai_connectors` (group Connectors, default not trimmed, so connectors stay on) is not one of those keys: it sets `ENABLE_CLAUDEAI_MCP_SERVERS=false` on that workspace's Claude chats. A stored `claude_ai_connectors: false` whose trim map lacks that key is read once as trimmed; the next registry save drops the old field. Claude chats pass the deny list, that layer and the connectors env to `claude-agent-acp` as `_meta.claudeCode.options` (`disallowedTools`, `settings` as an object, and `env` only when connectors are off) on `session/new`, `session/load` and `session/resume`. A change to them reloads the same session, and a change during a background turn waits for that turn to finish. Routine triggers (`RemoteTrigger` and the `schedule` skill) are trimmed by default like every other option, because Ciaobot's own schedules replace them; a workspace can un-trim one in Settings, after which Claude can create claude.ai routines outside Ciaobot's schedules, bypassing the PWA's scheduling and notifications. The loop family (`CronCreate`, `CronDelete`, `CronList`, `ScheduleWakeup`, and the `loop` skill) is not in the catalog: `ALWAYS_DENIED_TOOLS` and `ALWAYS_DENIED_SKILLS` deny it in every Claude chat with no switch, and the adapter's `CLAUDE_CODE_DISABLE_CRON=1` (set in `CLAUDE.env`) stops durable cron jobs in a project's `.claude/scheduled_tasks.json` from firing. Workspace `disallowed_tools` adds extra denies on top of the trim defaults and never replaces them; `none` and `[]` mean no extras. Deny alone still lists a skill, so a trimmed skill gets both levers: `skillOverrides` hides it, and `Skill(name)` blocks execution if it is re-enabled downstream. The PWA edits the map through `PATCH /api/workspaces/<name>`. See [README — What we change from stock Claude Code](../README.md#what-we-change-from-stock-claude-code).

## Frontend

The installed PWA manifest offers app-icon shortcuts and an optional OS share
target. A multipart POST to `/share-target` is intercepted by the service
worker, which stages the text and files locally in IndexedDB; only an explicit
Home action adds them to a draft, and the engine never receives a share
automatically. Logout clears pending shares. The file viewer offers outbound
native Share where supported alongside Download. The worker caches only the
public same-origin app shell and static assets, never `/api/*` responses.

`web/` is a Vue 3 + Vite + Pinia + TypeScript PWA. The hierarchy is workspace → project → chat. Configured logical workspaces live in `CiaoConfig.workspaces` (loaded from `.runtime/workspaces.json`, the only source of the list, which Settings owns; a fresh install bootstraps it from the vault) and are exposed through `GET /api/workspaces`. Each workspace may set an optional `color` accent preset (`pink` default, plus `cyan` / `amber` / `emerald` / `violet` / `blue` / `teal` / `lime` / `fuchsia`); the PWA applies it as accents only when that workspace is active. The Pinia project store loads that endpoint; the sidebar workspace switcher and empty-state General chat buttons render from the configured workspace list. Backend project discovery, completion, restore, schedule routing and `CIAO_ACTIVE_WORKSPACE` also read from the workspace registry. The model picker has one section per provider: Anthropic (via Claude Code) and OpenCode.

The shell presents the same durable model everywhere: **request → run → output → durable knowledge**. Home uses the Workbench composition: `HomeIntake.vue` starts an ordinary project chat while keeping unsent text scoped to its workspace, and `HomeReviewSummary.vue` surfaces active-workspace tasks-in-review and automation state and labels checking, stale, empty, and failed snapshots, sitting in a side rail beside the request column on wide panes and stacking below it under 980px; chat keeps reasoning in the transcript while a conditional Context / Activity / Output inspector exposes existing run and file state. Project remains the context envelope; Memory's To decide section (suggestions and notes to revisit, one page with a filter) is the durable-knowledge inbox and its Map (Graph/List) is the exploration mode. These are frontend compositions over existing stores and APIs, not new persisted object types. Shared schedule and retirement load contracts keep a pending or failed fetch from rendering as a successful empty list.

**Notifications.** The bell popover is one frontend-derived view of what needs the user across the active workspace and installation-wide notices. Memory passes never contribute a row, blocked or not; their lifecycle stays on Home's memory-insight rows. It adds no persisted object, API, event log or localStorage list; the removed tray log, `notifications.jsonl` and `/api/menubar-notifications` stay removed, and Web Push and chat read sync are unchanged. Each source reports `checking`, `ready`, `stale` or `unavailable`: a stale source keeps its last rows marked *May be out of date*, and the inbox is never all clear unless every source is ready. The data comes from the owners' existing WebSocket invalidations, reconnect hydration and polls, plus a focus refresh throttled to five seconds; a late response from another workspace is rejected by a generation token.

Memory (`/memory/<section>`, `MemoryMapView.vue`) has four sections — Unsure, Map, Categories, Import — listed in the sidebar the way Settings lists its tabs; each is a route and bare `/memory` returns to the section last visited (the map on a first visit). There is no review queue: the agent writes memory directly, Git is the record and the undo, and what it is unsure of is a line in `Workspace/Unsure.md`. Unsure (`/memory/unsure`, `MemoryUnsurePanel.vue`) reads that file through `GET /api/workspace-file` and lists its unticked lines with a link to open the file; the file is the only state, so the page has no write path. The Map section renders the active workspace's vault as a browsable graph: notes as nodes, `related:` frontmatter and relative markdown links as edges, from `GET /api/vault/graph`. It follows the same shell pattern as Schedules/Settings — a route pointing at `ChatLayout.vue`, which switches `viewMode` and renders the pane — rather than introducing a second app shell. The node/edge data itself is exactly what `ciao vault-index`'s `scan_vault()`/`_build_graph()` already compute for `INDEX.md` and `--neighbors`; the route only serializes that to JSON and optionally scopes it to one `?workspace=`. Each node also carries its verification age (`updated:` frontmatter or mtime) judged by the same staleness detector the audit uses, and the review queue's `unverified` signal uses the same rule (`memory_audit.note_verification`), so the map's "unchecked" count, the list view's Checked column and the note tile's callout cannot disagree with each other or with what daily curation acts on. The tile names the age and the rule when a note is past its limit, and lists the facts inside it that nobody has re-checked (`entry_coverage`).

The map has two surfaces with parity of action. The graph canvas is driven by Pointer Events through `web/src/lib/graphGesture.ts` (unit-tested without a DOM): one pointer owns a gesture, tap slop separates a tap from a drag, `pointercancel`/`lostpointercapture` abandon it, and a second or non-primary pointer is refused — so a touch tap selects, a drag pans, and a cancelled or extra-finger gesture never activates an unintended note. `touch-action: none` is scoped to the canvas so page scroll and browser zoom stay available everywhere else. The list view is the keyboard/touch-complete alternative: each note title is a native named button, and closing the note restores focus to the control that opened it. A selected note opens in a docked tile — `PinnedFilePanel`, the same component a chat's pinned file uses, with the map's stale-note callout and linked notes in its `lead`/`after` slots — and at 900px and below that tile becomes a focus-contained bottom sheet. There is no path finder: selecting a note highlights its neighbours, which is the connection question the map answers.

Primary navigation uses native button/link semantics with visible keyboard focus, and mobile controls keep a 44px minimum target on every coarse-pointer layout. Browser zoom remains enabled; Settings font scaling is an additional preference rather than a replacement for platform accessibility controls. Tab bars are a shared `TabBar` component carrying the ARIA tablist contract — a single Tab stop with Left/Right/Home/End moving between tabs and selection following focus — so the behaviour cannot be dropped by copying the markup, which is how the memory-map review bar first shipped without it. Modal-like surfaces use `useModalFocus.ts` for initial focus, Tab containment, Escape capture before global shortcuts, inert background content, and opener restoration; native button semantics determine Enter, so a visible Cancel target can never confirm a destructive dialog. `composables/useModalOpen.ts` reports whether any `aria-modal="true"` element is in the document, so the toast stack can sit under an open dialog. Context menus use menu/menuitem roles, focus their first action, support Arrow/Home/End/Escape, and return focus to the trigger. In ChatLayout, unmodified number keys `1`–`9` switch to the corresponding workspace in the sidebar's displayed order (a user-set, persisted order; when no workspace is named `personal` the main workspace stays first); the shortcut is ignored while typing and the workspace buttons show their assigned key. On the home screen, Needs You, Working, Unread, and Earlier are the authoritative lane order; arrow navigation follows the rendered lane layout: stacked workspace lanes use up/down between lanes and left/right within a lane, while side-by-side lanes use the corresponding horizontal/vertical mapping. The sidebar independently discloses each chat's running subagents inside an expanded project, while opening a subagent's read-only view reopens its parent group. Automation details preserve their title on narrow screens by moving secondary actions into an overflow menu, collapse long prompt previews, and explain stale project/chat targets without exposing raw runtime IDs.

Each workspace has a "General" project plus auto-discovered projects from its configured `vault_root/projects/active/`. Reorderable projects (not General or an auto-managed project, which stay pinned first) are saved per workspace through `POST /api/projects/reorder`: the body's `expected_order` must match the order the client last saw, else 409 `project_order_conflict` writes nothing, and the sidebar restores its order and says so. Chats stream over WebSocket; image uploads and pending comments are scoped to the active chat, then attached to that chat's next prompt. Closing an unused new chat deletes its server-side draft; closing a completed chat disconnects it. A non-image file dropped into a chat is uploaded through the chat attachment contract and inserts a bounded opaque reference; the provider-only prompt expansion resolves the server-side path. Pinned files belong to a chat (server-owned) and render in a split layout beside that chat. Commenting in that sidebar stays open while a turn streams — the comment simply rides on the next message — and the panel's auto-reload at turn end is deferred while a text edit or comment draft is open, then applied once the user saves or cancels.

**One engine, one origin, one browser.** Multi-device node mode is gone. There
is no host/client role, no standby proxy, no second loopback origin, and no
local-control capability: a browser either talks to the engine it reached over
one origin, or it does not. `/api/*` needs the signed session cookie (with the
same small public allowlist as before), every `/ws/*` handshake is checked for
same-origin and then for the session, and every state-changing `/api/*` request
must present a matching `Origin`/`Referer` — the general guards, unchanged.
`/api/desktop-drop` is a normal session-protected route again rather than a
local-control one, and Finder drop events still carry only an opaque grant and
bounded display names; absolute paths stay in the server-side grant. A second
device installs its own engine and opens `/api/addresses` to find this one.

There are no native commands left to grant: the macOS shell is retired (`#656`),
so a page served from the engine origin has no capability surface at all. This is the
direct browser/engine trust model that replaced the retired client-origin
model: `docs/REMOTE_BOUNDARY.md` records what it is. Ciaobot applies no file or credential policy to agents: each CLI's own permission mode and settings decide. Ciaobot passes the linked repository to Claude as an add-dir and to OpenCode as `skills.paths` in `OPENCODE_CONFIG_CONTENT` when the chat is in code mode, that is when the repository folder exists and the chat is not a memory pass. The path is fixed when the provider process starts; a change applies from the next turn. A CLI that cannot read runtime state exits 77 with `RuntimeStateUnreadable` rather than guessing a layout. The same `OPENCODE_CONFIG_CONTENT` caps OpenCode tool output
(the removed HTTP driver capped `tool_output` at 1000 lines / 20,000 bytes, `TOOL_OUTPUT_MAX_*`; the ACP path applies no such cap) below OpenCode's 2000-line / 51,200-byte default. The file viewer is not covered. Credential and storage-isolation work tracked by #546 is still open.

The completed-reply mention probe (`POST /api/chats/{chat_id}/file-paths/resolve`, #2118) is the one automatic file discovery, and it is confined. It searches only the chat's project's registered workspace: before the re-rooting that is the workspace's vault, never the shared install root, and after it the workspace's agent root and nested vault. A code-mode repo is added only when the chat is not a memory pass, and only the recorded worktree when one is recorded. Every batch snapshots the membership, roots, layout and repo identity before and after the lookup, and returns rows only when the two match, so a change during the lookup nulls the results. The probe keeps no server cache, reads no file content, and runs no subprocess per candidate. Its byte and count caps bound the work, not the latency of a stalled host filesystem. The existing viewer policy, which serves allowlisted absolute host paths, is intentional and unchanged by this probe. Legacy install-relative spellings are deliberately unsupported, not silently repaired.

The client side of that probe is `web/src/composables/useFileMentions.ts`, and only the final reply bubble in `ChatPanel` uses it. A generation is one chat layout plus one completed-turn revision. A context change clears confirmed links at once; a finished turn, `invalidate()` or disposal starts a generation that keeps the links until its answer arrives. Nothing is extracted or dispatched while streaming. The caps are 100 examined message revisions, 262,144 content characters, 200 candidates and 20 requests per generation, sent in batches of 50 items and 32 KiB. At most one request is in flight, and a stale completion writes no state. Extraction and rendering do no I/O: the assistant bubble has its own render cache, keyed by the identity of the confirmed-target map, separate from the trace and user caches. Legacy install-relative spellings deliberately stay unlinked; only vault-relative or in-vault absolute spellings link.

Write/Edit/MultiEdit/NotebookEdit tool calls are tagged with `file_touch` by
`ciao/web/chat_broker.py` and surface as standalone `_filecard` entries on
reload, rendered as inline clickable preview cards that open `FileViewerModal`
(see `PWA_API.md` → "File-touch cards" for the WS + `/messages` contract). On
every file-touch event the broker also schedules a debounced content snapshot
via `ProjectChatManager.snapshots` (`ciao/web/file_snapshots.py`,
`SnapshotStore`), which writes append-only per-(chat, file) copies under
`.runtime/snapshots/<chat_id>/<urlencoded_path>/NNNN.snap` plus a sibling
`meta.json`. The PWA reads these back via `/api/file-history`,
`/api/file-content`, and `/api/file-restore` to power the FileViewerModal's
Preview / History / Diff tabs and one-click restore; `/api/vault/backlinks`
lists the notes linking to a markdown note, using the same relative/path/stem
link resolution as the preview, but the modal has no Backlinks tab that calls
it. Preview renders text/markdown, images, PDF/PPTX (via a binary preview), and
HTML artifacts; diagrams live inside HTML artifacts as inline SVG. History/Diff
remain text-snapshot based. An in-modal Edit mode posts user-edited text content

Archived chats are read-only but can be continued into a new active chat via the "Continue in new chat" button (calling `POST /api/chats/{chat_id}/continue`). A header "files touched" chip in `ChatPanel.vue` summarizes the dedupped set of files written/edited in the chat and links each entry back to the modal.

Background subagents (Agent tool dispatches with `run_in_background`) keep running after the parent turn ends. Background shells are tracked, and a finished one gives the chat one wake turn (`ciao/shell_wake.py`, origin `background_run`). What the wire carries, checked against live captures (`tests/fixtures/acp/shell_*_wire_background.jsonl`, `tests/test_shell_wire_integration.py`): **OpenCode** sends `rawOutput.metadata.pid` and `metadata.shellID` on the launch acknowledgement, so the shell is polled by pid; it sends no end signal (the end is the pid leaving the process table, so no exit code), and no structured output path (the path is only in the acknowledgement text, which is never read), so its notice has no output tail. **Claude** sends no pid (the shell is tracked by call id, never polled), its launch metadata carries `claudeCode.toolResponse.backgroundTaskId`, the output path only inside `terminal_output_delta` text (never read), and it ends the shell with `terminal_exit`, whose `exit_code` was null in the capture, so its notice says the exit status is unknown and has no tail. **The provider also continues on its own.** Captured frames (`shell_opencode_native_continuation.jsonl`, and the Claude capture): when a background shell ends and no prompt intervenes, the agent resumes the session itself, about 6 s later (OpenCode) or about 1 s later (Claude), with its own reply and no `session/prompt`. This is declared per provider by `AgentSpec.continues_after_shell` (OpenCode and Claude set it). Each finished shell's notice is held for its own 20 s window (`SHELL_FINISHED_WINDOW_S`). When a continuation starts speaking on that chat, the session asks its host hook (`AcpSession.continuation_hook`, set per chat to `ProjectChatManager._continuation_started`) for the notices of the shells that ended before it started. The notice is journaled as a `user` record with `turn_origin: background_run` ahead of the reply, so a reload renders the card before the reply (`_render_acp_journal`, a system row with that origin); the live stream sends the same card as a `user_echo` (from a `WakeNoticeEvent`) before the reply; and the recorded turn takes the notice as its prompt. Ciaobot sends no wake of its own for a claimed shell, and a claimed turn is not one of Ciaobot's wakes, so it does not count toward the wake limit. A provider's own notification text is never replaced: when the continuation's turn cannot carry the notice, the claimed shells are announced with Ciaobot's wake instead. A continuation that started within 15 s before a shell's end (the end is observed a little after the process ends) answers that shell, and no wake is sent for it. A held notice is not lost on shutdown: `begin_shutdown` delivers it, and a turn started there is one restart resume continues. A crash that kills the process before the window closes loses the notice, since held notices are in memory. Stated plainly: the claim cannot tell a continuation caused by a shell from an unrelated text reply that starts inside the window, so such a reply claims the notice too. A subagent completion with no reply text does not claim. The transcript renderer ends a reply's text run at each `result` record, so a continuation's text never runs on into the previous reply. A shell that the provider never settles is never announced.

Subagents a chat spawns (`Agent`/`Task` dispatches) show as their dispatch tool row, with the subagent's own tool calls nested under it in the live trace; there is no subagent route.

Settings tabs (sidebar labels), in two groups. At turn end, for a chat in code mode only, `ChatStreaming.drive` collects absolute directory hints from each tool call (`file_touches` parents and `ToolUseEvent.work_dirs` from `cd`, `git -C` and `workdir`/`cwd`) and awaits `refresh_repo_location`, which stores `ChatInfo.repo_location` (`{}` or `{path, branch, is_worktree, exists}`) and re-broadcasts `project_updated` with fresh repo state. Keyboard shortcut preferences are stored in `.runtime/app_settings.json` and shared through the authenticated `/api/settings/keyboard` endpoint plus `/ws/events` snapshots and change events. Appearance preferences (text contrast, body font, theme, font scale and custom colours) live in the same `.runtime/app_settings.json`, are shared through `/api/settings/appearance` and ride `/ws/events` as the snapshot's `appearance` and `appearance_settings_changed`. or reloading the PWA restores each chat's draft on that device; dispatching the
message clears only that chat's cached draft.

## Workspace git sync

Every instance is identical (no primary/secondary, no cloud). Sync and the memory backup operate on the repo containing the vault root (`ciao/local_session.py::sync_root`): with the default layout (vault inside the workspace) that resolves to the workspace repo; a vault that lives elsewhere in its own repo is synced there instead, and a missing/non-git vault falls back to the workspace root. Ciaobot never creates or switches local branches: it works on whatever branch that checkout is currently on (`ciao/local_session.py::workspace_branch`). Roots that are not git repositories or have no `origin` remote report `not_configured` and are re-checked every tick, so adding a remote while the engine runs is enough (a fresh `ciao setup` initializes local repos, but they have no remote until the user adds one).

**Sync flow** (`ciao/local_session.py`, `LocalSessionManager`). When the user clicks "Sync with Remote" in Settings, `POST /api/local/handback` commits pending work, pulls from origin (merge-based), and pushes the current branch. Workspace sync never requests app deploy; app updates happen through package upgrades. A **conflicting pull** is left in the tree and `POST /api/handover/merge` opens an **interactive chat** in the personal `General` project: the chat's agent resolves the conflicts, asking the user via `AskUserQuestion` (push-notified) when ambiguous, then pushes the branch (it does not redeploy). After that chat lands, `POST /api/local/resync` merges `origin/<branch>` into the checkout after committing any pending work (fast-forwarding in the normal case). It merges rather than force-resetting, so it works on the live workspace's dirty tree and never discards local commits. See `PWA_API.md` → "Workspace git sync".

**One mutation at a time** (`ciao/git_mutation.py`, #674). Every public git mutation — `commit_pending`, `push_branch`, `push_backup_ref`, `sync_branch`, `resync_branch`, the manager methods driving them, and the admin snapshot route — runs inside `repository_mutation`, a task-reentrant lock keyed by the repository's canonical top level. Manual sync, the conflict resync, the five-minute memory backup and admin snapshots therefore never interleave git commands in one checkout (and a workspace root, a vault root in its own repo, and any subdirectory of either share one lock), while two unrelated repositories stay concurrent. Branch detection in `LocalSessionManager` runs inside that lock, so a sync cannot commit to a branch it has already stopped being on. Holding the lock means holding it until git has actually exited: a cancelled writer waits out its in-flight step, because `asyncio.to_thread` cannot stop a running thread and releasing on cancellation would hand the checkout to the next writer while the abandoned process is still writing the same index (the admin snapshot route does this in `_snapshot_git`). Two rules come with it: a failed git step is never reported as success (`commit_pending` raises `GitOperationError(step, detail)`; sync/resync/push convert it into the failure result they already return, and the admin snapshot route returns an error for failed status or commit without pushing after a failed commit), and a git operation Ciaobot did not start is respected rather than removed — a preexisting `.git/index.lock` or an in-progress merge/rebase makes the mutation report a failure, and the file is left for its owner. A merge Ciaobot *did* start is exempt: the check happens at the outer entry, before the body runs.

**Memory backup** (`ciao/backup_service.py`, #689). Every five minutes the engine commits the durable-data scope of the same repository the sync flow targets and pushes what is not on the remote yet. It replaces a push-only 30s loop that decided once at startup whether there was a repository and an `origin` (so an install configured later never backed up anything until a restart) and that pushed whatever branch it found without committing anything (so on a plain data repository the notes were never in a commit at all). What changed, in the terms the status reports: readiness is re-evaluated every tick, so `not_configured` becomes `ready` without a restart; the commit is `commit_scoped` over `backup_scope`, so an unattended run can only ever commit `memory-vault/`, `skills/`, `subagents/`, `commands/`, the `AGENTS.md` guide and archived workspaces — never a credential, a cache, the transcript archive or application source; a run with nothing pending and nothing unpushed creates nothing at all, while unpushed existing commits are still uploaded; and a failed push keeps the local commit exactly where it is (no reset, no force-push, no discarded work) and reports `offline` or `needs_attention` instead of claiming a backup that did not happen. The interval is the named constant `BACKUP_INTERVAL_S = 300` — not an env var and not a setting — with a bounded backoff (×12, an hour) for a failure that cannot self-heal at that cadence, an overdue-resume on the first tick, and a `paused` gate that reads the durable `enabled`/`paused` flags on every tick so a pause survives a restart and a resume takes effect on the next one. A Mac that is not the host (the `legacy_node_state` verdict, the same one the scheduler asks) never runs it, and says so in its status. A coverage gap is reported on its own field rather than through a state: `BackupStatus.coverage_gap` counts the tracked paths the scope refuses, the run's `extra` carries it so the Automation row can show a partly covered repository without a red error, and a landed run through a gap is `ready` — a permanent property of a repository that is also a checkout is not a fault of a run, and `needs_attention` stays reserved for the three failures only the owner can fix (#733). `GET`/`PATCH /api/local/backup` and `POST /api/local/backup/run` expose the status, the owner's switch and a manual run; the manual run is the same serialized call the loop makes, so the two cannot overlap. An install with no remote is reached through one canonical setup prompt rather than through Git instructions: `GET /api/local/backup/setup-prompt` returns it with the trusted context it was rendered from, and `POST /api/local/backup/setup-chat` sends that same text into a chat in the host workspace — sending, not drafting, and idempotent, because a repeated click or a retry re-enters the live setup chat (found by its stable title) instead of putting a second agent on the same repository. Readiness stays where it already was: re-derived from the repository on every tick and every status read, so an external agent's setup is detected with no restart, and a guided setup that verifies turns the backup on unless the owner has paused it. No new state store, no new loop, no new env var. See `PWA_API.md` → "Unattended memory backup".

## Package updates and setup

**App updates.** Workspace git handback never implies a deploy. `GET /api/package/status` reports `ciao.__version__` and a best-effort latest version from GitHub. A production macOS install is the engine alone, and an installer-managed engine no longer updates itself: macOS updates it through Ciaobot for Mac (Sparkle), Linux through `docs/LINUX.md`; see `docs/DEVELOPMENT.md` → "End-user distribution". `POST /api/package/update` is retained as a diagnostic response that points users to that update path; it does not invoke Homebrew, PyPI, or `pip`. Editable git checkouts still use `git pull`.

**Setup readiness.** When `PWA_AUTH_TOKEN` is absent, Ciaobot starts in bootstrap mode using `~/.ciao/bootstrap` (or `CIAO_BOOTSTRAP_WORKSPACE`) and persists a generated temporary auth token under that workspace's `.runtime/`. `GET /api/setup-status` is public like startup status, because the first-run wizard needs it before a normal session exists. It reports workspace/vault/token/push-contact checks plus Claude Code and OpenCode readiness probes, without returning secret values. The local first-launch URL `/?setup=<token>` redeems `.runtime/setup-token` on localhost only, sets the signed PWA session cookie, deletes the one-time token, and redirects to `/`. The wizard finishes with `POST /api/setup/finish`, which is bootstrap-only and localhost-only: `workspace` is required (the wizard's primary folder question), `password` is required (the wizard asks for it in the main flow because protection is always on; the inherited bootstrap token is machine-generated and unusable from a second device), the chosen provider is persisted on the first logical workspace, and `vault_root` is optional, defaulting to `<workspace>/memory-vault`. It writes the real workspace `.env`, scaffolds the configured vault root and provider asset catalogs, ensures workspace and vault are (in) git repositories with their protective `.gitignore`s (see "Workspace layout"), creates the server LaunchAgent, then requests the normal restart exit so launchd can relaunch into the real workspace. There is no native shell: the engine runs under launchd and the PWA at localhost is the whole surface. The retired rumps tray and the generated `Ciaobot Server.app` launcher it lived in are gone, and the macOS app itself is retired (`#579`); setup removes both, plus the `com.ciao.menubar` LaunchAgent, from installs upgrading from an older version. A foreground `ciao run` supervises the restart exit itself: when the server exits with the restart code, the CLI re-execs a fresh `ciao run` (picking up newly installed code) instead of dying.

Provisioning completion (`.runtime/setup-completed-at`) is only a setup/catch-up marker, and `.runtime/welcome-pending` only controls the one-time generated-password card. Neither represents onboarding completion. The owner-private `.runtime/onboarding.json` receipt tracks resumable lifecycle state independently: supported fresh setup creates `in_progress`, receipt-less established installs are `legacy_exempt`, and existing receipts always win. Startup initializes it under the instance lock before importing legacy workspaces. Existing notes or incidental `.env` files are not install evidence; bootstrap auth/lock files are not legacy evidence. Malformed receipts fail closed rather than being reset.

## Project naming convention

Every configured workspace uses the same shape: a project is a folder under `<workspace.vault_root>/projects/active/<name>/` with a same-named main doc `<name>/<name>.md` (or `README.md`). On completion it moves to `<workspace.vault_root>/projects/completed/<name>/` via the PWA's "Complete" button (or `complete_project()`). Completion and restore both move the folder through `project_folder_move.move_project_folder`, which repoints references to and from the moved notes before the move and puts them back if the move fails.

Completed projects can be restored. The sidebar footer has an archive icon next to "+ New Project" that opens a modal listing the current workspace's completed projects (`ProjectChatManager.list_completed_projects()` scans the `projects/completed/` tree read-only). Each entry has a Restore button: `restore_project(workspace, stem)` moves the folder back to `projects/active/`, flips frontmatter `status: completed` back to `active`, and re-runs auto-discovery to recreate the PWA project. Auto-discovery derives a stable id from the workspace and folder slug; the original chats stay archived. Routes: `GET /api/projects/completed` (optional `?workspace=`) and `POST /api/projects/completed/restore` (see `PWA_API.md`).

The whole-install re-root migration (`ciao/workspace_reroot.py`) also updates explicit install-relative paths in user schedule prompts from its actual move map, including promoted global directories. It validates the raw schedule store before writing and records each changed prompt's before/after text in the migration receipt. Undo checks that each recorded schedule still exists exactly once with the migrated prompt before any filesystem mutation, then restores only those prompt fields while keeping runtime metadata and unrelated schedules.

Undo journals filesystem operations in the runtime migration directory. Captures live under `ciao-undo/<uuid>/` in the absolute per-worktree Git directory. Undo requires the capture and worktree paths to share a filesystem with exclusive rename, hard links, and directory sync. Capture temporarily vacates the live name. Publication and compensation fail if another writer occupies that name. Recovery reconciles journaled moves before returning captured artifacts to their original paths. On completion, `capture_inventory` names the permanent inventory. A process holding an open descriptor can still write to a captured inode. Operators review and remove captures manually after those writers have closed their descriptors. Undo and recovery acquire the per-worktree Git index lock, compare the staged entries, and publish a verified index while holding the lock. A competing staged change stops the update. Undo and recovery refuse affected entries with index flags, including intent-to-add, assume-unchanged and skip-worktree, before changing the worktree. Publication verifies that unrelated flags survive. An unrecognized Git index diagnostic format stops undo for inspection. A process killed while holding the lock can leave a stale Git lock requiring operator inspection before retry. Parent directory topology must remain stable during undo. For receipts that predate created-file fingerprints, undo retains each extant listed file or symlink and reports its original path and capture location in `unverified_created_files`. The inventory records its identity and fingerprint at undo time. Unexpected entry types block undo for inspection. Interrupted journals from an older format may require manual recovery.

Workspaces are archived the same way rather than deleted (`ciao/workspace_archive.py`). Settings → Overview → All workspaces → Archive removes the workspace from the registry — so the sidebar, pickers, per-workspace system routines (Workspace care), skill sync, vault scans, the Memory Map and the Unsure list all stop seeing it, since each enumerates the registry — and moves its folder intact to `<install>/.archived-workspaces/<name>-<YYYYMMDD-HHMMSS>/`. Before the move, its projects are removed through the same `_remove_project` path `complete_project` uses (open chats are transcript-archived, then removed), and its user schedules (matched by `workspace`, target project or target chat) are taken out of `.runtime/schedules.json` into the archive's `archive.json`. After it, its rows leave the search index and, on a shared-vault install, `INDEX.md` is rebuilt so it stops listing its notes. Nothing is merged into another workspace. A workspace with a running chat is refused, as are the primary and the last workspace. The Archived workspaces list under the workspace cards restores one: the folder moves back, the registry entry and schedules return, and discovery recreates its projects; old chats stay archived.

- **Folder name** is the slug used internally (`vault_folder`). Lowercase + kebab-case is preferred but not enforced; spaces, mixed case, and underscores all work. Avoid path separators and leading dots.
- **PWA display name** comes from frontmatter `name:` (or `title:` if `name:` is absent), so it can be any human-friendly string with spaces (e.g. `name: AI Championship Project`). If both are missing, the folder name is used as the label.
- **Project context** — the blurb injected into every user turn as `[Project context: ...]` — is frontmatter `description:`, and the doc is its source of truth. The two are kept in sync both ways: `update_project()` writes an edit made in the PWA back into `description:` (`_set_frontmatter_description` rewrites that key surgically, leaving the rest of the file byte-for-byte), and every auto-discovery pass re-reads the doc so an edit made by hand — or by the agent writing the doc directly — reaches the preamble. Discovery reads are memoised on the doc's `(mtime, size)` because it runs on every `list_projects()` call. An empty `description:` never clears a context the registry already holds; the next save pushes it into the file. The one exception to doc-wins is the first bind, when a manually-created project adopts a matching vault folder: a context typed in the PWA before the folder existed survives and is written into the doc instead, since the README it is adopting was most likely scaffolded. Only the *path* of the doc is injected alongside it (`[Canonical doc: ...]`), so the body stays out of the per-turn token cost and the agent opens it on demand.
- Top-level reference docs that live directly under `projects/` never "complete"; don't put real projects there.
- A stray `projects/active/<Name>.md` at the top level gets auto-promoted to `<Name>/<Name>.md` on the next server start, so the folder+file invariant always holds.
- Every workspace has an auto-created `General` project bound to `projects/active/general/`. It is marked `is_auto` and displays the "auto" chip in the sidebar. It's where ad-hoc chats land and where scheduled automations run; don't delete it.
