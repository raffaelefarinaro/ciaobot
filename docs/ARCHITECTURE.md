# Ciaobot Architecture

Orientation doc for the codebase. Read this before making any change in `ciao/`, `web/`, `scripts/`, or `deploy/`. After a change that affects layout, capabilities, env vars, endpoints, or commands, update this file, `docs/DEVELOPMENT.md`, and `INTEGRATIONS.md` so they match the repo.

## A meta-harness for personal AI assistance

Ciaobot is a **meta-harness**: a persistent personal workspace around existing agent harnesses, not a replacement model/tool execution loop. The layers are:

1. **Ciaobot — context and continuity.** Workspace and project context, chats and transcripts, files and feedback, automations, memory extraction and review, and scope-enforcing application operations.
2. **Agent harnesses — execution.** Claude Code through the Claude Agent SDK, and OpenCode through its V2 server, handle model interaction and tool execution using the user's configured provider access. Ciaobot starts and supervises these sessions through provider adapters.
3. **Models and tools.** The configured cloud or local models, filesystem access, and integrations reached through each harness.

The product is organised around one person's work and knowledge, not an autonomous company's org chart. Its continuity loop is **request → run → output → durable knowledge**: project context accompanies work, archived conversations can produce scoped Markdown facts, and uncertain facts wait for review.

Provider-neutral application context and durable Markdown knowledge do not imply provider-session portability or identical tools, permissions, and capabilities. Switching harnesses preserves the personal workspace, not every detail of the execution environment. Application-operation guards are not a sandbox for arbitrary agent filesystem or credential access.

For task-oriented reading paths, start with the [documentation hub](README.md).

Three surfaces answer "what did an upgrade leave here?": the Home strip (`operator_actions.detect_actions`, polled every 60s and on focus), the `upgrade_notices` section of `os_audit` (a diagnostic, never red), and since #833 the "After this update" catalog, whose card is an offer the operator may dismiss where the report is not theirs to silence. They used to hold separate copies of two conditions, and the copies drifted: the vault-location predicate existed twice, and the audit's remedy taught a hand migration (move the folder, hand-edit the registry) that the engine refuses and that `docs/VAULT_MIGRATION_PROMPT.md` no longer teaches; the wikilink notice had two *applicability* rules, Home asking for an adopted vault and the audit asking only for a receipt, so the two surfaces answered different questions about the same vault. Here each probe owns its condition, its applicability and every sentence about it, and every surface references them. `vault_location_findings` is two registry-resolved paths and one `is_dir()` — no scan — and its remedy is the managed `ciao vault-relocate` sentence with its undo, its restart, and the shapes `--apply` refuses (symlink, non-empty destination, a vault root that IS the install root, a shared root claimed twice, a nested destination, uncommitted changes, a vault outside the install's git worktree), stating a manual route only for the two refusals that really carry one and leaving the rest to the preview, which is `vault_relocate.plan`'s authority and not this notice's to pre-empt. The wikilink notice applies when no **completed** link-migration receipt exists (`read_receipt` gates on `status == "migrated"`, so a half-finished run does not silence it) **and** a walk actually found a wikilink; there is no `vault_mode` gate, because a scratch vault is the one an operator can hand a wikilink and the audit losing that is not a parity win. Who may establish the second half is the whole of the cost difference, and it is named functions rather than a flag: `resolve_links` walks (the audit, which is already a full-install pass, and the off-loop refresh) and publishes what it found; `cached_links` only reads that (Home — the strip may not walk, on open, on focus or on the poll); `start_links_scan` puts the walk on `async_reads.run_read` — coalesced, admission-capped, never on the event loop — starts it DETACHED from `GET /api/housekeeping` exactly as `_cached_update_hint` starts the release lookup, keeps one in flight at a time, observes the task's outcome rather than leaving it for the garbage collector, and is torn down by `shutdown_links_scan`, which `ciao/main.py` registers ahead of the read-executor close. A cold engine therefore shows no card until the next poll picks the verdict up. The third notice, `unrehomed_people`, has no walk at all: `rehomed_people_finding` is a registry read plus a completed-receipt read through `completed_rehome` (which is `vault_rehome.read_receipt`, so a `partial` run keeps the finding and a receipt predating the `status` field clears it), gated on more than one registered workspace because a single workspace has no counterpart for a person note to be misfiled FROM — an unactionable offer is how a fresh install learns to ignore the strip. That answer stays **broad and advisory on purpose**, because it is a diagnostic: it cannot know anything is misfiled, which is why the wording says *may* be. Since #833 it also backs an install-scoped update task, the first notice whose Home surface is a *dismissible card* rather than a tile — and the card deliberately asks a **different, harder** question. `rehome_legacy_candidates` runs `vault_rehome.plan_rehome` on the shared vault (the same plan the operator's preview prints) and offers only a `mechanical` candidate, because a receipt check is satisfied for free by every fresh install that never needed the migration: #833's review caught exactly that false positive. Four gates run before the walk and each one *proves* a mechanical candidate is unreachable — a completed receipt (the remedy refuses a second pass, so the card would be unactionable), one workspace, no shared vault directory (per-root has no workspace segment, so `vault-rehome` cannot act there at all and the task must not exist), and no bound tag role at all (`detect_misfiled_people` needs a tag naming a role that is bound; ONE bound role is enough, and a gate asking for two was a false negative on `[work, clientA]` — found by R2 review — because a note filed under a workspace that plays no role has no `own_role` to disagree with). The asymmetry is pinned both ways — task offered ⇒ audit reports, audit silent ⇒ task not offered — and nothing in this module reads an update-task record, so dismissing the card silences the card and never the report. `tests/test_unrehomed_people_update_task.py` pins the fresh-install silence, the mechanical candidate, the per-root silence without a walk, every receipt shape against completion, a hand-written `completed` record with no receipt on disk, and that the one walk runs off the loop through `run_read` once per window. A published answer is one of three states — `LINKS_FOUND`, `LINKS_CLEAN`, `LINKS_FAILED` — and only `found` is ever a finding: a walk that could not finish is an unknown, cached as such so a broken vault is not re-walked and re-logged every 60s, and never as `clean`, which would be the notice quietly lying. `LINKS_SCAN_TTL_S` (300, the same window `update_tasks.APPLICABILITY_TTL_S` gives its detectors, and deliberately one clock rather than one per surface) bounds reuse; the answer is keyed on the receipt file's own mtime and size, so a migration, an un-migration or a retry of a partial one all invalidate it, and on the runtime root and vault path, so two installs in one process cannot share one. Because a finding exists only once a walk found a note, the card names it instead of hedging on a receipt's absence, and a clean vault reaches zero for a reason other than "a migration ran" — and no Home-side suppression is an input to any of these, so a card #833 made a dismissible catalog task still cannot silence the audit. `tests/test_migration_notices.py` pins the parity, the scratch-vault diagnostic, the audit resolving its own verdict rather than reading the cache, the three scan states and the window that keeps a failure from being retried per poll, the task's start/observe/cancel lifecycle, the absence of any catalog row for the wikilink notice (still no honest completion receipt — its receipt is per install, not per vault, so a per-workspace loop over the remedy is not available either), and the Home bound — counted filesystem accesses under the vault at 1 note and at 400, never a timing assertion.
  provider_registry.py         Single enumeration of the two supported runtime providers, Claude and OpenCode (id, labels, capabilities, auth/status hooks).
  provider_service.py          Provider request builder and execution wrapper.
  control_plane.py             Provider-neutral, scope-enforcing application operations shared by MCP and PWA-owned managers. The rare-admin group (workspace/project/Google-Workspace/context operations: `workspaces_list`, `projects_list`, `project_get`, `project`, `project_action`, `gws_status`, `context_get`) is now CLI-only and surfaced to the agent as `ciao workspace list`, `ciao project …`, `ciao gws status`, and `ciao context get`.
  async_reads.py               Bounded off-loop execution for synchronous vault reads. `run_read(key, operation)` runs a read on a dedicated small `ThreadPoolExecutor` (default 4 workers) instead of the shared default one, and coalesces identical in-flight reads by key so N concurrent `vault_search` calls for the same workspace/query share one scan. Admission is also capped (`MAX_VAULT_READ_BACKLOG`, default 12): `ThreadPoolExecutor`'s queue is unbounded and a cancelled caller deliberately leaves its read running, so a burst of distinct keys or disconnected callers would otherwise pile up full-vault scans; over the cap a caller waits for a slot without blocking the loop, and same-key callers never consume a slot. The server registers `shutdown_vault_read_executor()` as a shutdown callback, so a restart discards the queued backlog (`cancel_futures=True`) instead of joining it. The worker owns its SQLite connection end to end (opened and closed there), so no connection crosses threads. `asyncio.to_thread` cannot be cancelled, so a cancelled awaiter only detaches: the worker runs to completion, stays joinable by a later caller under the same key, and its exception is always observed (`_observe_failure`) so a detached failure is never silent. Each caller awaits its own bridge future fed by a done-callback, never the shared future, so cancelling one waiter cannot cancel the work other same-key waiters depend on. `keyed_lock(key)` is a process-wide lock used to serialize the write phase of concurrent index passes against one SQLite database file (SQLite takes one file-level write lock), while the read-only search phase stays concurrent; the archive postprocess takes the same lock when it indexes a newly archived file. `reset_vault_read_executor()` is the test isolation hook.
  workspaces.py                Shared logical-workspace registry rules (validation, serialization, persistence) used by the PWA routes and the control-plane workspace tools.
  mcp_server.py                Agent control-plane core: the shared operation table (`OPERATIONS`, one entry per operation with name, `_READ`/`_WRITE`/`_DESTRUCTIVE` annotations, docstring, and the `(service, **kwargs)` function), the `AgentSessionRegistry` bearer-token verifier, the `_invoke` envelope/plan-mode gate/telemetry, and project `.mcp.json` discovery (env-key status + observed/probed tools for Settings). The MCP adapter was removed in S6; the agent dispatcher (`ciao/agent_surface.py`) resolves the same table, so argument validation is shared by construction. There is no argv auto-approval: every `ciao …` shell command keeps a card in `auto` mode (an argv allow prefix is a shell-suffix bypass risk), and users switch to `bypass` for no cards.
  signals.py                   Restart / deploy signals.
  instance_lock.py             Process-lifetime lock for one backend per runtime directory (`.runtime/server.lock`).
  agent_paths.py               Where the provider CLIs keep per-workspace state (D-03/D-04, #696), checked against recorded observations in `tests/fixtures/agent_discovery/`. `claude_project_slug(path)`: Claude Code's `~/.claude/projects/<slug>` name — every character that is not an ASCII letter or digit becomes `-`, on every OS (`/Users/me/ciao` → `-Users-me-ciao`, `C:\dev\ciaobot` → `C--dev-ciaobot`).
  supervise.py                 `ciao supervise`: the cross-platform supervisor. Runs `ciao run --supervised` as a child (spawned with `tree_spawn_options(dies_with_engine=True)`, so a service manager's group kill still reaches it) and owns the relaunch loop — exit code 75 relaunches, any other code is returned, SIGTERM/SIGINT/SIGBREAK forward `ProcessTree.terminate()` and then `kill()` after `STOP_GRACE_S`. A crash loop of more than `CRASH_LOOP_MAX_RESTARTS` *consecutive* restarts waits `BACKOFF_INITIAL_S`, doubling, capped at `BACKOFF_MAX_S`; a child that ran longer than `CRASH_LOOP_WINDOW_S` did real work first, so its restart starts the count over. CLI: `ciao supervise [-- <ciao run args>]`.
  os_support/                  The one home for POSIX/Windows differences that are not provider-specific (#696); call sites import from here and never branch on `sys.platform`. `locks.py`: `lock_exclusive(fd, *, blocking)` / `unlock(fd)` with `flock` semantics — `fcntl.flock` on POSIX, `LockFileEx` on one byte at offset 2**63-2 on Windows (the lock file stays readable, a second handle conflicts, contention raises `BlockingIOError`). `users.py`: `user_key()` tells local accounts apart in shared per-user paths — the uid on POSIX, the account SID string on Windows. `files.py`: `open_fd(path, flags, mode, *, follow_symlinks=True)` is `os.open` with POSIX semantics — `O_NOFOLLOW` on POSIX; on Windows every descriptor is `O_BINARY` (a text-mode descriptor rewrites `\n` to `\r\n` even under `fdopen(fd, "wb")`) and a symlink or junction is refused with `ELOOP`. `links.py`: `link_dir`/`link_file`/`is_link`/`points_to`/`link_source`/`link_target`/`remove_link` for the `sync_skills` catalog mirrors — relative symlinks on POSIX; on Windows a directory is an NTFS junction and a file a hard link with an ownership sidecar `<name>.ciao-link` (the source, relative to the mirror's folder), so no Developer Mode is needed and a file without a sidecar is never treated as a mirror. `processes.py`: spawn with `**tree_spawn_options()` and wrap the pid in `ProcessTree`, whose `terminate()`/`kill()` reach every descendant — `start_new_session` + `killpg(SIGTERM/SIGKILL)` on POSIX; `CREATE_NEW_PROCESS_GROUP` + a Job Object (`CTRL_BREAK_EVENT`, `TerminateJobObject`) on Windows. `private.py`: `make_private`/`make_private_dir`/`is_private`/`open_private`/`carry_mode` — `0o600`/`0o700` mode bits on POSIX; on Windows a protected DACL granting only the current user and SYSTEM (inheritable on a directory), set with `SetNamedSecurityInfoW`, raising on failure. `tool_path.py`: `terminal_path()` is the PATH the user's own terminal resolves against — an interactive login shell on POSIX; on Windows the two registry `Path` values a new logon is built from (`HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\Environment` then `HKCU\Environment`, `%VARS%` expanded, read with `winreg` and no subprocess, uncached because a registry read costs less than the shell it replaces) — plus `resolve_executable(cmd, path=...)`, which honours `PATHEXT` on Windows and resolves a command wrapper (any `.cmd`/`.bat`/`.ps1`, in any prefix, so nvm-windows and a custom `npm prefix` count too) to the executable it launches, read off the shim's last argument line and never guessed; a wrapper that launches an interpreter raises `ToolResolutionError` (an `OSError`, which `providers.opencode` and the wizard already degrade on) rather than resolving to `node.exe`, and a wrapper is never returned as the tool itself. The PATHEXT search, the shim reader and the registry join are defined above the platform split so they are tested on every OS.
  execution_modes.py           Claude/opencode provider approval policies and the CLI control-plane posture. Since S6 there is no argv allow/ask prefix list (`AGENT_CLI_ALLOW_PATTERNS` / `AGENT_CLI_ASK_PATTERNS` were removed with the argv auto-approval): every `ciao …` shell command keeps a card in `auto` mode (an argv allow prefix is a shell-suffix bypass risk), and users switch to `bypass` for no cards. The security floor stays server-side in the control plane (mode gates, `unattended_forbidden`, workspace confinement).
  tool_path.py                 Resolve external CLI tools against the user's real terminal PATH (Homebrew, nvm, `~/.local/bin`; on Windows npm's global shims, WinGet's links and `%USERPROFILE%\.local\bin`). It merges that PATH with the process one and resolves against the result; what "the user's terminal" means — and what a tool resolves to — is `os_support/tool_path.py`, so nothing here branches on the platform. The POSIX terminal-PATH probe spawns an interactive login shell (~0.74s), so it is cached against a fingerprint of the files such a shell reads — the rc candidates plus `$ZDOTDIR`'s, `/etc/paths`, `/etc/paths.d/*` and `$SHELL` — rather than a TTL: the setup wizard polls every 2s and a saved rc file must still be picked up on the next poll. Concurrent probes share one spawn.
  git_proc.py                  Timeout-safe git subprocess spawning for `local_session`: git runs in its own process tree (`os_support.processes`) so a timeout kills the forked `ssh` too, and the child is reaped and its pipes closed (a bare `proc.kill()` leaked 2 fds per timeout — issue #470). `run_git_sync` is the read-only counterpart, for questions answerable off-loop.
  git_mutation.py              The one serialization point for git mutations (#674). `repository_mutation(workspace)` is an async context manager holding a task-reentrant lock keyed by the canonical work-tree top level, so manual sync, the post-conflict resync, the background backup push and admin snapshots cannot interleave git commands in one checkout, while two unrelated repositories run concurrently. Nested helpers in the SAME task reenter (a child task still waits); the lock is released in a `finally` and its registry entry dropped as soon as nothing holds or waits on it. `ensure_mutable` is the external-state half: it reports a preexisting `index.lock` or an in-progress merge/rebase — resolved through `git rev-parse --git-path`, so a linked worktree finds its own — and never removes it. Callers turn that refusal into their existing return shape, including an error response from the admin snapshot route.
  local_session.py             Current-branch git sync flow (LocalSessionManager): preflight, commit + pull + push, conflict chat. Every public mutation runs inside `git_mutation.repository_mutation`, and none reports a failed git step as success: `commit_pending` raises `GitOperationError(step, detail)` on add/status/commit failure (it is the one operation with no envelope to fail in), and sync/resync/push convert that into the failure result they already return, without fetching or pushing after a failed commit. The unattended pair rides the same lock and the same rules with one of its own: `commit_scoped(workspace, *, branch, relpaths, message)` stages `git add -A -- <paths>` over the named pathspecs and commits with a pathspec (which implies `--only`), so a deleted note is recorded and an unrelated file the user had staged stays staged and uncommitted; it verifies `branch` rather than assuming it, because the caller is about to push that one. `preflight_scoped(config, workspace)` runs the same secret scan (`scan_file_for_secrets`, shared with `LocalSessionManager.preflight`, so there is one set of rules) over the eligible set only and returns `backup_scope.tracked_excluded` as blockers. `commit_pending` and `LocalSessionManager.preflight` — the manual, whole-tree path — are unchanged by either.
  backup_scope.py              The explicit path scope an unattended backup may commit (#685), used by `local_session.commit_scoped`/`preflight_scoped`. An ALLOWLIST, not a denylist, in three kinds of scope base resolved from configuration: an agent root (`agent_root_targets`, so the per-workspace re-rooting needs no second rule) where only `memory-vault/`, `skills/`, `subagents/`, `commands/` and the `AGENTS.md` guide are durable; the configured vault, whose directory name is the operator's choice and whose internal layout is the app's own, so provenance rather than a fixed name list is what makes its contents durable; and `.archived-workspaces/`, a container holding one archived agent root per child. On top of that sits a flat set of refusals that hold at any depth: credentials (`.env`, `.envrc`, `secrets/`), runtime state (`.runtime/`), the mirrors `sync-skills` regenerates (`.claude/`, `.agents/`, `.opencode/`, `opencode.json`), dependency trees, build output and caches; plus two refusals that are narrower than a name, both settled in #734. The derived transcript archive (`Logs/`, written under the vault before the re-rooting and under the install root after) is denied at its resolved `config.logs_root` rather than at the bare name, so a notes folder the operator called `Logs` inside their own vault is backed up; the denial still wins where the vault *is* the archive, and under an archived agent root — a copy of a workspace as it was, which the resolved location cannot point at — its `Logs/Chats/` transcript subtree is denied by shape. And one file is carved out of `.runtime/` — `ALLOWED_FILES`, the automation store `.runtime/schedules.json`, which every other `.runtime` path still excludes (the credential preflight applies to it like any other eligible path); the scaffolded ignore rules have to agree, which is why `cli._WORKSPACE_GITIGNORE_ENTRIES` writes `**/.runtime/*` plus `!/.runtime/schedules.json` rather than the directory, since git cannot re-include a file inside an ignored directory — the `**` and the root-pinned negation are what keep nested runtime directories (a `client/.runtime/` holding credentials) ignored, which a root-anchored `.runtime/*` would have silently stopped matching. Bare top-level durable roots stay out by design: a root reaches the top of the data root only where the data root is itself an agent root, and the status line says so rather than leaving the owner to find it. `data_root` is `local_session.sync_root` — never the frontend URL, never an agent cwd; a path outside it is ineligible whatever it is called, symlinks resolved. `tracked_excluded` reports what git already tracks outside the scope, which is how a committed `.env` becomes a reported blocker instead of a silent gap (`.gitignore` never un-commits anything, and the manual sync path still stages the whole tree).
  backup_service.py            The unattended five-minute memory backup (#689), and the whole of the backup service: `BACKUP_INTERVAL_S = 300` as a named constant (no env var, no setting), one `BackupService` instance per process built in `main` and published as `app.state.backup_service`, and the `BackupStatus` the API serves. `run_backup` is the single serialized path the five-minute loop and `POST /api/local/backup/run` both call, so there is no second git loop and the two can never interleave: it takes `git_mutation.repository_mutation` + `ensure_mutable` at its own entry, re-reads root/branch/remote at run time (never at process start, which is what let an install configured later never back up anything), runs `local_session.preflight_scoped`, commits through `commit_scoped` only when the scope has eligible changes, and pushes when `git rev-list --count origin/<branch>..HEAD` says something is unpushed — so a clean run creates neither a commit nor a push.    memory_receipts.py           Recoverable receipts for managed memory mutations. Every region write, queue resolution and prune records a stable-id receipt in the per-workspace `Workspace/Memory-Receipts.jsonl` (append-only JSONL, latest row per id wins) with actor (`operator`/`agent`/`auto`/`system`), surface (`pwa`/`cli`/`archive`/`mcp`/`startup`), expected/before/after revisions, before/after images and a `prepared`→`applied`/`rolled_back`/`failed`/`conflict`/`undone` status. `commit_region_change` serializes the read-merge-write under the guide lock (a lock that cannot be taken is a retryable `MemoryLockError`, never a fall-through to an unlocked write) and re-checks the revision before the atomic replace, so an external direct edit is a `RevisionConflict` rather than a silent overwrite. Discovery scans each workspace vault journal and each agent root's guide-local fallback journal. `undo_receipt` refuses a changed destination and rejects legacy/unsupported rows. Read side: `GET /api/memory/receipts` and `POST /api/memory/receipts/{id}/undo`.
    note_receipts.py             Revision-checked note writes: the receipt protocol narrowed to one existing `.md` file inside the canonical configured vault, so an arbitrary note change can be recovered and undone. `commit_note_change` takes a vault-*relative* path — absolute paths, `..`, symlinked files or ancestors, and anything that is not a regular Markdown file are refused, as is the app's own bookkeeping under `Workspace/` (`vault_index.is_reserved_bookkeeping`, the queue and curation logs the memory pipelines maintain themselves); each component is spelled the way the vault has it, so both spellings of a name on a case-insensitive filesystem are one file, one per-file lock and one recorded `relative_path` rather than two writers reaching one note unlocked against each other. Only the vault root is `resolve()`d, so a symlink planted inside the vault cannot redirect the write out of it. **The transaction is whole-note; a range is a composition.** There is no range parameter on `commit_note_change` and there is not going to be one: a receipt keeps a full before image and a full after image precisely so an undo can put a file back without knowing how the file changed. `apply_entry_edit` is a *composer*, not a second protocol — it re-reads the note under the note's own lock, resolves one entry by `note_entries.entry_identity` (which takes no line number and no offset, so a caller whose offsets went stale with the note still gets the entry it named), confirms the entry's `refresh_fingerprint` is still the one that was judged, splices exactly that entry's span (a delete takes the terminating newline with it, so a removed bullet does not become a blank line) and hands the composed `after_text` to `commit_note_change` unchanged. A replacement must be exactly one list item, checked through the same parser the entry came from; a re-stamp is not a separate case but a replacement whose fingerprint is unchanged, which is what `entry_verification.stamp_entry` produces. An identity that names no entry, or a fingerprint that does not match, is a `RevisionConflict` with nothing written — a fingerprint mismatch never overwrites. An *entry* retirement deletes that one span through this helper and comes back through the same whole-note undo; a whole-file retirement stays `vault_review.trash_note`'s, and this module reaches no trash at all. Notes are read and written as bytes, so a BOM, CRLF pairs and an unterminated final line survive verbatim, and the replacement is revision-checked against the exact text the caller read: a stale expectation is a `RevisionConflict`, not an overwrite. Content that is not UTF-8, or whose image exceeds `MAX_IMAGE_CHARS`, is refused before the mutation, because an image the journal cannot hold would leave an `applied` row nobody can undo. Under the same per-file `queue_lock` the apply takes, the row goes down `prepared` first (a journal that cannot record it aborts the write), the bytes are written to a sibling temp file and `os.replace`d with the mode preserved and the revision rechecked immediately before the rename, and a failed write settles `rolled_back` only while the note still matches its before image. `recover_pending` classifies an interrupted `note_apply` by the note's current revision — after→`applied`, before→`rolled_back`, anything else or a missing note→`conflict` — and never rewrites note content; recovery and undo resolve the target against the vault derived from the *journal's own location*, so a forged or moved receipt cannot write outside it. `undo_note_receipt` restores the before image as its own journaled `note_undo` write carrying `undo_of`, and only then marks the original `undone`; an interrupted undo (including the window between the reverse rename and the original's settlement) is finished by one idempotent `settle_open_undo_links` pass, and an undo that loses that final append says the undo *landed* rather than reporting a write error against a note that is already restored. The before image must still hash to the receipt's own `before_revision` or the undo is refused, so a tampered journal row cannot install content it never recorded; a write that changed nothing is recorded `undoable=False`, so History never offers an undo for it. Undo is not offered for undo. Scope is this one mutation protocol only: the business verification/proposal rules that consume it are a later child. Tests: `tests/test_note_receipts.py`, with `tests/test_memory_receipts.py` as read-only regression coverage.

   curation_run.py              Deterministic worklist, run budget and lease for the nightly Workspace care run. `build_worklist` answers in code the empty/no-op and due-date questions the Workspace care schedule prompt used to spend model turns on (pending routable proposals, region usage at or over the ~85% consolidation threshold or holding expired entries, aging and event-shaped region entries, stale vault notes, learnings at x3 or x1-past-30-days, the `last_full_pass` marker's age, a weekly guide-body review, logs over 64KB, skill proposals), so an idle workspace is computable as idle without a model turn. `PASS_STALE_NOTE` sits directly after `PASS_AUDIT` because both are "verify, don't guess" work over facts somebody has been asserting, and it is not a weekly-hygiene key: a note goes stale on its own clock, not the marker's. It is the **cheap, model-free selection** half of note verification — one `WorklistItem` per stale note, keyed by its vault-relative path, oldest first — and it calls `memory_audit.find_stale_notes` rather than forking the thresholds, exempt types, alias resolution and frontmatter-then-mtime date rule, so the nightly plan, `os-audit`, the Memory Map's `stale` flag and the review queue's `unverified` signal cannot disagree about which notes count. It adds the two filters the audit does not apply: `vault_review.never_queued` (a note the review queue would never show a person — `Workspace/` bookkeeping, templates, completed projects — is not tonight's question, and disuse alone never justifies dropping a durable fact) and `note_verification.should_check` (a note whose check is still in its 30-day cooldown or still waiting on the proposal that check pinned has already been asked; without this the same cooled-down notes take the first slots nightly and the backlog starves). It plans at most `STALE_NOTE_MAX_ITEMS` of them per run, capped AFTER the cooldown filter, because the pass sits ahead of the two required hygiene keys and the budget is a whole-run allowance — an uncapped backlog would spend it and `last_full_pass` could never advance. It reaches no verdict; the one thing it reads is the flagged note's own bytes, to state the `content_revision` its item's `reason` carries as the `expected_revision` the operation requires. `PASS_STALE_ENTRY` sits directly after it, for the same "verify, don't guess" reason and because a note is not the unit a person keeps current: a note's `updated:` is one date for every fact in it, so re-verifying the address last week silently re-certified the landlord's name from 2019 with it. Its selection walks **every** note rather than only the stale ones, and ages each entry on **its own** date where it has one — a valid `[verified:]` stamp is aged from that day against the same entity-type horizon the audit measured the note with (a custom category's `stale_after_days` included), and an unstamped or unusable-stamp entry inherits the note's date, so a bullet stamped two years ago in a note re-stamped yesterday is still work and a whole-note selection can never see it. Exempt types and `never_queued` are the audit's and the queue's, not second copies, and the two stale passes share one `scan_vault` walk. Each item is keyed by `note_entries.entry_identity` — not a path, not a line, not an offset — and filtered by `entry_verification.should_check_entry`, the same predicate `verify_entry` short-circuits on, so the plan cannot offer an entry the operation would refuse to judge. It plans at most `STALE_ENTRY_MAX_ITEMS` per run, a cap separate from the note pass's (a shared allowance would let one enormous fact list spend the whole entry budget on a single note), applied after the filter; order is age descending, then path, then the entry's own position, so two runs produce the same list and a short budget drops the youngest fact. Its `reason` carries the entry's own fingerprint and span, the two values a caller cannot rederive without reimplementing a hash and guessing wrong. A re-stamped fact's fingerprint is unchanged, so a settled entry stops being work immediately. That is the managed `verify_note` operation's work (`control_plane.verify_note` → `note_verification.verify_note`, agent surface `verify_note`, CLI `ciao note verify --payload-file FILE`), which takes the verdict as a payload FILE inside the caller's own workspace root, refuses a payload naming another workspace, runs as one bounded coalesced off-loop read (`async_reads.run_read`, keyed by runtime dir + workspace + note + expected revision + a digest of the whole payload, so two callers only share a read when they ask the same question), journals `source` from the turn (`curation` unattended, `chat` attended), and reports an oversized payload or note as `unverified` rather than `applied`. A `needs_review` verdict there files **exactly one** typed `note_edit` proposal and pins the check to its queue row id — the wiring `note_edit_proposals.py` (#726-C) was written for and had no caller for; auto-applied verdicts file nothing, and a retirement is never applied at all. Before this pass, the Workspace care prompt told the *agent* to open stale notes and stamp `updated:` by hand, which produced no receipt, no check state and no record of who decided. `plan_run` applies the run budget, splitting a pass rather than deferring it whole, and the persisted cursor in `<vault>/Workspace/Curation-State.json` lets a budget-limited run resume at the remainder instead of restarting at pass 1. `begin_run`/`end_run` hold a TTL lease (the TTL *is* the elapsed-time budget, so a run cannot outlive its own serialization) — two curation runs cannot overlap. Nothing else holds this lease: the archive-time auto-apply that used to stand down while it was held was deleted with the one-shot pipeline (#627), so the Workspace care schedule prompt's own consolidation is the only writer that lease serializes now. `end_run(advance_marker=True)` stamps `last_full_pass` only once both required weekly checks are recorded done and only after it has confirmed the caller still owns the lease, so an unreliable index refresh or audit — or a run whose lease expired under it — leaves the weekly pass due. CLI: `ciao curation-plan|curation-begin|curation-progress|curation-end`; `curation-progress` and `curation-end` require the `--holder` `curation-begin` returned, and exit 75 means another run holds the lease.
   vault_review.py              Deterministic workspace-scoped vault-note review candidates, append-only dispositions, reversible trash/restore, project completion, and attended permanent deletion; bookkeeping is excluded from ordinary review candidates. A candidate is identified by (workspace, vault-relative path, content hash), so an edited note cannot inherit an old destructive decision. Dispositions: `keep` (stamps `updated:`), `reopen` (undoes a keep), `trash`/`restore` (reversible workspace trash), `delete` (attended, requires a trashed note plus exact confirmation), `complete` (close a project out), `vanished` (written by the system for a note that left the vault some other way). `complete` is the only disposition that MOVES a note rather than removing it: `complete_project_note` takes a note whose declared `type:` is `project`, or any note under a `projects/` segment that declares no type at all (a declared type always wins, so a `type: person` note filed under `projects/` is not a project), and moves it to `projects/completed/` — the whole folder for a `projects/active/<slug>/` project, the single file for a flat `projects/<name>.md` — rewriting `status: active` to `status: completed` using the same `status:` line anchor as the PWA's own completion, matched inside the frontmatter block here and substituted over the whole text there, because a review candidate is any note in the vault and a body line reading `status: active` — inside a fenced example, a pasted transcript — is prose rather than the note's own state. Whatever the candidate was, a folder project moves as a FOLDER: every note under it moves, so every reference to any of them is repointed in both dialects (`related:`/wikilink and relative markdown) via the pure `vault_rehome.rewrite_references` primitive, and a candidate can be a note nested below the entry markdown (`projects/active/<x>/meetings/2026-01.md`), with `new_path` naming where that note lands inside the moved folder. It is one transaction: the links are resolved and rewritten BEFORE the move (resolution needs the notes on disk), every rewrite is staged and swapped as a unit, each file is re-read and compared against the text its rewrite was computed from immediately before the swap, and a failure at any point — staging, the move, or the ledger append — restores every file already written and leaves the project where it was, because a row claiming a closed project while notes still point at the old path is the one state this workflow must not produce. The ledger row records `previous_path`, `new_path`, `status_rewritten`, `edited_backlinks` and the `undo` images that make it reversible, each keyed at the path its note has WHILE COMPLETED, so a note inside a moved folder and a note that referred to it need two different keys. Reads and writes in this feature go through exact-newline helpers, so a CRLF note keeps its line endings and a rollback is byte-exact. `restore_completed` is the reverse: it undoes only the latest `complete` row for an id, and refuses when there is none, when the completed note is gone, when the original path or project folder is occupied (`shutil.move` would nest it), or when a note the completion rewrote has been edited since. A `complete` row is terminal and suppresses: the note is no longer at the path the row names, and a completed project is already exempt from candidates (`never_queued`) and from `vanished` rows, which would otherwise report the move as a deletion. It also reads the managed verification state (#726-E), so the queue and the pass cannot ask the same question twice: `read_note_checks` is consulted once per scan, a check that `_check_settles` (the very predicate `verify_note` short-circuits on and the curation worklist filters its plan by) says already answers the note's current revision clears the `unverified` signal, and a check carrying a `proposal_id` for THAT revision is reported as a **pending verification** rather than as a second decision to make. The candidate payload then carries `pending_verification` (the queue row and the sidecar id behind it, with the outcome, coverage, citations and the reason) and `retirement_offered`, and the panel links the proposal instead of offering *Still true* / *Retire* on the same revision — two buttons in two places asking one question and able to disagree is the defect. `retirement_offered` is False only when a pending proposal is the note's SOLE reason for being queued: another signal (unlinked, duplicate, superseded wording) is an independent finding about the note and the queue must not lose it because the pass reached the same note first. A proposal pinned to a revision the note has since left is reported as `conflicted` and suppresses nothing, because its accept would refuse as a conflict and the note is due again. The same scan reads the entry-level detector (#785) and reports it as a separate `unverified_entries` signal plus an `entry_verification` evidence block: the exact list items with the lines around them, whether the date on one is its own stamp or the file's `updated:` carried onto it, and the pending `note_edit` proposals keyed by the same entry identity. It **links** those proposals rather than offering a second accept — the row's own buttons are about the whole file, and a fact is not the file — and reports `conflicted` on an entry proposal the accept would refuse. `unverified_entries` is in `CHECK_ONLY_SIGNALS`, a set rather than one hard-coded name precisely so a new "check this" signal cannot start offering Retire on a note whose only finding is that nobody read one of its bullets. Coverage (`uncovered`, i.e. prose, a table or a quote nothing here can read as a fact) is reported in the same block and is deliberately **not** a signal: a note whose facts live in prose is unmeasured, not wrong, and making it a row would fill a queue whose terminal action is deletion with every short note in the vault. `checked_at` rides along separately from the note's own `updated:` and the two are never collapsed: a verdict that came back `unverified` writes nothing, so a note can be checked yesterday and still carry last year's `updated:`.
  memory_proposals.py          The memory-proposal queue, the bounded regions it promotes into, and the receipts both leave. A proposal is one bullet in `Workspace/Memory-Proposals.md` tagged with its destination (`memory`/`profile`/`project`/`people:<Name>`/`learnings`/`review`); a person or the agent files one by hand (`ciao memory-proposal-add`, `append_proposals`), the review surface lists and dismisses them, and a user accepts one into its destination (`accept_region_fact`, `reconcile_region_fact`). Regions get a trailing learned-at `[YYYY-MM-DD]` stamp and dedupe compares stamp-stripped. `reconcile_region_fact` is the ADD/UPDATE/COVERED step on the accept path: one small model call compares the new fact against current entries so a superseded entry is replaced (old text to the Memory-Consolidations undo log first) instead of accumulating beside its successor; any failure degrades to the plain append. The write is not a plain append: it goes through the `ciao.memory_audit` event-shape guard, stamps the `fact_candidates` provenance row, and logs every replace. A `[learnings]` accept writes `Workspace/Learnings.md` through `append_learning`, which since #755 is the canonical writer: it parses with `learning_records.parse_learnings`, folds the sighting in with `observe_learning`, and renders the one line with `render_learning` — the private regex, key, normalizer and line formatter this module used to own are deleted, not shadowed. The entity-note writer is the category's, not a hardcoded folder's: `write_entity_note`/`entity_note_path` take the notes root the note is written under AND the agent vault root the category is read from (`entity_types.load_entity_types`; the two are the same directory only on a re-rooted install) and refuse a category that has no folder, is disabled, is unknown, or whose folder is not one inside the notes root, so a `[people]` accept lands in `People/<Name>.md` typed `person`, a category the owner added has a writer too, and an owner's `person.folder: Humans` is what an accept honours (#637); `render_entity_note` is the same body without the write, so the review card's preview and the accept cannot disagree. `record_dismissal`/`record_promotion` write every decision (web, CLI and accept alike) to the per-workspace `Memory-Proposals.dismissed.jsonl` sidecar with `via` (pwa/agent), `destination` and `outcome`; `read_decisions`/`history_row_id` are its read side, served by `GET /api/proposals/history` — what was accepted or dismissed, by whom, and from where. The one-shot producer of these bullets is gone (#627): the memory pass, a chat of the app's own, writes memory directly now.
  learning_records.py           The canonical record model for `Workspace/Learnings.md` (#732, #755): `parse_learnings` reads a learnings document into `LearningRecord`s with immutable, workspace-scoped identities, `render_learning` writes the canonical line plus a machine-readable `<!-- ciao:learning {...} -->` comment, `migrate_learnings` rewrites only recognized Active entry spans while preserving every other byte, and `observe_learning` folds one sighting into a record. A `## Promoted / Resolved` entry is not reconciled at all, and a line the parser cannot read is reported and left exactly as written.   engine_update.py             The update transaction for installer-managed installs, in two halves. Staging (`ciao update stage`) is lock + durable operation record under ~/.local/state/ciaobot/updates, signed-manifest and wheel-digest verification, and a fully installed staged env, all before any downtime. Applying (`ciao update apply`, the same `apply_update` the #571 settings UI calls) closes admission through the loopback-only `POST /api/admin/drain` and waits for three consecutive readings with no `active_chat_ids` — re-POSTing the same drain rather than reading `/api/active-chats`, which is a public route any peer can read and would let a caller drain one machine while waiting on another's chats. The wait is bounded, because a drain that never completes must not cost the user their engine, and on timeout (or a Ctrl-C, SIGHUP or SIGTERM, which the CLI turns into the same path) it reopens admission (`/api/admin/drain/cancel`) and leaves the running engine untouched. Once drained it bootstraps a one-shot `com.ciao.updater` LaunchAgent (KeepAlive false, AbandonProcessGroup true) running `<staged env>/bin/python -I -m ciao.engine_update run-apply --operation <id>`: a *sibling* of `com.ciao.server`, because the swap has to survive `launchctl bootout` of the engine, and launched from the staged env so it is not the environment it replaces. `run_apply` boots the engine out before touching a file (its install watcher would otherwise relaunch into a half-swapped env), renames the live uv tool env aside to `<stage>/previous-env`, moves the staged env — itself a real uv tool env, resolved and verified once at stage time — into the live env's place, rewriting only what a move breaks (the `bin` shebangs, and the entry points `bin_dir` links into the env) so no resolver runs during the swap and the apply needs no network, rewrites the install receipt, starts the service and waits for `/api/startup-status` to report the target version *and* `overall_ready`. Any failure after the swap began rolls back: env moved back, receipt restored from `previous-receipt.json`, the engine waited to stop answering, service restarted and the old version re-verified. A phase write that fails (a full disk, usually the same one that broke the swap) cannot stop the rollback or undo an update that already passed readiness. The old env is retained until the next update succeeds, so exactly one rollback generation exists. Every outcome is persisted (`applied`, `rolled_back`, `rollback_failed`, `failed`) and the job exits 0 regardless — the record is the outcome. launchctl, uv, HTTP, sleep, clock, uid and paths are all injected, so the failure-injection tests never touch launchd, uv or a network. A swap interrupted by a reboot, a logout or a killed updater job is picked up by a *durable* recovery agent, because the crash window it has to cover is one where the engine cannot start at all: `live_env` is renamed to `previous-env` and the staged env is not yet in its place, so `com.ciao.server`'s program does not exist, launchd cannot launch the engine, and nothing running inside it can notice the swap is stranded. So `apply_update` installs a second LaunchAgent of its own — `com.ciao.recover`, `RunAtLoad` true, `StartInterval` 30, `KeepAlive` false, `AbandonProcessGroup` true — from the staged interpreter and *before* the engine is ever stopped, and it is re-checked on that interval rather than run once, which is what lets it outlive the crash, the reboot, the logout and the death of the updater job; `run_apply` re-points it at `<stage>/previous-env/bin/python` the moment the live env is renamed aside and before the staged env is moved in, because the swap consumes the directory it was installed from and a net whose program is a dangling path is no net at all — the `previous-env` exists from that instant, is a complete old install, and is only moved again by the rollback. Its program is the same `run-recover --operation <id>`, and `recover_apply` takes the update lock *without waiting* before it looks at anything: every tick that lands while a swap is in flight is the normal case, so it stands down for that tick and leaves itself loaded rather than joining a second rollback over one env. Once it holds the lock it is the only writer, and a missing, superseded or already-settled record means there is nothing to undo — the agent then retires its own job and plist (bootout *and* delete, or the next login reloads it) and, because it never drained anything, posts nothing and mutates no record. Otherwise it stops the engine and runs the same total `_rollback` the apply would have, treating the retained `previous-env` as the evidence that the move happened — so a crash in `starting`/`verifying_start`, where the staged env already *is* the new live env, still replaces that half-installed env with the old one instead of restoring the old receipt over the new engine — settles `rolled_back`/`rollback_failed` and retires itself. A `com.ciao.updater` that is *running* (a live pid in `launchctl print`, not merely a loaded job, since a one-shot job stays loaded after it dies) defers. `recover_interrupted_apply`, called once from `ciao/main.py` (macOS only, before the server binds), stays as the fast path for the cases where the engine does come back: it recognises a record left in `swapping`, `starting`, `verifying_start` or `rolling_back` and bootstraps the one-shot `com.ciao.updater` job in `run-recover` mode. Pre-move and terminal phases are left alone by both. In the other direction, `run_apply` refuses before it moves anything when the loaded `com.ciao.server` does not run the env the install receipt names: the authority is the *loaded* job's effective program, read with `launchctl print gui/<uid>/com.ciao.server`, so a plist rewritten after launchd loaded it (a reinstall, a hand edit, an app over a terminal install) cannot pass a check the loaded service fails; the on-disk plist answers only for a job that is genuinely not loaded, and a missing plist is allowed, since the rollback's start step is what registers the service. CLI: `ciao update stage|apply|status`.

## Vocabulary

Three terms describe where things live. They are pinned here because the same
word once meant two different things.

- `workspace_root` — the install root directory (e.g. `~/repos/ciao`). Holds the
  vault, `.runtime/`, config, and the user's agent assets. Meaning unchanged from
  today.
- `workspace` — the logical workspace name (e.g. `personal`, `work`). A label,
  not a path. Meaning unchanged from today.
- `agent_root` — the per-workspace directory that will hold that workspace's own
  `AGENTS.md`, `.mcp.json`, `.claude/` assets, and `memory-vault/`. Today it
  resolves to `workspace_root` for every workspace, so it is a seam and not yet a
  distinct directory. The re-rooting release makes it a real subdirectory.

`handover` is pinned for the same reason: it is a provider-session word, and
the persisted key `handover_context_pending` cannot be renamed. It moves one
chat's recent turns into a fresh provider session
(`ChatInfo.handover_messages`, `handover_context_pending`); the workspace
re-rooting reuses it to mark chats whose old provider session was stranded by
the move (`workspace_reroot.flag_stranded_sessions`). The multi-device host /
client role handover that once shared the word is gone, along with
`/api/node/handover`; `POST /api/chats/{id}/handover` and
`POST /api/handover/merge` are both this provider/git sense of it.

## Workspace layout

`workspace_guide.migrate_config` follows `CiaoConfig.agent_root_targets()` rather than the raw install path. Before the workspace re-rooting, that seam returns the install root because it is the shared agent root; after the re-rooting it returns only the per-workspace roots, because `workspace_reroot` has moved the shared guide into the primary root and the install root is no longer an agent root. A root-level guide found after that transition is not a filename-migration target: it may be repository metadata or re-root drift, and renaming it independently would either mutate unrelated instructions or leave a parent guide for providers to load.

The app repo above is the installable package. A `workspace_root` is a separate directory (created by `ciao setup`, never committed to this repo) that holds the user's data and per-instance state: one root folder containing the vault (`memory-vault/` by default) alongside `commands/`, `subagents/`, `skills/`, `.runtime/`, and config. A fresh first logical workspace and every workspace created later in Settings are user-named folders under that configured vault root (`<vault>/<workspace-name>/`); Settings never accepts a filesystem path for them or follows a named-folder symlink outside the vault. Setup can preserve an existing notes folder in place, and upgrade compatibility can temporarily pin any older nonstandard vault root. The AI OS audit reports each nonstandard root with a Ciaobot-chat migration prompt so the model can inspect conflicts, back up the source, update the registry, and restart into the standard nested layout without moving data silently. Setup ensures the `workspace_root` is a git repository: if the chosen folder is not already inside one, it runs `git init -b main`, writes a `.gitignore` guarding `.env`, `.runtime/`, `.claude/`, and `*.log`, and makes an initial commit; pre-existing repos are left untouched apart from appending any missing `.gitignore` guards. The vault may also point elsewhere (`CIAO_VAULT_ROOT`, e.g. an existing notes folder): in that case setup initializes that folder as its own git repository (`git init -b main`, a minimal `.gitignore` for `.DS_Store` and `.obsidian/workspace*`, and an initial commit); a vault nested inside the `workspace_root` repo — the default layout — is never double-initialized.

## Server and chat pipeline

Linux production hosts run the engine under systemd. Settings uses the
authenticated `POST /api/admin/restart` endpoint, selected by `restart_only` in
`/api/local/status`, to enter the same chat-drain/re-exec lifecycle without a
source checkout or desktop rebuild. Code updates remain administrator-managed;
developer mode retains the deploy endpoint. `restart_only` is also true for
the legacy bundled-app install mode (`detect_install_mode() == "bundled_app"`,
whatever the dev mode) and for any macOS install that is not a deployable
checkout. The re-exec happens in-process (`ciao.cli._run_server`), so the
`com.ciao.server` LaunchAgent keeps tracking the same pid, and its `KeepAlive`
relaunches the job if the exec fails. `ciao supervise` (`ciao/supervise.py`) is
the cross-platform alternative: it runs `ciao run --supervised` as a child,
relaunches it on exit code 75 (with a crash-loop backoff) and forwards
SIGTERM/SIGINT (SIGBREAK on Windows); the Windows logon task is the service
file that uses it (below). `POST /api/admin/deploy` refuses a bundled app up
front.

**Windows lifecycle (#696).** There is no LaunchAgent or systemd unit on
Windows. `ciao setup --load-launchd` (the flag name is historical: on macOS
and Windows it means "register the per-user service") writes
`%LOCALAPPDATA%\Ciaobot\service\Ciaobot-Engine.xml` and registers it as the
per-user Task Scheduler task `\Ciaobot\Engine` through
`ciao/windows_service.py`. The task fires at that user's logon and runs
`pythonw.exe -m ciao.cli supervise` with the workspace as its working
directory. `pythonw.exe` has no console, so `ciao supervise` redirects its
stdio to `<workspace>\.runtime\ciao.stdout.log` and `ciao.stderr.log`. The
supervisor starts `ciao run --supervised` as a child in a Job Object, so
ending the task (`ciao service stop`, `schtasks /End`) terminates the whole
tree. When the engine exits with `RESTART_EXIT_CODE` (75: Settings -> Restart,
the setup wizard, a package update) the supervised `_run_server` returns the
code instead of calling `os.execv`, and the supervisor relaunches the child
with the crash-loop backoff above; any other exit code ends the supervisor,
and the task's `RestartOnFailure` (every minute, up to 999 times) is the outer
retry. The operator-facing guide is [WINDOWS.md](WINDOWS.md).

`ciao/` is a Starlette web server that mounts the PWA frontend, exposes a JSON API for projects/chats/schedules, and drives Claude Agent SDK sessions for each chat turn. Auth is a pre-shared token (`PWA_AUTH_TOKEN` — the dashboard password) traded for a signed session cookie, and it is required by default: an unset `PWA_AUTH_REQUIRED` protects any workspace that has a token, and only an explicit `PWA_AUTH_REQUIRED=false` runs the dashboard open. Settings can change the password but not disable protection. Operational state lives in `.runtime/` under `CIAO_WORKSPACE`; durable memory lives under `CIAO_VAULT_ROOT` (default `<CIAO_WORKSPACE>/memory-vault`).

One backend process owns a runtime directory at a time. The engine is the only
process: on macOS it runs as the `com.ciao.server` LaunchAgent and the UI is the
localhost PWA, which treats the workspace `.env` (`PWA_PORT`,
`CIAO_RUNTIME_ROOT`) as authoritative. A browser cannot hand a page a Finder
path, because HTML `File` objects carry no absolute paths, so Finder drops
arrived through a native handler that wrote the exact paths into a five-minute,
single-use grant under `.runtime/desktop-drop-grants/` and dispatched only that
grant ID into the page. The local `/api/desktop-drop` endpoint consumes
the grant: the route returns bounded opaque file references, and the server
expands those references only in the provider prompt; clients transfer the
file bytes into the active project on the host. This does not add a native command
or general filesystem capability to the remote page. That shell is retired
(`#656`) and the grant route stays only for an old one still in the field.
`ciao/instance_lock.py`
holds `.runtime/server.lock` for the engine process lifetime, so a normal
server and `ciao dev` cannot run against the same registry concurrently.
Project/chat writes use a short-lived registry lock, merge field-level local
deltas onto the latest revision, and append mutation IDs to
`.runtime/web_projects.audit.jsonl`. Vault-backed project IDs are
deterministic for newly discovered `(workspace, vault_folder)` pairs. At
startup, archive discovery resolves both display names and vault-folder slugs;
missing active rows are reconstructed from normalized runtime transcripts only
when a surviving provider session or a non-deleted audit record proves they
were active. Explicit deletion clears provider state, normalized transcripts,
and session state so recovery cannot revive it.

Chat transcripts are streamed via WebSocket and archived to `<logs root>/Chats/<chat-id>/<provider>/` (`transcripts.py`), where the logs root is `CiaoConfig.logs_root` — `<vault>/Logs` before the re-rooting and `<install>/Logs` after it, decided by the same migration receipt as `agent_root`. Every reader goes through that seam (or the standalone `config.logs_root_for` when it holds only paths): deriving it as `vault_root / "Logs"` resolves to a path that does not exist on a migrated install, so archiving would recreate it and split the archive in two. `Logs/` is global: a sibling of the workspaces inside the vault root, not a subfolder of any one of them. It stays global through the re-rooting release, which promotes it to `<install>/Logs/` without moving the files, because it holds 1423 of 1985 vault notes (72%), it is derived output rather than curated content, and 1350 chat ids cannot each be resolved back to one workspace. Archive, delete, and new-session cleanup disconnect the live supported provider before reclaiming its session: Claude SDK JSONL blobs via `delete_session` and OpenCode sessions via `DELETE /api/session/{id}`. Cleanup is fail-open so a provider outage cannot prevent the durable Ciaobot archive, and it includes prior session IDs created by rotation. Archived `/messages` falls back to the vault markdown when the supported provider session is gone. The Claude Agent SDK is configured in `ciao/providers/claude.py` with a `fallback_model` chain (Fable to Opus to Sonnet to Haiku) and `setting_sources=["user", "project", "local"]` so `.claude/skills/`, `.claude/agents/`, and `.claude/commands/` auto-discover.

Chat document attachments convert supported files into Markdown in the active
project vault folder. Existing host sources remain at their original paths;
remote uploads use a temporary host source and persist only Markdown. Images
and ordinary text retain their existing behavior, and conversion errors are
per-file and non-fatal.

The control plane runs as the agent CLI surface. `CiaoControlPlane` wraps the
existing project/chat, schedule,
subagent, vault, memory, file-history, workspace-health, local-session, and
lifecycle managers; `CiaoMcpService` only performs bearer authentication,
operation dispatch (via the `AgentDispatcher`), plan-mode mutation policy,
stable error envelopes, and
telemetry. Each managed provider process receives a short-lived capability
carrying a chat/project/workspace/provider principal. What that principal
enforces is workspace confinement plus chat attribution, not isolation between
chats: every ownership check resolves through `_workspace`, so a chat token
reaches sibling chats in its own workspace and no others. The chat half drives
plan mode, the child-mode ceiling, background-run ownership, revocation and
telemetry. Claude receives the server and
Authorization header through `ClaudeAgentOptions.mcp_servers`; opencode receives
equivalent per-process configuration, which is why it runs one server process
per chat (reclaimed by the idle sweep in
`ProjectChatManager.reap_idle_providers`). Project servers remain in `.mcp.json`
and credentials stay as environment references. Self-disconnecting operations
defer until their caller chat drains. The native file tools are denied `.env`,
`.runtime/` (by name, plus the resolved `CIAO_RUNTIME_ROOT` path) and
`secrets/` on both providers
(`ciao/execution_modes.py::credential_path_deny_rules`), because
`PWA_AUTH_TOKEN` in `.env` buys strictly more than any scoped agent token. The
`.env.example`-style templates are deliberately not denied, matching
`local_session.py`. See `docs/AGENT_CLI.md`.

The agent CLI control plane is mandatory and is the only agent-facing control
surface: there is no skill/direct-file fallback and no per-chat or
per-server surface selector. `ProjectChatManager.build_agent_request` raises
`AgentSurfaceUnavailableError` when the control plane or the chat's project is missing,
and `_drive` turns that into a normal failed turn in the transcript, so a chat
never runs an agent that silently cannot reach Ciaobot. First-run setup is the
one state without a control plane (no workspace yet); a chat attempted there
fails with the same error. The `legacy`/`auto` surfaces and the
`ciao benchmark-control-surfaces` evaluator that compared them were removed
once the evaluation had settled on MCP. Two deliberate CLI exceptions remain,
both for surfaces that are not control-plane CRUD: the memory-proposal queue
(`ciao memory-proposal-add`, `ciao memory-proposals`,
`ciao memory-proposal-dismiss`) is driven by the nightly curation agent because
one shell command beats an MCP round-trip per row, and the vault-maintenance
verbs (`ciao index`, `ciao lint`) wrap tools a file tool cannot replicate.
Reviewing and accepting proposals still happens in the PWA or through those
CLI verbs; the MCP surface keeps `memory_status`/`memory_update` for bounded
memory itself.

Server restart requests drain chat work before shutting down: active broker streams, already-queued follow-up turns, and background-subagent watchers are allowed to settle, while brand-new turns are rejected once draining begins. When drain starts, `ProjectChatManager.begin_restart_drain` publishes `server_restarting` on `/ws/events` (and the connect snapshot carries `restarting: true`) so every open PWA shows the full-screen restart overlay instead of treating turn rejection as a chat error. Shutdown starts only after several consecutive idle observations so the handoff from a completed parent turn to its background-agent watcher or synthesis stream cannot create a false-idle race. `ciao service restart` uses `/api/active-chats` as a guard before its direct launchd restart and asks the operator to retry once active chats finish.

When the model calls `AskUserQuestion` (which the headless CLI can't render, and would otherwise auto-answer empty), `ProjectChatManager._drive` interrupts the turn so generation stops at the question; the PWA surfaces it in its own picker (persisted as `ChatInfo.pending_question` so it survives a reload) and the user's reply resumes the session as a fresh turn.

If a turn fails before any provider progress with a quota or session-limit error, `ProjectChatManager` stores the last prompt and schedules an hourly deferred retry; the chat view and sidebar surface the pending state, and `/api/chats/{chat_id}/retry` lets the UI set, stop, or run that retry immediately.

Conversation forks let a user start a new chat in the same project starting from any completed agent answer in an active or archived chat. When a fork is created via `/api/chats/{chat_id}/fork`, the system performs a provider-neutral history copy, copying the visible chat history up to the selected assistant response, normalizing the messages (with system notes for truncated older messages if bounds are exceeded), duplicating referenced images to ensure source independence, and initializing a new chat with `handover_context_pending=True`.

## Memory, insights, and self-improvement

Durable memory is written by the memory pass, not by the archive. The pass is a chat of the app's own — an attended `bypass` turn in the per-workspace `Memory` system project, on the configured session-insights model (`ciao/web/memory_pass.py`; model chosen in Settings → Models) — and it does the vault work with its own tools instead of behind an extraction prompt: it reads the archived transcript, updates the note a person or a project already has, folds Decisions and open loops into that project's canonical doc, creates a note only for a genuinely new entity, promotes a durable fact to a region through the `ciao` CLI, and queues anything it is not sure about in `Workspace/Memory-Proposals.md`. One pass runs per workspace at a time, FIFO, because two turns writing the same vault notes would race. A turn the transcript marks as automated is not the user's, and the pass is told not to record it — extracting a maintenance session's own operating rules used to auto-promote the machinery's self-description into the bounded regions. Every queued bullet still names its destination (`[memory]`, `[profile]`, `[project]`, `[people: <Name>]`, `[learnings]`, `[review]`) and a time-bound fact still carries `[as-of:]`/`[expires:]` (design rationale: docs/MEMORY_DESIGN.md; retrieval eval: docs/MEMORY_EVAL.md).

Archiving a chat writes the markdown transcript, indexes it for search, and — when session insights is on and the archive has turns to read — queues a memory pass, a chat of the app's own that does all the vault work (the project-doc fold, region facts, people notes, learnings and proposals), so it can be resumed, inspected and steered like any other chat. The pass records its state on the archived chat as `postprocess` (`{steps: {memory_pass: {status, extra: {chat_id}}}, updated_at}`), published as the `chat_postprocess` event and persisted with the chat, so the archived chat can link to the pass that read it. On load only that step is kept; records from before the trajectory stage was removed also carried that pipeline's run state and manifest view.

Each session gets its bounded memory through the provider's native guide load, not an injected block: every chat, schedule, and subagent runs a CLI with `cwd` set to the workspace's agent root, so both read `<root>/AGENTS.md`, regions included. `core_prompt.py` injects only the compact Ciaobot core, and does not render `ciao:memory` or `ciao:profile` into a second prompt block. Caps are advisory (3000 chars for `ciao:memory`, 1375 for `ciao:profile`; `ciao/memory_tool.py`); `os_audit` reports over-cap, oversize, duplicate, and invisible-Unicode issues. Consolidating entries a region already holds is the one region write the unattended nightly curator does perform, and only once usage reaches ~85% of the cap: it merges duplicate and superseded entries, drops entries whose `[expires:]` date has passed, tightens wording, and moves project-scoped facts out to their owning doc. Three guardrails bound it: every removed or replaced entry is copied verbatim into `<vault>/Workspace/Memory-Consolidations.md` under a dated, region-named heading first, so nothing is lost and any line can be restored; a removal needing judgment is never made, and becomes a one-line `[review]` question in the proposals queue instead (dismissing it keeps the entry, dropping it takes an attended chat that edits the region and then dismisses the question — the queue itself cannot apply a drop); and a durable fact is never dropped merely to fit a cap. Promoting a NEW fact into a region is reviewable, not refused: the memory pass is an attended turn that can write one directly, an attended "remember" is explicit, and the unattended nightly curator never promotes a new region fact. A region still over cap after consolidation is reported for the user to act on — an attended chat consolidates further, or the region stays over its advisory cap. The agent edits the regions either with `Edit` or through the control-plane `memory_status` / `memory_update` operations, exposed as `ciao memory status` and `ciao memory update --region {memory,profile} --action {add,replace,remove}` (`ciao/agent_cli.py`). Reviewable proposals are filed (`ciao memory-proposal-add --kind memory --source <chat id> --text-file <fact-file>`, which the nightly curator uses when it finds a bounded-region fact in a transcript the pass never saw), then listed and dismissed from the CLI (`ciao memory-proposals`, `ciao memory-proposal-dismiss --text-file <file>`), which the nightly curation agent and the user share; promotion is an explicit region Edit first, then dismiss. A bounded entry tagged `[expires: YYYY-MM-DD]` remains active through that date. After it, the entry is deleted from the guide before the next turn: `ProviderService.execute_streaming` runs `prune_expired_entries` on the chat's agent-root guide before every turn and reconnects the provider when anything was removed, so a just-expired fact never stays in the native snapshot (daily curation drops them too). Curation removes only entries with valid, passed dates and reports malformed tags instead of guessing. `ciao/memory_proposals.py` is the accept-path half that outlived the deleted one-shot producer (#627): the memory pass, a chat of the app's own, writes memory directly, and what this module owns is everything a write goes through or a reviewer reaches — a person or the agent files a proposal by hand (`ciao memory-proposal-add`, `append_proposals`), the review surface lists and dismisses them, and a user accepts one into its destination (`accept_region_fact`, `reconcile_region_fact`). Accepting is a guarded write, not a plain append: the bullet goes through the `ciao.memory_audit` event-shape guard (only the "Durable rule:" clause or a bullet that passes it reaches a region), the entry gets a trailing learned-at `[YYYY-MM-DD]` stamp, and `fact_candidates` provenance is stamped beside it. `reconcile_region_fact` is the ADD/UPDATE/COVERED step on that path — one small model call compares the new fact against the region's current entries, so a changed fact replaces its predecessor (old text to the `Memory-Consolidations.md` undo log first) instead of accumulating beside its successor, and any failure degrades to the plain append. `memory-audit` reports entries whose `[as-of:]` or learned-at date has aged out, for the nightly curator to re-verify. People notes merge rather than overwrite, and learnings entries are structured (`- [key] [first → last] (xN) … — sources:`) so re-observation increments a count instead of duplicating. `[project]` facts are owned by the doc fold (`ciao/project_doc_update.py`): consumed ones are dropped, and facts the fold skipped stay queued addressed to their doc so a one-click accept can fold them later. There is no queueing heuristic left: the caller decides, and anything unsure or failed waits in `Workspace/Memory-Proposals.md` for human or curator promotion. Daily memory curation also appends durable learnings to the vault's `Workspace/Learnings.md`. Startup `ensure_regions` + legacy `~/.ciao/memory.md`/`user.md` migration folds old files into the regions once. Region contents are git-tracked with the workspace.

`provider_service.py` prunes valid expired entries from the guide before
provider startup, and the typed MCP `memory_status`/`memory_update` operations
write the same guide rather than maintaining a parallel store.

### Memory write policy matrix

Every path that can write durable memory, with its approval rule. The
machine-readable copy is `ciao/memory_policy.py`; tests pin this table and the
stock assets to it so they cannot drift apart again.

| Context | Destinations | Approval rule | Cap semantics | Undo |
| --- | --- | --- | --- | --- |
| Attended explicit remember | regions, project doc, people, learnings; `review` when unsure | Explicit user request may write live; otherwise queued | Advisory | — |
| Memory pass (post-archive) | regions, project doc, people, learnings; `review` when unsure | Attended pass writes live; an accept is a reviewer action; unattended transcript turns never lifted | Advisory | Replaced region entry → `Memory-Consolidations.md` |
| Unattended curation | existing region entries only (consolidation); queue for any new fact | Never promotes a new region fact; defers approval-requiring work | Advisory | Required before any removal/replacement |
| Direct edit / `memory_update` | regions | Human-controlled maintenance | Advisory (`over_cap` reported) | — |
| Proposal acceptance (PWA/CLI) | regions, people, learnings | Reviewer action | Advisory | Replaced region entry → undo log |

**Why curation is narrower than the memory pass.** The pass runs right after the
user's own conversation, so a fact it lifts is attributable to a turn the user
typed; the unattended curator runs nightly with no reviewer, so it only consolidates
the region's existing entries and queues everything new.
**Unattended runs defer; they do not route around the missing reviewer.** The
capsule marker (`ciao/context/capsule.py`, one string in
`ciao/memory_policy.py`) tells a schedule/automation turn not to ask or wait and
to report deferred work — a NEW region fact, a vault-note trash/delete, a
write into another workspace, a new automation in another workspace, and public
or destructive git actions — in its final output instead. The memory pass reads
the same marker in the transcript it is handed, and is told never to record a
fact out of an automation turn.

### Lesson routing contract

Where a reusable lesson goes, and what each route is allowed to do. A lesson is
the general case; the memory pass's skill-review section is one producer of
these routes, and so is `/remember` and the nightly care run.

| The lesson applies to… | Destination | What may happen |
| --- | --- | --- |
| A skill this workspace owns under `skills/` | a skill proposal (`ciao skill-proposal-add`) | a person accepts it, a helper edits the file, reads it back, verifies and syncs, and only then is it `applied` |
| A packaged, mirrored or shared skill | a `[review]` draft (`ciao skill-draft-add`) | a person approves the **sanitized** body; the attended approval searches for a matching issue and links it, or files one and records the URL |
| No skill at all | a `[review]` draft for a new skill | a person approves; the file is created under `skills/`, read back, checked and synced, and only then does the row settle |
| A project this workspace owns | that project's canonical vault note | the existing `[project]` accept |
| A cross-project preference or identity | the existing `[memory]`/`[profile]` proposal policy | the existing accept |
| A one-off episode | the event log | the existing pass behaviour |

Three rules hold across every row, and each is enforced in code rather than
asked for in a prompt.

**An inventory match is a candidate, not proof.** The filer must read the
target's current source and cite both why it applies and the actual observed
failure or correction. A finding whose target the conversation never loaded is
recorded through the structured `origins` link to the learning — never as a
`sources` entry or a `turn`, because those would claim a transcript demonstrated
something it did not. `ciao skill-proposal-add` therefore accepts a payload
carrying `origins` and no `sources`, and refuses one carrying neither.

**Nothing is promoted unattended.** An unattended run may prepare a draft and
report it; it may not edit a skill, edit `AGENTS.md`, settle a proposal, create a
skill, or open a public issue. The first three are stated in the Workspace care
schedule's ground rules and deferred-actions list; the last is already
`memory_policy.UNATTENDED_DEFERRED_ACTIONS` and is enforced by
`upstream_drafts.approve_draft(unattended=True)` raising. `x3+` recurrence is a
**routing priority**, not permission: the care schedule's old "promote an x3+
learning into the AGENTS.md body or the relevant skill/doc" instruction is gone.

**`/remember` keeps a real origin.** A `/remember` of a lesson usually happens in
a chat that is never archived, so there is no transcript turn to cite. The queue
bullet carries the user-request identifier instead (`ciao memory-proposal-add
--kind learnings --request ID`), the accepted line cites `req:<id>`, and the
learning model deduplicates on it — so a retry of the same `/remember` cannot
inflate a recurrence count. The alternative, manufacturing an archive, would be a
citation to a conversation that never happened. `source` and `request` are
separate fields because they are different facts: one names a transcript that can
be re-read, the other names a request.

**A filed upstream issue is not a deployed lesson.** `filed` on a draft means the
issue exists. The lesson is still not in any local skill, so nothing about the
local guidance changes and the learning stays Active until a local destination
is verified.

**Decisions behind this matrix (AI-01).** The policy is published as the
current behavior, not changed to match the older prose. Archive-time
auto-save was the default when this was written: confident, state-shaped
facts were applied at archive time, exactly as the code already did. That
default is gone with the one-shot pipeline (#627); the memory pass is the
post-archive writer now, and it runs attended. No "review everything" setting
is added — it would be new scope with its own migration, and the queue already
holds everything the guards reject. Because the default moved in code rather
than behind a setting, no migration is required. Making an uncertain or stale
reconciliation decision *queue* the competing fact rather than append it is a
separate behavior change tracked by AI-06 (#459); this document does not
reinterpret user consent that was given under the current defaults.

The server registers a Claude `PreToolUse` hook in `ciao/observability/hooks.py`.
It rewrites only Claude `Bash` calls with `run_in_background: true` to run in
the foreground. Runtime, workspace, project, and vault-entity context is built
once by `ciao/context/capsule.py` and prepended to the request for both supported
providers; a second Claude `UserPromptSubmit` injection is intentionally not
installed. Retrieval is driven by the system prompt (`vault_search` tool) rather
than a per-turn heuristic hint. The managed SDK CLI owns background shell
processes and stops them when the turn ends, while their terminal notification
is delayed until a later turn resumes the session. Keeping these calls in the
active turn makes the real shell result part of the same streamed response.

## Schedules and background automation

Schedule dispatch (`ciao/schedules.py`) runs cron-shaped jobs through the normal chat pipeline. One packaged routine is left and it is `per_workspace`: **Workspace care** retains the persisted base id `system-memory-curation`. Fan-out materializes `<base-id>@<workspace>` rows with independent enable and last-run state. The other packaged routine, **Skill reflection** (`system-skill-evolution`), was removed in #697; because the set is derived from the packaged file on every read, its persisted `<base>@<workspace>` rows retire by id and never by a name match, so a user-authored schedule is untouched. Workspace care carries its curation procedure directly in the packaged schedule prompt; it processes memory proposals and learnings every night, then uses `Workspace/Curation-Log.md`'s `last_full_pass` marker to run an overdue full pass even when the server missed Sunday. The full pass refreshes `INDEX.md`/`VOCABULARY.md`, reviews stale notes without unattended deletion, runs `os-audit --scope workspace`, and applies only safe structural repairs. Install-wide failures are not a weekly model schedule: startup triage and Automation surface failed jobs on every install, housekeeping surfaces upgrade actions, and development mode adds the verbose debug report. Proposal helper chats carry persisted proposal IDs and an archive policy; resolution helpers archive only after a clean idle turn and after every owned proposal is absent, while review/discussion helpers remain manual. User schedules live in `.runtime/schedules.json`; mutable packaged state lives in `.runtime/system_schedules_state.json`. Compare persisted and live system IDs through `system_base_id` because fan-out qualifies live IDs by workspace.

Sub-day recurrence is the `interval` frequency of the same primitive — what used to be a second one, in-chat loops. An interval entry carries `interval_minutes` (floor: 1) and fires that many minutes after its last dispatch rather than at a wall-clock slot, so it needs no `daily_time_utc`.

Bound to an existing chat via `web_chat_id`, an interval entry keeps everything the loop primitive guaranteed: each run uses the target chat's own model and mode (an empty `model` means "inherit", which `schedule_effective_routing` resolves at dispatch, and `prepare_schedule_chat` does not overwrite the chat's settings for these); overlap protection is skip-not-queue, so a run due while the chat still has a turn in flight is skipped and retried on the next ~20s tick with `last_status: "busy"` rather than queued; a target chat that was archived is forked and one that is gone is replaced inside the entry's own project, and only when no project resolves either is the entry disabled with `last_status: "missing-chat"`. Bound to a `web_project_id` instead, an interval entry opens a fresh chat per run with its own model and provider — the combination neither primitive offered before the merge.

A fixed-chat binding is the same dead-target hazard at any cadence, not just interval: dispatching into an archived chat resumes a reclaimed provider session and fails in under a second with a `stream error` that nothing user-visible ever reports (issue #407). `prepare_schedule_chat` therefore re-homes a chat-bound entry whose target is archived or missing at any frequency — fork the archived transcript, or open a fresh chat in the entry's project (primary binding, then `fallback_project_id`, then General) — and re-points `web_chat_id` at the replacement, exactly as the interval path already did. A dispatch failure is also stamped as `last_status: "error"` on the stored row, so the Automations sidebar flags the schedule for attention instead of leaving an endless string of invisible failed job records; the PWA detail view shows the status row for a wall-clock entry that carries one.

Every dispatch path stamps `last_status: "running"` before the turn starts and the dispatch pipeline writes the outcome back, because `last_triggered_on`/`last_dispatched_at` are stamped at dispatch and therefore cannot tell a served slot from one whose turn died mid-flight. Without that distinction an interrupted run (a server restart, a killed provider subprocess) marked the day as fired: `catch_up` skipped it, the Missed list excluded it, and the work was silently lost until the next occurrence — a week, for a weekly routine (issue #486). `run_failed_since` is the shared rule: a dispatch at or after the expected fire satisfies its slot only if the run it started did not fail. A failed run therefore reports as missed in the PWA, where "Run all" can recover it, and `catch_up` re-fires it on the next launch. Two bounds keep that from replaying work: only `"error"` qualifies — a completed run, and a `"skipped"` one still waiting on the user or the provider, are never re-dispatched — and `last_recovered_on` spends one automatic recovery per slot, so a run that keeps failing (or that takes the server down with it) leaves the entry flagged for the operator rather than dispatching again on every restart. An outcome is applied only to the dispatch that produced it. `last_dispatch_id` (`<slot-day>#<token>`, minted on the entry before the run starts and carried back by the entry snapshot the pipeline holds) is what makes that possible: `last_dispatched_at` and `last_status` are separate fields, so two non-interval dispatches that overlap — a manual "Run now" started shortly before the cron slot — used to pair the newer timestamp with whichever run happened to finish last, which hid an interrupted slot from catch-up in one completion order and retried an already-successful one in the other (issue #490). `stamp_run_outcome` splits the two things being recorded: `last_status` describes the entry's latest dispatch, so a superseded run's status is dropped rather than misattributed (its own result stays in the job-run log, which records the `dispatch_id`, and in its chat), while `last_completed_on` records the occurrence a completed run *served* whether or not a later dispatch replaced it — which is what stops a slot whose work is done being replayed because a second run for it failed. The occurrence is decided at dispatch and never re-derived at completion, so a run dispatched at 23:58 for the 23:55 slot belongs to that slot however long past midnight it streams; `last_triggered_on` already worked that way, and this composes with it. `reconcile_interrupted_runs` runs at the head of `catch_up` and converts a `"running"` stamp left by a previous process into `"error"`, which is how a hard kill is recognised; ownership is tracked by schedule id in memory, not by comparing timestamps, so the startup tick and the catch-up pass can race without a run this process just started ever being replayed. Both automatic paths are host-only: `tick()` and `catch_up()` return immediately when the startup writer gate says this machine is not the host — the one boot verdict from `ciao.legacy_node_state`, which is the whole gate now that node mode's routes can no longer rewrite the role under a running server — so a former client Mac neither dispatches slots nor rewrites run state (the catch-up guard sits ahead of `reconcile_interrupted_runs` for exactly that reason). Manual `dispatch_now` is deliberately not gated — "Run now", the MCP run tool, and the operator strip's "fire missed one-timers" are a person asking for a run on this machine, not an automation.

Two things interval entries deliberately do not participate in. `compute_last_expected_run` returns `None` for them, so they never report a missed run: their cadence is relative, and every skipped tick (a busy chat, a paused entry, a restart) would otherwise read as missed. And `catch_up()` skips them, so a restart resumes the cadence instead of replaying every interval that elapsed while the server was down. `last_status` is what reports their health instead.

There is one runtime flag, `enabled`, where loops had two (`running` now, `autostart` after a boot). The split existed so a loop could tick until the next restart and then be silently dead — the "model says running, loop isn't" failure — so it was collapsed rather than carried over. A legacy `.runtime/loops.json` is imported once on startup by `schedules.migrate_loops`, keeping each `loop-…` id as the `schedule_id` (deep links and recorded ids keep resolving) and mapping `autostart` to `enabled`; the file is then renamed `loops.json.migrated` with one log line. A loop's `web_project_id` becomes `fallback_project_id`, not `web_project_id`: on an interval entry that field is the primary binding and means "a fresh chat per run", which outranks `web_chat_id`, so carrying it across would change what the automation does — but it was the loop's re-home target when its fixed chat went away, and dropping it sent those runs to the workspace's General instead. `resolve_automation_project` therefore tries the primary binding, then `fallback_project_id`, then General, each step a weaker claim about where the user meant the run to land. The loop compatibility surface is fully retired: the `loops_list`/`loop`/`loop_action` MCP tools, their control-plane backing methods, the `GET/POST /api/loops`, `PATCH/DELETE /api/loops/{id}`, and `POST /api/loop-run/{id}` REST routes, and the `loops_changed` event are all gone. `schedule`/`schedule_action` and `schedules_changed` are the only automation surfaces.

Background command runs (`ciao/background.py`) are the third dispatch primitive, sitting between a plain `nohup` and a subagent: one command, no model in the loop, no tool access. A chat starts one with `background_run_start` and ends its turn; the run is launched with `asyncio.create_subprocess_exec` on an argv list (never a shell) in its own process session, its merged stdout/stderr streams into `.runtime/background/<run_id>.log` (trimmed at 2 MB, same threshold as `job_runs`), and the registry lives in `.runtime/background/state.json`. Completion is detected by awaiting the process, not by polling; the owning chat is then woken through the same coalescing window subagents use (`_background_wake_pending`, 5s), so a batch of scripts finishing together produces one turn carrying each run's status, exit code, log tail, and log path. A run belongs to exactly the chat that started it: `background_run_status` and `background_run_cancel` report a run owned by another chat as not found. `cwd` is confined to the workspace root, `env` cannot set loader hooks or Ciaobot's own session token, and the inherited environment is stripped of server credentials before the child sees it. Every finished run is also recorded as a `background_run` job so the Automation page shows it, and terminal runs are pruned with their logs after 7 days. Shutdown terminates every live run, so a graceful restart leaks nothing; a run left behind by a *crash* resolves at the next boot to `error` with its last-known PID and log path in the wake, rather than being killed blind — after a crash that PID may belong to something else.

Background automations are instrumented through `ciao/job_runs.py`: title generation, schedule dispatch, the memory pass, and startup/system tasks (vault index refresh, skills update, the five-minute memory backup, Google token health, the one-time legacy memory migration) each record one run (status, duration, model/provider, error) to `.runtime/job_runs.jsonl`. The debug report (`ciao/debug_report.py`) reads the grouped view, and the workspace audit checks the log files; jobs in `RETIRED_JOBS` (removed from the code, but still present in the never-expiring `job_runs_latest.json`) are left out.

`GET /api/agent-assets/audit` exposes `ciao.os_audit.run_os_audit()` to Settings. A successful response is the full report object: `status` (`healthy`, `needs_attention`, or `error`), `total_issues`, `total_errors`, `timestamp`, section objects for `setup_audit`, `vault_hygiene`, `skill_audit`, `rule_audit`, `memory_hygiene`, and `job_runs_audit`, plus the flattened `scan_errors` list. `error` means the scan was not reliable, not merely that actionable findings exist. An unexpected handler failure returns HTTP 500 with `{"error":"failed to run AI OS audit"}`.

Schedules carry an `archive_policy`: `manual` or `auto`. All schedules execute through the normal chat pipeline for permissions and transcripts. `auto` runs a post-run classifier and archives only when the user does not need to see the result; failed, permission-blocked, retrying, or useful runs stay visible.

**Automatic behavior.** Ciaobot automatically archives chat transcripts. When session insights is enabled, archiving a chat with a transcript to read enqueues a memory pass: an attended chat of the app's own, in the per-workspace `Memory` system project, on the configured session-insights model, which reads the archive and does the vault work itself (notes, the project doc, region facts, and the proposals queue for anything it is unsure about). One pass per workspace at a time, and a pass whose turn ends cleanly is auto-archived while one that does not is left open for the owner. Ciaobot also dispatches enabled schedules, records background-job telemetry, refreshes the vault index, updates configured skill mirrors, and backs up the device branch according to the startup/system automation configuration.

**Not automatic.** The memory pass records what it is confident about, but it will not lift a fact out of an unattended turn, and anything it is unsure about waits in the proposals queue instead; the unattended nightly curator never promotes a new region fact. A skill proposal is a draft under the vault's `Workspace/Skill-Proposals/`; Ciaobot does not apply those edits automatically. Scheduled chats still run through the normal provider pipeline and permission flow, and an unattended run defers and reports any approval-requiring action instead of seeking an alternate route. A schedule with `archive_policy: auto` is archived only when the post-run classifier says the result does not need user attention; failed, blocked, retrying, or useful runs remain visible. Routine-model choices do not change an active chat's selected provider/model.

## Providers

The set of runtime providers lives in one place: `ciao/provider_registry.py`. Each `ProviderDescriptor` carries the provider's id, its label forms, and dotted import paths for its factory, login command, system-skill listing, readiness probe, and CLI upgrade, plus its thinking levels, default model/bucket, and default-model settings attribute. Paths resolve lazily, so enumerating providers never imports an agent SDK. Everything that needs to list, label, validate, or probe providers reads the registry rather than repeating a provider-name literal, and `ciao/provider_service.py` resolves the factory and owns the live instance. Adding a provider is a descriptor plus an adapter.

Dispatch is provider-driven, not model-driven. Each chat and schedule carries an explicit provider and model. The two supported runtime providers are `claude`, which runs Claude Code / Claude Agent SDK against Anthropic, and `opencode`, which requires OpenCode 2.0.16+ and runs one `opencode serve` process per active chat on an ephemeral loopback port behind a per-process `OPENCODE_SERVER_PASSWORD`. A shared server would be cheaper, but Ciaobot scopes its control-plane MCP token per chat while OpenCode configures MCP at server scope, so per-chat processes keep that token scoped. Readiness reads the V2 server identity from `/api/info` and verifies the used operations against `/openapi.json`; retired V1 routes are never probed. Chat output uses the `/api/event` SSE stream. Per-session `agent`, `model`, and ordered `permissions` carry the mode mapping. Credential denies include both the resolved absolute runtime root and, when it is inside the session location, its V2 workspace-relative spelling. Prompts use V2's `text`/`files` body with queued delivery, so a mid-turn message remains a later turn. Because V2 has no stable per-prompt system field, Ciaobot's compact core/runtime context is carried in the same text behind `[CIAO_CONTEXT_BEGIN]` markers; transcript rendering and permission-rotation handovers strip those markers before showing or copying visible history. Flat V2 message records are normalized once at the provider boundary into the small `{info, parts}` representation used by transcript rendering and recovery. Active children come from `/api/session/active`; child discovery uses `/api/session?parentID=...`. Fork, interrupt, session-scoped permission replies, forms rendered as AskUserQuestion cards, and real child sessions are native. Native form fields retain their required/conditional/format/length/range/pattern metadata in the PWA; invalid non-empty values are blocked before the action is sent, while optional empty answers remain an explicit reply rather than a cancel. Delivery cards stay mounted until the provider result is acknowledged, and a disconnected chat socket queues a native response for the next connection. OpenCode is bring-your-own-provider: the model catalog joins active `/api/provider` rows with the flat `/api/model` snapshot, addresses models as `providerID/modelID`, exposes reasoning variants from each entry's V2 array, and reports no unified quota. It needs almost no asset projection because it discovers `.claude/skills`, `.agents/skills`, and `AGENTS.md` natively — only `.opencode/agents/`, `.opencode/commands/`, and the `mcp` object in `opencode.json` are generated.

Anything the two supported providers do not serve directly is reached through OpenCode, which is bring-your-own-provider: a user configures Ollama, OpenRouter, or any OpenAI-compatible endpoint in OpenCode itself, and Ciaobot lists whatever OpenCode reports as connected. Ciaobot previously reached those upstreams itself by injecting `ANTHROPIC_BASE_URL` into the Claude Code CLI; that layer is gone. The backend keeps provider routing explicit so schedules, handovers, and archived chats remain reproducible.

### Claude harness overrides

Ciaobot runs the vendors' CLIs but hides the harness surfaces the PWA already owns. In `ciao/execution_modes.py:24` nine skills are removed from the model's context via `skillOverrides` (`schedule`, `loop`, `design-sync`, `update-config`, `fewer-permission-prompts`, `doctor`, `run`, `run-skill-generator`, `dataviz`) and the same nine are denied as `Skill(name)` in `ciao/config.py:30`; `ciao/providers/claude.py:536` wires `settings={"skillOverrides": …}` with `setting_sources=["user","project","local"]` so workspace skills and agents still resolve. In the tool layer `ciao/config.py:30` also denies `EnterPlanMode`/`ExitPlanMode`, `DesignSync`, `NotebookEdit`, `CronCreate`/`CronDelete`/`CronList`, `ScheduleWakeup`, `PushNotification`, and `RemoteTrigger` — the PWA owns notifications, plan approval, and scheduling, so those CLI tools have no UI to render. Deny alone still lists the skill, so both levers are needed: overrides save context and hide the picker entry, denies block execution if re-enabled downstream. See [README — What we change from stock Claude Code](../README.md#what-we-change-from-stock-claude-code).

## Frontend

The installed PWA manifest offers app-icon shortcuts and an optional OS share
target. A multipart POST to `/share-target` is intercepted by the service
worker, which stages the text and files locally in IndexedDB; only an explicit
Home action adds them to a draft, and the engine never receives a share
automatically. Logout clears pending shares. The file viewer offers outbound
native Share where supported alongside Download. The worker caches only the
public same-origin app shell and static assets, never `/api/*` responses.

`web/` is a Vue 3 + Vite + Pinia + TypeScript PWA. The hierarchy is workspace → project → chat. Configured logical workspaces live in `CiaoConfig.workspaces` (loaded from `.runtime/workspaces.json`, the only source of the list, which Settings owns; a fresh install bootstraps it from the vault) and are exposed through `GET /api/workspaces`. Each workspace may set an optional `color` accent preset (`pink` default, plus `cyan` / `amber` / `emerald` / `violet`); the PWA applies it as accents only when that workspace is active. The Pinia project store loads that endpoint; the sidebar workspace switcher and empty-state General chat buttons render from the configured workspace list. Backend project discovery, completion, restore, schedule routing, spawned-agent `GWS_PROFILE`, and `CIAO_ACTIVE_WORKSPACE` also read from the workspace registry. The model picker has one section per provider: Anthropic (via Claude Code) and OpenCode.

The shell presents the same durable model everywhere: **request → run → output → durable knowledge**. Home uses the Workbench composition: `HomeIntake.vue` starts an ordinary project chat while keeping unsent text scoped to its workspace, and `HomeReviewSummary.vue` surfaces active-workspace proposals/upkeep/automation state and labels checking, stale, empty, and failed snapshots, sitting in a side rail beside the request column on wide panes and stacking below it under 980px; chat keeps reasoning in the transcript while a conditional Context / Activity / Output inspector exposes existing run and file state. Project remains the context envelope; Memory's To decide section (suggestions and notes to revisit, one page with a filter) is the durable-knowledge inbox and its Map (Graph/List) is the exploration mode. These are frontend compositions over existing stores and APIs, not new persisted object types. Shared schedule and retirement load contracts keep a pending or failed fetch from rendering as a successful empty list.

Memory (`/memory/<section>`, `MemoryMapView.vue`) has five sections — To decide, Map, Categories, Retired, History — listed in the sidebar the way Settings lists its tabs; each is a route, bare `/memory` returns to the section last visited, and the old `/proposals` address redirects to To decide. To decide (`/memory/review`) shows the proposal queue and the notes to revisit together, narrowed by `?show=suggested|revisit`. The Map section renders the active workspace's vault as a browsable graph: notes as nodes, `related:` frontmatter and relative markdown links as edges, from `GET /api/vault/graph`. It follows the same shell pattern as Schedules/Settings — a route pointing at `ChatLayout.vue`, which switches `viewMode` and renders the pane — rather than introducing a second app shell. The node/edge data itself is exactly what `ciao vault-index`'s `scan_vault()`/`_build_graph()` already compute for `INDEX.md` and `--neighbors`; the route only serializes that to JSON and optionally scopes it to one `?workspace=`. Each node also carries its verification age (`updated:` frontmatter or mtime) judged by the same staleness detector the audit uses, and the review queue's `unverified` signal uses the same rule (`memory_audit.note_verification`), so the map's "unchecked" count, the list view's Checked column, the note tile's callout and the notes to revisit cannot disagree with each other or with what daily curation acts on. Each node also carries the managed check state for its current revision (`check`), and a check that `_check_settles` says already answers the note **clears** the node's `stale` flag: a note somebody checked inside its cooldown is not "unchecked" however old its own `updated:` reads, and neither is one a proposal is waiting on. Without this the map flagged notes as needing review and linked onward to a queue that had deliberately stopped asking about them. The tile leads with the state that explains the flag's absence, in order: a pending proposal (with a link to it), then a recorded verdict with its coverage and retry date, then a conflicted proposal, and only then the stale callout. The check state is read once per vault target and a note's body is hashed only when it HAS a check, so a vault nobody has verified costs no extra reads on the map's hot path. The History tab's `GET /api/proposals/history` resolves each `note_edit` decision back to its filed record and ships it as a `note_edit` block — the note it is about, the exact before/after, the evidence the verdict rested on, how much of the note the check covered, and whether the decision is still open — because the decision sidecar keeps only the bullet's one line (that text is the dedupe key), and without the record a settled verification reads as an opaque sentence with a destination and nothing a reader could check it against. An accepted `replace`/`restamp` carries a `note_apply` receipt, so it gets the ordinary Undo; an accepted `retire` moved the note to the review trash and journalled no memory receipt, so it is reported as `reversible_by: restore` (Vault Review's restore) rather than as "no change snapshot available" — a different claim, beside a change that really happened. A still-open row is shown as still open, and a refused accept (a conflict) leaves no receipt and is never rendered as an applied change.

The map has two surfaces with parity of action. The graph canvas is driven by Pointer Events through `web/src/lib/graphGesture.ts` (unit-tested without a DOM): one pointer owns a gesture, tap slop separates a tap from a drag, `pointercancel`/`lostpointercapture` abandon it, and a second or non-primary pointer is refused — so a touch tap selects, a drag pans, and a cancelled or extra-finger gesture never activates an unintended note. `touch-action: none` is scoped to the canvas so page scroll and browser zoom stay available everywhere else. The list view is the keyboard/touch-complete alternative: each note title is a native named button, and closing the note restores focus to the control that opened it. A selected note opens in a docked tile — `PinnedFilePanel`, the same component a chat's pinned file uses, with the map's stale-note callout and linked notes in its `lead`/`after` slots — and at 900px and below that tile becomes a focus-contained bottom sheet. There is no path finder: selecting a note highlights its neighbours, which is the connection question the map answers.

Primary navigation uses native button/link semantics with visible keyboard focus, and mobile controls keep a 44px minimum target on every coarse-pointer layout. Browser zoom remains enabled; Settings font scaling is an additional preference rather than a replacement for platform accessibility controls. Tab bars are a shared `TabBar` component carrying the ARIA tablist contract — a single Tab stop with Left/Right/Home/End moving between tabs and selection following focus — so the behaviour cannot be dropped by copying the markup, which is how the memory-map review bar first shipped without it. Modal-like surfaces use `useModalFocus.ts` for initial focus, Tab containment, Escape capture before global shortcuts, inert background content, and opener restoration; native button semantics determine Enter, so a visible Cancel target can never confirm a destructive dialog. Context menus use menu/menuitem roles, focus their first action, support Arrow/Home/End/Escape, and return focus to the trigger. In ChatLayout, unmodified number keys `1`–`9` switch to the corresponding workspace in the sidebar's displayed order; the shortcut is ignored while typing and the workspace buttons show their assigned key. On the home screen, Needs You, Working, Unread, and Earlier are the authoritative lane order; arrow navigation follows the rendered lane layout: stacked workspace lanes use up/down between lanes and left/right within a lane, while side-by-side lanes use the corresponding horizontal/vertical mapping. The sidebar independently discloses each chat's running subagents inside an expanded project, while opening a subagent's read-only view reopens its parent group. Automation details preserve their title on narrow screens by moving secondary actions into an overflow menu, collapse long prompt previews, and explain stale project/chat targets without exposing raw runtime IDs.

Each workspace has a "General" project plus auto-discovered projects from its configured `vault_root/projects/active/`. Chats stream over WebSocket; image uploads and pending comments are scoped to the active chat, then attached to that chat's next prompt. Closing an unused new chat deletes its server-side draft; closing a completed chat disconnects it. A non-image file dropped into a chat is uploaded through the chat attachment contract and inserts a bounded opaque reference; the provider-only prompt expansion resolves the server-side path. Pinned files are scoped per-chat (persisted in local storage, falling back to project scope if no active chat exists) and render in a split layout sidebar. Commenting in that sidebar stays open while a turn streams — the comment simply rides on the next message — and the panel's auto-reload at turn end is deferred while a text edit or comment draft is open, then applied once the user saves or cancels.

**One engine, one origin, one browser.** Multi-device node mode is gone. There
is no host/client role, no standby proxy, no second loopback origin, and no
local-control capability: a browser either talks to the engine it reached over
one origin, or it does not. `/api/*` needs the signed session cookie (with the
same small public allowlist as before), every `/ws/*` handshake is checked for
same-origin and then for the session, and every state-changing `/api/*` request
must present a matching `Origin`/`Referer` — the general guards, unchanged.
`/api/desktop-drop` is a normal session-protected route again rather than a
local-control one, and Finder drop events still carry only an opaque grant and
bounded display names; absolute paths stay in the server-side grant. A second
device installs its own engine and opens `/api/addresses` to find this one.

There are no native commands left to grant: the macOS shell is retired (`#656`),
so a page served from the engine origin has no capability surface at all. This is the
direct browser/engine trust model that replaced the retired client-origin
model: `docs/REMOTE_BOUNDARY.md` records what it is, and it is still not
completion of the broader credential, file-confinement, or storage-isolation
work tracked by #546.

Write/Edit/MultiEdit/NotebookEdit tool calls are tagged with `file_touch` by
`ciao/web/chat_broker.py` and surface as standalone `_filecard` entries on
reload, rendered as inline clickable preview cards that open `FileViewerModal`
(see `PWA_API.md` → "File-touch cards" for the WS + `/messages` contract). On
every file-touch event the broker also schedules a debounced content snapshot
via `ProjectChatManager.snapshots` (`ciao/web/file_snapshots.py`,
`SnapshotStore`), which writes append-only per-(chat, file) copies under
`.runtime/snapshots/<chat_id>/<urlencoded_path>/NNNN.snap` plus a sibling
`meta.json`. The PWA reads these back via `/api/file-history`,
`/api/file-content`, and `/api/file-restore` to power the FileViewerModal's
Preview / History / Diff tabs and one-click restore; `/api/vault/backlinks`
lists the notes linking to a markdown note, using the same relative/path/stem
link resolution as the preview, but the modal has no Backlinks tab that calls
it. Preview renders text/markdown, images, PDF/PPTX (via a binary preview), and
HTML artifacts; diagrams live inside HTML artifacts as inline SVG. History/Diff
remain text-snapshot based. An in-modal Edit mode posts user-edited text content
via `POST /api/workspace-file`, which captures a `tool="PWAEdit"` snapshot, and
guards dirty edits against close, reload, or opening another file. Snapshots are
wiped on chat delete and preserved on archive.

Archived chats are read-only but can be continued into a new active chat via the "Continue in new chat" button (calling `POST /api/chats/{chat_id}/continue`). A header "files touched" chip in `ChatPanel.vue` summarizes the dedupped set of files written/edited in the chat and links each entry back to the modal.

Background subagents (Agent tool dispatches with `run_in_background`) stay visible after the parent turn ends. Unlike background Bash, Agent calls are not rewritten by the foreground Bash hook. `ciao/subagent_tracking.py` parses the parent session JSONL for async dispatches and their `<task-notification>` completions; a per-chat watcher in `ProjectChatManager` publishes `chat_subagents_ready {remaining}` on `/ws/events` whenever the running count changes (the connect snapshot carries `background_agents` so reloads heal stale counts). While agents run, the PWA shows a pulsing "N agents" pill in the chat header and a dimmed sidebar dot, polls `/api/chats/{id}/subagents` for a near-live feed, and renders each transcript in a `SubagentPanel` anchored under the dispatching turn via the server-computed `turn_index`. Between turns the manager also drains the idle SDK stream (`ClaudeProvider.drain_events`): when a finished agent triggers a CLI-initiated parent follow-up turn, its events are forwarded live on a background `ChatStream` and announced like a normal result. Without the drain, those buffered messages would silently corrupt the next turn's `receive_response()`. The parser also records CLI-owned tasks (Monitor, background Bash, workflow launches) with `kind="task"` from their `toolUseResult.taskId`; they stay out of the agent counts and sidebar rows, and the same watcher delivers one wake turn via `_deliver_wake` when the owning CLI process is gone while such a task is still running, so a dead CLI can no longer orphan a long-lived command silently. On startup `sweep_orphaned_cli_tasks` wakes chats whose tasks were running when the server died (bounded to chats active within the last 7 days so the first upgrade does not wake months-old Monitors), and the wake prompt itself marks those tasks `lost` in the JSONL so it is sent once.

Subagents a chat spawns (`Agent`/`Task` dispatches) are surfaced as sidebar rows beneath the chat, and each row opens a read-only view of that agent's own conversation. `GET /api/subagents/running` returns dispatch metadata only — no transcripts — and only for the chats `ProjectChatManager.active_chat_ids()` already considers active, so the sidebar costs one JSONL parse per working chat rather than one per registry row; `subagent_tracking.running_agents` names the rows behind that count, with the same transcript-idle fallback, so a parent turn killed mid-dispatch cannot leave a row pinned forever. The rows are what the parent session can name: an agent enters its state only when the `tool_result` carrying the `agentId` lands, which for a background dispatch is the launch receipt but for a foreground Task is its completion — so a running foreground agent is invisible there by construction, and shows in the chat's own live trace instead (its turn is still streaming). The PWA polls it only while something is working and replaces the map wholesale, which is how a finished agent's row disappears. A row (and the `SubagentPanel` header inside the Activity trace) links to `/chat/{chat_id}/subagent/{agent_id}` — `SubagentChatView.vue`, fed by `GET /api/chats/{id}/subagents`. The view is read-only because a Claude Code subagent is a transcript file, not a resumable session: the composer is disabled rather than removed, and Esc returns to the parent chat instead of closing it. Nothing is archived when an agent finishes — the completed transcript stays in the chat's Activity trace.

Settings tabs (sidebar labels): Home (deploy, the notifications card, the session-insights switch, theme and font scaling, local session, PWA password, workspace health, package updates, a dev-mode Debug card, and the "Other devices" address card), Models (per-provider default model and thinking for new chats, plus title/insights/critique model pickers, visible main workspace/vault roots, read/written via `GET`/`PATCH /api/settings/routines`, persisted in `.runtime/app_settings.json` by `ciao/app_settings.py` and overlaid on the live config without a restart), Providers (Claude Code/OpenCode CLI authentication; no API keys to enter; per-provider default model, permission mode (manual/auto/bypass), and thinking for new chats), Workspaces (logical workspace registry plus the Google Workspace / `gws` install, OAuth, and profile cards), Skills (route `/settings/skills`: expandable skill inventory with Claude/OpenCode install badges), Subagents (route `/settings/subagents`: expandable subagent and slash-command inventory with create/edit/delete), and MCP (route `/settings/mcp`: creates/updates/deletes project entries in `.mcp.json`, writes env-key secrets into `.env`, and probes tools). ALL FOUR of those tabs are scoped to the workspace selected in the sidebar: they send `workspace` on every read and write, and the backend resolves it through `ciao.workspaces.agent_root_for` so the list and the edit behind each row name the SAME agent root. Reads degrade (they fall back to the whole install, and an unregistered name is not an error), but a WRITE that omits or misnames the workspace is a 400: redirecting it to the install root would file the asset somewhere the user did not ask for, and a delete would remove a different workspace's file. The MCP candidate list deliberately matches what the runtime reads — a workspace's own `.mcp.json` first, then the shared install-root files — because the panel previously read only the shared file and so disagreed with the agent about which servers a workspace could reach. Stock skills are unaffected by the scoping: `sync-skills` installs them into every agent root. `GET /api/agent-assets` surfaces the subagent and slash-command inventory with provider/workspace metadata plus workspace health (health stays install-wide; it reports the machine's roots, not one catalog). `POST /api/agent-assets/subagents` and `POST /api/agent-assets/commands` create workspace-owned assets under `subagents/` or `commands/`, mirror a note into that workspace's `memory-vault/Workspace/`, and sync Claude `.claude/` links plus OpenCode-native `.opencode/` assets.

Unsent composer text is cached in browser-local storage by chat id. Switching chats
or reloading the PWA restores each chat's draft on that device; dispatching the
message clears only that chat's cached draft.

`ChatPanel.vue` is being decomposed in behaviour-preserving steps, and the
boundary is stated rather than implied. `composables/useChatComposer.ts` owns
the composer: the draft ref and its synchronous persistence, prompt-history
recall, textarea auto-sizing, caret insertion, and every attachment path
(paste, drag-drop, the native desktop drop grant, the image picker). It takes
no store and no lifecycle hooks — the ids it needs arrive as getters and the
store methods it calls arrive as one small interface — so composer behaviour is
testable without mounting the panel. `ChatTurnActivity.vue` owns the rendering
of one *completed* turn's `Activity` disclosure; it holds no state at all, and
reports every action (toggle, body click, open file, expand a lazy reasoning
step) as an emit. `ChatPanel` keeps what genuinely spans the pane: the send
path, the slash-command and @-mention pickers, the open/closed trace map, the
memoised markdown renderer, scroll anchoring, and the live (streaming) trace.
Trace styling lives in `components/chatTrace.css`, pulled into both components
through `<style scoped src>`, because a parent's scoped rules do not reach a
child's subtree.

`SettingsView.vue` is being decomposed the same way, one settings surface at a
time, into `components/settings/`. The MCP tab is the first: `composables/
useMcpServers.ts` owns every MCP ref (status, per-server edit drafts, the
expansion map, secret inputs, tool probes, the add form) and every `/api/mcp/*`
call, taking its API client, its two notify callbacks and its delete
confirmation as options so it imports no store, no router and no lifecycle
hook. `components/settings/SettingsMcpServers.vue` owns only the markup: it
receives that controller as one prop and emits `create-via-chat`, because
creating a chat and navigating needs the project store and the router, which
stay in `SettingsView`. `SettingsView` also keeps the decision of *when* MCP
data loads — its `onMounted` calls `fetchStatus()` and `fetchUsage()` for every
tab, as before, so opening a different tab still issues the same requests.
`/api/mcp/usage` is fetched although nothing renders it: the operator reads
that endpoint by hand to decide which MCP tools to prune. Shared settings
styling lives in `components/settings/settingsPanels.css`, pulled into both
`SettingsView` and the panel with `<style scoped src>`; the rules are in their
original order and the shared block loads first, so the cascade is unchanged.
Origin badges for skills, subagents, commands and MCP servers come from the
Vue-free `lib/assetOrigin.ts`.

When a chat reply, approval request, or model question needs the user's attention, `PushManager` sends its payload to every Web Push subscription; each device opts in on its own in Settings. A chat read mutation appends a clear control and sends it to every Web Push subscription; service workers close the matching notification tag, and unread state is derived from `.runtime/web_projects.json`. A deliberate "mark unread" (`POST /api/chats/{id}/unread`, `ProjectChatManager.mark_unread`) clears `last_read_at` so the chat is unread again on every device and publishes a `chat_unread` event; opening the chat or sending a turn marks it read through the normal paths.

Rendered markdown is sanitized through the shared frontend renderer before any `v-html` use. Keep new markdown surfaces on that helper. Chat tables render inside their own keyboard-focusable horizontal viewport: compact tables shrink to their contents, while wide tables scroll without widening the conversation or collapsing key columns. Fenced code blocks are wrapped by the chat renderer with a copy button (`web/src/lib/codeCopy.ts`) that copies the block's raw text; because chat markdown is injected with `v-html` and rebuilt on every streamed token, the button is plain markup driven by one delegated click listener on the chat panel, and it stays dimmed-but-visible rather than hover-only. Completed chat traces render as compact `Activity` disclosures; deduplicated file touches move to an `Outputs` group below the final answer, while interrupted turns retain them inside the trace. The build outputs to `ciao/web/static/` so the same Starlette server hosts both the API and the PWA.

Workspace HTML artifacts are rendered in a sandboxed frame with no network or session access. Their CSP permits only inline code and `data:` images, fonts, audio, and video; `blob:` media and external requests remain blocked so self-contained artifacts stay offline.

## Workspace git sync

Every instance is identical (no primary/secondary, no cloud). Sync and the memory backup operate on the repo containing the vault root (`ciao/local_session.py::sync_root`): with the default layout (vault inside the workspace) that resolves to the workspace repo; a vault that lives elsewhere in its own repo is synced there instead, and a missing/non-git vault falls back to the workspace root. Ciaobot never creates or switches local branches: it works on whatever branch that checkout is currently on (`ciao/local_session.py::workspace_branch`). Roots that are not git repositories or have no `origin` remote report `not_configured` and are re-checked every tick, so adding a remote while the engine runs is enough (a fresh `ciao setup` initializes local repos, but they have no remote until the user adds one).

**Sync flow** (`ciao/local_session.py`, `LocalSessionManager`). When the user clicks "Sync with Remote" in Settings, `POST /api/local/handback` commits pending work, pulls from origin (merge-based), and pushes the current branch. Workspace sync never requests app deploy; app updates happen through package upgrades. A **conflicting pull** is left in the tree and `POST /api/handover/merge` opens an **interactive chat** in the personal `General` project: the chat's agent resolves the conflicts, asking the user via `AskUserQuestion` (push-notified) when ambiguous, then pushes the branch (it does not redeploy). After that chat lands, `POST /api/local/resync` merges `origin/<branch>` into the checkout after committing any pending work (fast-forwarding in the normal case). It merges rather than force-resetting, so it works on the live workspace's dirty tree and never discards local commits. See `PWA_API.md` → "Workspace git sync".

**One mutation at a time** (`ciao/git_mutation.py`, #674). Every public git mutation — `commit_pending`, `push_branch`, `push_backup_ref`, `sync_branch`, `resync_branch`, the manager methods driving them, and the admin snapshot route — runs inside `repository_mutation`, a task-reentrant lock keyed by the repository's canonical top level. Manual sync, the conflict resync, the five-minute memory backup and admin snapshots therefore never interleave git commands in one checkout (and a workspace root, a vault root in its own repo, and any subdirectory of either share one lock), while two unrelated repositories stay concurrent. Branch detection in `LocalSessionManager` runs inside that lock, so a sync cannot commit to a branch it has already stopped being on. Holding the lock means holding it until git has actually exited: a cancelled writer waits out its in-flight step, because `asyncio.to_thread` cannot stop a running thread and releasing on cancellation would hand the checkout to the next writer while the abandoned process is still writing the same index (the admin snapshot route does this in `_snapshot_git`). Two rules come with it: a failed git step is never reported as success (`commit_pending` raises `GitOperationError(step, detail)`; sync/resync/push convert it into the failure result they already return, and the admin snapshot route returns an error for failed status or commit without pushing after a failed commit), and a git operation Ciaobot did not start is respected rather than removed — a preexisting `.git/index.lock` or an in-progress merge/rebase makes the mutation report a failure, and the file is left for its owner. A merge Ciaobot *did* start is exempt: the check happens at the outer entry, before the body runs.

**Memory backup** (`ciao/backup_service.py`, #689). Every five minutes the engine commits the durable-data scope of the same repository the sync flow targets and pushes what is not on the remote yet. It replaces a push-only 30s loop that decided once at startup whether there was a repository and an `origin` (so an install configured later never backed up anything until a restart) and that pushed whatever branch it found without committing anything (so on a plain data repository the notes were never in a commit at all). What changed, in the terms the status reports: readiness is re-evaluated every tick, so `not_configured` becomes `ready` without a restart; the commit is `commit_scoped` over `backup_scope`, so an unattended run can only ever commit `memory-vault/`, `skills/`, `subagents/`, `commands/`, the `AGENTS.md` guide and archived workspaces — never a credential, a cache, the transcript archive or application source; a run with nothing pending and nothing unpushed creates nothing at all, while unpushed existing commits are still uploaded; and a failed push keeps the local commit exactly where it is (no reset, no force-push, no discarded work) and reports `offline` or `needs_attention` instead of claiming a backup that did not happen. The interval is the named constant `BACKUP_INTERVAL_S = 300` — not an env var and not a setting — with a bounded backoff (×12, an hour) for a failure that cannot self-heal at that cadence, an overdue-resume on the first tick, and a `paused` gate that reads the durable `enabled`/`paused` flags on every tick so a pause survives a restart and a resume takes effect on the next one. A Mac that is not the host (the `legacy_node_state` verdict, the same one the scheduler asks) never runs it, and says so in its status. A coverage gap is reported on its own field rather than through a state: `BackupStatus.coverage_gap` counts the tracked paths the scope refuses, the run's `extra` carries it so the Automation row can show a partly covered repository without a red error, and a landed run through a gap is `ready` — a permanent property of a repository that is also a checkout is not a fault of a run, and `needs_attention` stays reserved for the three failures only the owner can fix (#733). `GET`/`PATCH /api/local/backup` and `POST /api/local/backup/run` expose the status, the owner's switch and a manual run; the manual run is the same serialized call the loop makes, so the two cannot overlap. An install with no remote is reached through one canonical setup prompt rather than through Git instructions: `GET /api/local/backup/setup-prompt` returns it with the trusted context it was rendered from, and `POST /api/local/backup/setup-chat` sends that same text into a chat in the host workspace — sending, not drafting, and idempotent, because a repeated click or a retry re-enters the live setup chat (found by its stable title) instead of putting a second agent on the same repository. Readiness stays where it already was: re-derived from the repository on every tick and every status read, so an external agent's setup is detected with no restart, and a guided setup that verifies turns the backup on unless the owner has paused it. No new state store, no new loop, no new env var. See `PWA_API.md` → "Unattended memory backup".

## Package updates and setup

**App updates.** Workspace git handback never implies a deploy. `GET /api/package/status` reports `ciao.__version__` and a best-effort latest version from GitHub. A production macOS install is the engine alone: the one-line installer verifies the signed engine manifest and replaces the engine, then restarts the LaunchAgent. `POST /api/package/update` is retained as a diagnostic response that points users to the one-line installer; it does not invoke Homebrew, PyPI, or `pip`. Editable git checkouts still use `git pull`.

**Setup readiness.** When `PWA_AUTH_TOKEN` is absent, Ciaobot starts in bootstrap mode using `~/.ciao/bootstrap` (or `CIAO_BOOTSTRAP_WORKSPACE`) and persists a generated temporary auth token under that workspace's `.runtime/`. `GET /api/setup-status` is public like startup status, because the first-run wizard needs it before a normal session exists. It reports workspace/vault/token/push-contact checks plus Claude Code and OpenCode readiness probes, without returning secret values. The local first-launch URL `/?setup=<token>` redeems `.runtime/setup-token` on localhost only, sets the signed PWA session cookie, deletes the one-time token, and redirects to `/`. The wizard finishes with `POST /api/setup/finish`, which is bootstrap-only and localhost-only: `workspace` is required (the wizard's primary folder question), `password` is required (the wizard asks for it in the main flow and setup always writes `PWA_AUTH_REQUIRED=true`; the inherited bootstrap token is machine-generated and unusable from a second device), the chosen provider is persisted on the first logical workspace, and `vault_root` is optional, defaulting to `<workspace>/memory-vault`. It writes the real workspace `.env`, scaffolds the configured vault root and provider asset catalogs, ensures workspace and vault are (in) git repositories with their protective `.gitignore`s (see "Workspace layout"), creates the server LaunchAgent, then requests the normal restart exit so launchd can relaunch into the real workspace. There is no native shell: the engine runs under launchd and the PWA at localhost is the whole surface. The retired rumps tray and the generated `Ciaobot Server.app` launcher it lived in are gone, and the macOS app itself is retired (`#579`); setup removes both, plus the `com.ciao.menubar` LaunchAgent, from installs upgrading from an older version. A foreground `ciao run` supervises the restart exit itself: when the server exits with the restart code, the CLI re-execs a fresh `ciao run` (picking up newly installed code) instead of dying.

## Project naming convention

Every configured workspace uses the same shape: a project is a folder under `<workspace.vault_root>/projects/active/<name>/` with a same-named main doc `<name>/<name>.md` (or `README.md`). On completion it moves to `<workspace.vault_root>/projects/completed/<name>/` via the PWA's "Complete" button (or `complete_project()`).

Completed projects can be restored. The sidebar footer has an archive icon next to "+ New Project" that opens a modal listing the current workspace's completed projects (`ProjectChatManager.list_completed_projects()` scans the `projects/completed/` tree read-only). Each entry has a Restore button: `restore_project(workspace, stem)` moves the folder back to `projects/active/`, flips frontmatter `status: completed` back to `active`, and re-runs auto-discovery to recreate the PWA project. Auto-discovery derives a stable id from the workspace and folder slug; the original chats stay archived. Routes: `GET /api/projects/completed` (optional `?workspace=`) and `POST /api/projects/completed/restore` (see `PWA_API.md`).

Workspaces are archived the same way rather than deleted (`ciao/workspace_archive.py`). Settings → Workspaces → Archive removes the workspace from the registry — so the sidebar, pickers, per-workspace system routines (Workspace care), skill sync, vault scans, the Memory Map, vault review and the proposals queue all stop seeing it, since each enumerates the registry — and moves its folder intact to `<install>/.archived-workspaces/<name>-<YYYYMMDD-HHMMSS>/`. Before the move, its projects are removed through the same `_remove_project` path `complete_project` uses (open chats are transcript-archived, then removed), and its user schedules (matched by `workspace`, target project or target chat) are taken out of `.runtime/schedules.json` into the archive's `archive.json`. After it, its rows leave the search index and, on a shared-vault install, `INDEX.md` is rebuilt so it stops listing its notes. Nothing is merged into another workspace. A workspace with a running chat is refused, as are the primary and the last workspace. The Archived workspaces list under the workspace cards restores one: the folder moves back, the registry entry and schedules return, and discovery recreates its projects; old chats stay archived.

- **Folder name** is the slug used internally (`vault_folder`). Lowercase + kebab-case is preferred but not enforced; spaces, mixed case, and underscores all work. Avoid path separators and leading dots.
- **PWA display name** comes from frontmatter `name:` (or `title:` if `name:` is absent), so it can be any human-friendly string with spaces (e.g. `name: AI Championship Project`). If both are missing, the folder name is used as the label.
- **Project context** — the blurb injected into every user turn as `[Project context: ...]` — is frontmatter `description:`, and the doc is its source of truth. The two are kept in sync both ways: `update_project()` writes an edit made in the PWA back into `description:` (`_set_frontmatter_description` rewrites that key surgically, leaving the rest of the file byte-for-byte), and every auto-discovery pass re-reads the doc so an edit made by hand — or by the memory pass's doc fold in `project_doc_update.py` — reaches the preamble. Discovery reads are memoised on the doc's `(mtime, size)` because it runs on every `list_projects()` call. An empty `description:` never clears a context the registry already holds; the next save pushes it into the file. The one exception to doc-wins is the first bind, when a manually-created project adopts a matching vault folder: a context typed in the PWA before the folder existed survives and is written into the doc instead, since the README it is adopting was most likely scaffolded. Only the *path* of the doc is injected alongside it (`[Canonical doc: ...]`), so the body stays out of the per-turn token cost and the agent opens it on demand.
- Top-level reference docs that live directly under `projects/` never "complete"; don't put real projects there.
- A stray `projects/active/<Name>.md` at the top level gets auto-promoted to `<Name>/<Name>.md` on the next server start, so the folder+file invariant always holds.
- Every workspace has an auto-created `General` project bound to `projects/active/general/`. It is marked `is_auto` and displays the "auto" chip in the sidebar. It's where ad-hoc chats land and where scheduled automations run; don't delete it.
