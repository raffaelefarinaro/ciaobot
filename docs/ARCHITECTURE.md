# Ciaobot Architecture

Orientation doc for the codebase. Read this before making any change in `ciao/`, `web/`, `scripts/`, or `deploy/`. After a change that affects layout, capabilities, env vars, endpoints, or commands, update this file, `docs/DEVELOPMENT.md`, and `INTEGRATIONS.md` so they match the repo.

## App repo layout

```
README.md                      Product intro, quickstart, doc index.
AGENTS.md                      Contributor guide for coding agents. Native providers load it at session start (Claude Code reads it directly since 2.1.277).
INTEGRATIONS.md                Operator config (env vars, OAuth, MCP connectors, server runtime knobs).
PWA_API.md                     PWA API reference (endpoints, auth flow, state path).
CONTRIBUTING.md                Contribution guide.
docs/                          Long-form docs (this file, DEVELOPMENT.md).

ciao/                          Python backend (Starlette).
  main.py                      Web server entry point, route wiring, startup hooks.
  cli.py                       Packaged `ciao` CLI: run, setup, setup-url, dev, auth, scaffold, sync-skills, skills-sync, skills, critique, vault-index, vault-search, vault-lint, os-audit, memory-audit, label-hygiene, cleanup-sdk-blobs, create-chat, eval, public-preflight, package-smoke, prepare-release, health, desktop, and desktop-service commands.
  setup_status.py              Bootstrap/setup readiness API and wizard finish handler.
  dev.py                       Local dev runner: backend on :8543 plus Vite frontend on :5173. CLI: `ciao dev`.
  config.py                    Env var loading, workspace config.
  providers/                   Claude Agent SDK, opencode HTTP server, and routing helpers.
    stdio_rpc.py               Async JSON-lines RPC process transport used by CLI app-server adapters.
    opencode.py                OpenCode 2.0.16+ provider over per-chat `opencode serve` (ephemeral loopback port, scoped MCP token, V2 OpenAPI fail-closed readiness, flat-message normalization, queued mid-turn delivery).
    oneshot.py                 Single-turn provider call (max_turns=1, no tools). Used by critique.py and routine-model automations.
  context/                     Provider-neutral per-turn context capsule (workspace, project, vault hints).
  observability/               Hooks: PreToolUse keeps Claude Bash jobs in the active turn. Runtime/entity context is built once in the request capsule.
  schedules.py                 Cron-style schedule dispatch.
  agent_cli.py                 `ciao <noun> <verb>` agent commands (`memory`, `vault`, `file`, `chat`, `project`, `schedule`, `run start|status|cancel`, `gws status`, `workspace list`, `context`, `help`): argparse to `(operation, arguments)`, POST to `CIAO_AGENT_URL/<op>` with `CIAO_AGENT_TOKEN`, one JSON envelope on stdout, exit 0/1/2. `is_agent_invocation` decides which argv `ciao.cli.main` hands over before the operator parser is built (`ciao run` alone stays the server launcher, `ciao gws <profile> …` the passthrough).
  agent_surface.py             Agent CLI transport behind `POST /agent/v1/{op}` (route in ciao/web/routes_agent.py): verifies the bearer token with the agent session registry, then runs the shared operation function inside the same auth context, so guards, envelope, validation and telemetry are shared; records `surface: "cli"`.
  background.py                Background command runs: one command per run in a tracked subprocess (`create_subprocess_exec`, never a shell), output to a rotating `.runtime/background/<run_id>.log`, registry in `.runtime/background/state.json`. Backs the `background_run_*` MCP tools; completions wake the owning chat through `ProjectChatManager`.
  dag.py                       Tiny DAG runner (Node kinds: bash / prompt / gate / subagent / retention; edges: ok / fail / always). Subprocess nodes can merge per-node env overrides for routed models. Subagent nodes accept an opt-in `requires` post-condition list (file paths, optionally with a `contains` line regex): exit 0 without the required files is a node failure, not a silent success. Each node is timed via `job_runs.track_sync`, so Automation page shows per-node status. Used by skill evolution and workspace-owned DAG workflows.
  sessions.py                  Session state, auth, signed cookies, JSON-backed StateStore for `.runtime/state.json`.
  jsonio.py                    Small JSON I/O helpers.
  transcripts.py               Provider-neutral live transcripts and archives under memory-vault/Logs/Chats/.
  native_sessions.py           Read-only detection of locally-running Claude Code CLI sessions (mtime-cached JSONL scan + pid liveness) for the handover warning.
  upgrade.py                   Packaged skill install/update helpers used at boot. Production app updates go through the Tauri updater/installer, not this module. External-package installs (LibreOffice, gws) are deliberately not automated here: the app surfaces status and an install-prompt chat, never a brew/npm call (issue #359).
  app_settings.py              Runtime-mutable app settings (automatic session insights and trajectory capture, title/insights/critique models, per-provider default model/thinking/permission-mode and routine models), persisted at `.runtime/app_settings.json` and overlaid on CiaoConfig. One-time `CIAO_INSIGHTS_DISABLED` and `CIAO_TRAJECTORIES_DISABLED` migrations write the privacy switches before the retired env values are ignored. Edited via Settings → Models & providers.
  error_log.py                 Rotating file handler for server ERROR+ logs (`server_errors.log`), plus an opt-in DEBUG sibling (`server_debug.log`, enabled by `CIAO_LOG_LEVEL=debug`) surfaced through the debug issue report. Consumed by the error-triage schedule and the debug issue report.
  debug_report.py              Aggregate runtime issues (server error log + failed job runs) for the dev-mode `GET /api/debug/issues` endpoint and the `{{ISSUE_REPORT}}` schedule placeholder.
  startup_triage.py            Startup error triage: harvest runtime errors into a fix-it chat through the schedule pipeline.
  setup_marker.py              First-time-setup receipt (`.runtime/setup-completed-at`, written only when setup creates a workspace's `.env` from scratch). Startup reads it to hold system-routine catch-up for 24h, so a brand-new install is greeted by its onboarding chat rather than four parallel routine chats replaying missed runs.
  job_runs.py                  Fail-open recorder for background-job runs. Appends one JSON record per run to `.runtime/job_runs.jsonl` (size-trimmed like `error_log.py`). Background tasks wrap their work in `track()`/`track_sync()`; `automation_summary()` feeds the Settings → Automation page. Also holds the live view: an in-memory in-flight registry (`inflight_runs()`) plus an optional publisher (`set_publisher()`, attached at startup to the chat manager's event bus) so a job can be shown as running, not only after it lands. `JobSpec.step_of` marks a step that runs inside another job's task on that job's trigger, reported as the owner's `steps` rather than as a peer automation.
  models.py                    Shared data models (ChatContext, AgentRequest, etc.).
  model_tiers.py               Claude's tier vocabulary (haiku / sonnet / opus / fable) recognized as bare model aliases; no cross-provider mapping tables.
  provider_registry.py         Single enumeration of the two supported runtime providers, Claude and OpenCode (id, labels, capabilities, auth/status hooks).
  provider_service.py          Provider request builder and execution wrapper.
  control_plane.py             Provider-neutral, scope-enforcing application operations shared by MCP and PWA-owned managers. The rare-admin group (workspace/project/Google-Workspace/context operations: `workspaces_list`, `projects_list`, `project_get`, `project`, `project_action`, `gws_status`, `context_get`) is now CLI-only and surfaced to the agent as `ciao workspace list`, `ciao project …`, `ciao gws status`, and `ciao context get`.
  async_reads.py               Bounded off-loop execution for synchronous vault reads. `run_read(key, operation)` runs a read on a dedicated small `ThreadPoolExecutor` (default 4 workers) instead of the shared default one, and coalesces identical in-flight reads by key so N concurrent `vault_search` calls for the same workspace/query share one scan. Admission is also capped (`MAX_VAULT_READ_BACKLOG`, default 12): `ThreadPoolExecutor`'s queue is unbounded and a cancelled caller deliberately leaves its read running, so a burst of distinct keys or disconnected callers would otherwise pile up full-vault scans; over the cap a caller waits for a slot without blocking the loop, and same-key callers never consume a slot. The server registers `shutdown_vault_read_executor()` as a shutdown callback, so a restart discards the queued backlog (`cancel_futures=True`) instead of joining it. The worker owns its SQLite connection end to end (opened and closed there), so no connection crosses threads. `asyncio.to_thread` cannot be cancelled, so a cancelled awaiter only detaches: the worker runs to completion, stays joinable by a later caller under the same key, and its exception is always observed (`_observe_failure`) so a detached failure is never silent. Each caller awaits its own bridge future fed by a done-callback, never the shared future, so cancelling one waiter cannot cancel the work other same-key waiters depend on. `keyed_lock(key)` is a process-wide lock used to serialize the write phase of concurrent index passes against one SQLite database file (SQLite takes one file-level write lock), while the read-only search phase stays concurrent; the archive postprocess takes the same lock when it indexes a newly archived file. `reset_vault_read_executor()` is the test isolation hook.
  workspaces.py                Shared logical-workspace registry rules (validation, serialization, persistence) used by the PWA routes and the control-plane workspace tools.
  mcp_server.py                Agent control-plane core: the shared operation table (`OPERATIONS`, one entry per operation with name, `_READ`/`_WRITE`/`_DESTRUCTIVE` annotations, docstring, and the `(service, **kwargs)` function), the `AgentSessionRegistry` bearer-token verifier, the `_invoke` envelope/plan-mode gate/telemetry, and project `.mcp.json` discovery (env-key status + observed/probed tools for Settings). The MCP adapter was removed in S6; the agent dispatcher (`ciao/agent_surface.py`) resolves the same table, so argument validation is shared by construction. There is no argv auto-approval: every `ciao …` shell command keeps a card in `auto` mode (an argv allow prefix is a shell-suffix bypass risk), and users switch to `bypass` for no cards.
  signals.py                   Restart / deploy signals.
  instance_lock.py             Process-lifetime lock for one backend per runtime directory (`.runtime/server.lock`).
  execution_modes.py           Claude/opencode provider approval policies and the CLI control-plane posture. Since S6 there is no argv allow/ask prefix list (`AGENT_CLI_ALLOW_PATTERNS` / `AGENT_CLI_ASK_PATTERNS` were removed with the argv auto-approval): every `ciao …` shell command keeps a card in `auto` mode (an argv allow prefix is a shell-suffix bypass risk), and users switch to `bypass` for no cards. The security floor stays server-side in the control plane (mode gates, `unattended_forbidden`, workspace confinement).
  tool_path.py                 Resolve external CLI tools against the user's real login-shell PATH (Homebrew, nvm, `~/.local/bin`). The terminal-PATH probe spawns an interactive login shell (~0.74s), so it is cached against a fingerprint of the files such a shell reads — the rc candidates plus `$ZDOTDIR`'s, `/etc/paths`, `/etc/paths.d/*` and `$SHELL` — rather than a TTL: the setup wizard polls every 2s and a saved rc file must still be picked up on the next poll. Concurrent probes share one spawn.
  git_proc.py                  Timeout-safe git subprocess spawning for `local_session`: git runs in its own process group so a timeout kills the forked `ssh` too, and the child is reaped and its pipes closed (a bare `proc.kill()` leaked 2 fds per timeout — issue #470).
  local_session.py             Current-branch git sync flow (LocalSessionManager): preflight, commit + pull + push, conflict chat.
  node_state.py                Node identity and host/client role state for multi-device mode (`active`/`standby` migrated to `host`/`client`).
  node_proxy.py                StandbyProxyMiddleware: client-mode tunnel that mirrors the host's API, WebSockets, and UI bundle.
  network_addresses.py         Enumerate the LAN URLs the PWA is reachable at (node sharing, tray fallback).
  rate_limits.py               Rate-limit tracking and persistence.
  insights.py                  Post-archive session insights extraction, and the stage runner (`run_archive_pipeline`) shared by the live archive path and archive-job resume. Each stage re-derives its own completion so a resume is idempotent. Extraction has two modes over one shared rule block (`_INSIGHTS_RULES`, so the grounding and citation requirements cannot drift between them): the Markdown contract on the session JSONL, and the text-mode contract on the rendered archive when the JSONL is gone.
  insights_agent.py            Agent-mode variant of the same extraction (#586), for the experiment only: the text-mode system prompt plus rules that require reading the vault before tagging (`AGENT_SYSTEM_PROMPT`), over `providers/oneshot.run_readonly_agent`'s Read/Grep/Glob tool surface. The transcript is copied into a private `<vault>/.ciao-compare-*/` directory and named in the prompt rather than pasted, so the agent reaches it with the same tool it uses for everything else; the directory and the copy are removed afterwards, so a dry run leaves the vault as it found it. Writes nothing and applies nothing — `insights_compare.py` routes the answer. The opencode variant adds a note that only the read tool exists, because the V2 read-only ruleset cannot scope a search.
  insights_compare.py          Dry-run comparison of the two extraction modes over real archived chats (#586), behind `ciao insights-compare`. `select_archives` walks the backfill's own `Chats/<id>/<provider>/*.md` tree, takes the workspace from `.runtime/web_projects.json` (an archive's path names the chat, not the workspace), skips sub-800-char stubs, and samples either the newest N or, by default, three length terciles drawn round-robin from a seeded shuffle so the run is not a length-ordered accident. `compare_one` runs the one-shot path and the agent path over the same body with the same model (`provider_insights_models` → `resolve_insights_model` → `_resolve_insights_call`), routes both answers through `memory_proposals.route_insights` so the only variable measured is extraction quality, and caches one JSON record per chat under `.runtime/insights_compare/<run id>/` — which is what makes an interrupted run resume instead of re-paying. `render_report` writes per-provider totals and one section per chat with no verdict: the operator reads both extractions and decides. Applies nothing — no proposals file, no regions, no archive edits.
  archive_jobs.py              Persisted per-archive pipeline manifest: one JSON file per archive under `.runtime/archive_jobs/`, keyed by chat + archive path + pipeline version, with a pending/running/succeeded/failed/skipped/blocked/tombstoned state per stage. Written atomically, and `save_job` reports whether the write landed so a stage never mutates the archive without its recovery evidence. A tombstone (chat deleted) can never be cleared by a race, and a changed archive revision blocks a resume rather than resuming beside unknown content. `resume_revision_matches` admits the pipeline's own insights append only when the on-disk section hashes to the exact output recorded before `_append_section` wrote it (`insights_append_revision`); a manifest without that evidence leaves the crashed-append window blocked, so an edit confined to the appended body is refused rather than folded into derived state. Not a queue service — the local single-owner model only needs a durable record plus the startup resume in `ProjectChatManager.resume_interrupted_jobs`.
  critique.py                  Multi-model adversarial review. Runs each reviewer through ciao/providers/oneshot.py, dispatching by the entry's `opencode:` prefix or to Claude Code when unprefixed. CLI: `ciao critique` (`python -m ciao.critique` works from source but not from the app bundle, whose `bin/` holds only the `ciao` wrapper). Used by the adversarial-review skill.
  fts_search.py                SQLite FTS5 full-text indexing and search for vault and transcripts. The database is owned by ONE install: `get_db_path(runtime_dir)` resolves `<runtime_dir>/vault-fts.db` (the app, CLI, MCP, os-audit and startup indexing all pass `config.state_path.parent`), so a production install and a dev checkout can no longer clear each other's derived index the way the legacy global `~/.ciao/vault-fts.db` allowed; `CIAO_MEMORY_DIR` remains an explicit override for tests and tooling and a shared override is diagnosed in the log. Row keys are paths relative to the INSTALL root (`path_base`), so two agent roots each holding a `memory-vault/` cannot overwrite each other's rows; the stored base is recorded in `search_config` and a change to it drops the index (with a warning) rather than mixing two key formats. The prune is scoped to the subtree being indexed, so indexing one root leaves the others alone — which means a workspace-scoped search must pass `path_prefix` (see `vault_key_prefix`) to stay inside its own root, since isolation is no longer a side effect of the prune deleting everything else. Memory bookkeeping never enters the index (`RESERVED_UNINDEXED_FILES`: the proposals queue, consolidations undo log, curation/weekly-review logs) and any note can opt out with `search: false` frontmatter — the memory system's paperwork must not compete with the memories it manages. A multi-word query that matches nothing under AND degrades to OR so paraphrase queries return BM25-ranked hits instead of nothing, and every result set is appended to `.runtime/vault_search_hits.jsonl` (size-capped, best-effort) as the disuse signal memory-audit reads (`retrieved_recently` on stale notes); the append and its cap rotation are one per-log critical section (`keyed_lock`) with an atomic replace, so concurrent searches in the read worker pool cannot drop a record or leave a malformed line. `expand_note` is the scoped evidence drill-down the behavioural-eval recall contracts exercise (the `vault_expand` tool that exposed it to agents was deleted in the CLI-first migration's D-03; an agent now widens a truncated snippet with a second, narrower search): the snippet the search returns is capped at 32 tokens and keeps only highlighted lines, which is what keeps unrelated private lines out of a recall answer but also cuts away qualifications, negations and the paragraph naming the current value. It widens ONE note the caller's own search already matched — the key must be a live `vault_fts` row under the caller's `path_prefix`, and the resolved file must still sit under the vault root, so a transcript, an opted-out note, a traversal, a symlink out of the vault and another workspace's note are all refused — and returns only the markdown block around each matched line, bounded by `EXPAND_MAX_WINDOWS`/`EXPAND_MAX_LINES`/`EXPAND_MAX_CHARS`, with frontmatter dropped and credential-shaped values redacted. Every heading is a block boundary, so a sibling block's secret is never in the answer; the reference is the path rather than an expiring handle, and the index pass plus the file read happen per call, so a changed note is answered at its current revision. Which lines are widened around is decided by the query's content words only (`_EXPAND_STOPWORDS`): the term list feeds a substring test over the note's lines, so before the filter a "for" or a "the" in a natural-language query anchored a window on an unrelated block, which is neither purpose-driven nor bounded by what was asked. A query left with no content word — or one no line carries — returns `reason: "no_line_match"` plus a single fallback block, which the recall contracts treat as context rather than evidence, so recall abstains instead of answering from it.
  vault_index.py               Build/query memory-vault/INDEX.md and VOCABULARY.md from frontmatter and relative Markdown links in note bodies; owns the canonical `type:` set and the shared link helpers (`vault_link_ref`, `resolve_vault_link`, `markdown_destination`). CLI: `ciao vault-index`. `scan_vault` takes an explicit `workspace` stamp and `path_prefix`: after the re-rooting a vault belongs to exactly one workspace and its first path segment is a FOLDER name, so the legacy `_workspace_of` inference reports things like `projects` and any `?workspace=` filter drops nearly everything. `scan_targets` merges the vaults named by `CiaoConfig.vault_scan_targets()` — one shared vault before the re-rooting, one per agent root after — rendering each root's paths under `<name>/memory-vault` so two roots holding a note of the same name do not produce the same node id, and returning a rendered-path -> file map because those paths are no longer a fixed offset from one vault root. One scan per target, so a `related:` link cannot resolve across roots.
  vault_lint.py                Read-only vault health validation for frontmatter, relative Markdown links, orphans, and duplicate stems. CLI: `ciao vault-lint`.
  vault_links.py               Text-level primitives shared by every module that reads links out of vault markdown: the frontmatter/fence/inline-code/markdown-link/wikilink patterns, `is_escaped`, `is_link_start`, `parse_wikilink`, `alias_separator`. A leaf module by design — it imports nothing from `ciao`, which is what lets `vault_index`, `vault_lint`, `vault_migrate_links`, and `vault_rehome` all depend on it without a cycle. Resolution stays in `vault_index` (`resolve_related`, `resolve_vault_link`, `markdown_destination`); receipts and the vault git rail stay in `vault_migrate_links`.
  vault_migration.py           One-off migration of an existing vault onto the canonical `type:` vocabulary. Applies aliased renames, reports types with no canonical equivalent. CLI: `ciao vault-migrate`.
  okf.py                       Export the vault (or one workspace) as a portable Open Knowledge Format bundle: notes plus a bundle-root `index.md` carrying `okf_version`, as one .tar.gz. Refuses a vault still written in wikilinks. CLI: `ciao vault-export`.
  vault_migrate_links.py       One-off conversion of vault `[[wikilinks]]` to relative Markdown links; also detects an unmigrated vault for the `os-audit` notice, `ciao vault-lint --migrate-links`, and the existing-folder onboarding offer (frontmatter `related:` becomes bare refs). Dry-run by default, receipt-gated under `.runtime/migration/vault-links.json` with an exact reverse map. Refuses a `--vault-root` nested inside the configured vault, preview included: refs resolve against the root it is handed, so a workspace subtree makes every link out to the vault's shared notes look dead. CLI: `ciao vault-migrate-links`, `ciao vault-unmigrate-links`.
  vault_rehome.py              One-off re-homing of person notes a global memory-curation run filed into the wrong workspace: moves the tag-obvious ones (`TAG_WORKSPACE_ROLES` maps a tag to a workspace *role*, bound to a registered name) and repoints every inbound reference in both link dialects plus frontmatter refs; notes with no workspace-naming tag are queued in that workspace's `Workspace/Memory-Proposals.md` and never moved. Dry-run by default, receipt-gated under `.runtime/migration/vault-rehome.json` with an exact reverse map. CLI: `ciao vault-rehome`, `ciao vault-unrehome`.
  proposal_kinds.py            Sole owner of the proposal-queue kinds (memory, profile, user, rehome), the bullet pattern derived from that table, and each kind's accept descriptor. Replaced three divergent private regexes that between them never matched `[rehome]` and left 64 real queue rows uncountable. A rehome accept is a file move, structurally distinct from a bounded-region edit.
  proposal_actions.py          The transport-neutral half of resolving one proposal, shared by the PWA routes and the CLI. Two things live here. `ProposalActionResult` is the per-row payload an accept or dismiss returns (region, destination, rehome candidate, usage, error), built once in `build_accept_result` for the single-row and the batch route alike — the two used to hand-build the same dictionary and had already drifted. `record_decision` is the one handler that writes a settled row to both ledgers, in a fixed order: `memory_proposals`' decision sidecar first (append-time dedupe reads it, so a missing row means the curator re-files the fact), then `proposal_outcomes`' tally, and only for the extraction kinds. Ownership boundary: this module never imports Starlette and takes no `Request` — `routes_api.py` keeps request parsing, status mapping and the 409/503 guards, `ciao/web/proposal_service.py` keeps the queue files and performs the promotions, and `ciao memory-proposal-dismiss` reaches the same recorder without going through the web layer.
  proposal_tracking.py        Stable content-derived proposal IDs shared with the proposals routes, plus a cheap re-scan of pending IDs (no rehome evidence) used by proposal helper chats to verify their target proposal has actually left the queue before auto-archiving.
    proposal_outcomes.py         Fail-open outcome log for memory-proposal resolutions: every promote/dismiss that actually settles a queued row (PWA single/batch/sweep routes, or the `ciao memory-proposal-dismiss` CLI the nightly curation agent drives) appends one JSON line (`ts`, `workspace`, `kind`, `action` promoted/dismissed, `via` pwa/agent) to `.runtime/proposal_outcomes.jsonl`. `tally()` folds the log into totals, a per-workspace split and a 30-day window; `tally_cached()` serves it to Settings → Automation through a short TTL so the endpoint stays cheap. This is whether memory extraction is *useful*, where job_runs only says it *ran*. It stays a count-only tally, not a per-fact record — `memory_proposals.py`'s decision sidecar is that.
    operator_actions.py          Home-screen housekeeping strip: a registry of cheap detectors that turn detected install conditions (update, vault location, retired vocabulary, unmigrated links, missed one-timers) into clearable operator actions. Detection reads receipts and registry values only, never walks the vault; pending proposals are not an action, since Home's *What changed* rail already counts them; the PWA endpoints live in routes_api.py. Actions may also carry an external link (release notes, the GitHub star nudge) and a "Later" dismissal that writes a suppression receipt (`dismiss_action`), so an ask-style action can be snoozed rather than only fixed.
  workspace_reroot.py          Plan and receipt for the per-workspace agent-root migration. Classifies every top-level vault path into moved, kept global, regenerated or ignored, and REFUSES on anything unclassified: an unregistered directory, a loose unrecognised file, a symlink, a registered workspace with no vault, or a non-empty destination. Planning never writes. `read_receipt` gates on `status == "migrated"`, so a rehearsal cannot make the real migration look done. Also rebuilds each root's INDEX.md/VOCABULARY.md with no path prefix and drops and rebuilds the FTS database, since every pre-migration row points at a path under the shared vault. Repoints the workspace registry and records an exact before-image, and `CiaoConfig.agent_root` flips to the per-workspace subdirectory only once a migrated receipt exists, which makes the change atomic per install. Moves the whole skill catalog (`skills/`) to the primary root and writes `Workspace/Skill-Triage.md` with every destination blank, because 16 of 20 skills are scoped to one workspace and copying the catalog into every root would rebuild the global catalog the release ends; `skills-src/` is created as a shared mirror source, not a workspace. Splits the shared guide (`AGENTS.md`): the file itself moves to the primary root with `git mv`, so its regions stay byte-identical and history follows, and it must not be left at the install root because providers walk UP from cwd for a guide and a survivor would re-inject the primary's memory regions into every root. Every other root is written the same unbounded body with EMPTY bounded regions, and the primary's region entries are queued into that root's `Workspace/Memory-Proposals.md` as one parseable bullet each — nothing lost, nothing guessed. Then `bootstrap_root` installs each root's agent assets through the same code `--repair` uses, so "after a migration `--repair` is a no-op" is an invariant rather than a coincidence. Finally every open chat holding a provider session is marked `handover_context_pending` and the count reported: a session is keyed by the cwd it started in and the migration changes that cwd, so the next turn starts fresh — carrying a context capsule and saying so beats silently forgetting. Only the ids it set are recorded, so undo clears exactly those and leaves a flag another path set alone. It writes the chat state file directly, so the migration must run with the app stopped; it is moving the vault out from under a running server either way. Nothing seeds a per-root guide while the install root still holds an unsplit one (`guide_split_pending`): the packaged stock guide has empty memory regions, so seeding it there would replace the user's guide and silently drop every remembered fact. `--repair` reconciles an already-migrated install back to the registry and is idempotent: it creates a missing root with its agent assets, renames a surviving legacy `CLAUDE.md` onto the root's `AGENTS.md` (reported as `legacy_guide` drift), re-mirrors packaged, own and shared (`skills-src/`) skills into the root's catalog, rebuilds an `INDEX.md` that is absent or still keys entries under a workspace name, and drops and rebuilds the search index when an indexed path no longer resolves. Three drifts are REPORTED, never guessed, and any of them makes the command exit 1: a root with no vault (which notes belong to a workspace is a question about the user's own material), a `.mcp.json` absent against a shared one (an MCP entry grants credentialed access and per-root composition does not exist yet), and a root with no guide while the install root still holds the pre-migration one — seeding the packaged stock guide there would replace the user's guide with empty memory regions, so the split has to run first. It refuses outright on an install that has not re-rooted: there, a workspace prefix in the shared `INDEX.md` is correct and is what `_entity_visible_in_workspace` filters on, so "repairing" it would leave no filter over the index. `migrate_if_needed(config)` is the unattended entry point: `ciao/main.py` calls it at every start, after the git sync so the clean-tree gate judges the real tree and before the index refresh so the indexes are rebuilt for the layout that now exists, and before the server binds so no chat holds a session in a directory that moves. It never raises — a migration that cannot run is a condition to surface, not a reason to fail an upgrade — and it is receipt-gated, so it is a no-op on every start after the first. When it refuses, `operator_actions._detect_workspace_unmigrated` reads the refusal back out of the receipt (via `peek_receipt`, which unlike `read_receipt` returns a refused one) and raises a `blocking` housekeeping action whose run button retries through the same `migrate_if_needed`, so the button cannot drift from what startup does. ## Vocabulary
```

Three terms describe where things live. They are pinned here because the same
word once meant two different things.

- `workspace_root` — the install root directory (e.g. `~/repos/ciao`). Holds the
  vault, `.runtime/`, config, and the user's agent assets. Meaning unchanged from
  today.
- `workspace` — the logical workspace name (e.g. `personal`, `work`). A label,
  not a path. Meaning unchanged from today.
- `agent_root` — the per-workspace directory that will hold that workspace's own
  `AGENTS.md`, `.mcp.json`, `.claude/` assets, and `memory-vault/`. Today it
  resolves to `workspace_root` for every workspace, so it is a seam and not yet a
  distinct directory. The re-rooting release makes it a real subdirectory.

`handover` is pinned for the same reason — two unrelated things share the word:

- **Provider handover** moves one chat to a different provider, carrying its
  recent turns into a fresh provider session (`ChatInfo.handover_messages`,
  `handover_context_pending`). That flag is a persisted state key and cannot be
  renamed; the workspace re-rooting reuses it to mark chats whose old provider
  session was stranded by the move (`workspace_reroot.flag_stranded_sessions`),
  which is stranded-session context carry-over, not device handover.
- **Device handover** switches this machine between the multi-device host and
  client roles (`ciao/node_state.py`, `/api/node/handover`; legacy
  `active`/`standby` values persist as accepted aliases of `host`/`client`).

No state is shared between the two.

## Workspace layout

`workspace_guide.migrate_config` follows `CiaoConfig.agent_root_targets()` rather than the raw install path. Before the workspace re-rooting, that seam returns the install root because it is the shared agent root; after the re-rooting it returns only the per-workspace roots, because `workspace_reroot` has moved the shared guide into the primary root and the install root is no longer an agent root. A root-level guide found after that transition is not a filename-migration target: it may be repository metadata or re-root drift, and renaming it independently would either mutate unrelated instructions or leave a parent guide for providers to load.

The app repo above is the installable package. A `workspace_root` is a separate directory (created by `ciao setup`, never committed to this repo) that holds the user's data and per-instance state: one root folder containing the vault (`memory-vault/` by default) alongside `commands/`, `subagents/`, `skills/`, `.runtime/`, and config. A fresh first logical workspace and every workspace created later in Settings are user-named folders under that configured vault root (`<vault>/<workspace-name>/`); Settings never accepts a filesystem path for them or follows a named-folder symlink outside the vault. Setup can preserve an existing notes folder in place, and upgrade compatibility can temporarily pin any older nonstandard vault root. The AI OS audit reports each nonstandard root with a Ciaobot-chat migration prompt so the model can inspect conflicts, back up the source, update the registry, and restart into the standard nested layout without moving data silently. Setup ensures the `workspace_root` is a git repository: if the chosen folder is not already inside one, it runs `git init -b main`, writes a `.gitignore` guarding `.env`, `.runtime/`, `.claude/`, and `*.log`, and makes an initial commit; pre-existing repos are left untouched apart from appending any missing `.gitignore` guards. The vault may also point elsewhere (`CIAO_VAULT_ROOT`, e.g. an existing notes folder): in that case setup initializes that folder as its own git repository (`git init -b main`, a minimal `.gitignore` for `.DS_Store` and `.obsidian/workspace*`, and an initial commit); a vault nested inside the `workspace_root` repo — the default layout — is never double-initialized.

## Server and chat pipeline

Linux production hosts run the engine under systemd. Settings uses the
authenticated `POST /api/admin/restart` endpoint, selected by `restart_only` in
`/api/local/status`, to enter the same chat-drain/re-exec lifecycle without a
source checkout or desktop rebuild. Code updates remain administrator-managed;
developer mode retains the deploy endpoint. `restart_only` is also true for
the packaged Ciaobot.app (`detect_install_mode() == "bundled_app"`, whatever
the dev mode) and for any macOS install that is not a deployable checkout. The
re-exec happens in-process (`ciao.cli._run_server`), so the `com.ciao.server`
LaunchAgent keeps tracking the same pid, and its `KeepAlive` relaunches the
job if the exec fails. `POST /api/admin/deploy` refuses a bundled app up front.

`ciao/` is a Starlette web server that mounts the PWA frontend, exposes a JSON API for projects/chats/schedules, and drives Claude Agent SDK sessions for each chat turn. Auth is a pre-shared token (`PWA_AUTH_TOKEN` — the dashboard password) traded for a signed session cookie, and it is required by default: an unset `PWA_AUTH_REQUIRED` protects any workspace that has a token, and only an explicit `PWA_AUTH_REQUIRED=false` runs the dashboard open. Settings can change the password but not disable protection. Operational state lives in `.runtime/` under `CIAO_WORKSPACE`; durable memory lives under `CIAO_VAULT_ROOT` (default `<CIAO_WORKSPACE>/memory-vault`).

One backend process owns a runtime directory at a time. On macOS,
`Ciaobot.app` is the sole visible desktop process while the Python engine
remains a separate `com.ciao.server` LaunchAgent. The app discovers its
workspace and fallback port from the server plist, then treats the workspace
`.env` (`PWA_PORT`, `CIAO_RUNTIME_ROOT`) as authoritative. The external
localhost PWA has no Tauri capabilities or native commands, and the main
webview refuses navigation away from the local engine/bundled startup origins.
Finder drops stay in the
native Tauri handler because WKWebView removes absolute paths from HTML
`File` objects. Tauri writes the exact dropped paths into a five-minute,
single-use grant under `.runtime/desktop-drop-grants/` and dispatches only
that grant ID into the page. The local `/api/desktop-drop` endpoint consumes
the grant: the route returns bounded opaque file references, and the server
expands those references only in the provider prompt; clients transfer the
file bytes into the active project on the host. This does not add a native command
or general filesystem capability to the remote page. If the engine is unavailable
at launch, the main window shows a bundled, capability-free recovery page,
requests a service start through `ciao desktop-service`, and navigates to the
PWA after the tray health poll observes recovery. A second bundled
`startup.html` window is kept hidden for the native update flow: the tray shows
it before replacing the engine/app, then streams milestone progress and
collapsible terminal details through a local browser event. `ciao/instance_lock.py`
holds `.runtime/server.lock` for the engine process lifetime, so a normal
server and `ciao dev` cannot run against the same registry concurrently.
Project/chat writes use a short-lived registry lock, merge field-level local
deltas onto the latest revision, and append mutation IDs to
`.runtime/web_projects.audit.jsonl`. Vault-backed project IDs are
deterministic for newly discovered `(workspace, vault_folder)` pairs. At
startup, archive discovery resolves both display names and vault-folder slugs;
missing active rows are reconstructed from normalized runtime transcripts only
when a surviving provider session or a non-deleted audit record proves they
were active. Explicit deletion clears provider state, normalized transcripts,
and session state so recovery cannot revive it.

Chat transcripts are streamed via WebSocket and archived to `<logs root>/Chats/<chat-id>/<provider>/` (`transcripts.py`), where the logs root is `CiaoConfig.logs_root` — `<vault>/Logs` before the re-rooting and `<install>/Logs` after it, decided by the same migration receipt as `agent_root`. Every reader goes through that seam (or the standalone `config.logs_root_for` when it holds only paths): deriving it as `vault_root / "Logs"` resolves to a path that does not exist on a migrated install, so archiving would recreate it and split the archive in two. `Logs/` is global: a sibling of the workspaces inside the vault root, not a subfolder of any one of them. It stays global through the re-rooting release, which promotes it to `<install>/Logs/` without moving the files, because it holds 1423 of 1985 vault notes (72%), it is derived output rather than curated content, and 1350 chat ids cannot each be resolved back to one workspace. Archive, delete, and new-session cleanup disconnect the live supported provider before reclaiming its session: Claude SDK JSONL blobs via `delete_session` and OpenCode sessions via `DELETE /api/session/{id}`. Cleanup is fail-open so a provider outage cannot prevent the durable Ciaobot archive, and it includes prior session IDs created by rotation. Archived `/messages` falls back to the vault markdown when the supported provider session is gone. The Claude Agent SDK is configured in `ciao/providers/claude.py` with a `fallback_model` chain (Fable to Opus to Sonnet to Haiku) and `setting_sources=["user", "project", "local"]` so `.claude/skills/`, `.claude/agents/`, and `.claude/commands/` auto-discover.

Chat document attachments convert supported files into Markdown in the active
project vault folder. Existing host sources remain at their original paths;
remote uploads use a temporary host source and persist only Markdown. Images
and ordinary text retain their existing behavior, and conversion errors are
per-file and non-fatal.

The control plane runs as the agent CLI surface. `CiaoControlPlane` wraps the
existing project/chat, schedule,
subagent, vault, memory, file-history, workspace-health, local-session, and
lifecycle managers; `CiaoMcpService` only performs bearer authentication,
operation dispatch (via the `AgentDispatcher`), plan-mode mutation policy,
stable error envelopes, and
telemetry. Each managed provider process receives a short-lived capability
carrying a chat/project/workspace/provider principal. What that principal
enforces is workspace confinement plus chat attribution, not isolation between
chats: every ownership check resolves through `_workspace`, so a chat token
reaches sibling chats in its own workspace and no others. The chat half drives
plan mode, the child-mode ceiling, background-run ownership, revocation and
telemetry. Claude receives the server and
Authorization header through `ClaudeAgentOptions.mcp_servers`; opencode receives
equivalent per-process configuration, which is why it runs one server process
per chat (reclaimed by the idle sweep in
`ProjectChatManager.reap_idle_providers`). Project servers remain in `.mcp.json`
and credentials stay as environment references. Self-disconnecting operations
defer until their caller chat drains. The native file tools are denied `.env`,
`.runtime/` (by name, plus the resolved `CIAO_RUNTIME_ROOT` path) and
`secrets/` on both providers
(`ciao/execution_modes.py::credential_path_deny_rules`), because
`PWA_AUTH_TOKEN` in `.env` buys strictly more than any scoped agent token. The
`.env.example`-style templates are deliberately not denied, matching
`local_session.py`. See `docs/AGENT_CLI.md`.

The agent CLI control plane is mandatory and is the only agent-facing control
surface: there is no skill/direct-file fallback and no per-chat or
per-server surface selector. `ProjectChatManager.build_agent_request` raises
`AgentSurfaceUnavailableError` when the control plane or the chat's project is missing,
and `_drive` turns that into a normal failed turn in the transcript, so a chat
never runs an agent that silently cannot reach Ciaobot. First-run setup is the
one state without a control plane (no workspace yet); a chat attempted there
fails with the same error. The `legacy`/`auto` surfaces and the
`ciao benchmark-control-surfaces` evaluator that compared them were removed
once the evaluation had settled on MCP. Two deliberate CLI exceptions remain,
both for surfaces that are not control-plane CRUD: the memory-proposal queue
(`ciao memory-proposal-add`, `ciao memory-proposals`,
`ciao memory-proposal-dismiss`) is driven by the nightly curation agent because
one shell command beats an MCP round-trip per row, and the vault-maintenance
verbs (`ciao index`, `ciao lint`) wrap tools a file tool cannot replicate.
Reviewing and accepting proposals still happens in the PWA or through those
CLI verbs; the MCP surface keeps `memory_status`/`memory_update` for bounded
memory itself.

Server restart requests drain chat work before shutting down: active broker streams, already-queued follow-up turns, and background-subagent watchers are allowed to settle, while brand-new turns are rejected once draining begins. When drain starts, `ProjectChatManager.begin_restart_drain` publishes `server_restarting` on `/ws/events` (and the connect snapshot carries `restarting: true`) so every open PWA shows the full-screen restart overlay instead of treating turn rejection as a chat error. Shutdown starts only after several consecutive idle observations so the handoff from a completed parent turn to its background-agent watcher or synthesis stream cannot create a false-idle race. The macOS menu-bar action uses `/api/active-chats` as a guard before its direct launchd restart and asks the operator to retry once active chats finish.

When the model calls `AskUserQuestion` (which the headless CLI can't render, and would otherwise auto-answer empty), `ProjectChatManager._drive` interrupts the turn so generation stops at the question; the PWA surfaces it in its own picker (persisted as `ChatInfo.pending_question` so it survives a reload) and the user's reply resumes the session as a fresh turn.

If a turn fails before any provider progress with a quota or session-limit error, `ProjectChatManager` stores the last prompt and schedules an hourly deferred retry; the chat view and sidebar surface the pending state, and `/api/chats/{chat_id}/retry` lets the UI set, stop, or run that retry immediately.

Conversation forks let a user start a new chat in the same project starting from any completed agent answer in an active or archived chat. When a fork is created via `/api/chats/{chat_id}/fork`, the system performs a provider-neutral history copy, copying the visible chat history up to the selected assistant response, normalizing the messages (with system notes for truncated older messages if bounds are exceeded), duplicating referenced images to ensure source independence, and initializing a new chat with `handover_context_pending=True`.

## Memory, insights, and self-improvement

When Automatic session insights is enabled, archiving a chat filters the raw session JSONL and passes it through a fast model to extract durable insights (errors, dead ends, new entities, decisions, reusable code) which are appended as a `## Session insights` section; when Automatic trajectory capture is enabled, the same pipeline records the structured trajectory. The insights section is the preferred input for memory curation and downstream automation (`ciao/insights.py`; model chosen in Settings → Models). Startup and manual backfill route each archive through its provider directory and chat-registry workspace, and defer any archive already owned by an unfinished manifest so restart recovery cannot process it twice. Every bullet carries a destination tag, time-bound facts carry `[as-of:]`/`[expires:]`, and both prompts refuse to extract a maintenance session's own operating rules as facts. A system-schedule chat (curation, hygiene, skill evolution) still gets its insights section — it is the audit trail of the unattended run — but its archive skips the project-doc fold (`_job_inputs` passes no project doc for a system-schedule chat); other destinations still go through the normal gates, where facts citing only automation turns are deferred to the queue and the extraction prompts refuse a maintenance session's own operating rules — extracting the curation prompt's own rules used to auto-promote the machinery's self-description into the bounded regions (design rationale for all of this: docs/MEMORY_DESIGN.md; retrieval eval: docs/MEMORY_EVAL.md). Settings can compare its headings and output against a small sample of existing processed archives without editing them.

All of this is one task, not four automations: `extract_and_append` runs session insights, then the project-doc fold, then the trajectory (even when extraction failed, so a failed extraction still leaves one), then the write-time region reconcile (`plan_region_reconcile`, best-effort), then memory proposals. The chat manager owns that pipeline's lifecycle and records it on the chat as `postprocess` (`{state, step, expected, steps}`, plus a `job` manifest view once it settles), published as the `chat_postprocess` event and persisted with the chat — so the PWA can show a muted "tidying up" signal while it runs and a settled "insights added · 3 memory proposals · trajectory saved" line on the archived chat afterwards. A record still marked `running` at load time is downgraded to `done` and flagged `interrupted`: the task died with the previous process.

The pipeline is stage-resumable (`ciao/archive_jobs.py`). Each archive gets a small manifest keyed by the chat, the archive path and the pipeline version, holding a pending/running/succeeded/failed/skipped/blocked state per stage. A crash between stages is repaired without re-running model extraction: `extract_and_append` no longer returns early when the archive already carries insights, so insights is skipped while the fold, trajectory and proposals still run; a resume after insights landed picks up exactly the later stages. Every stage re-derives its own completion from the archive/destinations (the section marker, the doc's equal-content guard, the trajectory's deterministic filename, the queue/sidecar/region dedupe), so a retry cannot duplicate region entries, proposal rows, learning recurrence counts or project updates. A stage that fails inside its helper (`update_project_doc`, `build_and_persist_trajectory`, `proposals_from_archive` all catch their own errors) is settled `failed`, not `succeeded`: each returns a distinct error through an `error_out` out-parameter so a provider timeout or an unwritable queue stays retryable, while a genuine no-op (NO_CHANGES, nothing to queue) still settles cleanly. A job whose archive revision changed under it is blocked with a reason instead of resumed — the pipeline's own insights append is accepted only when it authenticates against the exact section the pipeline recorded before writing it, so an edit confined to that section is treated as an external change — and a deleted chat tombstones its job so a racing task or the next boot cannot revive it. At startup `ProjectChatManager.resume_interrupted_jobs` makes interrupted `running` stages retryable and resumes eligible local jobs with bounded concurrency; blocked and tombstoned jobs are left alone, and a dependent stage is not auto-resumed while the predecessor it needs has exhausted its automatic budget (it would only skip for lack of output). A `running` stage whose attempt budget was exhausted is reset so it is genuinely eligible again; a job whose archive is missing is blocked and surfaced rather than left stale. Deleting an archived chat cancels the retained in-flight task (a stage already awaiting a model call would otherwise write derived state for the deleted chat) and re-checks the tombstone before each stage write. The archived-chat postprocess line and the Home "unfinished steps" lane offer a retry that resumes every unfinished stage and reports partial completion.

In the same archive hook, `ciao/trajectory_builder.py` writes a structured trajectory JSON (turns, tool counts, skills loaded, errors) to `~/.ciao/trajectories/YYYY-MM/<session-id>.json`; a weekly schedule runs `ciao/skill_evolution.py` to mine those trajectories and draft skill-edit proposals under the vault's `Workspace/Skill-Proposals/`. The per-skill pipeline inside `run_evolution_pass` is a small DAG executed by `ciao/dag.py`, so each step (proposal generation, semantic check, test gate, write) shows up in the Automation page with its own timing and error.

Each session gets its bounded memory through the provider's native guide load, not an injected block: every chat, schedule, and subagent runs a CLI with `cwd` set to the workspace's agent root, so both read `<root>/AGENTS.md`, regions included. `core_prompt.py` injects only the compact Ciaobot core, and does not render `ciao:memory` or `ciao:profile` into a second prompt block. Caps are advisory (3000 chars for `ciao:memory`, 1375 for `ciao:profile`; `ciao/memory_tool.py`); `os_audit` reports over-cap, oversize, duplicate, and invisible-Unicode issues. Consolidating entries a region already holds is the one region write the unattended nightly curator does perform, and only once usage reaches ~85% of the cap: it merges duplicate and superseded entries, drops entries whose `[expires:]` date has passed, tightens wording, and moves project-scoped facts out to their owning doc. Three guardrails bound it: every removed or replaced entry is copied verbatim into `<vault>/Workspace/Memory-Consolidations.md` under a dated, region-named heading first, so nothing is lost and any line can be restored; a removal needing judgment is never made, and becomes a one-line `[review]` question in the proposals queue instead (dismissing it keeps the entry, dropping it takes an attended chat that edits the region and then dismisses the question — the queue itself cannot apply a drop); and a durable fact is never dropped merely to fit a cap. Promoting a NEW fact into a region is reviewable, not refused: archive time auto-applies confident, state-shaped facts, an attended "remember" is explicit, and the unattended nightly curator never promotes a new region fact. A region still over cap after consolidation is reported for the user to act on — an attended chat consolidates further, or the region stays over its advisory cap. The agent edits the regions either with `Edit` or through the control-plane `memory_status` / `memory_update` operations, exposed as `ciao memory status` and `ciao memory update --region {memory,profile} --action {add,replace,remove}` (`ciao/agent_cli.py`). Reviewable proposals are filed (`ciao memory-proposal-add --kind memory --source <chat id> --text-file <fact-file>`, which the nightly curator uses when it finds a bounded-region fact in a transcript that archive-time routing never saw), then listed and dismissed from the CLI (`ciao memory-proposals`, `ciao memory-proposal-dismiss --text-file <file>`), which the nightly curation agent and the user share; promotion is an explicit region Edit first, then dismiss. A bounded entry tagged `[expires: YYYY-MM-DD]` remains active through that date. After it, the entry is deleted from the guide before the next turn: `ProviderService.execute_streaming` runs `prune_expired_entries` on the chat's agent-root guide before every turn and reconnects the provider when anything was removed, so a just-expired fact never stays in the native snapshot (daily curation drops them too). Curation removes only entries with valid, passed dates and reports malformed tags instead of guessing. `ciao/memory_proposals.py` routes archived `## Session insights` facts to their destination at archive time: the extraction prompts tag every bullet (`[memory]`, `[profile]`, `[project]`, `[people: <Name>]`, `[learnings]`, `[review]`), and confident, state-shaped facts are auto-applied — regions via the event-shape audit (only the "Durable rule:" clause or a bullet that passes it is written), people as stub notes when absent, learnings as structured recurrence-counted entries under `Workspace/Learnings.md`'s Active section. Region writes stamp each entry with a trailing learned-at `[YYYY-MM-DD]` and run through the ADD/UPDATE/COVERED reconcile when its decision map is available, so a changed fact replaces its predecessor (undo-logged) instead of coexisting with it; `memory-audit` reports entries whose `[as-of:]` or learned-at date has aged out for the nightly curator to re-verify. `[project]` facts are owned by the doc fold: consumed ones are dropped, and facts the fold skipped are queued addressed to their doc so a one-click accept can fold them later. The extraction prompt's known context also excerpts the existing note of each known person or project the transcript mentions (its `description:` and newest lines, headed by the tag that files into it), so the model can omit what a note already says and pick `[project: <name>]` / `[people: <Name>]` from the roster; code resolves those names to the note (people to the existing file's stem) rather than guessing from wording, and only a bare `[project]` defers to the chat's own doc. Three queue-quality filters run before anything is queued: a Decision with no destination, or one shaped as a changelog line ("Added…", "Deleted…") with no standing rule, is dropped; a `[review]` fact whose subject is a known person or project, or that names exactly one known project, is re-addressed to that note or doc, and an undated restatement of a known entity is dropped; and a fact the session already wrote (it cites the same turn as a `## Vault changes` bullet and names that file) is suppressed. Shape is not evidence, so a second gate runs before any of that: `ciao/fact_candidates.py` lifts each bullet into a fact candidate v1 record (text, destination, cited message ids, evidence excerpt, `[as-of:]`/`[expires:]` bounds, whether the supporting turn was attended, extraction and policy versions) and checks it against the normalized transcript the extraction model was actually shown. A fact is deferred to the queue when it cites nothing, cites a turn that does not exist, cites only assistant output or an automation turn, quotes an excerpt the turn does not contain, is carried only by pasted or tool material rather than the user's own words, is negated or offered as a hypothetical example by the turn it cites, is corrected by a later user turn, or is addressed outside the destination registry — never on a confidence number the model supplied about itself. The verdict code, the cited ids and the policy version ride along on the defer row, and a written fact stamps the same provenance onto its receipt, so a saved fact can be traced back to the turn that established it and the rules that admitted it. Archives with no transcript to check against (text-mode extraction forbids `[idx=N]` outright) are recorded as explicit unknown provenance rather than gated on indices that were never meant to exist. Everything unsure or failed waits in `Workspace/Memory-Proposals.md` for human or curator promotion. Daily memory curation also appends durable learnings to the vault's `Workspace/Learnings.md`. Startup `ensure_regions` + legacy `~/.ciao/memory.md`/`user.md` migration folds old files into the regions once. Region contents are git-tracked with the workspace.

`provider_service.py` prunes valid expired entries from the guide before
provider startup, and the typed MCP `memory_status`/`memory_update` operations
write the same guide rather than maintaining a parallel store.

### Memory write policy matrix

Every path that can write durable memory, with its approval rule. The
machine-readable copy is `ciao/memory_policy.py`; tests pin this table and the
stock assets to it so they cannot drift apart again.

| Context | Destinations | Approval rule | Cap semantics | Undo |
| --- | --- | --- | --- | --- |
| Attended explicit remember | regions, project doc, people, learnings; `review` when unsure | Explicit user request may write live; otherwise queued | Advisory | — |
| Archive extraction | regions, people stubs, learnings, project doc via the fold; unsure/failed → queue | Confident, state-shaped facts auto-applied; unattended transcript turns never lifted | Advisory | Replaced region entry → `Memory-Consolidations.md` |
| Unattended curation | existing region entries only (consolidation); queue for any new fact | Never promotes a new region fact; defers approval-requiring work | Advisory | Required before any removal/replacement |
| Direct edit / `memory_update` | regions | Human-controlled maintenance | Advisory (`over_cap` reported) | — |
| Proposal acceptance (PWA/CLI) | regions, people, learnings | Reviewer action | Advisory | Replaced region entry → undo log |

**Why curation is narrower than archive extraction.** Archive extraction runs
right after the user's own conversation, so a confident, state-shaped fact is
attributable to a turn the user typed; the unattended curator runs nightly with
no reviewer, so it only consolidates the region's existing entries and queues
everything new. **Unattended runs defer; they do not route around the missing
reviewer.** The capsule marker (`ciao/context/capsule.py`, one string in
`ciao/memory_policy.py`) tells a schedule/automation turn not to ask or wait and
to report deferred work — a NEW region fact, a vault-note trash/delete, a
write into another workspace, a new automation in another workspace, and public
or destructive git actions — in its final output instead. The archive-time
extraction prompts read the same marker (`ciao/insights.py`) to never lift a
fact from an automation turn.

**Decisions behind this matrix (AI-01).** The policy is published as the
current behavior, not changed to match the older prose. Archive-time
auto-save stays the default: confident, state-shaped facts are applied at
archive time, exactly as the code already did. No "review everything" setting
is added — it would be new scope with its own migration, and the queue already
holds everything the guards reject. Because no saving default changes, no
migration is required. Making an uncertain or stale reconciliation decision
*queue* the competing fact rather than append it is a separate behavior change
tracked by AI-06 (#459); this document does not reinterpret user consent that
was given under the current defaults.


The server registers a Claude `PreToolUse` hook in `ciao/observability/hooks.py`.
It rewrites only Claude `Bash` calls with `run_in_background: true` to run in
the foreground. Runtime, workspace, project, and vault-entity context is built
once by `ciao/context/capsule.py` and prepended to the request for both supported
providers; a second Claude `UserPromptSubmit` injection is intentionally not
installed. Retrieval is driven by the system prompt (`vault_search` tool) rather
than a per-turn heuristic hint. The managed SDK CLI owns background shell
processes and stops them when the turn ends, while their terminal notification
is delayed until a later turn resumes the session. Keeping these calls in the
active turn makes the real shell result part of the same streamed response.

## Schedules and background automation

Schedule dispatch (`ciao/schedules.py`) runs cron-shaped jobs through the normal chat pipeline. The two packaged routines are both `per_workspace`: **Workspace care** retains the persisted base id `system-memory-curation`, and **Skill reflection** retains `system-skill-evolution`. Fan-out materializes `<base-id>@<workspace>` rows with independent enable and last-run state. Workspace care dispatches the canonical `memory-curation` skill daily; that skill processes memory proposals and learnings every night, then uses `Workspace/Curation-Log.md`'s `last_full_pass` marker to run an overdue full pass even when the server missed Sunday. The full pass refreshes `INDEX.md`/`VOCABULARY.md`, reviews stale notes without unattended deletion, runs `os-audit --scope workspace`, and applies only safe structural repairs. Skill reflection reads only that workspace's trajectories and canonical user-owned `skills/` directory, and upserts one reviewable `Workspace/Skill-Proposals/<skill>.md` file per skill. Install-wide failures are not a weekly model schedule: startup triage and Automation surface failed jobs on every install, housekeeping surfaces upgrade actions, and development mode adds the verbose debug report. Proposal helper chats carry persisted proposal IDs and an archive policy; resolution helpers archive only after a clean idle turn and after every owned proposal is absent, while review/discussion helpers remain manual. User schedules live in `.runtime/schedules.json`; mutable packaged state lives in `.runtime/system_schedules_state.json`. Compare persisted and live system IDs through `system_base_id` because fan-out qualifies live IDs by workspace.

Sub-day recurrence is the `interval` frequency of the same primitive — what used to be a second one, in-chat loops. An interval entry carries `interval_minutes` (floor: 1) and fires that many minutes after its last dispatch rather than at a wall-clock slot, so it needs no `daily_time_utc`.

Bound to an existing chat via `web_chat_id`, an interval entry keeps everything the loop primitive guaranteed: each run uses the target chat's own model and mode (an empty `model` means "inherit", which `schedule_effective_routing` resolves at dispatch, and `prepare_schedule_chat` does not overwrite the chat's settings for these); overlap protection is skip-not-queue, so a run due while the chat still has a turn in flight is skipped and retried on the next ~20s tick with `last_status: "busy"` rather than queued; a target chat that was archived is forked and one that is gone is replaced inside the entry's own project, and only when no project resolves either is the entry disabled with `last_status: "missing-chat"`. Bound to a `web_project_id` instead, an interval entry opens a fresh chat per run with its own model and provider — the combination neither primitive offered before the merge.

A fixed-chat binding is the same dead-target hazard at any cadence, not just interval: dispatching into an archived chat resumes a reclaimed provider session and fails in under a second with a `stream error` that nothing user-visible ever reports (issue #407). `prepare_schedule_chat` therefore re-homes a chat-bound entry whose target is archived or missing at any frequency — fork the archived transcript, or open a fresh chat in the entry's project (primary binding, then `fallback_project_id`, then General) — and re-points `web_chat_id` at the replacement, exactly as the interval path already did. A dispatch failure is also stamped as `last_status: "error"` on the stored row, so the Automations sidebar flags the schedule for attention instead of leaving an endless string of invisible failed job records; the PWA detail view shows the status row for a wall-clock entry that carries one.

Every dispatch path stamps `last_status: "running"` before the turn starts and the dispatch pipeline writes the outcome back, because `last_triggered_on`/`last_dispatched_at` are stamped at dispatch and therefore cannot tell a served slot from one whose turn died mid-flight. Without that distinction an interrupted run (a server restart, a killed provider subprocess) marked the day as fired: `catch_up` skipped it, the Missed list excluded it, and the work was silently lost until the next occurrence — a week, for a weekly routine (issue #486). `run_failed_since` is the shared rule: a dispatch at or after the expected fire satisfies its slot only if the run it started did not fail. A failed run therefore reports as missed in the PWA, where "Run all" can recover it, and `catch_up` re-fires it on the next launch. Two bounds keep that from replaying work: only `"error"` qualifies — a completed run, and a `"skipped"` one still waiting on the user or the provider, are never re-dispatched — and `last_recovered_on` spends one automatic recovery per slot, so a run that keeps failing (or that takes the server down with it) leaves the entry flagged for the operator rather than dispatching again on every restart. An outcome is applied only to the dispatch that produced it. `last_dispatch_id` (`<slot-day>#<token>`, minted on the entry before the run starts and carried back by the entry snapshot the pipeline holds) is what makes that possible: `last_dispatched_at` and `last_status` are separate fields, so two non-interval dispatches that overlap — a manual "Run now" started shortly before the cron slot — used to pair the newer timestamp with whichever run happened to finish last, which hid an interrupted slot from catch-up in one completion order and retried an already-successful one in the other (issue #490). `stamp_run_outcome` splits the two things being recorded: `last_status` describes the entry's latest dispatch, so a superseded run's status is dropped rather than misattributed (its own result stays in the job-run log, which records the `dispatch_id`, and in its chat), while `last_completed_on` records the occurrence a completed run *served* whether or not a later dispatch replaced it — which is what stops a slot whose work is done being replayed because a second run for it failed. The occurrence is decided at dispatch and never re-derived at completion, so a run dispatched at 23:58 for the 23:55 slot belongs to that slot however long past midnight it streams; `last_triggered_on` already worked that way, and this composes with it. `reconcile_interrupted_runs` runs at the head of `catch_up` and converts a `"running"` stamp left by a previous process into `"error"`, which is how a hard kill is recognised; ownership is tracked by schedule id in memory, not by comparing timestamps, so the startup tick and the catch-up pass can race without a run this process just started ever being replayed. Both automatic paths are host-only: `tick()` and `catch_up()` return immediately when `NodeStateManager.is_active()` says this machine is a client, so a second device neither dispatches the slots the host owns nor rewrites the host's run state (the catch-up guard sits ahead of `reconcile_interrupted_runs` for exactly that reason). Manual `dispatch_now` is deliberately not gated — "Run now", the MCP run tool, and the operator strip's "fire missed one-timers" are a person asking for a run on this machine, not an automation.

Two things interval entries deliberately do not participate in. `compute_last_expected_run` returns `None` for them, so they never report a missed run: their cadence is relative, and every skipped tick (a busy chat, a paused entry, a restart) would otherwise read as missed. And `catch_up()` skips them, so a restart resumes the cadence instead of replaying every interval that elapsed while the server was down. `last_status` is what reports their health instead.

There is one runtime flag, `enabled`, where loops had two (`running` now, `autostart` after a boot). The split existed so a loop could tick until the next restart and then be silently dead — the "model says running, loop isn't" failure — so it was collapsed rather than carried over. A legacy `.runtime/loops.json` is imported once on startup by `schedules.migrate_loops`, keeping each `loop-…` id as the `schedule_id` (deep links and recorded ids keep resolving) and mapping `autostart` to `enabled`; the file is then renamed `loops.json.migrated` with one log line. A loop's `web_project_id` becomes `fallback_project_id`, not `web_project_id`: on an interval entry that field is the primary binding and means "a fresh chat per run", which outranks `web_chat_id`, so carrying it across would change what the automation does — but it was the loop's re-home target when its fixed chat went away, and dropping it sent those runs to the workspace's General instead. `resolve_automation_project` therefore tries the primary binding, then `fallback_project_id`, then General, each step a weaker claim about where the user meant the run to land. The loop compatibility surface is fully retired: the `loops_list`/`loop`/`loop_action` MCP tools, their control-plane backing methods, the `GET/POST /api/loops`, `PATCH/DELETE /api/loops/{id}`, and `POST /api/loop-run/{id}` REST routes, and the `loops_changed` event are all gone. `schedule`/`schedule_action` and `schedules_changed` are the only automation surfaces.

Background command runs (`ciao/background.py`) are the third dispatch primitive, sitting between a plain `nohup` and a subagent: one command, no model in the loop, no tool access. A chat starts one with `background_run_start` and ends its turn; the run is launched with `asyncio.create_subprocess_exec` on an argv list (never a shell) in its own process session, its merged stdout/stderr streams into `.runtime/background/<run_id>.log` (trimmed at 2 MB, same threshold as `job_runs`), and the registry lives in `.runtime/background/state.json`. Completion is detected by awaiting the process, not by polling; the owning chat is then woken through the same coalescing window subagents use (`_background_wake_pending`, 5s), so a batch of scripts finishing together produces one turn carrying each run's status, exit code, log tail, and log path. A run belongs to exactly the chat that started it: `background_run_status` and `background_run_cancel` report a run owned by another chat as not found. `cwd` is confined to the workspace root, `env` cannot set loader hooks or Ciaobot's own session token, and the inherited environment is stripped of server credentials before the child sees it. Every finished run is also recorded as a `background_run` job so the Automation page shows it, and terminal runs are pruned with their logs after 7 days. Shutdown terminates every live run, so a graceful restart leaks nothing; a run left behind by a *crash* resolves at the next boot to `error` with its last-known PID and log path in the wake, rather than being killed blind — after a crash that PID may belong to something else.

Background automations are instrumented through `ciao/job_runs.py`: title generation, schedule dispatch, session insights, project doc update, memory proposals, trajectory capture, weekly skill evolution, and startup/system tasks (git sync, vault index refresh, skills update, device-branch backup, Google token health, the one-time legacy memory migration) each record one run (status, duration, model/provider, error) to `.runtime/job_runs.jsonl`. `GET /api/automation` serves the grouped view that powers Settings → Automations; each registered job also exposes static `trigger`, `schedule_id`, `one_time`, `uses_model`, and `produces_outcome` metadata, so the page can explain a never-run job. Three kinds of row are deliberately not served: jobs in `RETIRED_JOBS` (removed from the code, but still present in the never-expiring `job_runs_latest.json`), `schedule_only` jobs whose schedule is not installed on this machine, and bulk variants of another job — the insights backfill is reported as Session insights' `sub_jobs` rather than as its own automation. Whether that pipeline is *useful* is a separate signal: `ciao/proposal_outcomes.py` logs every memory-proposal promotion or dismissal to `.runtime/proposal_outcomes.jsonl`, and the Automation tab shows "promoted vs dismissed" next to the job stats — served through `GET /api/automation?include=outcomes`, whose default response stays the bare job list for existing consumers.

`GET /api/agent-assets/audit` exposes `ciao.os_audit.run_os_audit()` to Settings. A successful response is the full report object: `status` (`healthy`, `needs_attention`, or `error`), `total_issues`, `total_errors`, `timestamp`, section objects for `setup_audit`, `vault_hygiene`, `skill_audit`, `rule_audit`, `memory_hygiene`, and `job_runs_audit`, plus the flattened `scan_errors` list. `error` means the scan was not reliable, not merely that actionable findings exist. An unexpected handler failure returns HTTP 500 with `{"error":"failed to run AI OS audit"}`.

Schedules carry an `archive_policy`: `manual` or `auto`. All schedules execute through the normal chat pipeline for permissions and transcripts. `auto` runs a post-run classifier and archives only when the user does not need to see the result; failed, permission-blocked, retrying, or useful runs stay visible.

**Automatic behavior.** Ciaobot automatically archives chat transcripts; when enabled, it runs the configured session-insights model on archived session JSONL, appends `## Session insights`, records a structured trajectory JSON when trajectory capture is enabled, and then runs a heuristic pass over those insights to draft memory proposals. It also dispatches enabled schedules, records background-job telemetry, refreshes the vault index, updates configured skill mirrors, and backs up the device branch according to the startup/system automation configuration. The Settings → Models page only exposes routines that have a selectable model; heuristic follow-on jobs such as memory proposals and trajectory capture are tracked in Settings → Automation instead.

**Not automatic.** Archive-time extraction auto-applies only confident, state-shaped facts (and only from turns the user typed — never an unattended turn); event-shaped, unsure, and failed facts wait in the proposals queue, and the unattended nightly curator never promotes a new region fact. Skill-evolution output is a draft proposal under the vault's `Workspace/Skill-Proposals/`; Ciaobot does not apply those edits automatically. Scheduled chats still run through the normal provider pipeline and permission flow, and an unattended run defers and reports any approval-requiring action instead of seeking an alternate route. A schedule with `archive_policy: auto` is archived only when the post-run classifier says the result does not need user attention; failed, blocked, retrying, or useful runs remain visible. Routine-model choices do not change an active chat's selected provider/model.

## Providers

The set of runtime providers lives in one place: `ciao/provider_registry.py`. Each `ProviderDescriptor` carries the provider's id, its label forms, and dotted import paths for its factory, login command, system-skill listing, readiness probe, and CLI upgrade, plus its thinking levels, default model/bucket, and default-model settings attribute. Paths resolve lazily, so enumerating providers never imports an agent SDK. Everything that needs to list, label, validate, or probe providers reads the registry rather than repeating a provider-name literal, and `ciao/provider_service.py` resolves the factory and owns the live instance. Adding a provider is a descriptor plus an adapter.

Dispatch is provider-driven, not model-driven. Each chat and schedule carries an explicit provider and model. The two supported runtime providers are `claude`, which runs Claude Code / Claude Agent SDK against Anthropic, and `opencode`, which requires OpenCode 2.0.16+ and runs one `opencode serve` process per active chat on an ephemeral loopback port behind a per-process `OPENCODE_SERVER_PASSWORD`. A shared server would be cheaper, but Ciaobot scopes its control-plane MCP token per chat while OpenCode configures MCP at server scope, so per-chat processes keep that token scoped. Readiness reads the V2 server identity from `/api/info` and verifies the used operations against `/openapi.json`; retired V1 routes are never probed. Chat output uses the `/api/event` SSE stream. Per-session `agent`, `model`, and ordered `permissions` carry the mode mapping. Credential denies include both the resolved absolute runtime root and, when it is inside the session location, its V2 workspace-relative spelling. Prompts use V2's `text`/`files` body with queued delivery, so a mid-turn message remains a later turn. Because V2 has no stable per-prompt system field, Ciaobot's compact core/runtime context is carried in the same text behind `[CIAO_CONTEXT_BEGIN]` markers; transcript rendering and permission-rotation handovers strip those markers before showing or copying visible history. Flat V2 message records are normalized once at the provider boundary into the small `{info, parts}` representation used by transcript rendering and recovery. Active children come from `/api/session/active`; child discovery uses `/api/session?parentID=...`. Fork, interrupt, session-scoped permission replies, forms rendered as AskUserQuestion cards, and real child sessions are native. Native form fields retain their required/conditional/format/length/range/pattern metadata in the PWA; invalid non-empty values are blocked before the action is sent, while optional empty answers remain an explicit reply rather than a cancel. Delivery cards stay mounted until the provider result is acknowledged, and a disconnected chat socket queues a native response for the next connection. OpenCode is bring-your-own-provider: the model catalog joins active `/api/provider` rows with the flat `/api/model` snapshot, addresses models as `providerID/modelID`, exposes reasoning variants from each entry's V2 array, and reports no unified quota. It needs almost no asset projection because it discovers `.claude/skills`, `.agents/skills`, and `AGENTS.md` natively — only `.opencode/agents/`, `.opencode/commands/`, and the `mcp` object in `opencode.json` are generated.

Anything the two supported providers do not serve directly is reached through OpenCode, which is bring-your-own-provider: a user configures Ollama, OpenRouter, or any OpenAI-compatible endpoint in OpenCode itself, and Ciaobot lists whatever OpenCode reports as connected. Ciaobot previously reached those upstreams itself by injecting `ANTHROPIC_BASE_URL` into the Claude Code CLI; that layer is gone. The backend keeps provider routing explicit so schedules, handovers, and archived chats remain reproducible.

### Claude harness overrides

Ciaobot runs the vendors' CLIs but hides the harness surfaces the PWA already owns. In `ciao/execution_modes.py:24` nine skills are removed from the model's context via `skillOverrides` (`schedule`, `loop`, `design-sync`, `update-config`, `fewer-permission-prompts`, `doctor`, `run`, `run-skill-generator`, `dataviz`) and the same nine are denied as `Skill(name)` in `ciao/config.py:30`; `ciao/providers/claude.py:536` wires `settings={"skillOverrides": …}` with `setting_sources=["user","project","local"]` so workspace skills and agents still resolve. See [README — What we change from stock Claude Code](../README.md#what-we-change-from-stock-claude-code).

## Frontend

`web/` is a Vue 3 + Vite + Pinia + TypeScript PWA. The hierarchy is workspace → project → chat. Configured logical workspaces live in `CiaoConfig.workspaces` (loaded from `.runtime/workspaces.json`, the only source of the list, which Settings owns; a fresh install bootstraps it from the vault) and are exposed through `GET /api/workspaces`. Each workspace may set an optional `color` accent preset (`pink` default, plus `cyan` / `amber` / `emerald` / `violet`); the PWA applies it as accents only when that workspace is active. The Pinia project store loads that endpoint; the sidebar workspace switcher and empty-state General chat buttons render from the configured workspace list. Backend project discovery, completion, restore, schedule routing, spawned-agent `GWS_PROFILE`, and `CIAO_ACTIVE_WORKSPACE` also read from the workspace registry. The model picker has one section per provider: Anthropic (via Claude Code) and OpenCode.

The shell presents the same durable model everywhere: **request → run → output → durable knowledge**. Home uses the Workbench composition: `HomeIntake.vue` starts an ordinary project chat while keeping unsent text scoped to its workspace, and `HomeReviewSummary.vue` surfaces active-workspace proposals/upkeep/automation state and labels checking, stale, empty, and failed snapshots, sitting in a side rail beside the request column on wide panes and stacking below it under 980px; chat keeps reasoning in the transcript while a conditional Context / Activity / Output inspector exposes existing run and file state. Project remains the context envelope; Memory's Suggested and To revisit sections are the durable-knowledge inbox and its Map (Graph/List) is the exploration mode. These are frontend compositions over existing stores and APIs, not new persisted object types. Shared schedule and retirement load contracts keep a pending or failed fetch from rendering as a successful empty list.

Memory (`/memory/<section>`, `MemoryMapView.vue`) has five sections — Suggested, To revisit, Map, Retired, History — listed in the sidebar the way Settings lists its tabs; each is a route, bare `/memory` returns to the section last visited, and the old `/proposals` address redirects to Suggested. The Map section renders the active workspace's vault as a browsable graph: notes as nodes, `related:` frontmatter and relative markdown links as edges, from `GET /api/vault/graph`. It follows the same shell pattern as Schedules/Settings — a route pointing at `ChatLayout.vue`, which switches `viewMode` and renders the pane — rather than introducing a second app shell. The node/edge data itself is exactly what `ciao vault-index`'s `scan_vault()`/`_build_graph()` already compute for `INDEX.md` and `--neighbors`; the route only serializes that to JSON and optionally scopes it to one `?workspace=`. Each node also carries its verification age (`updated:` frontmatter or mtime) judged by the same staleness detector the audit uses, and the review queue's `unverified` signal uses the same rule (`memory_audit.note_verification`), so the map's "unchecked" count, the list view's Checked column, the note tile's callout and To revisit cannot disagree with each other or with what daily curation acts on.

The map has two surfaces with parity of action. The graph canvas is driven by Pointer Events through `web/src/lib/graphGesture.ts` (unit-tested without a DOM): one pointer owns a gesture, tap slop separates a tap from a drag, `pointercancel`/`lostpointercapture` abandon it, and a second or non-primary pointer is refused — so a touch tap selects, a drag pans, and a cancelled or extra-finger gesture never activates an unintended note. `touch-action: none` is scoped to the canvas so page scroll and browser zoom stay available everywhere else. The list view is the keyboard/touch-complete alternative: each note title is a native named button, and closing the note restores focus to the control that opened it. A selected note opens in a docked tile — `PinnedFilePanel`, the same component a chat's pinned file uses, with the map's stale-note callout and linked notes in its `lead`/`after` slots — and at 900px and below that tile becomes a focus-contained bottom sheet. There is no path finder: selecting a note highlights its neighbours, which is the connection question the map answers.

Primary navigation uses native button/link semantics with visible keyboard focus, and mobile controls keep a 44px minimum target on every coarse-pointer layout. Browser zoom remains enabled; Settings font scaling is an additional preference rather than a replacement for platform accessibility controls. Tab bars are a shared `TabBar` component carrying the ARIA tablist contract — a single Tab stop with Left/Right/Home/End moving between tabs and selection following focus — so the behaviour cannot be dropped by copying the markup, which is how the memory-map review bar first shipped without it. Modal-like surfaces use `useModalFocus.ts` for initial focus, Tab containment, Escape capture before global shortcuts, inert background content, and opener restoration; native button semantics determine Enter, so a visible Cancel target can never confirm a destructive dialog. Context menus use menu/menuitem roles, focus their first action, support Arrow/Home/End/Escape, and return focus to the trigger. In ChatLayout, unmodified number keys `1`–`9` switch to the corresponding workspace in the sidebar's displayed order; the shortcut is ignored while typing and the workspace buttons show their assigned key. On the home screen, Needs You, Working, Unread, and Earlier are the authoritative lane order; arrow navigation follows the rendered lane layout: stacked workspace lanes use up/down between lanes and left/right within a lane, while side-by-side lanes use the corresponding horizontal/vertical mapping. The sidebar independently discloses each chat's running subagents inside an expanded project, while opening a subagent's read-only view reopens its parent group. Automation details preserve their title on narrow screens by moving secondary actions into an overflow menu, collapse long prompt previews, and explain stale project/chat targets without exposing raw runtime IDs.

Each workspace has a "General" project plus auto-discovered projects from its configured `vault_root/projects/active/`. Chats stream over WebSocket; image uploads and pending comments are scoped to the active chat, then attached to that chat's next prompt. Closing an unused new chat deletes its server-side draft; closing a completed chat disconnects it. A non-image file dropped into a host or client chat is uploaded through the chat attachment contract and inserts a bounded opaque reference; the provider-only prompt expansion resolves the server-side path. Pinned files are scoped per-chat (persisted in local storage, falling back to project scope if no active chat exists) and render in a split layout sidebar. Commenting in that sidebar stays open while a turn streams — the comment simply rides on the next message — and the panel's auto-reload at turn end is deferred while a text edit or comment draft is open, then applied once the user saves or cancels.

In client mode, a failed remote-host WebSocket tunnel emits the dedicated
`host_unreachable` connection state. The PWA keeps it out of conversation
history, shows one reconnecting notice regardless of retry count, and offers a
confirmed local force-handover action to disconnect and become host.

**Client mode is a mirror, with one labeled exception.** `StandbyProxyMiddleware`
(`ciao/node_proxy.py`) tunnels the API, the WebSockets, *and* the UI bundle, so a
connected client is meant to be indistinguishable from opening the host's own URL
in a browser: same build, same Settings, same state. `index.html` and unknown
`/assets` hashes come from the host; hashed names the local build also has are
content-identical and served locally to save a hop. `/api/auth/settings` is
mirrored too, because the password a client logs in with is the host's.

The exception is the machine itself. `/device` (`DeviceView.vue`) is served from
the local bundle, sits outside the router's auth guard and outside `ChatLayout`,
and calls only never-proxied routes (`/api/node/*`, `/api/device/*`,
`/api/startup-status`): role, host connection, disconnect, and this machine's own
version and update. It is the escape hatch, so it must work with the host down —
which is also why an unreachable host answers a *navigation* with the local shell
instead of a blank page, while non-navigations get an honest 503. Host-scoped
Settings names the host node it is editing (`host_node_id` on
`/api/node/status`), and the client banner links to `/device` rather than to
Settings. Session cookies the host issues (for example after a password change
made from a client) are captured into `node_state` and stripped from the
forwarded response, so the tunnel survives a rotated host secret and the
browser's cookie stays this node's own local session.

Client mode has two loopback origins: the content origin (`localhost`) serves
proxied host UI/API traffic, while the device origin (`127.0.0.1`) is the only
origin accepted for `/api/node/*`, `/api/device/*`, `/api/desktop-drop`, and
`/device`. The device origin also requires an explicit local-control header on
API requests and a loopback TCP peer. A client request to a device route from
the content origin is rejected, and a non-control navigation from the device
origin is redirected to the content origin. Host redirects are not followed by the relay.
The macOS capability grants native commands only to bundled local pages; remote
PWA content has no Tauri capability or update command. Finder drop events carry
only an opaque grant and display names; absolute paths stay in the Rust/server
grant. This is a relay compatibility boundary, not completion of the broader
credential, file-confinement, storage-isolation, or protocol work tracked by
#546.

Write/Edit/MultiEdit/NotebookEdit tool calls are tagged with `file_touch` by
`ciao/web/chat_broker.py` and surface as standalone `_filecard` entries on
reload, rendered as inline clickable preview cards that open `FileViewerModal`
(see `PWA_API.md` → "File-touch cards" for the WS + `/messages` contract). On
every file-touch event the broker also schedules a debounced content snapshot
via `ProjectChatManager.snapshots` (`ciao/web/file_snapshots.py`,
`SnapshotStore`), which writes append-only per-(chat, file) copies under
`.runtime/snapshots/<chat_id>/<urlencoded_path>/NNNN.snap` plus a sibling
`meta.json`. The PWA reads these back via `/api/file-history`,
`/api/file-content`, and `/api/file-restore` to power the FileViewerModal's
Preview / History / Diff tabs and one-click restore; `/api/vault/backlinks`
lists the notes linking to a markdown note, using the same relative/path/stem

it. Preview renders text/markdown, images, PDF/PPTX (via a binary preview), and

Archived chats are read-only but can be continued into a new active chat via the "Continue in new chat" button (calling `POST /api/chats/{chat_id}/continue`). A header "files touched" chip in `ChatPanel.vue` summarizes the dedupped set of files written/edited in the chat and links each entry back to the modal.

Background subagents (Agent tool dispatches with `run_in_background`) stay visible after the parent turn ends. Unlike background Bash, Agent calls are not rewritten by the foreground Bash hook. `ciao/subagent_tracking.py` parses the parent session JSONL for async dispatches and their `<task-notification>` completions; a per-chat watcher in `ProjectChatManager` publishes `chat_subagents_ready {remaining}` on `/ws/events` whenever the running count changes (the connect snapshot carries `background_agents` so reloads heal stale counts). While agents run, the PWA shows a pulsing "N agents" pill in the chat header and a dimmed sidebar dot, polls `/api/chats/{id}/subagents` for a near-live feed, and renders each transcript in a `SubagentPanel` anchored under the dispatching turn via the server-computed `turn_index`. Between turns the manager also drains the idle SDK stream (`ClaudeProvider.drain_events`): when a finished agent triggers a CLI-initiated parent follow-up turn, its events are forwarded live on a background `ChatStream` and announced like a normal result. Without the drain, those buffered messages would silently corrupt the next turn's `receive_response()`. The parser also records CLI-owned tasks (Monitor, background Bash, workflow launches) with `kind="task"` from their `toolUseResult.taskId`; they stay out of the agent counts and sidebar rows, and the same watcher delivers one wake turn via `_deliver_wake` when the owning CLI process is gone while such a task is still running, so a dead CLI can no longer orphan a long-lived command silently. On startup `sweep_orphaned_cli_tasks` wakes chats whose tasks were running when the server died (bounded to chats active within the last 7 days so the first upgrade does not wake months-old Monitors), and the wake prompt itself marks those tasks `lost` in the JSONL so it is sent once.

Subagents a chat spawns (`Agent`/`Task` dispatches) are surfaced as sidebar rows beneath the chat, and each row opens a read-only view of that agent's own conversation. `GET /api/subagents/running` returns dispatch metadata only — no transcripts — and only for the chats `ProjectChatManager.active_chat_ids()` already considers active, so the sidebar costs one JSONL parse per working chat rather than one per registry row; `subagent_tracking.running_agents` names the rows behind that count, with the same transcript-idle fallback, so a parent turn killed mid-dispatch cannot leave a row pinned forever. The rows are what the parent session can name: an agent enters its state only when the `tool_result` carrying the `agentId` lands, which for a background dispatch is the launch receipt but for a foreground Task is its completion — so a running foreground agent is invisible there by construction, and shows in the chat's own live trace instead (its turn is still streaming). The PWA polls it only while something is working and replaces the map wholesale, which is how a finished agent's row disappears. A row (and the `SubagentPanel` header inside the Activity trace) links to `/chat/{chat_id}/subagent/{agent_id}` — `SubagentChatView.vue`, fed by `GET /api/chats/{id}/subagents`. The view is read-only because a Claude Code subagent is a transcript file, not a resumable session: the composer is disabled rather than removed, and Esc returns to the parent chat instead of closing it. Nothing is archived when an agent finishes — the completed transcript stays in the chat's Activity trace.

## Workspace git sync

Every instance is identical (no primary/secondary, no cloud). Sync and branch backup operate on the repo containing the vault root (`ciao/local_session.py::sync_root`): with the default layout (vault inside the workspace) that resolves to the workspace repo; a vault that lives elsewhere in its own repo is synced there instead, and a missing/non-git vault falls back to the workspace root. Ciaobot never creates or switches local branches: it works on whatever branch that checkout is currently on (`ciao/local_session.py::workspace_branch`). A background loop pushes that branch for backup; roots that are not git repositories or have no `origin` remote skip all git background work with a single INFO log (a fresh `ciao setup` initializes local repos, but they have no remote until the user adds one).

**Sync flow** (`ciao/local_session.py`, `LocalSessionManager`). When the user clicks "Sync with Remote" in Settings, `POST /api/local/handback` commits pending work, pulls from origin (merge-based), and pushes the current branch. Workspace sync never requests app deploy; app updates happen through package upgrades. A **conflicting pull** is left in the tree and `POST /api/handover/merge` opens an **interactive chat** in the personal `General` project: the chat's agent resolves the conflicts, asking the user via `AskUserQuestion` (push-notified) when ambiguous, then pushes the branch (it does not redeploy). After that chat lands, `POST /api/local/resync` merges `origin/<branch>` into the checkout after committing any pending work (fast-forwarding in the normal case). It merges rather than force-resetting, so it works on the live workspace's dirty tree and never discards local commits. See `PWA_API.md` → "Workspace git sync".

## Package updates and setup

**App updates.** Workspace git handback never implies a deploy. `GET /api/package/status` reports `ciao.__version__` and a best-effort latest version from GitHub. Production macOS installs are self-contained app bundles: the Tauri updater verifies and replaces the signed app archive, including the embedded engine, then restarts the LaunchAgent. `POST /api/package/update` is retained as a diagnostic response that points users to the one-line installer; it does not invoke Homebrew, PyPI, or `pip`. Editable git checkouts still use `git pull`.

**Setup readiness.** When `PWA_AUTH_TOKEN` is absent, Ciaobot starts in bootstrap mode using `~/.ciao/bootstrap` (or `CIAO_BOOTSTRAP_WORKSPACE`) and persists a generated temporary auth token under that workspace's `.runtime/`. `GET /api/setup-status` is public like startup status, because the first-run wizard needs it before a normal session exists. It reports workspace/vault/token/push-contact checks plus Claude Code and OpenCode readiness probes, without returning secret values. The local first-launch URL `/?setup=<token>` redeems `.runtime/setup-token` on localhost only, sets the signed PWA session cookie, deletes the one-time token, and redirects to `/`. The wizard finishes with `POST /api/setup/finish`, which is bootstrap-only and localhost-only: `workspace` is required (the wizard's primary folder question), `password` is required (the wizard asks for it in the main flow and setup always writes `PWA_AUTH_REQUIRED=true`; the inherited bootstrap token is machine-generated and unusable from a second device), the chosen provider is persisted on the first logical workspace, and `vault_root` is optional, defaulting to `<workspace>/memory-vault`. It writes the real workspace `.env`, scaffolds the configured vault root and provider asset catalogs, ensures workspace and vault are (in) git repositories with their protective `.gitignore`s (see "Workspace layout"), creates the server LaunchAgent, then requests the normal restart exit so launchd can relaunch into the real workspace. `Ciaobot.app` owns the Dock window, tray, notifications, and login toggle. The rumps menu-bar companion and the generated `Ciaobot Server.app` launcher it lived in are gone; setup removes both, plus the `com.ciao.menubar` LaunchAgent, from installs upgrading from an older version. Without the desktop app there is no tray — the engine still runs under launchd and the PWA is reachable at localhost. A foreground `ciao run` supervises the restart exit itself: when the server exits with the restart code, the CLI re-execs a fresh `ciao run` (picking up newly installed code) instead of dying.

## Project naming convention

Every configured workspace uses the same shape: a project is a folder under `<workspace.vault_root>/projects/active/<name>/` with a same-named main doc `<name>/<name>.md` (or `README.md`). On completion it moves to `<workspace.vault_root>/projects/completed/<name>/` via the PWA's "Complete" button (or `complete_project()`).

Completed projects can be restored. The sidebar footer has an archive icon next to "+ New Project" that opens a modal listing the current workspace's completed projects (`ProjectChatManager.list_completed_projects()` scans the `projects/completed/` tree read-only). Each entry has a Restore button: `restore_project(workspace, stem)` moves the folder back to `projects/active/`, flips frontmatter `status: completed` back to `active`, and re-runs auto-discovery to recreate the PWA project. Auto-discovery derives a stable id from the workspace and folder slug; the original chats stay archived. Routes: `GET /api/projects/completed` (optional `?workspace=`) and `POST /api/projects/completed/restore` (see `PWA_API.md`).

Workspaces are archived the same way rather than deleted (`ciao/workspace_archive.py`). Settings → Workspaces → Archive removes the workspace from the registry — so the sidebar, pickers, per-workspace system routines (Workspace care, Skill reflection), skill sync, vault scans, the Memory Map, vault review and the proposals queue all stop seeing it, since each enumerates the registry — and moves its folder intact to `<install>/.archived-workspaces/<name>-<YYYYMMDD-HHMMSS>/`. Before the move, its projects are removed through the same `_remove_project` path `complete_project` uses (open chats are transcript-archived, then removed), and its user schedules (matched by `workspace`, target project or target chat) are taken out of `.runtime/schedules.json` into the archive's `archive.json`. After it, its rows leave the search index and, on a shared-vault install, `INDEX.md` is rebuilt so entity hints stop naming its notes. Nothing is merged into another workspace. A workspace with a running chat is refused, as are the primary and the last workspace. The Archived workspaces list under the workspace cards restores one: the folder moves back, the registry entry and schedules return, and discovery recreates its projects; old chats stay archived.

- **Folder name** is the slug used internally (`vault_folder`). Lowercase + kebab-case is preferred but not enforced; spaces, mixed case, and underscores all work. Avoid path separators and leading dots.
- **PWA display name** comes from frontmatter `name:` (or `title:` if `name:` is absent), so it can be any human-friendly string with spaces (e.g. `name: AI Championship Project`). If both are missing, the folder name is used as the label.
- **Project context** — the blurb injected into every user turn as `[Project context: ...]` — is frontmatter `description:`, and the doc is its source of truth. The two are kept in sync both ways: `update_project()` writes an edit made in the PWA back into `description:` (`_set_frontmatter_description` rewrites that key surgically, leaving the rest of the file byte-for-byte), and every auto-discovery pass re-reads the doc so an edit made by hand — or by the archive-time insights fold in `project_doc_update.py` — reaches the preamble. Discovery reads are memoised on the doc's `(mtime, size)` because it runs on every `list_projects()` call. An empty `description:` never clears a context the registry already holds; the next save pushes it into the file. The one exception to doc-wins is the first bind, when a manually-created project adopts a matching vault folder: a context typed in the PWA before the folder existed survives and is written into the doc instead, since the README it is adopting was most likely scaffolded. Only the *path* of the doc is injected alongside it (`[Canonical doc: ...]`), so the body stays out of the per-turn token cost and the agent opens it on demand.
- Top-level reference docs that live directly under `projects/` never "complete"; don't put real projects there.
- A stray `projects/active/<Name>.md` at the top level gets auto-promoted to `<Name>/<Name>.md` on the next server start, so the folder+file invariant always holds.
- Every workspace has an auto-created `General` project bound to `projects/active/general/`. It is marked `is_auto` and displays the "auto" chip in the sidebar. It's where ad-hoc chats land and where scheduled automations run; don't delete it.
