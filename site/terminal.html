A shell on the computer running Ciaobot

The terminal panel opens a real shell on the machine Ciaobot runs on. Here is where that shell lives, what it is allowed to do, and how long a session lasts.

Where it runs

The panel is not a shell that lives in the browser. It is a process on the computer Ciaobot runs on, started by the engine, with the account the engine runs as. What you see in the panel is the bytes that process writes, sent to your browser as they arrive.

The shell it starts is the engine account's login shell on macOS and Linux, and PowerShell on Windows.

It is not sandboxed, and it is not confined to your notes folder. Whatever the engine's account can read, the terminal can read, and the workspace's File access setting does not apply to it. How file access works →

That matters most on a shared or rented machine, where the engine runs as the service's own account. Treat the terminal panel as a full shell on that machine, and treat anyone who can sign in to Ciaobot on this engine as someone who can open it.

What gets you in

Your signed-in session is what opens the terminal. There is no second password prompt: the same browser session that can talk to the agent can open the panel, because on this engine those are already the same level of access.

The panel still holds a separate, short-lived permission in a cookie your page's own script cannot read: a grant that lasts fifteen minutes and belongs to this browser. It is how the panel knows which browser may hold the socket. Signing out of Ciaobot ends it, and so does changing your password: a new password ends every grant, on every device, including the one that changed it. While the panel is open and the engine closes the socket, it asks for a fresh grant for itself, so the fifteen minutes bound a grant rather than an open pane.

A workspace that denies the agent a shell does not deny you one. If a workspace removes the agent's Bash tool, or confines its shell to the workspace, the browser terminal still opens the engine account's own shell. The signed-in session is the boundary; keep that account, and who can sign in to it, as the thing you protect.

Opening a terminal

A terminal belongs to one chat or one project. Open the panel from the chat you are in, or from the project, and the shell starts in the folder Ciaobot resolves for that target: the chat's code-mode worktree if the chat has one, otherwise the project's linked repository, otherwise the workspace folder. You do not pick the folder, and neither can the agent.

The panel lists the sessions opened for that chat or project, so a shell you left running is still there to come back to.

Hide, End and the fifteen minutes

  • Hide detaches. The panel closes and the shell keeps running on the machine. Open the panel again and the session is there, with what it has printed since.
  • End closes the shell and removes the session. It is the only action that stops the process.
  • A session nobody is attached to is reclaimed after fifteen minutes. The clock is fixed: a session that keeps printing is reclaimed on the same clock as one that sits idle, and output does not push the deadline back.
  • At most four terminal sessions exist at once, counted across your chats and projects.

From a phone

The terminal is a panel in the app, so it works from a phone or another computer the same way it works on the machine Ciaobot runs on: the shell is on that machine, and the panel is a window onto it.

One rule comes with it. From another device the connection has to be HTTPS; plain HTTP is accepted only from a browser on the engine's own machine. On a host you reach over the network, run tailscale serve --bg 8443 and use the https address it prints. How to reach a remote Ciaobot →

On a phone the on-screen keyboard sends text and Return, and it has no Ctrl key, so use the shell's own commands to stop a running program.

Scrollback is bounded

To be able to come back to a session, Ciaobot keeps its last 256 KB of output. That is the whole history it has of what the shell printed.

If a session has produced more than that, the earliest output is gone. The panel says the replay was truncated and shows the bytes that are left; it does not rebuild a screen from bytes it no longer has. A long-running session can therefore lose the beginning of its scrollback.

What the terminal is not

  • Not the agent's shell. The agent works under the workspace's File access setting. The terminal panel is yours, and the agent cannot drive it.
  • Not a background job. A long command you want reported back in a chat belongs in a background run, not in a terminal session that nobody is watching.
  • Not a terminal window on the engine's desktop. Opening a real window on that machine is a different feature, and only a browser on that machine may ask for it.
