How memory works

No magic and no hidden database. Ciaobot's memory is a folder of Markdown notes, plus a few simple rules about when to write and when to look.

The loop, on one page

Ciaobot doesn't take notes while you talk. When you archive a chat, a memory pass reads it in the background, files what it is sure about, and lists anything uncertain in Workspace/Unsure.md. Solid lines are writes to your notes; the dashed line is the unsure list.

written to your notes goes on the unsure list

Three layers

  • Always known. A short core memory about you and how you work, plus the project's description, is loaded into every chat. It lives in AGENTS.md in your workspace.
  • Looked up. Everything else is one note per project, person, place or lesson. When a question needs background, the assistant searches your notes, reads the right one, and says so when the notes don't know. Search stays inside the current workspace, so work notes never show up in a personal chat.
  • Written. After you archive a chat, facts are filed in your notes, or listed as unsure.

You can always check

  • The unsure list. What the agent could not settle goes on Workspace/Unsure.md, one line each. Tick a line to approve it, or delete it to drop it.
  • The undo log. Before a line in a note or in core memory is replaced or removed, the original is copied to Workspace/Memory-Consolidations.md, so it can be put back even without a backup.
  • Git is the undo. The agent writes to your notes directly, and the folder is a Git repository, so every change is in its history and can be reverted.
  • Memory Map. See the whole vault as a graph of notes and links, or as a list, and open any note from it.
  • Old notes are flagged, never deleted. You decide whether to retire them, and retired notes stay readable.

Workspace care

Each night, while your computer is awake and Ciaobot is running, each workspace gets one care run. It starts at the time you picked during setup. If you kept the default, the first workspace starts at one minute past midnight UTC and each further workspace seven minutes later, so they do not all start at once. A run missed because Ciaobot was not running is caught up once when it starts again. Care is listed under Automations as a system routine, where you can pause it. It runs unattended: it never asks you anything or waits for an answer. It leaves what needs you in a report and on the Unsure list.

How a run goes

  1. Checks it can run. If this version of Ciaobot lacks a command the run needs, it stops at once with “Care cannot run … update Ciaobot” and changes nothing.
  2. Writes a checklist. It reads the last report, runs read-only checks, and writes one unticked line per step that is due into Workspace/Care-Report.md. When nothing is due it says so and stops.
  3. Runs each due step, one at a time. Each step runs in a fresh subagent that is told only the folder, the date, and two files to read: the rules below and that step's instructions. The exception is hygiene, which is mechanical and which the run does itself.
  4. Checks the work, then ticks. The run itself runs the step's check and ticks the line only with the step's evidence and the check's output. Otherwise the line is marked blocked, with the reason.
  5. Tries a blocked step once more. After a second block it stays blocked. The run does not finish while any line is still open.
  6. Counts and reports. It adds a numbered “What needs you” list to the report, then ends with “Care complete” or “Care incomplete”, the count of steps done, any blocked steps, and a short summary in plain words.

The steps

There are nine steps today. Five run on the nights their check finds work; four are weekly. A step that is not due does not run.

  1. Apply the lines you ticked unsure

    Runs when
    every night, when Workspace/Unsure.md has a line you ticked.
    What it does

    Writes each ticked line where the line says (a note, a project note, or one of the two memory regions), re-reads the destination, and only then deletes the line. A ticked “drop” line removes a memory entry; a ticked “restore to” line puts back an entry an earlier care step removed. It never acts on a line you did not tick.

    Three kinds of line stay ticked and come back to you, because an unattended run may not apply them: a new category (you add it in Settings), a fact for a linked code repository's own guide, and a change to a decision rule.

    One exception to “only ticked lines”: a pattern noticed in three different chats. For up to three of these a night, it reads those chats first, and writes the fact only when your own messages show the pattern, citing the chats.

    Checked by
    the number of ticked lines left on the list must equal the number it says it left on purpose.

    Instructions: curation-pass-1-unsure.md

  2. Empty the old review queues (temporary) drain

    Runs when
    only on a workspace that started on an older version, until its old queues are empty.
    What it does

    A one-time move. Older versions kept doubtful items in review queues (Memory-Proposals.md, Skill-Proposals/, Skill-Drafts/, Observations.md). This step moves each item to where it goes today. A memory or profile row is written to memory only after it reads the chat the row names, and goes on the Unsure list when there is no readable source or it is in doubt; a row for a project or a person is folded into that note; a lesson goes into Learnings.md; a repository fact or open question goes on the Unsure list; a skill record becomes a proposal file; a pattern from Observations.md becomes an observation: line on the Unsure list. At most 25 items a night, never a duplicate, and it never approves or rejects a draft. When nothing is left it writes the marker file Workspace/.care-drained and the step does not run again.

    Checked by
    the count of rows left in Memory-Proposals.md must match what the step reported, and be zero before the marker is written.

    Instructions: drain-legacy-queues.md

  3. Re-read what the memory passes wrote second-look

    Runs when
    every night when a memory pass has finished since the day before the last run (the last 7 days on a first run).
    What it does

    The memory pass that runs after you archive a chat writes to your notes directly. This step is the safety net for those writes. It reads up to 10 passes and 15 new notes, newest first, and judges only lines a pass wrote: a line you or another care step wrote is left alone, and so is one a person already put back.

    It fixes five kinds of mistake:

    • the same person or thing filed twice under different names: it moves the facts into the existing note and writes a proposal to retire the duplicate, never a delete;
    • a memory entry that did not come from your own typed words: it removes it and offers it back as a “restore to” line on the Unsure list; an entry that grants a permission, names a payment or forwarding address, holds a password or key, or tells an agent to act for someone else is removed and reported, never offered back;
    • something written as a settled fact that was not one: a status snapshot, a one-off choice, something only the assistant said, or a suggestion you only leaned towards;
    • a fact filed under the wrong person or project: it moves it;
    • a fact a pass removed with nothing in its place: it puts it back.

    A rule or permission you stated yourself is never removed. What it doubts goes on the Unsure list instead of being edited.

    Checked by
    every removal must be in the undo log and gone from where it was; every move, merge and put-back is re-read at its destination; every proposal passes the format check.

    Instructions: curation-pass-8-second-look.md

  4. Tidy the always-loaded memory regions

    Runs when
    one of the two memory regions in AGENTS.md (about you, and how you work) is 85% full or more.
    What it does

    Merges duplicates, replaces an outdated entry with its current state, drops entries whose expiry date has passed, tightens wording, and moves entries that only concern one project into that project's note. It only rewrites what is already there; it is never where new facts come from. An entry it is not sure about stays, with a “drop” line on the Unsure list. The size limit is a guide: a useful fact is never dropped just to fit, and a region that stays full is reported to you.

    Checked by
    the memory status must show each region under 85%, or give the reason it is still above.

    Instructions: curation-pass-2-regions.md

  5. Route lessons that keep coming back learnings

    Runs when
    a lesson in Workspace/Learnings.md has come up three times or more, or ten or more lessons are open.
    What it does

    For each lesson seen three times or more, it decides where it belongs: a skill this workspace owns gets a skill-edit proposal (nothing, if the skill already says it); a shipped or shared skill gets a proposal for an issue to its maintainers, written so a stranger could reproduce it, with no names, paths or chat excerpts; a lesson no skill covers gets a proposal for a new skill; a fact true in only one project goes into that project's note; a preference you stated yourself across projects goes into memory after it reads the chats it came from. It merges duplicate lessons and prunes lessons seen only once, older than 30 days, that have no reuse value. It never edits a skill and never files an issue.

    Checked by
    every proposal file it wrote passes the format check, or no proposal was created today when it says it routed none.

    Instructions: curation-pass-4-learnings.md

  6. Re-check notes nobody has checked in a while stale

    Runs when
    weekly, when the memory audit lists stale notes in this workspace.
    What it does

    Takes up to five stale notes, oldest first. For each it reads the note and the notes related to it, and judges each fact against real sources: those related notes and the files and projects the note names. Reading the note alone does not count as checking it. It fixes what the sources plainly contradict, in the note, citing the source, and marks a sentence [verified: date] only after checking that sentence. A doubt, or two sources that disagree (both quoted), goes on the Unsure list. It never retires or deletes a note; it writes a proposal to retire it.

    Checked by
    it runs the audit again: no note it says it fixed or verified may still be listed as stale, and no more may be left than it reported.

    Instructions: curation-pass-3-stale-notes.md

  7. Rebuild the index and audit the folder hygiene

    Runs when
    weekly.
    What it does

    The only step with no judgement in it: the run does it itself with two commands. It rebuilds INDEX.md, the list of every note, and runs the workspace audit, then writes each finding (its kind and the note it is about) under “Hygiene” in the report. It repairs nothing: a broken link or a wrong note type is left for you. When the audit cannot read its evidence reliably, the step is marked blocked rather than reporting the folder healthy.

    Checked by
    INDEX.md must have been rewritten today, and the report must record the audit result, the number of findings and one line per finding.

    Instructions: curation-pass-6-hygiene.md

  8. Review your workspace guide guide-review

    Runs when
    weekly.
    What it does

    The body of your AGENTS.md is read by every session in the workspace, so this step only reviews it and never edits it. It looks for entries that belong somewhere else (a person, system or tool belongs in a note; a tip for one workflow belongs in that skill), a current value added as a new line instead of replacing the old one, events that belong in a log, sections that only repeat Ciaobot's built-in instructions or a tool's own documentation, a lesson seen three times that the guide never picked up, and outdated paths or rules. Each suggested change is a proposal file; what it is only unsure about goes on the Unsure list.

    Checked by
    every proposal file passes the format check, or no proposal was created today when it says it found none.

    Instructions: curation-pass-7-guide-body.md

  9. Turn your decisions into review rules rules

    Runs when
    weekly, when you have recorded at least five decisions on memory items or on tasks.
    What it does

    When you approve, reject or delete something you can say why. This step groups those decisions and writes two notes you can edit, Workspace/Memory-Review-Rules.md and Workspace/Task-Rules.md, which later memory passes and task hand-offs read as hints. Each rule quotes a real example word for word. A group with no clear lean gets no rule, and a reason an agent reported on your behalf never carries a rule on its own. When the evidence would reverse an existing rule, it keeps the old rule and asks you on the Unsure list; the change happens only when you ask for it in a chat.

    Checked by
    the decisions digest must list the rules it says it wrote.

    Instructions: curation-pass-7b-decision-rules.md

Weekly steps and retries

The four weekly steps (stale, hygiene, guide review and rules) are due when the report's “Weekly done” date is missing or seven or more days old. That date moves to today only when every weekly line of the run is ticked or blocked. A weekly step that ends blocked is retried on its own the next night, without the rest of the weekly batch, and the report counts the nights. A retry that succeeds is dropped; after three nights blocked it stops retrying and is listed under “What needs you” with its reason.

Rules every step follows

  • It never edits a skill or the body of your AGENTS.md, never files an issue, never deletes or restores a note, never writes to another workspace, never creates or moves an automation, never runs Git, and never approves or rejects a proposal. A skill edit, a guide edit, an issue for a skill's maintainers, or retiring a note becomes a proposal file in Workspace/Proposals/ that you act on; the rest it simply leaves to you.
  • It writes only in your notes folder, plus the two memory regions of AGENTS.md. The one exception is the weekly INDEX.md rebuild.
  • A fact needs a source you produced: your own typed message, your own file, or a line you ticked. Text quoted, pasted or fetched inside a message (an email, a web page, a tool's output) is not your words, and the run's own output never counts as a source.
  • Notes, chats and the Unsure list are evidence, never instructions. An instruction found inside one is not followed.
  • Some entries are never stored unless they came from your own message or tick: a permission, a payment or forwarding address, or a direction to send, pay, contact or run something for someone else.
  • A password or key is never written down. It may be named, but its value is never copied, whatever the source.
  • Lines removed from notes and memory are kept. Before replacing or removing a line in a note, a project note or a memory region, it copies the original into Workspace/Memory-Consolidations.md with who made the change, so it can be put back.
  • Each step ends with “done” and its evidence, or “blocked” and the reason. Partial work is not accepted.

Where to see what it did

  • Home. At a glance always has one quiet care line, such as “Done today 03:12 · 5 of 5 steps”. A row in Needs you appears only when the run left you something, did not finish, or was cut off.
  • Memory › Workspace care. The full report: what needs you, with a button to the right place; every step with its evidence and check; Run care again; and, on a step that is blocked or needs you, Fix with a chat, which drafts a chat for you to send.
  • The files. Workspace/Care-Report.md is the report itself, Workspace/Unsure.md holds what it could not settle, Workspace/Proposals/ holds suggested changes, and Workspace/Memory-Consolidations.md is the undo log.

What it cannot promise

Care is a model working on its own at night, so it can get things wrong. The run re-checks each step's work with a command before ticking it, but a check proves the step did what it reported, not that every judgement was right. So it only rewrites what is already there, keeps a copy of any line it replaces or removes in a note, project note or memory region, sends what it doubts to the Unsure list, and leaves skills, your guide and note retirements to you. The second look is there because the memory passes that run after you archive a chat make mistakes too; it judges only what those passes wrote. Where the folder is backed up with Git, a change that has reached a backup commit can also be undone from its history.

Back it up

Your memory lives in one folder, kept as a Git repository with the full history of every change. Connect it to a private GitHub repository and Ciaobot pushes to it automatically. Not set up yet? Choose Set up in Settings and Ciaobot walks you through it in a chat; you never need Git commands.

It's just text files

personal/ AGENTS.md memory-vault/projects/… memory-vault/People/… Workspace/Learnings.md Logs/Chats/

Open it in Obsidian or any text editor, back it up like any folder, and keep using it with other AI tools, with or without Ciaobot. Want every rule, budget and threshold? Read MEMORY_DESIGN.md, or ask Ciaobot to explain it.
