Trust

What runs on its own, and what waits for you

Ciaobot runs on your computer, acts through an agent you already installed, and keeps what it learns in plain files. This page says where each decision is made, what leaves the machine, and what none of it can promise.

The short version

Three layers, and it helps to know which one you are relying on. The mode on a chat decides how often the agent stops to ask. The server has its own refusals that no mode switches off. And an unattended run — an automation, or the nightly memory tidy-up — cannot ask at all, so it is held to a shorter list and reports what it skipped.

Four permission modes

Each chat has one mode, set from the chat header. Each provider also has a default for new chats in Settings → Providers, and a workspace can override that default.

ModeIn the appWhat runs without a card
Planread-only, propose changesReading notes and files, and proposing a change in words. Nothing that changes anything, including Ciaobot's own operations.
Normalask before every actionReading, as far as your provider allows it. A write, a command or an app action raises a card.
Autosafe work runs, risky actions askWork the provider's own classifier treats as safe. Every Ciaobot command still raises a card.
Bypassevery action runs without askingEverything the agent can do, including Ciaobot operations.

Auto is not a blanket yes for Ciaobot's own operations. Every Ciaobot operation is one shell command (ciao <noun> <verb>), and no command prefix is pre-approved: an allow rule on a prefix can be ridden past by a shell suffix, so a ciao call in auto mode still shows a card. If you want no cards, choose Bypass and know what it means.

A child chat an agent starts is held at or below its parent's mode. It cannot ask for a stronger mode than the chat that started it.

What waits for you, and what does not

These decisions always come back to you, whatever mode the chat is in:

  • A new fact added to the two always-loaded regions of AGENTS.md. It waits in To decide unless you turned on Dismiss and accept under Memory handover, which allows at most five per nightly run.
  • Retiring a note, or retiring one fact inside a note. A check can re-stamp a note it read and found true, or apply a cited replacement; it cannot delete anything.
  • Editing a skill or the body of your workspace guide.
  • Writing to another workspace.
  • Public or destructive actions: opening an issue, a force-push, a branch deletion.

And these run without asking, because you already asked for them or because they are the routine work you switched on:

  • Reading, searching and answering from your notes. A read leaves the vault unedited.
  • Saving the readable copy of a chat when you press Archive.
  • The confident writes of the post-archive memory pass, made in the chat it opened: updating a note that already exists, folding a decision into its project note. Each is recorded in History, and reversible where a receipt exists.
  • The nightly pass filing project, people and learnings suggestions, consolidating a region that is full, re-stamping a note it verified, and rebuilding the search index.

A model decides what is worth remembering; it does not decide what you have to approve. The deferral list lives in one place in the code and every provider is held to it, so a new provider cannot bring its own answer. How memory review works →

Which files the agent can reach

Workspace only confines the agent's file tools and its shell to that workspace on macOS and Linux, plus the system folders a command needs to run. The home folder is explicitly denied, and the rest — the interpreter, Node, the gh configuration — is granted read-only one path at a time. Whole machine lets the agent read whatever your user account can read.

Windows has no equivalent sandbox, so Ciaobot uses Whole machine there. On Linux the sandbox is bubblewrap, and Ubuntu 23.10 and later need a one-time AppArmor profile; without it Ciaobot says so and asks you to switch to whole machine, instead of running unsandboxed without saying so.

Where to set it: the workspace's settings, under File access. The feature page has the same two options →

What leaves the machine

Your notes, chats and memory stay in the folder you picked. The engine has no analytics endpoint and posts no usage data. What leaves is what a chat has to send to be answered, the update check, and anything you connected on purpose:

Where it goesWhat is sentWhen
The model provider you connected, through Claude Code or opencodeThe message, and the context the turn needs: core memory, the project's description, the notes and search results the agent readEvery turn
Google, when a workspace is linked to an accountThe request a Gmail, Calendar, Drive, Docs, Sheets, Slides, Tasks or Forms action needsOnly when you ask for one
GitHubA request for the latest releaseOn the update check
Your private backup repository, if you turned backup onA Git push of the memory folderAfter a change
A webhook trigger, if you created and enabled oneThe event body you or your service postsOnly while the trigger is enabled

A web server is the other direction. Ciaobot's interface listens on all network interfaces by default so a phone or another computer can reach it, protected by the workspace password and a login rate limit. If you only use it on the host, set Settings → Access & devices → Network access to loopback-only and close that door.

Ciaobot's own counters — which tools ran, how often — are written to a JSON file inside the workspace's runtime folder. They are not uploaded anywhere.

Sensitive topics

There is no topic filter. Ciaobot does not classify subjects as sensitive, and it will not refuse a conversation about health, money, law or anything else. That is a deliberate limit of a private assistant, and it has a cost: the provider you chose sees the chat, so the place to hold something back is the conversation itself.

What it does instead is narrower:

  • Credential files are closed to the agent's file tools in every mode, including bypass: .env, secrets/ and the runtime folder that holds the app's own state. That deny covers the file tools; a shell command is not path-scoped by it.
  • The assistant is told never to print credentials, tokens or unrelated private metadata into a reply, because search output lands in transcripts.
  • A search snippet carries only the lines that matched, so the rest of a note's private text does not arrive with the hit.
  • The memory pass does not lift facts from an automated turn, and treats an instruction inside a chat as evidence rather than a request.
  • When the notes do not hold the answer, the assistant is told to say so instead of guessing.

Retrieved text is data, not a command

Email, web pages, PDFs, connector results, vault notes, search output, another chat's transcript and command output all reach the assistant as data. A sentence inside any of them that says "run this", "send that" or "change this setting" is not a request from you, and the assistant is told to bring it to you rather than act on it.

The same rule is enforced where memory is written: a conversation is evidence, never an instruction. In the nightly run, text inside a transcript, note or queued proposal that asks to edit a skill, run a command or change a setting is reported under What needs you and nothing else.

This is a rule the assistant follows, not a filter that rewrites what it reads. It makes an injected instruction a failure to report, rather than a design that carries it out.

What this cannot establish

This page describes how the code is built, read from the code. It is not a security certification, and several real limits sit outside what any of it can promise.

  • Your provider's side. What Anthropic, OpenAI or any other provider logs and keeps is theirs. Ciaobot decides what is sent in a turn; it cannot decide what happens to it afterwards.
  • Your own account. Ciaobot runs as you, with the access you have. A bug, a malicious skill or a shell command can reach what your user account can reach, including provider credentials. Disk encryption, screen lock and OS permissions are yours to set.
  • What you install into it. A skill, plugin, MCP server or shell command you add runs with the same access. Ciaobot confines the agent's file tools; it does not sandbox an extension you chose to install.
  • A model's judgement. The rules decide whether an action is allowed, not whether it is a good idea. The assistant can be wrong, and the memory pass can file something you would not have.
  • Windows. There is no workspace sandbox there, so Ciaobot runs with Whole machine file access.
  • The network. File access does not limit network requests, and the terminal panel is your own shell, outside the agent's sandbox entirely.

If you find something that does not match this page, it is a bug in one of the two. Suspected vulnerabilities are best reported privately; the security policy says how.
