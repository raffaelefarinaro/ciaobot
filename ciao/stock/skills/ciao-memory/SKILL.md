# Durable memory and vault care

Use the configured vault root as the durable memory source. The `<ciao-context>` block names it as `vault=<path>` — write under **that** path and nowhere else. Do not infer the location from where existing notes happen to sit: an older single-workspace curator may have filed notes under a different workspace.

Read-only recall is handled inline by the system prompt (`ciao vault search`, answer from vault evidence only). This skill covers writes and curation, not a special agent role. The nightly Workspace care schedule owns its own lease, worklist, budget, and unattended rules; follow that prompt for the run. Perform mutating vault passes sequentially, whether in the main chat or a delegated task.

## Destinations and categories

- Vault pages hold durable facts about projects, people, ideas, resources, and logs. `<vault>/Workspace/Memory-Proposals.md` is the review queue for uncertain facts and unresolved destinations, not a pass log. `<vault>/Workspace/Skill-Proposals/` holds skill-edit suggestions and `<vault>/Workspace/Skill-Drafts/` holds the `[review]` drafts for lessons whose target this workspace does not own; the review queue shows a one-line `[review <id>]` bullet for each, and the record behind it is what carries the details.
- **Propose a skill; never edit or settle one unattended.** A skill-edit suggestion is filed with `ciao skill-proposal-add NAME --input-file FILE` and settled with `ciao skill-proposal-remove <name>` — `--applied` only once the change is really in the file and verified, a plain dismissal for a decision against, `--interrupted --reason ...` when the work stopped (which is not a decision and leaves the row queued). An unattended run may file and may add evidence; it may **not** edit a skill, edit the `AGENTS.md` body, or settle a proposal or draft, and it reports every one it filed under **What needs you**. A recurring learning is a *routing* priority — how often the lesson was seen, never who decided to act on it.
- Bounded memory regions live in this workspace's own `AGENTS.md`: `ciao:memory` holds cross-project preferences, environment, and lessons; `ciao:profile` holds identity and communication style. Project-specific facts never belong in these regions.
- The **Categories** section of `<vault>/VOCABULARY.md` names each category, its folder, and its canonical `type:`; do not memorize this list. Read it before writing a note and file the note in the folder its line names. If no category fits, queue a new-category question in `Workspace/Memory-Proposals.md` instead of inventing a type or stretching a category. When editing a note whose type appears in "Types (drift)", fix it. Prefer existing tags; genuinely new tags use `namespace/value`. Give People and project notes `aliases:` with terms a person would search for, since recall is lexical.
- **A person** → this workspace's configured person folder (usually `<vault>/People/`). Workspaces have no shared people folder; don't write into another workspace. **A specific project** → its canonical vault doc and log if present, not a bounded region. **Reusable how-to across projects** → `<vault>/Workspace/Learnings.md`; a sighting from a *new* source increments the structured entry's count rather than duplicating it, while re-filing one already recorded is a no-op (so a retry cannot inflate a learning towards promotion), and an entry already under `## Promoted / Resolved` stays there — record the new evidence on its line and leave the decision alone. A learning *read* off the file with no attributable source (a bare bullet, a date-only legacy line) stays `[unknown → unknown] (?)` and is deliberately not promotable: its count is unknown, not zero, so the care schedule will not plan it until real evidence accumulates. An accept with no source is the one case that still files an `x1` — the writer witnessed that sighting — with no citation on the line. **Standing operating directives** → the `AGENTS.md` body outside the bounded regions and `CIAO_CUSTOMIZATION.md`, not remembered-fact regions. When unsure about moving a fact out of the guide body, propose the move.
- **Provenance a `/remember` has to keep.** A lesson is usually remembered in a chat that is never archived, so there is no transcript turn to cite. File it with `ciao memory-proposal-add --kind learnings --request <id>` — the request id is the sighting's real origin, and the accepted line cites it as `req:<id>`, which is also what makes a retry of the same request a no-op instead of a second sighting. **Never manufacture a turn, a chat id or an archive path to satisfy the citation**, and never claim an archived turn the conversation does not have. A `/remember` inside a chat that *was* archived may carry both `--source <chat-id>` and `--request <id>`; the citation shows the archive and the dedupe keys on the request.
- **Where a lesson goes** (the routing contract, #728-D). A reusable tool/workflow instruction routes to the best matching skill this workspace **owns** under `skills/` — an inventory match is a *candidate*, not proof: read the skill and cite both why it applies and the failure you actually observed, and if the skill already says it, file nothing. A matching skill that the conversation never loaded is still a candidate; record that finding through the proposal's `origins` link to the learning, never as a `sources` entry or a `turn`. A lesson about a **packaged, mirrored or shared** skill is not yours to edit — a local edit there is discarded by the next sync — so file a `[review]` draft with `ciao skill-draft-add --input-file FILE` naming the skill, the owning repository and version when identifiable, and a `body` a stranger could reproduce with no transcript excerpt, path, name or credential in it. A lesson **no** skill covers is a `[review]` draft for a new skill instead: give the proposed name, its purpose, the trigger that should load it and the instruction it should carry — a person creates the file, and `ciao skill-proposal-add` refuses a name that does not exist yet on purpose. Opening the public issue and creating the skill are attended (`ciao skill-draft-approve`); an unattended run prepares the draft and reports it. Filing upstream is not deploying: the lesson is still not in any local skill.

## Review and consolidation

- The attended memory pass may file confident state-shaped facts directly. An unattended curation run never promotes a new fact into `ciao:memory` or `ciao:profile`; queue it for review instead. To queue a discovered fact, put the text in a scratch file and use `ciao memory-proposal-add --kind memory|profile --text-file <file> [--source <chat-id>]`. Never put untrusted fact text, names, or paths directly into a shell argument. The queue dedupes re-filed text.
- Region caps (~3000 memory / ~1375 profile chars) are advisory. Check `ciao memory status`. At or above ~85%, consolidate existing entries before adding: merge duplicates, remove expired entries, and MOVE project-scoped facts into their canonical doc. Never drop a durable fact merely to meet the cap; report an over-cap region if everything is high-signal. The cap is advisory on every path: `ciao memory update` writes and reports `over_cap` with `used_chars`/`char_limit`.
- For unattended consolidation, copy every removed or replaced entry verbatim first into `<vault>/Workspace/Memory-Consolidations.md` under a dated heading naming its region. If a drop requires judgment, queue a one-line `[review] Keep "<entry>" in ciao:<region>? Proposed action: drop because <reason>. (memory curation)` question instead; flatten multiline text and do not duplicate a pending question. Dismissing this question keeps the entry; removing it requires an attended edit.
- List pending proposals with `ciao memory-proposals`. When promoting, write the fact to its destination **before** dismissing it with `ciao memory-proposal-dismiss --text-file <file> --promoted`; a plain dismissal means it was rejected. The proposal text belongs in a file, never a shell argument. Settled skill proposals likewise stay on disk as decision records.
- **Note verification goes through the managed operation, never a direct edit.** When the care schedule's `stale_note` pass hands you a note whose facts have gone unverified, read the note, judge it against real sources, and call `ciao note verify --payload-file <file>` with the verdict as a JSON document — never edit the note's body or its `updated:` by hand. A hand edit leaves no receipt, no check state and no record of who decided, and it is exactly what the operation exists to replace. The file carries `relative_path`, `expected_revision`, `outcome` (`still_valid` | `update` | `retire` | `unverified`), `coverage`, the `evidence` citations and the exact `before`/`after` text; the path crosses in the flag because that prose is never safe as a shell argument. `expected_revision` is the hex SHA-256 of the note's full text as UTF-8, and the `stale_note` item you were given prints it as `revision <hex>` — copy it rather than guessing at the format, because a revision that does not match comes back `conflict` and verifies nothing. The reply's `status` is the decision: `applied` wrote the note through a durable receipt; `needs_review` means the rule refused to write it unattended and one typed `note_edit` proposal is now queued for the user, which an unattended run reports under **What needs you** rather than routing around; `unverified` and `conflict` wrote nothing, the first honestly and the second because the note moved since you read it. Retirement is never applied unattended at all.
- **When the worklist hands you an `stale_entry` item, the same call verifies that one fact.** A note is not the unit a person keeps current: its `updated:` is one date for every fact in it, so a whole-note verdict claims the address you re-checked AND the landlord's name from 2019. The `stale_entry` pass exists for exactly that, and its item's `reason` prints `<note> at revision <hex>, entry identity <hex>, entry fingerprint <hex> at characters <start>-<end>` — copy the revision into `expected_revision` and the fingerprint into `entry_fingerprint`, and add `entry` (that identity) to the payload file, **all 64 characters of it**: the item's label shows only the first twelve and the worklist key is a digest of the identity, so neither can be turned back into one, and anything but a full digest is refused before the note is even opened. The same operation judges that one list item. Copy every value **whole**: the fingerprint is compared as a string, so a truncated one is a different value and comes back `conflict`. In an entry payload `before`/`after` are the **entry's** text, not the note's: a whole-note replacement there would rewrite every other fact in the file to correct one. The reply gains `scope: "entry"`, and a `needs_review` entry verdict queues a `replace_entry` / `restamp_entry` / `retire_entry` proposal — whose accept changes, or removes, exactly that span and nothing else, and is undone from History like any other note write. A `still_valid` on an entry with no `[verified:]` stamp comes back `needs_review` rather than stamping one: writing a date nobody checked is inventing a verification. A fingerprint that does not match the entry as it stands is a `conflict` that writes nothing, which is the right answer to a fact that changed while you were reading it. **Re-read the note after every write.** The `revision <hex>` in the plan is the note as it stood when the worklist was computed, so the second `stale_entry` of one note — and a `stale_note` item for a note you have just written one entry of — comes back `conflict` and settles nothing; one bullet per note is the honest yield, and the rest wait for a plan built against the note as it now is. The `reason` also names **which kind of staleness** it is, and the difference is work rather than wording: `unverified for 400d against a 90d horizon` is a fact somebody checked and time passed, while `nobody has recorded a [verified:] check on this entry` is a fact nobody has ever looked at, and the two need different evidence before either is a verdict.
- **Author entity notes as one fact per bullet, and never stamp one you did not earn.** Every rule above depends on the note being written so the bullet *is* the unit: one assertion per `-` item, because two facts in one bullet share one `[verified: YYYY-MM-DD]` stamp and re-checking one silently re-certifies the other. A paragraph, a table or a code block is **not a fact this system can verify** — a note whose facts live in prose shows up as `uncovered` in the audit, the Memory Map and the review queue, which is an honest "we cannot check this" rather than a clean bill of health, and moving the facts into bullets is the only thing that fixes it. Add a `[verified: …]` stamp **only after actually going and checking that exact sentence**, never on save, never on a merge, and never as a side effect of editing anything else in the file; a stamp is a claim, and the write paths strip it from any bullet whose text they change (compared by fingerprint, not by date), so a reworded fact comes back as needing a check. **Never refresh a note's `updated:` on an ordinary save** — it is a whole-note re-stamp and belongs to the `still_valid` verdict alone; a note whose `updated:` moves on every edit can never show that one bullet in it is two years old. An entry in an explicit event section (`## Events`, `## History`, `## Log`, `## Journal`, `## Changelog`, …), a dated record in leading-date-plus-completed-past-tense form, and an exempt note type (`log`, `journal`, `workspace`) are never aged — but a bare calendar date is **not** an exemption, because a lease that ends on the 30th is a current-state assertion that happens to carry a date.
- Shape corrections as present-tense standing facts, not "User said X → assistant did Y" events. Search local memory before external sources, ask only when a missing detail blocks a correct attended write, and keep private data inside the user's workspace.
