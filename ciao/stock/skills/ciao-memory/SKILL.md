# Durable memory and vault care

Use the configured vault root as the durable memory source. The `<ciao-context>` block names it as `vault=<path>` — write under **that** path and nowhere else. Do not infer the location from where existing notes happen to sit: an older single-workspace curator may have filed notes under a different workspace.

Read-only recall is handled inline by the system prompt (`ciao vault search`, answer from vault evidence only). This skill covers writes and curation. The nightly Workspace care schedule owns its own lease, worklist, budget, and unattended rules; follow that prompt for the run. Perform mutating vault passes sequentially.

## Destinations and categories

- Vault pages hold durable facts about projects, people, ideas, resources, and logs. `<vault>/Workspace/Memory-Proposals.md` is the review queue for uncertain facts and unresolved destinations, not a pass log. `<vault>/Workspace/Skill-Proposals/` holds skill-edit suggestions and `<vault>/Workspace/Skill-Drafts/` holds the `[review]` drafts for lessons whose target this workspace does not own; the review queue shows a one-line `[review <id>]` bullet for each, and the record behind it is what carries the details.
- **Propose a skill; never edit or settle one unattended.** A skill-edit suggestion is filed with `ciao skill-proposal-add NAME --input-file FILE` and settled with `ciao skill-proposal-remove <name>` — `--applied` only once the change is really in the file and verified (a proposal that links learning findings also needs `--verification-file FILE` (a file holding the lines you changed, as you read them back) with `--applied`), a plain dismissal for a decision against, `--interrupted --reason ...` when the work stopped (which is not a decision and leaves the row queued). An unattended run may file and may add evidence; it may **not** edit a skill, edit the `AGENTS.md` body, or settle a proposal or draft, and it reports every one it filed under **What needs you**. A recurring learning is a *routing* priority — how often the lesson was seen, never who decided to act on it.
- Bounded memory regions live in this workspace's own `AGENTS.md`: `ciao:memory` holds cross-project preferences, environment, and lessons; `ciao:profile` holds identity and communication style. Project-specific facts never belong in these regions.
- The **Categories** section of `<vault>/VOCABULARY.md` names each category, its folder, and its canonical `type:`; do not memorize this list. Make each new note with `ciao note create --type <id> --title <T>` (more flags: `ciao help`); it stamps the frontmatter and files it in the category's folder. If no category fits, queue a new-category question in `Workspace/Memory-Proposals.md` instead of inventing a type or stretching a category. When editing a note whose type appears in "Types (drift)", fix it. Prefer existing tags; genuinely new tags use `namespace/value`. Give People and project notes `aliases:` with terms a person would search for, since recall is lexical.
- **A person** → this workspace's configured person folder (usually `<vault>/People/`). Workspaces have no shared people folder; don't write into another workspace. **A specific project** → its canonical vault doc and log if present, not a bounded region. **Reusable how-to across projects** → `<vault>/Workspace/Learnings.md`; a sighting from a *new* source increments the structured entry's count rather than duplicating it, while re-filing one already recorded is a no-op (so a retry cannot inflate a learning towards promotion), and an entry already under `## Promoted / Resolved` stays there — record the new evidence on its line and leave the decision alone. A learning *read* off the file with no attributable source (a bare bullet, a date-only legacy line) stays `[unknown → unknown] (?)` and is deliberately not promotable: its count is unknown, not zero, so the care schedule will not plan it until real evidence accumulates. An accept with no source is the one case that still files an `x1` — the writer witnessed that sighting — with no citation on the line. **Standing operating directives** → the `AGENTS.md` body outside the bounded regions and `CIAO_CUSTOMIZATION.md`, not remembered-fact regions. When unsure about moving a fact out of the guide body, propose the move.
- **Provenance a `/remember` has to keep.** A lesson is usually remembered in a chat that is never archived, so there is no transcript turn to cite. File it with `ciao memory-proposal-add --kind learnings --request <id>` — the request id is the sighting's real origin, and the accepted line cites it as `req:<id>`, which is also what makes a retry of the same request a no-op instead of a second sighting. **Never manufacture a turn, a chat id or an archive path to satisfy the citation**, and never claim an archived turn the conversation does not have. A `/remember` inside a chat that *was* archived may carry both `--source <chat-id>` and `--request <id>`; the citation shows the archive and the dedupe keys on the request.
- **A pattern seen once is an observation, not a fact.** A behavioural or preference pattern (of the user or of a person they deal with) that one chat does not prove is counted with `ciao observation-add`, never filed as a fact. It becomes a `[profile]` or `[people]` proposal only at three distinct chats.
- **Where a lesson goes** (the routing contract, #728-D). A reusable tool/workflow instruction routes to the best matching skill this workspace **owns** under `skills/` — an inventory match is a *candidate*, not proof: read the skill and cite both why it applies and the failure you actually observed, and if the skill already says it, file nothing. A matching skill that the conversation never loaded is still a candidate; record that finding through the proposal's `origins` link to the learning, never as a `sources` entry or a `turn`. A lesson about a **packaged, mirrored or shared** skill is not yours to edit — a local edit there is discarded by the next sync — so file a `[review]` draft with `ciao skill-draft-add --input-file FILE` naming the skill, the owning repository and version when identifiable, and a `body` a stranger could reproduce with no transcript excerpt, path, name or credential in it. A lesson **no** skill covers is a `[review]` draft for a new skill instead: give the proposed name, its purpose, the trigger that should load it and the instruction it should carry — a person creates the file, and `ciao skill-proposal-add` refuses a name that does not exist yet on purpose. Opening the public issue and creating the skill are attended (`ciao skill-draft-approve`); an unattended run prepares the draft and reports it. Filing upstream is not deploying: the lesson is still not in any local skill.

## Review and consolidation

- The attended memory pass may file confident state-shaped facts directly. An unattended curation run never promotes a new fact into `ciao:memory` or `ciao:profile`; queue it for review instead. Exception: operator-set Memory handover=all (see pass 1). To queue a discovered fact, put the text in a scratch file and use `ciao memory-proposal-add --kind memory|profile --text-file <file> [--source <chat-id>] [--decide nightly|you --decide-reason-file <file>]`. `nightly`: more context settles it; `you`: operator identity or preferences. Never pass fact text, names or paths as shell arguments. The queue dedupes.
- Region caps (~3000 memory / ~1375 profile chars) are advisory. Check `ciao memory status`. At or above ~85%, consolidate existing entries before adding: merge duplicates, remove expired entries, and MOVE project-scoped facts into their canonical doc. Never drop a durable fact merely to meet the cap; report an over-cap region if everything is high-signal. The cap is advisory on every path: `ciao memory update` writes and reports `over_cap` with `used_chars`/`char_limit`.
- For unattended consolidation, copy every removed or replaced entry verbatim first into `<vault>/Workspace/Memory-Consolidations.md` under a dated heading naming its region. If a drop requires judgment, queue a one-line `[review] Keep "<entry>" in ciao:<region>? Proposed action: drop because <reason>. (memory curation)` question instead; flatten multiline text and do not duplicate a pending question. Dismissing this question keeps the entry; removing it requires an attended edit.
- List pending proposals with `ciao memory-proposals`. It prints 20 at a time: when the output says `more with --offset N`, rerun with `--offset N` until nothing remains, so the whole queue is reviewed. When promoting, write the fact to its destination **before** dismissing it with `ciao memory-proposal-dismiss --text-file <file> --promoted`; a plain dismissal (`ciao memory-proposal-dismiss --text-file <file>`, without `--promoted`) means it was rejected. The proposal text belongs in a file, never a shell argument. Settled skill proposals likewise stay on disk as decision records.
- **Note verification goes through the managed operation, never a direct edit.** A hand edit leaves no receipt, no check state and no record of who decided, which is what the operation replaces. When the care schedule hands you a `stale_note` (or a single `stale_entry`):
  1. Read the note and judge it against real sources. Run `ciao note related <path>` first: a disagreeing note is cited evidence, and a related note you actually checked gets its own payload. Reading a note is not checking it.
  2. Write the verdict as a JSON file and call `ciao note verify --payload-file <file>`. Fields, the `expected_revision` rule, the entry-level steps and a worked example are in `references/note-verify.md`.
  3. Act on the reply's `status`: `applied` is done; `needs_review` means one proposal is queued for the user, so an unattended run reports it under **What needs you** rather than routing around it; `unverified` and `conflict` wrote nothing.
  4. Re-read the note after every write before judging a second fact, because its revision and each bullet's stamp move when the file changes.
  Retirement is never applied unattended.
- **Vault Review ordering:** In an attended pass, run `ciao vault review keep --candidate <ID>` before editing a candidate you intend to keep. Edits change its content-hash ID, so a later keep fails; editing does not stamp `updated:`.
- **When new advice supersedes stored guidance, the note keeps one instruction.** Include its source and date, and remove the superseded line rather than annotating it. If sources genuinely conflict, let them decide instead of picking silently. An attended pass asks, quoting both; an unattended run queues one `[review]` question quoting both and writes neither as the current instruction.
- **Writing entity notes** (people and project notes). Each list item is checked on its own `[verified: YYYY-MM-DD]` stamp, so:
  1. Write one fact per bullet: one assertion per `-` item. Two facts in one bullet share one stamp, so re-checking one silently re-certifies the other. Splitting a bullet to add a fact is fine; merging two facts into one bullet is not.
  2. A paragraph, table or code block is not a fact this system can verify. A note whose facts live in prose shows as `uncovered` in the audit, the Memory Map and the review queue, and moving the facts into bullets is the only fix.
  3. Add a `[verified: …]` stamp only after actually going and checking that exact sentence, never on save, on a merge, or as a side effect of another edit. A stamp is a claim; the write paths enforce it in both directions against the note as it stood before your save: a bullet whose text changes loses its stamp, and an untouched bullet has a re-dated stamp put back to the date it really carried. Nothing can undo a stamp you add to a brand-new bullet, which is why the answer to "should this fact get a stamp?" is always "only after checking".
  4. Leave the note's `updated:` alone on an ordinary save. It is a whole-note re-stamp that belongs to the `still_valid` verdict, and a note whose `updated:` moves on every edit can never show that one bullet in it is two years old.
  5. An entry in an explicit event section (`## Events`, `## History`, `## Log`, `## Journal`, `## Changelog`, …), a dated record in leading-date-plus-completed-past-tense form, and an exempt note type (`log`, `journal`, `workspace`) are never aged. A bare calendar date is not an exemption: a lease that ends on the 30th is a current-state assertion that happens to carry a date.
  6. Re-read the note after every write, before judging a second fact against it.
- Shape corrections as present-tense standing facts, not "User said X → assistant did Y" events. Search local memory before external sources, ask only when a missing detail blocks a correct attended write, and keep private data inside the user's workspace.
