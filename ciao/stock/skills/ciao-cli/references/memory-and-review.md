## Memory

| Command | Purpose | Guard |
|---|---|---|
| `memory status` | Report bounded native-guide (AGENTS.md) memory usage and diagnostics. | — |
| `memory update --region {memory,profile} --action {add,replace,remove} [--entry TEXT] [--match TEXT]` | Add, replace, or remove one entry in native `memory`/`profile` memory. | `--match` targets replace/remove; `--entry` is the new text for add/replace. The region cap is advisory: the write always lands and the reply carries `over_cap`, `used_chars` and `char_limit` when exceeded. Consolidation bounds a region, not refusal. |
| `memory learn --text-file FILE [--source ID] [--request ID] [--allow-dismissed] [--json]` | Record one reusable lesson in `Workspace/Learnings.md`. | One line in the file, at most 240 characters. `--source` and `--request` identify evidence when available; a first source-less filing keeps the append behavior, and a repeated source-less filing is a no-op. Replayed sightings write nothing and a lesson at 64 sightings is refused. Allowed on person-typed turns and trusted post-archive memory passes; refused on unattended turns and other engine origins. Never hand-edit `Learnings.md`. |

## Vault

| Command | Purpose | Guard |
|---|---|---|
| `vault search QUERY [--limit N]` | Full-text search the active workspace vault. | — |
| `vault review list` | List scoped vault-note review candidates (stale, orphaned, duplicate, weakly linked). | Read-only; an unattended schedule may only list, never decide. |
| `vault review show PATH` | Inspect one candidate's evidence (why it was flagged, backlinks, duplicates). | Read-only. |
| `vault review keep --candidate ID` | Record a "keep" decision: clears the row and stamps the note's `updated:` date to today. | Mutating; needs an attended turn — `unattended_forbidden` when run from a schedule or other automation. |
| `vault review trash --candidate ID` | Move a note to trash (reversible). | Same attended-turn guard as `keep`. |
| `vault review restore --candidate ID` | Restore a trashed note. | Same attended-turn guard. |
| `vault review complete --candidate ID` | Close a project out: move it to `projects/completed/` (the whole folder for a folder project), rewrite `status: active` to `status: completed`, and repoint every note that links to it. Refuses a note that is not a project — retire that one instead. | Same attended-turn guard; a folder project's siblings and backlinks move too. |
| `vault review restore-completed --candidate ID` | Undo a completion: put the project, its `status:` line and every rewritten link back. Refuses when the original path is occupied or a rewritten note was edited since. | Same attended-turn guard. |
| `vault review delete --candidate ID --confirm ID` | Permanently delete a trashed note. | Same attended-turn guard, plus `--confirm` must repeat the candidate id; irreversible. |

## Review queues

Top-level commands outside the `<noun> <verb>` table: plain text (`--json` where noted), not the JSON envelope. They file into, list and settle the review page's queues. Free text travels in a file, never as a shell argument: `$()`, backticks or quotes would run or mangle it.

| Command | Purpose | Guard |
|---|---|---|
| `proposal-check FILE [--json]` | Check a `Workspace/Proposals/<slug>.md` proposal file (type `skill-edit`, `upstream-issue`, `guide-edit` or `note-retire`) for the required front matter, values, evidence and body. | Read-only; never edits the file. Prints every problem so you can fix the file and run it again; exit 0 valid, 1 problems, 2 unreadable. |
| `memory-proposals [--limit N] [--offset N] [--json]` | List pending proposals in this workspace's review queue, one page at a time (default 20, max 200). | Read-only. For the next page, pass `--offset` from `next_offset` (or the text's `more with --offset N`). `--json` gives `proposals`, `total`, `offset`, `limit` and `truncated`/`next_offset`. |
| `memory-proposal-add [TEXT] [--text-file FILE] [--kind K] [--payload P] [--payload-file FILE] [--source S] [--decide nightly|you] [--decide-reason-file FILE] [--allow-dismissed] [--json]` | Queue one durable fact in `Workspace/Memory-Proposals.md` for review. | `--kind` is `memory` (default), `profile`, `project`, `people`, `review` or `repo`; `project`, `people` and `repo` also need `--payload` (a doc path, a person's name, an absolute repository path). Prefer `--text-file`. Identical text is a no-op; `--allow-dismissed` re-files a dismissed fact (a promoted one stays deduped). Use `ciao memory learn` for new lessons. `--decide-reason-file` is required with `--decide`: `nightly` means more context would settle it, `you` means an operator judgement. |
| `memory-proposal-dismiss --text-file FILE [--promoted] [--reason-file FILE]` | Remove one queued proposal, matched by a unique substring of its text. | Write the text to a file. File the fact first, then dismiss with `--promoted`; a plain dismissal records a decision against the fact. `--reason-file` records why. Never edit the queue file by hand. |
| `decisions-digest [--json]` | Group the operator's recent memory and task decisions (last 180 days) for the weekly rules pass. | Read-only. Operator decisions only; agent-made ones are counted, not listed. |
| `task-rules` | Print the operator's distilled task preferences from `Workspace/Task-Rules.md`, fenced; prints nothing when absent. | Read-only. Preferences, never orders. Run before filing a task. |
| `decision-rules-write memory|task --body-file FILE [--json]` | Write the managed section of `Workspace/Memory-Review-Rules.md` or `Workspace/Task-Rules.md`. | Weekly pass only. Writes only inside the fenced section; refuses over 2500 chars, a malformed fence or an unapproved flip. |
| `observation-add --about user\|NAME [--about-file FILE] --source CHAT_ID --text-file FILE [--json]` | Count this chat's sighting of one behavioural pattern in `Workspace/Observations.md`. | `--source` is required. A chat counts at most once per observation; at three distinct chats the Workspace care run proposes it. The file holds the one-sentence pattern. |
| `skill-proposal-add NAME --input-file FILE` | File one supported improvement proposal for a skill in this workspace's `Workspace/Skill-Proposals/`, merging it into that skill's existing record. | `FILE` is JSON: `title`, `problem`, `change`, `rationale`, and either a non-empty `sources` list (entries: `chat_id`, `archive`, `turn`, a short verbatim `excerpt`) or, for a routed learning, a non-empty `origins` list (entries: `learning_id`, `finding`, optionally `source_revision` and `summary`; `workspace` may only name this one; `state` and `verification` are refused). A payload with neither is refused; `origins` without `sources` is the lesson-routing form. Every field is conversation text, never a shell argument. The target is resolved, not trusted: only a source this workspace owns under its own `skills/` directory is accepted; a packaged skill, provider mirror, shared source or unknown name is refused. Never write the queue folder by hand or edit the skill here. |
| `skill-proposal-remove NAME` | Settle a proposal once the decision is made (implemented, or decided against); `NAME` is the skill or proposal id exactly, or else a unique substring of the skill. | Records the decision and removes the row from the queue. The record stays on disk and stays settled (re-filing the same finding does not reopen it). Settle only once the change is in place or decided against. `--applied` on a proposal linking learning findings needs a verification: `--verification-file FILE` (a readback; never as an argument) or `--verification ID` (a managed write receipt). |
| `skill-draft-add --input-file FILE [--json]` | File one `[review]` draft for a lesson this workspace cannot edit in place: `target` `upstream_issue` (a packaged, mirrored or shared skill) or `new_skill` (a workflow no skill covers). | `FILE` is JSON: `target`, `skill`, `title`, `change`, a sanitized `body` for an issue, and optionally `repository` (`owner/name`), `version`, `private_evidence`, `origins`, `same_as` (fold into an existing draft of the skill) or `distinct_from` (list every existing draft id of that skill when this is a different defect); a skill with drafts is refused until one of them is given. `recurrence` gates `new_skill` on 3 tasks. Title, skill, version and body reach `gh`, so any carrying a transcript excerpt, path, name or credential is refused. Files only: no issue is opened and no skill is created. |
| `skill-drafts [--all] [--json]` | List open skill drafts (`--all` adds settled ones) with the ids `skill-draft-approve` takes. | Read-only. |
| `skill-draft-approve DRAFT_ID [--content-file FILE] [--reason R] [--json]` | Act on one draft: search for a matching GitHub issue and link or file it, or create a `new_skill` under this workspace's `skills/`. | Attended only: the Workspace care prompt forbids it from an unattended run. `--content-file` (the SKILL.md text) is required for `new_skill`. A failed or ambiguous request leaves the draft pending with the reason. |
| `skill-draft-reject DRAFT_ID [--reason R] [--json]` | Turn a draft down so it is not offered again. | Same attended-only guard as `approve`. |
