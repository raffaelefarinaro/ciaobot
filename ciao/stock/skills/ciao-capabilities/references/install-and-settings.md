# App, settings and installation

## App and system surface

- **Settings page**: the sidebar's settings tabs are, under **Ciaobot**, **General**, **Appearance**, **Access & devices**, **Providers**, **Advanced** and **Workspaces** (including Google Workspace), then **Overview** (the active workspace's page: name, colour, provider, file access, claude.ai connectors, Google account, memory handover, update task history, archive), **Skills**, **Subagents**, **Commands** and **MCP servers** for the active workspace (read-only provider-native configuration and live chat status, with provider CLI setup/auth instructions). **Providers** holds chat provider connections and per-provider defaults, including each provider's Session insights model. **General** holds package updates, "What can Ciaobot do?", app install, notifications in the browser, keyboard shortcuts, start at sign-in, session insights and the open-source card. **Appearance** holds theme, font size, text contrast and body font. **Access & devices** holds the PWA password (always on), **Other devices** and **network access** (every interface or this computer only). **Advanced** holds the **This host** card (restart and app actions), memory backup, Ciaobot folder path (with **Move…**, on the computer running Ciaobot, to move the whole install folder elsewhere on the same disk: it stops, moves, repairs paths, repoints the service and restarts, and open chats carry on; the CLI twin is `ciao workspace-move <new folder> --apply`; on a Linux server the administrator runs that with `sudo` instead, because the service account cannot stop its own unit) (a warning appears under the path, in the setup wizard, the Move dialog and `ciao setup` when the folder is inside iCloud Drive, Dropbox, Google Drive or OneDrive, or in Desktop/Documents synced by iCloud), workspace health and the **developer** switches (developer mode, source checkout, log level), plus the Debug card in developer mode. **Automations is a page of its own in the sidebar**, not a settings tab. A workspace can live in Desktop, Documents or Downloads on a Mac where the installer added Ciaobot Server: macOS asks once for access (allow "Ciaobot Server"). Moving a workspace into or out of those folders with Move… is supported on a Mac with the Ciaobot Server host (the move runs as the host, so the same grant covers it); on a Mac without that host the move is refused.
- **Workspace extensions in the UI**: the Skills, Subagents, and Commands tabs in Settings manage Ciaobot assets.
- **MCP servers in Settings**: the **MCP servers** tab reads provider-native Claude Code and OpenCode configuration and the live connection state of already running chats in the selected workspace; it never writes configuration or secrets on its own and never starts a server. Its first box offers **Ask Ciao to add one**, which starts a chat that does the setup with you; below, a tab per CLI builds the add, list, sign-in and remove commands from a name and URL, with **Copy** and **Run in terminal**. Run in terminal types the command, prefixed with a `cd` into the workspace folder, into a separate Ciaobot session of the in-app Terminal (a remove is typed without pressing Enter); it never types into a session the user opened, and it copies the command instead when the terminal is locked or not ready.
- **Adding a server and signing in to it are two steps.** Adding writes configuration; a server that needs OAuth also needs a sign-in before its tools are usable, and one that needs no sign-in is usable as soon as it is added. Both steps happen in a terminal on the computer running Ciaobot, as the account the engine runs as, **in the workspace folder** — a provider resolves project scope from the working directory, so a command run elsewhere configures a different project than the chat reads. On a Linux server the engine is that computer, and a CLI signed in under the operator's own account is not the one the chat uses.
- **Claude Code** ([guide](https://code.claude.com/docs/en/mcp)): a remote server is `claude mcp add --transport http <name> <url>`; a local one is `claude mcp add <name> -- <command> [args...]`, where everything after `--` goes to the server rather than to the CLI. `--scope local` (the default) keeps it private to that project, `--scope project` writes `.mcp.json` in the project root and shares it, `--scope user` applies it to all your projects. Sign in with `claude mcp login <name>`, or from `/mcp` in a Claude Code session. `claude mcp list` reports each server's state, `claude mcp get <name>` shows one, and `claude mcp logout <name>` clears its stored credentials, and `claude mcp remove <name>` removes the server. Ciaobot's Claude chats run through the Agent SDK, which has no `/mcp` panel, so a sign-in has to happen outside the chat.
- **OpenCode** ([guide](https://opencode.ai/v2/docs/mcp-servers)): a remote server is `opencode mcp add <name> --url <url>`; a local one is `opencode mcp add <name> -- <command> [args...]`. The command writes the project configuration; `--global` applies it to every project. Remote servers use OAuth by default: sign in with `opencode mcp auth <name>`, or run `/mcps` inside OpenCode. `opencode mcp list` reports the state and `opencode mcp logout <name>` clears stored credentials. There is no `opencode mcp remove` — a server is removed by deleting its entry from the configuration it was added to.
- **A workspace's `.mcp.json` servers reach its Claude chats.** Every server a workspace's `.mcp.json` declares loads in that workspace's Claude chats, and `mcp__<name>` in the workspace's tool deny-list blocks one. An *interactive* `claude` session asks for approval before it uses a project-scoped server (`claude mcp reset-project-choices` forgets those choices), but Ciaobot's chats run through the Agent SDK, which loads them without asking. A server that still needs a sign-in has to be signed in outside the chat, because an SDK session has no `/mcp` panel. The per-workspace "claude.ai connectors" toggle in Settings → Overview keeps the Claude account's claude.ai connectors (Slack, Jira, …) out of that workspace's Claude chats.
- **Reloading after a change**: a new chat picks the new configuration up on its own. A chat that is already running picks it up when the agent runs `ciao chat reload` (same conversation, continues on its own).
- **Where the browser has to be.** In the default MCP sign-in of these two CLIs the browser ends on a loopback address on the computer running the CLI (`http://localhost:<port>/callback`, `http://127.0.0.1:<port>/callback`), so a browser on a phone or another computer cannot finish it on its own: the redirect lands on the wrong device. Other flows differ — a device-code flow can be finished on any device, and an Anthropic-hosted connector is authorized on claude.ai — so do not generalize the loopback rule to every sign-in.
- **The manual bridge.** The supported way to sign in from another device is the in-app Terminal, which is an interactive shell on the engine's computer (a real pty on macOS and Linux): run `claude mcp login <name> --no-browser` there, open the printed URL wherever you like, and paste the full redirect URL back at the CLI's own prompt. `ssh -t` is the alternative when the engine is remote. OpenCode's callback has to reach the CLI host — `opencode mcp auth <name>` and `/mcps` are the documented ways, and there is no paste-back for it. Keep the redirect URL and every token in the CLI or in a Settings field, never in a chat, a card or a command file.
- **Never report a step as done.** A card being opened, a browser being launched or a URL being printed proves nothing; only the provider's own state does. The quietest status is the app's own: Settings → MCP servers reads the live state of open chats and starts and writes nothing. A CLI status read is nonsecret but not free — `claude mcp list` health-checks the servers it lists, so it can contact them.
- **The agent offers, the user runs.** It may look, with its own permitted shell and under the workspace's file access, at whether a CLI exists and what it says (`--help`, `--version`), and it may read a status. For an interactive sign-in, an install or an MCP setup it hands over a command to review and run: the suggestion card never adds, authenticates or installs on the user's behalf, and a secret never goes into a card, a command file or a reply — a token belongs in the CLI or in a Settings field.
- **Google Workspace**: the card lives in Settings → Workspaces and it is the way in — the [`gws` CLI](https://github.com/googleworkspace/cli) is installed from that card, a GCP OAuth `client_secret.json` (Desktop app type) is uploaded per account, and **Sign in with Google** completes the consent in the browser, with no terminal needed. Where the browser is somewhere else, the same card's **Manual connect (paste code)** field takes the full redirect URL or the code, so it works from any browser. `ciao gws status` reports whether the workspace's account is connected and its token valid. On a headless engine, `ciao gws-auth-helper <profile>` prints the authorization URL and waits for the redirect URL to be pasted back.
- **Installing and updating**: the engine installs with one line — `curl -fsSL https://github.com/raffaelefarinaro/ciaobot/releases/latest/download/install.sh | sh` — and you open `http://localhost:8443` in a browser. To update, run that one line again, or use **Settings → General**, where one **Update & restart** click downloads, verifies and applies the engine update. There is no separate app to update: v1.0.0 retired the old macOS `Ciaobot.app`, and a machine that still has it runs the installer with `--migrate` (`... install.sh | sh -s -- --migrate`), which installs the engine *and* removes the old app bundle, and only if that removal could not run does `ciao desktop uninstall` still have to be run by hand (details in the repo README). The engine runs on macOS 13+ (Apple Silicon), on Linux, and on Windows 11 (x64 or ARM64, preview); the PWA itself is installable from any browser. When the browser offers no install prompt, the Home setup card links to the install steps for the platform and marks the step done once the app is installed.
- **Other devices**: open Ciaobot from a phone or another computer. Settings → Access & devices → Other devices lists every address this engine answers on, each with a QR code, and every device signs in with the Ciaobot password. Only an HTTPS address can install the app and get notifications: run `tailscale serve --bg 8443` and Ciaobot finds the Tailscale address on its own, or paste the address of another HTTPS proxy. Plain LAN addresses work in a browser only.
- **Forgotten password**: the installer generates a random one. On the host, the login page's **Sign in on this computer** opens a signed-in tab, and Settings → Access & devices → PWA password then sets a new one without the old password (only in a browser on the host; other devices still need the current one). Otherwise the password is `PWA_AUTH_TOKEN` in the workspace `.env` (default `~/Ciaobot/.env`), or `ciao setup-url --workspace <folder>` prints a one-time localhost login link. Nobody can reset it from another device.
- **Linux/VPS hosting**: the engine and PWA run on Ubuntu 24.04 (Python 3.12, Node 22) as a systemd service under a dedicated account, with application code administrator-owned and the workspace private to the service account. Use any browser or installed PWA as the client; agents execute on the server with its files and credentials. Setup details: `docs/LINUX.md` in the Ciaobot GitHub repo.
- **Windows 11 (preview)**: install from PowerShell with `irm https://github.com/raffaelefarinaro/ciaobot/releases/latest/download/install.ps1 | iex` — no administrator rights; it installs the engine for your account, puts `ciao` on your `PATH`, and registers a per-user logon task so the engine starts when you sign in. Claude Code installs with its native Windows installer and OpenCode 2.x with `npm install -g @opencode/cli`. Apple Intelligence is Mac-only. Engine updates on Windows use the same Settings → General card and `ciao update stage` / `ciao update apply` as on macOS; a failed update rolls back to the previous engine by itself. Details: `docs/WINDOWS.md` in the Ciaobot GitHub repo.
- **Local HTTP API**: the app serves an API for the PWA and the operator, behind the PWA session cookie; it is not a surface an in-chat agent drives. Agents use `ciao` commands, which apply workspace confinement, the plan-mode gate and telemetry. `ciao help` lists them with their flags. The API recipes for operators are in `PWA_API.md` in the Ciaobot GitHub repo (`raffaelefarinaro/ciaobot`).
