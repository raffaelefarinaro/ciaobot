# App, settings and installation

## App and system surface

- **Settings page**: the sidebar's settings tabs are, under **Ciaobot**, **General**, **Appearance**, **Access & devices**, **Providers**, **Advanced**, then **Overview** (the active workspace's page: name, colour, provider, Claude context trimming (including claude.ai connectors), Google account, memory handover (and, under it, one Ask me / Let Workspace care row each for Memory and Profile, which says whether that kind's accepts are approved by you or made by Workspace care, with a reset to inherited), update task history, archive), **Skills**, **Subagents**, **Commands** and **MCP servers** for the active workspace (read-only provider-native configuration and live chat status, with provider CLI setup/auth instructions). **Overview** ends with **All workspaces**, which lists every workspace (drag or menu reorder, New workspace) and holds archived workspaces. **Providers** holds chat provider connections and per-provider defaults, including each provider's Session insights model. **General** holds package updates, "What can Ciaobot do?", app install, notifications in the browser, keyboard shortcuts, start at sign-in and the open-source card. **Appearance** holds theme, font size, text contrast and body font. **Access & devices** holds the PWA password (always on), **Other devices** and **network access** (every interface or this computer only). **Advanced** holds the **This host** card (restart and app actions), memory backup, Ciaobot folder path (with **Move…**, on the computer running Ciaobot, to move the whole install folder elsewhere on the same disk: it stops, moves, repairs paths, repoints the service and restarts, and open chats carry on; the CLI twin is `ciao workspace-move <new folder> --apply`; on a Linux server the administrator runs that with `sudo` instead, because the service account cannot stop its own unit) (a warning appears under the path, in the setup wizard, the Move dialog and `ciao setup` when the folder is inside iCloud Drive, Dropbox, Google Drive or OneDrive, or in Desktop/Documents synced by iCloud), workspace health and the **developer** switches (developer mode, source checkout, log level), plus the Debug card in developer mode. **Automations is a page of its own in the sidebar**, not a settings tab. A workspace can live in Desktop, Documents or Downloads on a Mac where the installer added Ciaobot Server: macOS asks once for access (allow "Ciaobot Server"). Moving a workspace into or out of those folders with Move… is supported on a Mac with the Ciaobot Server host (the move runs as the host, so the same grant covers it); on a Mac without that host the move is refused.
- **Workspace extensions in the UI**: the Skills, Subagents, and Commands tabs in Settings manage Ciaobot assets.
- **Asked in a chat, set it up in that chat.** When the user asks to add an MCP server, read the CLI's `--help` if needed and offer a reviewed add command with `ciao chat needs-action command --command-file FILE`. For sign-in direct them to **Chat details → MCP**, which runs the agent's own MCP command in the in-app terminal; use Settings for provider login and configuration. **Ask Ciao to add one** opens a chat like the one they are already in. When the tab is worth pointing at (to watch the connection state, say), link it: [MCP servers](/settings/mcp). **Run it in the workspace folder.** The chat's terminal can open in the linked repository when the chat has one, and a project-scoped add (`claude mcp add` without `--scope user`, `opencode mcp add` without `--global`) writes its configuration into whatever folder the shell is in — so an add, sign-in, list or remove offered from a chat starts with a `cd` into the workspace folder, exactly as Settings' **Run in terminal** does: `cd -- '<workspace folder>' && claude mcp add …`. `<workspace folder>` is the absolute path of your own working directory (the workspace's agent root, `pwd`), single-quoted; never the linked repository. A `--scope user` or `--global` command needs no prefix.
- **Say the next step with the add, from the server's own docs.** In the reply that offers the add command, say what the server still needs before its tools work, read from its README or docs rather than guessed: a remote server that uses OAuth needs a sign-in: the user signs in with the agent's own MCP command, which **Chat details → MCP** opens; a claude.ai connector (`claude.ai …`) cannot be signed in from Ciaobot: the user connects it on claude.ai in Settings, Connectors; a local server (`-- npx …`, `-- uvx …`) has no sign-in — `opencode mcp auth` and `claude mcp login` do not apply to it — and usually reads a token from an environment variable, which the user puts in the configuration the add wrote (the `environment` block of `opencode.json`, or `claude mcp add -e NAME=…`), never in the chat; one that needs neither is ready after a reload. Say which case it is and what you will do once the user is done (`ciao chat reload`, then list the new tools). Never send the user to the interactive `opencode` or `claude` app to finish: nothing in Ciaobot needs it.
- **MCP servers in Settings**: the [MCP servers](/settings/mcp) tab is one button per installed agent, "Open MCP settings in {cli}", which starts that agent's CLI (`claude`, `opencode`, `codex`) in a separate Ciaobot session of the in-app Terminal and then types the CLI's MCP slash command (`/mcp`, or `/mcps` for OpenCode) once the CLI is running, so the CLI opens its own MCP view; the session is prefixed with a `cd` into the workspace folder. Ciaobot has no MCP sign-in of its own: the user signs in, adds and removes servers in the CLI. Its first box offers **Ask Ciao to add one**, which starts a chat that does the setup with you.
- **Adding a server and signing in to it are two steps.** Adding writes configuration; a server that needs OAuth also needs a sign-in before its tools are usable, and one that needs no sign-in is usable as soon as it is added. Manual CLI steps happen in a terminal on the computer running Ciaobot, as the account the engine runs as, **in the workspace folder** — a provider resolves project scope from the working directory, so a command run elsewhere configures a different project than the chat reads. On a Linux server the engine is that computer, and a CLI signed in under the operator's own account is not the one the chat uses.
- **Claude Code** ([guide](https://code.claude.com/docs/en/mcp)): a remote server is `claude mcp add --transport http <name> <url>`; a local one is `claude mcp add <name> -- <command> [args...]`, where everything after `--` goes to the server rather than to the CLI. `--scope local` (the default) keeps it private to that project, `--scope project` writes `.mcp.json` in the project root and shares it, `--scope user` applies it to all your projects. Sign in with `claude mcp login <name>`, or from `/mcp` in a Claude Code session. `claude mcp list` reports each server's state, `claude mcp get <name>` shows one, and `claude mcp logout <name>` clears its stored credentials, and `claude mcp remove <name>` removes the server. Ciaobot's standalone `/mcp` is app navigation, not the native CLI panel; use the chat's managed MCP sign-in for its session.
- **OpenCode** ([guide](https://opencode.ai/v2/docs/mcp-servers)): a remote server is `opencode mcp add <name> --url <url>`; a local one is `opencode mcp add <name> -- <command> [args...]`. The command writes the project configuration; `--global` applies it to every project. Remote servers use OAuth by default: sign in with `opencode mcp auth <name>`, or run `/mcps` inside OpenCode. `opencode mcp list` reports the state and `opencode mcp logout <name>` clears stored credentials. There is no `opencode mcp remove` — a server is removed by deleting its entry from the configuration it was added to.
- **A workspace's `.mcp.json` servers reach its Claude chats.** Every server a workspace's `.mcp.json` declares loads in that workspace's Claude chats, and `mcp__<name>` in the workspace's tool deny-list blocks one. An *interactive* `claude` session asks for approval before it uses a project-scoped server (`claude mcp reset-project-choices` forgets those choices), but Ciaobot's chats run through the Agent SDK, which loads them without asking. A server that still needs a sign-in is signed in with the CLI's own MCP command. **Claude context trimming** in Settings → Overview chooses which built-in Claude Code tools, bundled skills and features (artifacts, workflows, claude.ai connectors) that workspace's Claude chats leave out, to save context; the CLI's own scheduling tools stay hidden because Ciaobot's schedules replace them, and **Extra denied tools** adds names such as `mcp__<server>` or `Bash` on top. A change applies from each chat's next turn and does not affect OpenCode chats.
- **Reloading after a change**: a new chat picks the new configuration up on its own. A chat that is already running picks it up when the agent runs `ciao chat reload` (same conversation, continues on its own).
- **Where the browser has to be.** In the default MCP sign-in of these two CLIs the browser ends on a loopback address on the computer running the CLI (`http://localhost:<port>/callback`, `http://127.0.0.1:<port>/callback`), so a browser on a phone or another computer cannot finish it on its own: the redirect lands on the wrong device. Other flows differ — a device-code flow can be finished on any device, and an Anthropic-hosted connector is authorized on claude.ai — so do not generalize the loopback rule to every sign-in. For `gh` and `az` the agent can raise a device-code card that shows the code and a link, which works from any device.
- **Chat MCP navigation.** Standalone case-insensitive `/mcp` opens the current chat's MCP sidebar only for an actual Claude or OpenCode chat with a resolved owning workspace. For an unsupported provider or unresolved workspace the app shows a local reason, preserves raw text and staged state, and sends no turn. `/mcp ARG` and other arguments are ordinary prompts, not native TUI commands.
- **The manual bridge.** Ciaobot has no managed MCP sign-in and no callback paste-back: signing in is the CLI's own (`claude mcp login` or `opencode mcp auth`), and the operator manually pastes and runs commands in the Terminal or uses `ssh -t` on the engine host. In Chat details → MCP, **Terminal recovery** previews commands and **Copy** copies only; it never types or opens a terminal. Separately open **Chat details → Open → Terminal**, choose **Workspace if offered**, and review, paste and run the command yourself. Terminal authentication does not reconnect an already-running OpenCode provider: check provider state. Keep redirect URLs and tokens out of chat messages and command files.

- **Never report a step as done.** A card being opened, a browser being launched or a URL being printed proves nothing; only the provider's own state does. Ciaobot keeps no MCP status of its own: the CLI's own list (`claude mcp list`, `opencode mcp list`) is the status. A CLI status read is nonsecret but not free — `claude mcp list` health-checks the servers it lists, so it can contact them.
- **The agent offers, the user runs.** It may look, with its own permitted shell, at whether a CLI exists and what it says (`--help`, `--version`), and it may read a status. For an interactive sign-in, an install or an MCP setup it hands over a command to review and run: the suggestion card types the command into the chat's terminal only when the user asks and never presses Enter, so it never adds, authenticates or installs on the user's behalf, and a secret never goes into a card, a command file or a reply — a token belongs in the CLI or in a Settings field.
- **Google Workspace**: the row lives in Settings → Overview → Google account and it is the way in — the [`gws` CLI](https://github.com/googleworkspace/cli) is installed from its Connect dialog, a GCP OAuth `client_secret.json` (Desktop app type) is uploaded per account, and **Sign in with Google** completes the consent in the browser, with no terminal needed. Where the browser is somewhere else, the dialog's **Paste a code instead** field takes the full redirect URL or the code, so it works from any browser. `ciao gws status` reports whether the workspace's account is connected and its token valid. On a headless engine, `ciao gws-auth-helper <profile>` prints the authorization URL and waits for the redirect URL to be pasted back.
- **Installing and updating**: on macOS, Ciaobot is one app download that includes the engine — get it (DMG) from the [latest release](https://github.com/raffaelefarinaro/ciaobot/releases/latest); a machine updating from an older install gets the app offered from **Home**. The engine does not update itself outside the app: on an install that is not the app's, **Settings → General** says so and points at the app. On Linux, the engine installs with one line, run as the account that will own it: `curl -fsSL https://github.com/raffaelefarinaro/ciaobot/releases/latest/download/install.sh | sh` — it installs the wheel with uv, asks once for `sudo` to install the systemd unit, and an update is the same line again. A source-checkout install is installed and updated by the administrator. The [Linux hosting guide](https://github.com/raffaelefarinaro/ciaobot/blob/main/docs/LINUX.md) has the Linux steps, the installer's flags and the source-install migration. The engine runs on macOS 13+ (Apple Silicon) and on Linux; the PWA itself is installable from any browser. When the browser offers no install prompt, the Home setup card links to the install steps for the platform and marks the step done once the app is installed.
- **Restart or update requests**: the agent never restarts Ciaobot. When a change needs a restart (a Network access or log-level change, or a staged update), it can put a card in the chat (`ciao chat needs-action restart --reason config|update`) that opens the Settings control that restarts or updates, with the usual confirmation. An MCP server change needs no restart: `ciao chat reload` reloads the chat's MCP servers when the turn ends.
- **macOS privacy settings.** When a macOS privacy permission blocks something, the agent can put a card in the chat (`ciao chat needs-action system_setting --setting full_disk_access|calendars|contacts|reminders|photos|screen_recording|accessibility|automation|camera|microphone [--note TEXT]`). On the Mac, its button opens that pane of System Settings → Privacy & Security; on a phone the card says where to go on the Mac. Only when Ciaobot runs on macOS. The engine cannot see whether the user turned the permission on: after Continue, try the blocked step again. Full Disk Access applies after Ciaobot restarts, so that card links to the restart control in Settings.
- **First-run setup**: a fresh install opens the onboarding journey at `/onboarding`, five steps — **Location** (the main Ciaobot folder, then the workspace name), **Runtime** (a provider, then an explicit model), **Access & memory** (the approval mode, with a note that bypass gives full access to the user account, plus the memory handover), **Care** (when Workspace care should run) and **Finish** (a summary and an optional first task). Progress is saved per step, so **Leave setup** is safe: Home shows **Resume setup** until setup is finished, and a new workspace gets its own pending journey. Any step can be deferred; nothing starts a model turn on its own.
- **Other devices**: open Ciaobot from a phone or another computer. Settings → Access & devices → Other devices lists every address this engine answers on, each with a QR code, and every device signs in with the Ciaobot password. Only an HTTPS address can install the app and get notifications: run `tailscale serve --bg 8443` and Ciaobot finds the Tailscale address on its own, or paste the address of another HTTPS proxy. Plain LAN addresses work in a browser only.
- **Forgotten password**: the installer generates a random one. On the host, the login page's **Sign in on this computer** opens a signed-in tab, and Settings → Access & devices → PWA password then sets a new one without the old password (only in a browser on the host; other devices still need the current one). Otherwise the password is `PWA_AUTH_TOKEN` in the workspace `.env` (default `~/Ciaobot/.env`), or `ciao setup-url --workspace <folder>` prints a one-time localhost login link. Nobody can reset it from another device.
- **Linux/VPS hosting**: the engine and PWA run on Ubuntu 24.04 (a similar distribution works) as a systemd service under a dedicated account, whose workspace stays private; the one-line install puts the engine in the account's own uv tool directory, while a source checkout keeps application code administrator-owned. Use any browser or installed PWA as the client; agents execute on the server with its files and credentials. Setup details: `docs/LINUX.md` in the Ciaobot GitHub repo.
- **Local HTTP API**: the app serves an API for the PWA and the operator, behind the PWA session cookie; it is not a surface an in-chat agent drives. Agents use `ciao` commands, which apply workspace confinement, the plan-mode gate and telemetry. `ciao help` lists them with their flags. The API recipes for operators are in `PWA_API.md` in the Ciaobot GitHub repo (`raffaelefarinaro/ciaobot`).
