# Skills, models and providers, Google Workspace

## Skills, subagents, and commands (extensibility)

- **Stock skills** ship with the app and are synced into `.claude/skills/` (`ciao sync-skills`, runs at startup). A same-named skill in the workspace's `skills/` folder overrides the packaged copy.
- **When Ciaobot itself is failing**: the bundled `ciao-support` skill reads the local logs, checks whether a released version already fixes it, and files a GitHub issue with this repo's labels. A log tail is not a fix.
- **Plan mode**: writes are refused, so give the plan in the chat and say it can be saved as a file once the mode changes. Routine working docs (notes, analyses) follow the core prompt's file-routing rules.
- **Reloading changes**: after an MCP server, plugin or skill is added or changed, a running chat picks it up when the agent runs `ciao chat reload` (same conversation, continues on its own); new chats load it automatically.
- **Custom** skills, subagents, and slash commands are authored in the workspace (`skills/`, `subagents/`, `commands/`) and mirrored automatically.
- **Adding a skill**: place a folder `skills/<name>/SKILL.md` (or validated zip containing one top-level folder with `SKILL.md`) then run `ciao sync-skills`. Workspace git sync carries it to other operators. No GitHub fetch.
- **Skill improvement proposals**: when the memory pass finds a repeated failure or correction that traces back to one of this workspace's own skills, it files one plain-language proposal per skill in `Workspace/Skill-Proposals/`, never a silent edit. A reusable lesson in `Workspace/Learnings.md` routes the same way even when the conversation that produced it never loaded the skill — an inventory match is a candidate, not proof, and the link to the lesson is recorded rather than a transcript turn that does not exist. A lesson about a packaged (shipped) skill, or about a workflow no skill covers, becomes a `[review]` draft instead: an upstream issue for whoever maintains the packaged skill, or a proposed new skill, both created or filed only when you approve them, and the issue body is sanitized so no transcript excerpt, path, name or credential leaves your machine. The nightly Workspace care run files and reports these; it never edits a skill or the workspace guide, never settles a proposal, and never opens a public issue. You can inspect the queue with `ciao skill-drafts` and act on one with `ciao skill-draft-approve` / `ciao skill-draft-reject`.

## Models and providers

- Backends: **Claude Code** (signed in with your Claude account) and **opencode** (the open-source agent CLI, bring-your-own model provider — this is how you reach anything else, including Ollama, OpenRouter, or a local OpenAI-compatible server: configure it in opencode and its models appear here automatically). A message sent while a turn is still running appears in the queued-messages list above the composer, where each entry can be edited, reordered, removed, and switched between *Queue* (sent as the next turn when the active one finishes) and *Steer* (injected into the running turn through the provider's native steering, so the agent sees it at its next step). Choosing Steer, or *Steer all*, sends at once; several steered messages go together as one message in list order, images included. Settings → General → the keyboard shortcuts card → "While a reply is running, new messages" sets whether new mid-turn messages queue (the default) or steer. A steer that cannot be delivered falls back to the queue with a notice. After Stop, queued messages are held as *Waiting* until you press *Send now* (nothing sends by itself). Steering works on both Claude Code and opencode.
- **Other model backends**: Ollama, OpenRouter, LM Studio, and other OpenAI-compatible endpoints are reached through **opencode**. Configure the backend in opencode; Ciaobot discovers its connected models automatically and exposes them in the chat, workspace, and routine pickers. Ciaobot does not store or probe those backend credentials itself.
- Per-provider default model and thinking level for new chats (**Settings → Providers**, the chat providers card, which also shows each CLI's connection and lets you reconnect, verify, or log out) — no cross-provider tier mapping; each provider resolves `opus`/`sonnet`/`haiku`/`fable`-style aliases against its own catalog. Per-chat override in the picker, with Automatic resolving to the chat's own model.
- Per-provider default **permission mode** for new chats (**Settings → Providers**): *manual* asks before every action, *auto* (the default) runs safe reads and edits silently and asks before destructive ones, *bypass* allows everything. That default is the only permission control in the app — there is no in-chat mode switch. A single chat's mode can only be changed outside the UI, with `ciao chat update --mode` (which can lower a mode but never raise it above the calling chat's own) where the CLI allows it; otherwise it is the user's choice.
- Beyond per-chat routing, one chat can **reach another model without leaving the conversation**: a handover moves the whole chat to another provider.

## Google Workspace (`gws`)

- Ciaobot integrates with Gmail, Calendar, Drive, Docs, Sheets, Slides, and Tasks through the [`gws` CLI](https://github.com/googleworkspace/cli).
- **Settings → Manage workspaces**: install `gws`, upload a GCP OAuth `client_secret.json` per profile, and connect Google accounts from the browser (no terminal required). The Google Workspace card lives on that tab, with an inline setup checklist (add account → upload client → Sign in with Google → link a workspace); terminal and headless commands sit under Advanced. In-chat, `ciao gws status` reports whether the active workspace's Google account is connected and its token valid before you promise a Google call will work.
- Separate **personal** and **work** profiles; each workspace picks which profile to use in Settings → Overview → Google account.
- Stock **`gws-*` skills** ship with the app (Gmail, Calendar, Drive, Docs, Sheets, Slides, Tasks, Forms). Setup details: `gws-shared` skill and the setup checklist on the Google Workspace card.
