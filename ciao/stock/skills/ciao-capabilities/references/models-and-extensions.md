# Skills, models and providers

## Skills, subagents, and commands (extensibility)

- **Stock skills** ship with the app and are synced into `.claude/skills/` (`ciao sync-skills`, runs at startup). A same-named skill in the workspace's `skills/` folder overrides the packaged copy.
- **When Ciaobot itself is failing**: `ciao-capabilities` routes to its `references/support.md` procedure, which reads scoped local logs, checks whether a released version already fixes the problem, and explains how to prepare a GitHub issue with this repo's labels. Public reporting still requires the operator's approval; a log tail is not a fix.
- **Plan mode**: writes are refused, so give the plan in the chat and say it can be saved as a file once the mode changes. Routine working docs (notes, analyses) follow the core prompt's file-routing rules.
- **Reloading changes**: after an MCP server, plugin or skill is added or changed, a running chat picks it up when the agent runs `ciao chat reload` (same conversation, continues on its own); new chats load it automatically.
- **Custom** skills, subagents, and slash commands are authored in the workspace (`skills/`, `subagents/`, `commands/`) and mirrored automatically.
- **Adding a skill**: place a folder `skills/<name>/SKILL.md` (or validated zip containing one top-level folder with `SKILL.md`) then run `ciao sync-skills`. Workspace git sync carries it to other operators. No GitHub fetch.
- **Skill improvement proposals**: when the care run finds a lesson that keeps recurring and traces back to one of this workspace's own skills, it writes one plain-language proposal file under `Workspace/Proposals/` (type `skill-edit`), never a silent edit. A lesson about a packaged (shipped) skill becomes an `upstream-issue` proposal file for whoever maintains it, and a workflow no skill covers becomes a `skill-edit` proposal for a new skill. The file names its evidence, and an upstream-issue body is written so no transcript excerpt, path, name or credential leaves your machine. The agent checks each file with `ciao proposal-check`; you file the issue or apply the edit from the file, or ask the agent to in a chat. The daily Workspace care run writes and reports these; it never edits a skill or the workspace guide and never opens a public issue.

## Models and providers

- Backends: **Claude Code** (signed in with your Claude account), **Codex** (signed in with `codex login`; install and sign-in are in Settings → Providers) and **opencode** (the open-source agent CLI, bring-your-own model provider — this is how you reach anything else, including Ollama, OpenRouter, or a local OpenAI-compatible server: configure it in opencode and its models appear here automatically). A message sent while a turn is still running appears in the queued-messages list above the composer, where each entry can be edited, reordered and removed. Messages sent during a reply queue and run in order after it; there is no Queue/Steer choice and no Settings option for it. After Stop, queued messages are held as *Waiting* until you press *Send now* (nothing sends by itself).
- **Other model backends**: Ollama, OpenRouter, LM Studio, and other OpenAI-compatible endpoints are reached through **opencode**. Configure the backend in opencode; Ciaobot discovers its connected models automatically and exposes them in the chat, workspace, and routine pickers. Ciaobot does not store or probe those backend credentials itself.
- Per-provider default model and thinking level for new chats (**Settings → Providers**, the chat providers card, which also shows each CLI's connection and lets you reconnect, verify, or log out) — no cross-provider tier mapping; each provider resolves `opus`/`sonnet`/`haiku`/`fable`-style aliases against its own catalog. Per-chat override in the picker, with Automatic resolving to the chat's own model.
- Per-provider default **permission mode** for new chats (**Settings → Providers**): *manual* asks before every action, *auto* (the default) runs safe reads and edits silently and asks before destructive ones, *bypass* allows everything. The normal chat model picker also lets the user change that chat's mode (Manual, Auto, Bypass or Plan); it applies to subsequent turns, not the reply already running, and queued or external turns may start before a change is saved. An agent that needs a different mode asks with `ciao chat needs-action permission_mode --mode plan|normal|auto|bypass --note "why"`; the user sees what that mode allows and approves it in the chat, and it applies from the next turn. The agent can never apply a mode itself. `ciao chat update --mode` can still lower a mode, never raise it above the calling chat's own.
- Beyond per-chat routing, one chat can **reach another model without leaving the conversation**: a handover moves the whole chat to another provider.
- **Google Workspace** is not built in: connect it through the agent, like any MCP server or connector (Claude's or Codex's Google connectors, or the Google Workspace MCP server). See the site's companions page.
