# Memory and the vault

## Memory and the vault (second brain)

- **How memory works, in plain terms.** When a chat is archived, Ciaobot re-reads it and pulls out only what will matter later — a preference, a lesson, a person, a decision — and files each fact where it belongs: things true everywhere go into a small always-loaded memory (the `ciao:memory` / `ciao:profile` regions in `AGENTS.md`), project facts into that project's doc, people into `People/<Name>.md`, reusable how-to lessons into `Workspace/Learnings.md`. Every remembered fact is dated, and when a fact changes, the new version replaces the old one (the old text is kept in an undo log, never silently lost). A nightly "Workspace care" routine tidies all of this: it merges duplicates, retires expired facts, re-checks old notes, and rotates logs. Ciaobot also counts weak patterns across chats (how you like things done, habits of people you work with) and proposes one for your review once it has shown up in three separate conversations. Unconfirmed observations never appear in recall or prompts.
- **How memory works, in the app.** Every Memory section has a collapsed *How memory works* disclosure under its header: what is and is not saved, the order the memory pass and nightly run work in, and a table of who settles each tag. `project`, `people` and `learnings` are filed by the nightly run; `review` is decided by it, with a judgement call coming back as a yes or no; `memory` and `profile` are yours, and the nightly run only predicts what you would pick. The memory pass is an openable chat from Home. Every individual accept or dismiss in the queue asks for an optional reason before it writes — a quick chip or a line of your own, and you can continue without one; a re-home pick is the exception, because there the destination is the answer — a memory or profile change applied under Memory handover reads *Filed by Workspace care* (or *Dismissed by Workspace care*), with Undo on an accepted one, and tidied core memory is logged in `Workspace/Memory-Consolidations.md`. Once a week the same run re-verifies stale notes, tidies the workspace and reviews the guide (suggesting changes, never editing it), and — once enough new decisions have piled up — distills your decisions into `Memory-Review-Rules.md` and `Task-Rules.md`. A new category is added on the Categories tab.
- **What is automatic vs. what is yours.** Automatic: extracting facts from archived chats, filing confident state-shaped facts (including into the always-loaded `ciao:memory` / `ciao:profile` regions, project docs, people notes, and learnings), deduplicating, dating, nightly tidying, and search-index upkeep. The nightly Workspace care run settles the non-region suggestions (`project`, `people`, `learnings`, `review`) itself, except those marked `decide: you` and any it cannot settle, which it escalates to you. `[memory]` and `[profile]` suggestions get only a nightly prediction and stay yours, unless the workspace's Memory handover (Settings → General: Off, Dismiss, or Dismiss and accept) lets Workspace care act on that prediction: at most five accepts per run, each undoable in History, and not available on an install without a trusted service definition. Review from the app's **To decide** page or the CLI (`ciao memory-proposals`, `ciao memory-proposal-dismiss --text-file <file>`); you can also just tell any chat "remember this" or "forget that". Region caps are advisory — a full region never blocks a durable fact; consolidation (or raising the limit) is what makes room. Nothing is ever deleted automatically — aging or unused facts are only *reported* for you (or an attended chat) to decide. A History tab beside the queue shows every decision already made — what you or the nightly agent accepted or dismissed, and what archiving filed or recognized as already known on its own. A row shows the before/after of the write it performed and offers Undo when it has a reversible receipt — including an accept whose wording you edited first. Rows written before receipts existed, and the per-fact rows of a multi-fact batch (one row carries the batch's whole-file before image, so undoing the others would resurrect everything the batch removed) are view-only and say so. A verified note rewrite is shown in full there: the note it was about, the exact text before and after, the sources the verdict rested on and how much of the note the check covered, so a decision made months ago can still be judged on its evidence. A decision about **one fact inside** a note is shown at that scale: which operation it was (rewrite it, re-stamp it, or remove it), that one line before and after, and that the rest of the note was untouched — and it is reversible like any other managed write, so a removed fact can be put back with Undo. A retirement carries no new text — it moved the note to Retired, where Restore puts it back. **See the exact change before you accept it**: a proposal's preview names the destination and shows the before/after body the accept would produce — including when it recognizes a duplicate and writes nothing, or bumps a learning's recurrence count instead of appending a second copy — and re-previews as you edit the wording. Where the result genuinely cannot be known without writing (a fold into a project doc or an existing person note is decided by a model at accept time) it says so rather than guessing. On a very large destination the preview covers only the first 20,000 characters of each side. A change past that point — an append to a long learnings file, say — falls outside the window, and because there is then no visible difference to show, the panel reads "Nothing changes" rather than flagging the truncation. The accept still makes the change, so treat that reading as "not shown here" on a long destination rather than "nothing will happen". If the destination moved after you looked, the accept is refused and you are shown a refreshed preview, so a write never lands on top of an edit nobody saw. An optional per-workspace Memory handover (Settings, off by default) lets Workspace care act on its own predictions after you see its agreement rate; every such write is undoable from History.
- The vault is standard, open markdown: notes, project folders, `AGENTS.md` (which also holds the bounded memory regions), a vault `MEMORY.md` (curator notes — separate from the bounded regions), a generated `INDEX.md` and `VOCABULARY.md` from frontmatter and markdown links. It is agent-agnostic and remains useful without Ciaobot.
- Vault tooling: search (`ciao vault search`, which covers vault notes, not archived transcripts) before adding duplicate facts, and refresh the index (`ciao vault-index`) after larger edits. Read-only recall uses the matched `ciao vault search` snippets as private evidence; do not open full vault notes with generic file-read tools for pure recall, and admit when nothing is found. When a snippet is truncated and the answer turns on what it omits, search again with a narrower query built from that snippet's distinctive terms; when no snippet carries the answer, recall abstains rather than answering from an unmatched block. This is inline system-prompt policy, not a separate skill. The typed Ciaobot operations (projects, chats, subagents, automations) are the `ciao <noun> <verb>` commands, listed in the bundled `ciao-cli` skill and printed by `ciao help` — read that rather than guessing a name. The bounded memory regions can be edited directly with `Edit` on `AGENTS.md`, or, for text you wrote yourself, `ciao memory update` (check usage with `ciao memory status`). A fact from the user or a conversation goes through `/remember`, which queues it for review. Vault-maintenance edits are the `ciao` CLI (`ciao vault-index`, `ciao vault-lint`).
- **Memory Map** (`/memory`): an interactive graph and list view of the whole vault for one workspace — nodes are notes (colored/typed from frontmatter), edges come from `related:`/`relatedTo:` frontmatter and relative markdown links in note bodies. It is one of Memory's six sidebar sections (To decide, Map, Categories, Import, Retired, History); To decide lists suggested memories and notes to revisit on one page, with a filter for each. Search, filter by category, sort the list by links or by when each note was last checked; clicking a note opens it in a docked tile (the same one a pinned file uses) and lights up its neighbours, and notes unchecked too long carry an amber ring and link to the notes to revisit. A note is not the unit anybody keeps current, so a node also reports the **facts inside it**: each list item carries its own `[verified: YYYY-MM-DD]` stamp, and a note re-stamped last week can still hold an address nobody has checked since 2019. The tile names the overdue facts, the toolbar counts the notes holding them separately from the unchecked count (they overlap only partly, and collapsing them would hide exactly the case that matters), and it says plainly when part of a note is **not a fact anything here can check** — a paragraph, a table, a quote — which is an honest "we cannot measure this", not a clean bill of health. The nightly run's `stale_entry` pass works from that same list, so what the map shows is what tonight's plan will touch. A note the nightly pass has already checked inside its 30-day cooldown — or one a suggestion of its own is waiting on — is no longer counted as unchecked, whatever its `updated:` date says; its tile says which verdict was reached, how much of the note the check covered, and where the waiting suggestion is.
- **Vault Review**: inspect deterministic candidates for notes that are unverified past their type's horizon (project 30 days, person 90, everything else 180; logs, journals, `Workspace/` files, templates and completed projects never qualify — the same rule as the Memory Map's "unchecked" flag, so the two lists agree), unlinked, possible duplicates, say they were superseded (the row quotes the line and its line number), or carry no date, tags or aliases; review evidence in the PWA or through `ciao vault review`; keep (which clears the row and stamps the note's `updated:` date to today — a note with no frontmatter has nothing to stamp, and the app says so), trash, restore, or permanently delete with append-only audit records and reversible trash until confirmed deletion.  **Notes the nightly pass has already checked are not asked twice.** The nightly Workspace care run picks notes that have gone unchecked past their horizon, re-reads them, and reaches one of four verdicts: still true (it re-stamps the note's `updated:` date), needs an update, should be retired, or could not be confirmed (a source was unreachable, which is an answer, not a failure). The first two are applied for you through the same undo log as every other managed write; **a retirement is never applied unattended**, and any change the pass is not confident enough to make on its own becomes a suggestion you accept or dismiss like any other proposal. So nothing in a vault is ever promoted, edited or retired without you — the pass decides what to *ask*, and the queue holds the question until you answer it. A note it checked is left alone for 30 days before being asked again, and the moment the note changes it is due again immediately. Where such a suggestion is waiting, the notes-to-revisit row **links to that suggestion** instead of offering its own Still true / Retire on the same version of the note: the note stays visible, the row says which check led to it and on what evidence, and the decision is made in one place. If the note was edited after the suggestion was filed, the suggestion can no longer be applied and the row says so and hands the decision back to you. The same pass also judges **one fact at a time**, and a note can be current and still be holding something nobody checked. Those notes are queued on their own signal, the row names the exact bullet with the lines around it, says whether the date on it is its own stamp or just the file's `updated:` carried onto it, and links the suggestion already waiting about that one fact rather than offering a second decision of its own — the buttons on the row are about the whole file, and a fact is not the file. Where a suggestion was filed against text the note has since left, the row says so instead of offering a button that could only fail. A candidate left undecided simply stays in the queue. Trashed notes stay restorable until they are deleted — nothing is purged on a timer. A keep can be undone: "Recently cleared" lists the notes cleared that are still in the vault, and **Add back** returns one to the queue. A note that leaves the vault by an ordinary file deletion is recorded in the ledger too, so the audit trail accounts for everything that left. A row that is a **project** offers **Complete** in place of **Retire**: it moves the project to `projects/completed/`, rewrites `status: active` to `status: completed`, and repoints every note that links to it, which is what a finished project needs — retiring one only hides it and leaves the links behind.
- **Talk about a retirement candidate before deciding.** Every candidate row has "Talk about it": it opens a chat in that candidate's own workspace with the note pinned beside it and the composer pre-filled with the row's evidence — path, why curation flagged it, type, verification age, backlinks, duplicates — plus an instruction to change nothing. On a note nothing links to, the draft instead asks the agent to search the vault for the notes that *should* link to it and to write only the links that are approved — the repair that actually clears that flag. The message is a **draft, not sent**, so a specific question can be asked first, and the candidate stays queued whatever the answer. (The proposal queue's "talk about it" has the opposite shape: it runs in the background and reports back.)
- **Import conversations** (`/memory/import`, in Memory's sidebar and named in the first-run welcome — the same page either way): bring facts you already told another agent into this workspace, rather than re-typing them into a fresh vault. It reads **Claude Code** and **OpenCode** sessions the engine host already has for that workspace, and it is **opt-in and never automatic**: nothing is scanned until you press Find, and nothing is read until you tick a conversation.
  - **The consent screen is the feature.** You pick the conversations yourself (nothing is pre-selected), and before anything runs the confirmation names each one with its turn count, its own first date and what the reader omitted, then the provider and model that would receive the text, an input-volume estimate and the per-batch cap. Ciaobot's own conversations are never offered, an unreadable one says why, and a source whose version this importer cannot read says *Unsupported version, export a file instead* rather than offering a button that does nothing.
  - **Every fact waits for you.** The extraction is a single tool-less turn that can only file review proposals — it has no tools at all, so it cannot edit a note, run a command or call `ciao` even if the conversation contains an injection. Nothing reaches your memory until you press accept in **To decide**, each proposal carrying the date of the *message it came from*, so a two-year-old conversation files facts that stay two years old rather than looking verified today.
  - **One batch at a time, and you can stop it.** The runs list shows progress per conversation; cancelling stops the ones not yet started, keeps every proposal already filed, and says plainly that text already sent to the provider cannot be unsent. A conversation that changes is a new attempt beside the old bullets, never a silent overwrite.
  - **Old snapshots expire; memories do not.** Ciaobot keeps a private copy of what an import read and drops it about a month after the import settles if you never decided its proposals. A fact you accepted keeps a short record of the conversation and message it came from, so an imported fact stays attributable after that copy is gone. **Removing an import removes neither a queued proposal nor an accepted memory** — that is the ordinary review and undo path.
  - What it does not do: no continuous monitoring or background re-scan (run it when you want), no reading a Claude account export, no cache or cookie scraping, and nothing from a phone — the scan runs on the machine Ciaobot runs on, and a browser can only choose among what that machine already has.

- **Memory backup** (Settings → General → Memory backup). One private git repository at the data folder backs up every workspace together: their memory, skills, subagents, commands and archived workspaces, and never credentials, caches or the transcript archive. **Set up in Ciaobot** starts a setup chat that connects a private GitHub repository for it, which needs the GitHub CLI signed in. **Copy setup prompt** copies the same instructions for any agent to run on that machine. Once the repository is connected, the engine commits and pushes the durable scope every five minutes on its own, with no restart.

## Memory review rules
- **Ciaobot learns what you keep and drop.** Each week it distills your accept and dismiss decisions on memory proposals into `Workspace/Memory-Review-Rules.md`. Edit it freely outside the fenced section; the memory passes read it as evidence, and a rule that would flip is asked as a review question first.
