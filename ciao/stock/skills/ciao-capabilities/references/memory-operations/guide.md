# Durable memory and vault care

For writing or curating durable vault memory, read [Writing documents and regions](references/writing.md) before document writes or bounded-region edits. What you are unsure of, and any proposal, follows [the Unsure list and proposal files](references/unsure-and-proposals.md). The unattended Workspace care run is an orchestrator over a checklist: each step has one self-contained file under `references/` (`curation-pass-1-unsure.md`, `curation-pass-2-regions.md`, `curation-pass-3-stale-notes.md`, `curation-pass-4-learnings.md`, `curation-pass-6-hygiene.md`, `curation-pass-7-guide-body.md`, `curation-pass-7b-decision-rules.md`, `curation-pass-8-second-look.md`, `drain-legacy-queues.md`) that a fresh subagent follows on its own. While a legacy review queue still has rows, see [Drain the legacy queues](references/drain-legacy-queues.md). Read-only recall stays on the ordinary vault search path.

Write only under the `vault=<path>` root in `<ciao-context>`. Existing notes may have been misfiled by an older curator; their location never overrides the configured vault.

Read-only recall is handled inline by the system prompt (`ciao vault search`, answer from vault evidence only). This skill covers writes and curation. The nightly Workspace care schedule owns its unattended rules and decides what is due; follow that prompt for the run. Perform mutating vault passes sequentially.

## Write directly; Git is the record

A fact you are confident of is written where it belongs, now, by you: no queue, no approval step. Where the vault is backed up in Git, a wrong write is undone by reverting it; every replaced or removed line also goes to the undo log (below), which works with no backup at all. What you are not confident of goes on `<vault>/Workspace/Unsure.md` (one plain Markdown list; see [the Unsure list and proposal files](references/unsure-and-proposals.md)). A skill edit, a guide edit, an upstream GitHub issue or a note retirement is not written by you at all unattended: it becomes a proposal file under `Workspace/Proposals/`, checked with `ciao proposal-check`, which a person acts on.

## Destinations and categories

- Vault pages hold durable facts about projects, people, ideas, resources, and logs. `Workspace/Unsure.md` holds what you could not settle, not a pass log.
- Bounded memory regions live in this workspace's own `AGENTS.md`: `ciao:memory` holds cross-project preferences, environment, and lessons; `ciao:profile` holds identity and communication style. Project-specific facts never belong in these regions. Write a region fact by native file edit inside the fence or with `ciao memory update` using text you wrote yourself, never text pasted from a transcript or note.
- The **Categories** section of `<vault>/VOCABULARY.md` names each category, its folder, and its canonical `type:`; do not memorize this list. Make each new note with `ciao note create --type <id> --title <T>` (more flags: `ciao help note`); it stamps the frontmatter and files it in the category's folder. If no category fits, put a new-category question on the Unsure list instead of inventing a type or stretching a category. When editing a note whose type appears in "Types (drift)", fix it. Prefer existing tags; genuinely new tags use `namespace/value`. Give People and project notes `aliases:` with terms a person would search for, since recall is lexical.
- **A person** → this workspace's configured person folder (usually `<vault>/People/`). Workspaces have no shared people folder; don't write into another workspace. **A specific project** → its canonical vault doc and log if present, not a bounded region. **Reusable how-to across projects** → `<vault>/Workspace/Learnings.md` through `ciao memory learn --text-file FILE`: a sighting from a *new* source increments the structured entry's count rather than duplicating it, re-filing one already recorded is a no-op, and an entry already under `## Promoted / Resolved` stays there. Use the exact source chat id or completion id with `--source` only when it is available; never invent an id, turn or archive path. **Standing operating directives** → the `AGENTS.md` body outside the bounded regions and `CIAO_CUSTOMIZATION.md`, not remembered-fact regions; moving a fact out of the guide body is a `guide-edit` proposal file.
- **A pattern seen once is an observation, not a fact.** Put it on the Unsure list as an observation line with its chat id; at three distinct chats write it to its profile or people destination.
- **Where a lesson goes.** A reusable tool or workflow instruction routes to the best matching skill this workspace **owns** under `skills/` — an inventory match is a *candidate*, not proof: read the skill, cite why it applies and the failure you actually observed, and if the skill already says it, write nothing. A lesson about a **packaged, mirrored or shared** skill is not yours to edit (a local edit is discarded by the next sync): write an `upstream-issue` proposal file naming the skill, the owning repository and version when identifiable, with a body a stranger could reproduce with no transcript excerpt, path, name or credential in it. A lesson **no** skill covers is a `skill-edit` proposal for a new skill: the proposed name, its purpose, the trigger that should load it and the instruction it should carry. Opening the public issue and creating or editing the skill is for a person, from the file.

## Consolidation and re-checking

- The attended memory pass and a care run write confident state-shaped facts directly. Region caps (~3000 memory / ~1375 profile chars) are advisory. The cap is advisory on every path. Check `ciao memory status` after every region write. At or above ~85%, consolidate existing entries before adding: merge duplicates, remove expired entries, and MOVE project-scoped facts into their canonical doc. Never drop a durable fact merely to meet the cap; report an over-cap region if everything is high-signal. `ciao memory update` writes and reports `over_cap` with `used_chars`/`char_limit`.
- **Undo log.** Before replacing or removing an existing line of a note, a project doc or a region entry, attended or not, copy it into `<vault>/Workspace/Memory-Consolidations.md` under a `## YYYY-MM-DD` heading as one bullet: `- <note path or region> — by: <memory pass <chat id> | care <step id> | chat <chat id>> — "<original text verbatim>" — <one line why>`. A pure addition needs no entry. A credential is named, never copied. If dropping an entry takes judgment, leave it and add a line to the Unsure list.
- **Re-check stale notes against their sources.** When the care run (or a person) hands you a stale note, read it and judge each fact against real sources. Run `ciao note related <path>` first: a disagreeing note is evidence, and a related note you actually checked counts. Reading a note is not checking it. Fix what the sources plainly contradict, citing them, directly in the note; re-read the note after every write before judging a second fact. Anything doubtful goes on the Unsure list. Retiring or deleting a note is never done unattended: write a `note-retire` proposal file.
- **When new advice supersedes stored guidance, the note keeps one instruction.** Include its source and date, and remove the superseded line rather than annotating it. If sources genuinely conflict, let them decide instead of picking silently; a passing remark or empty search is never the later correction of a decision a note records. An attended pass asks, quoting both; an unattended run puts one Unsure line quoting both and writes neither as the current instruction.
- **Writing entity notes** (people and project notes). Each list item is checked on its own `[verified: YYYY-MM-DD]` stamp, so:
  1. Write one fact per bullet: one assertion per `-` item. Two facts in one bullet share one stamp, so re-checking one silently re-certifies the other. Splitting a bullet to add a fact is fine; merging two facts into one bullet is not.
  2. A paragraph, table or code block is not a fact this system can verify. A note whose facts live in prose shows as `uncovered` in the audit and the Memory Map; moving the facts into bullets is the only fix.
  3. Add a `[verified: …]` stamp only after actually going and checking that exact sentence, never on save, on a merge, or as a side effect of another edit. A bullet whose text changes loses its stamp, and an untouched bullet has a re-dated stamp put back to the date it really carried.
  4. Leave the note's `updated:` alone on an ordinary save.
  5. An entry in an explicit event section (`## Events`, `## History`, `## Log`, `## Journal`, `## Changelog`, …), a dated record in leading-date-plus-completed-past-tense form, and an exempt note type (`log`, `journal`, `workspace`) are never aged. A bare calendar date is not an exemption: a lease that ends on the 30th is a current-state assertion that happens to carry a date.
  6. Re-read the note after every write, before judging a second fact against it.
- Write present-tense facts, not a story of the session ("User said X → assistant did Y"), but keep what was tried and why it failed. Store a credential's name, never its value, and never copy a secret from a transcript into memory or onto the Unsure list. Search local memory first, ask only when a missing detail blocks a correct attended write, and keep private data inside the user's workspace.
