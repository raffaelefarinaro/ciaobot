# Workspaces, projects and chats

## Chats, projects, and workspaces

- Hierarchy: **workspace → project → chat**. A workspace is a life area (personal, work, a client); each workspace holds projects; each project holds chats plus durable context (files, notes, decisions) that Ciaobot injects into every chat inside it — the agent doesn't rediscover what you're working on each time.
- **Workspaces can have their own vault root, default provider, Google Workspace profile, and tool deny-list; MCP servers come from each workspace's own `.mcp.json`.** Default models are per provider (Settings → Providers), not per workspace. In-chat, `ciao workspace list` lists the configured workspaces and `ciao context get` reports the active one.
- **Workspace order**: All workspaces (the last card of Settings → Overview) reorders workspaces by drag, keyboard, or **Move up** / **Move down** in a row's menu (the way to do it on a touch screen). The order drives the switcher, the `1`–`9` shortcuts and every workspace list. When no workspace is named `personal`, the first one is the main workspace (the startup workspace, protected from archiving) and stays first.
- **File access per workspace.** Settings → Overview → **File access** is *Default*, *Workspace only* or *Whole machine*; each row in All workspaces shows the effective scope. When you point someone at one, link the real row: `[File access for NAME](/settings/workspace?workspace=NAME#file-access)`, taking NAME from the workspace named in the conversation or from `ciao workspace list` — never invent a name. The link switches to that workspace, opens Overview and focuses its File access selector, and never chooses or saves a value, so say which scope to pick rather than claiming the setting already changed. The default is Workspace only on macOS and Linux and Whole machine on Windows, which has no sandbox. Workspace only confines the agent's shell and file tools (Claude and OpenCode) to that workspace's folder plus what the engine itself needs. It does **not** restrict the network: the agent can still reach the internet and the `ciao` CLI. macOS uses the system sandbox; Linux uses bubblewrap (Ubuntu 23.10 and later need the one-time AppArmor setup in `docs/LINUX.md`). A script or venv that lives outside the workspace folder (for example in the main workspace root when this workspace is a subfolder) is not readable under Workspace only: switch that workspace to Whole machine, or move the file inside it. There is no list of extra folders: to let the agent reach a folder outside the workspace (for example `~/Documents`), pick Whole machine. On macOS the first time Ciaobot touches Desktop, Documents or Downloads, macOS asks to allow "Ciaobot Server"; the choice is in System Settings → Privacy & Security → Files and Folders.
  Under Workspace only the agent also cannot read your home folder's logins and config, so `gh` is not signed in and git commands outside the workspace folder are refused; Ciaobot's own version and this workspace's failed-job records stay available in chat through `ciao context logs` (engine-wide logs are omitted).
- **Archiving a workspace** (Settings → Overview → Archive this workspace) never deletes files and never merges them into another workspace. The workspace leaves the sidebar, pickers and routines; its chats are archived, its automations leave with it, and Ciaobot stops using its notes and memory (search, the index, the Memory Map). Its folder is kept byte for byte in `.archived-workspaces/<name>-<date>/` in the install folder, and the Archived workspaces list in All workspaces (the last card of Settings → Overview) restores it; the restore confirmation lists the settings it will apply, and its automations come back paused until re-enabled in Automations. The primary workspace and the last one cannot be archived. There is no in-chat command for it.
- **Usage statistics**: `ciao stats [--range 7|30|90|365]` (default 30 days) returns this workspace's activity as JSON: chats opened, messages you typed (per day for the last 182 days, by hour and by project), chats archived, memories saved, tasks completed, automation runs, tokens and the models used, each beside the preceding period of the same length. It reads what Ciaobot already records: turns sent by an automation and the engine's own helper chats do not count as your messages, and tokens cover the turns whose provider reported usage.
- A new chat starts on the workspace's default provider and that provider's default model; each chat can override the model from the picker.
- **Compact a long chat on demand**: the Compact action in the heading of Chat details → **Context**, above the context meter, shrinks the chat's history into a shorter summary when it is getting full. It is a manual action; Ciaobot does not compact on its own.
- **What every turn carries**: Chat details → **Always loaded** lists what is sent with every message, with token counts: Ciaobot's own system prompt (open the row to read the full text; it is added to the provider's own system prompt in every session), the workspace guide, the project brief and, in code mode, the repository instructions.
- **Projects are managed in-chat with `ciao project`**: `ciao project list [--include-completed]` lists a workspace's projects, `ciao project get [ID|NAME]` fetches one, `ciao project create --name` makes a new one and scaffolds its vault note (`projects/active/<slug>/<slug>.md`), `ciao project update ID [--name] [--context] [--vault-folder] [--repo PATH]` edits metadata, and `ciao project complete ID` / `ciao project restore STEM` / `ciao project delete ID` handle the lifecycle.
- **A project can be linked to a local git repository.** `ciao project create … --repo PATH` or `ciao project update ID --repo PATH` links the checkout (the path must be the repository's top folder; `--repo ""` unlinks), and `ciao repo candidates` lists the checkouts found one level under ~/repos, ~/code, ~/src, ~/dev, ~/Developer and ~/projects. The project then reports the repository's path, current branch and whether it has uncommitted changes. Chats keep working in the workspace; the repository is added to them.
- **Code mode** (automatic, no switch): chats in a project with a linked repository work in code mode automatically; put a chat in a project without a repository to keep it out. In code mode the chat loads the repository's AGENTS.md, skills and write access; Chat details shows the repository and branch in its Repository section (the `code` badge beside the chat title opens it). Linking, changing or removing the project's repository mid-chat applies from the chat's next message. A repository folder missing on this machine turns code mode off until it is back.
- **Starting a chat from the home screen**: each workspace lane has a **+ new** button that starts a chat in that workspace's *General* project in one click. When the workspace has more than one project, a caret sits beside it that opens a project picker, so a new chat can go straight into the right project without creating it in General and moving it.
- **Two chats side by side:** on a wide window, a sidebar chat's *Open beside* (a hover button, or the row menu on touch) opens it in the right-hand tile next to the open chat, sharing the slot a pinned file or the terminal uses (the newest takes it).
  - Each side has its own composer; click a side, or use `Cmd+Option+[` / `]`, to type there.
  - Esc closes the second chat.
  - The split is remembered per workspace in that browser and hidden on narrow windows.
- Push notifications; the PWA is installable on desktop and mobile.
- Chats can be spawned programmatically from within a chat via `ciao chat create`.
- **Forks**: any completed agent answer has a *Fork conversation from here* action. It creates an independent new chat in the same project, copies the visible history through that answer, and inherits the source's provider/model/mode/thinking level — but starts a fresh provider session and never syncs back to the source. Forks are titled `Original · Fork 1`, `Original · Fork 2`. Use it to explore a branch without disturbing the original.
- **Subagents**: a chat's agent can dispatch subagents to work in parallel. Running agents show in the composer bar's activity cluster beside Send (the segment labelled **1 agent** or **N agents**; on a narrow composer bar it shows the count alone) and in Chat details → **Running**, agents first; each agent row opens a read-only view of that agent's own conversation (read it, not steer it — a subagent is a transcript, not a chat you can send into). **Processes**, in the same popover, lists background shells, and Chat details lists them in the same **Running** list under the agents; both offer Stop where the engine can stop one. The chat's sidebar row carries only chat-level status — a working mark for a streaming chat or a running agent, plus a separate mark for background runs — never per-agent rows. That status is conditional: while the parent chat itself streams its tooltip reads **Working** rather than a count, and a higher-priority mark (needs your answer, memory attention) replaces the working mark. A finished agent leaves **Running** and keeps its steps in the parent chat's **Activity** trace, whose dispatch row opens the same read-only view. Ciaobot lists what the provider reports, so not every dispatch appears live: a foreground agent can run inside the streaming turn before the live list names it, the live agent count and the running list update on different clocks, and a transcript can be missing on another machine (the view then says "Transcript not on this machine"). An absent row, a quiet transcript, an unchanged **Activity** trace, or a clean worktree is not proof the worker stopped: the trace alone can stay quiet while the worker is still going. The read-only view's **State** is a display, not proof either: **Completed** can describe an earlier execution of the same agent rather than the one you are asking about. Confirm a stop only from an authoritative completion result for the current execution or a verified lifecycle from the provider; otherwise treat the worker as possibly active, and do not dispatch a second worker into the same worktree until the first is known stopped. Use for "investigate these four things in parallel".
- **Background runs**: for one long script rather than a whole agent task, models use their provider's own background shell (Claude's Bash `run_in_background` and `Monitor`, OpenCode's background shell): the chat is woken when it finishes, Ciaobot keeps the provider alive and shows the shell while it runs. The shell can be stopped while it runs, and its output stays readable. Use for "fetch, verify, enrich — one script each".
- **Plan mode** (read-only: the agent researches and proposes an approach without editing anything) is not a control in the app — the model picker only offers the model and thinking level, and the chat header shows no mode chip. The backend still accepts `mode: "plan"`, so a chat can be put into it with `ciao chat create|update --mode plan` where the CLI allows it. A plan-mode chat gets `plan_mode_read_only` back from every mutating `ciao` command, including `ciao chat update`, so it cannot switch itself back out; changing the mode again is something the user does or another chat does.
- **Turn resilience**: if a turn hits a provider connection error, Ciaobot auto-retries it with backoff instead of dropping the message; you can stop the retry or trigger one immediately. The active chat's live socket also auto-reconnects so a brief network blip doesn't lose the streaming result.
